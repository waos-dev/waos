# waos-local-processes

This computer as a machine a program acts on (`docs/proposals/2026-10-29-processes.md`, decision 2): the provider of `waos-capabilities`' `Machines` for the machine in front of the user, which offers this computer alone, as `this-computer`, named "This computer". A program acts on it only once its user picked it; what it runs then runs as the user running WaOS, outside the program's sandbox (decision 1). It depends on `waos-capabilities` only of ours, and is chosen per program, in its environment; an SSH machine's provider comes with the same traits.

- **Takes:** `waos-capabilities`' `Machines` and `Machine`, with their records; tokio, for the pipes of commands run with pipes, read and written on the program's runtime, each command's end waited for on a thread of its own, so its exit status answers how it really ended whatever becomes of the program's runtime; on Unix's systems portable-pty, for terminals, rustix, for signals to a command's process group, among them its end with its program (a hangup for one in a terminal, a termination for one with pipes, then a kill after a grace of two seconds; on Windows its job is ended), the end of one started in a terminal, the user's id and `uname`, and libc, for the user database's entry; on Windows windows-sys, for a command's job, its pseudoconsole, the user's logon environment and the processor Windows runs on.
- **Provides:** `LocalMachines`, this computer's machines, made with the `LoginEnvironment` its commands run in: the user's login shell's (`of_login_shell`), the one the user database names, on Windows the environment Windows builds for the user's logon, another shell's on Unix's systems with a timeout a `Timer` measures (`of_shell`), or variables given whole (`given`), as a test gives them; `THIS_COMPUTER`, the id it is kept by among a program's grants.
- **Used by:** `waos-local`, which assembles this computer's defaults; any embedder that picks it on its own.

This computer says what it runs, and its user's login shell, each read once as `LocalMachines` is made: on Unix's systems what `uname(2)` names (`platform`), read as an SSH machine's `uname -sm` is, so Android is Linux, and the shell the user database names for the user (`getpwuid_r`'s `pw_shell`, `user_database`), the one SSH and `login` start, `/bin/sh` where it names none; on Windows the processor Windows runs on, `IsWow64Process2`'s native machine, which is ARM64 even for an x64 WaOS emulated there, where `GetNativeSystemInfo` answers x64, and no login shell. This computer's files are given from `/` (`MachineFiles::Local`), which the engine serves. A command runs with pipes (`exec`), through tokio's processes, its input written by a task of its own in the order given and closed after it, its output and errors read in chunks; or in a terminal of its own (`exec_in_terminal`), a pseudo-terminal through portable-pty, which makes the command the leader of a session whose controlling terminal it is, as the experiment's `wasdk-io` proved: its reads, writes and end each on a thread of their own, its output read up to 64 reads ahead, a resize passed to the terminal, and the terminal's closing hanging the command up. portable-pty rather than rustix's `openpty` because it sets up the session and the controlling terminal itself, with no `unsafe` of ours before `exec`, and has Windows' ConPTY behind the same calls. Either way the command leads a process group of its own, which a signal goes to until its end is collected, `interrupt` as `SIGINT`, and its end is its code or the signal's name, as SSH names it.

A command runs in the user's login environment (decision 4), as VS Code reads it on this computer: the user's login shell, the one the user database names, as SSH starts it, whatever `SHELL` WaOS was started with, `/bin/sh` without an entry, runs once, at the first command, interactive and a login shell, in a terminal of its own so that a shell taking its terminal never stops WaOS's, and prints its environment between two marks, which keep apart what its startup files print. A shell that fails, or takes longer than ten seconds, is ended, and commands run in WaOS's own environment instead. The command's variables go on top, and it starts in the folder it names, or the user's home.

On Windows, which has no process groups and no signals (`windows`), a command's processes are in a job object of its own, given to the command as it is created (`PROC_THREAD_ATTRIBUTE_JOB_LIST`, through `std`'s attribute list for one with pipes, which tokio then reads and writes), so every process it starts is in it, and ending the job, or WaOS letting go of it, ends them all. A command with pipes gets a hidden console of its own, none of WaOS's. A terminal is a pseudoconsole WaOS starts the command on itself (`CreateProcessW` with the pseudoconsole and the job as attributes, its standard handles invalid so it never writes to WaOS's own), closed as the command's end is collected, so its output ends. A signal is what Windows has in its place: an interrupt is `^C` typed into the pseudoconsole, which the console turns into its Ctrl-C, and ends the job of a command with pipes, which has no console; a hang-up closes the pseudoconsole; anything else ends the job. A command's end is its exit code, and an end by Ctrl-C (`STATUS_CONTROL_C_EXIT`) the signal `INT`. A process started ignoring Ctrl-C, as one started in a process group of its own is, passes that on to its commands, whose interrupt is then lost; `waos` starts WaOS in none. A command starts at the user's `USERPROFILE` unless it names a folder; its environment is the one Windows builds for a new logon of the user (`CreateEnvironmentBlock`), with the changes made since WaOS started, Windows having no login shell.
