# waos-capabilities

The capability traits and their records, in WIT's shape: one trait per service a program uses (files, network, machines, sound devices, cameras, media, fonts), each in the shape of its `wasdk:platform` or `wasdk:media` interface; `ProgramEnvironment`, which holds one program's providers, what the user lets it use and where its output goes; and `ProgramGrants`, what the user lets one program use, which the store implements. It depends on nothing of ours, so a capability crate depends on it alone. The clipboard is not a capability: the platform has one, which every program shares, and the embedding app gives it to the engine whole (`waos`'s `ShellClipboard`); only its switches are here, in `ProgramGrants`. Opening links and files is not one either: it is the system's, which the shell reaches (`waos`'s `ShellOpener`); only a program's answers to its link schemes are here. Nor are notifications: they are the user's, shown by the system, which the shell reaches (`waos`'s `ShellNotifications`); only the answer to a program's question for them is here.

- **Takes:** nothing of ours; `valo-fontmgr`, whose `FontManager` is the fonts capability's trait; `web-audio-api`, Web Audio's graph, which a program's sound is; `futures`, what a machine's commands answer with.
- **Provides:** the traits a provider implements, the records that cross them, `AuditLog` and `AuditDay`, where a program's audit summary is kept and what one day of it holds, `ProgramOutput`, where a program's standard output and error go, `ProgramFolders`, a program's own folders, `ProgramEnvironment`, `ProgramGrants` with what it answers (`NetworkGrant` and its `DomainRule` of `Domain`s, `FileSystemGrant` and its `Mount`s, `Question`, `Switch`, `Answer`, `SimulatedSound`, `FileDialog`, and `Setting`, a program's own value of a setting or the global one), `AudioDevices` with `AudioOutput` and `AudioDeviceError`, `Machines` and `Machine` with what crosses them (`MachineChoice`, `Platform` with its `OperatingSystem` and `Architecture`, read from `uname`'s names by `Platform::of_uname`, `MachineFiles`, `Command`, `WithPipes`, `InTerminal`, `Child`, `ChildInput`, `Terminal`, `TerminalSize`, `Signal`, `ExitStatus` and `ExecError`), and `valo_fontmgr` and `web_audio_api`, re-exported.
- **Used by:** every crate under `capabilities/`, which provide them; `capabilities/local`, which assembles a `ProgramEnvironment`; `waos`, which serves them to a program, and its permissions from the grants; `waos-store`, which implements `ProgramGrants` over the user's settings; whoever runs a program, which chooses its output and its grants.

Built so far: `ProgramEnvironment` with `Default`, holding six fields. `output`: an `Arc<dyn ProgramOutput>` that takes the bytes the program writes to stdout or stderr as it writes them, each tagged with its `OutputStream`, or none, which leaves them to the engine's log (the design's decision 31). Whoever runs a program chooses, as `Command::stdout` does for a process: a run from `cargo waos` writes to its connection; the app's log window, later, is another. `fonts`: an `Arc<Mutex<dyn FontManager>>`, the fonts the engine serves `wasdk:platform/fonts` from, or none, which makes every answer empty, as on a machine with no fonts installed. Its trait is valo's `FontManager`, the platform's fonts in the shape of Skia's `SkFontMgr` (decision 33), not one of this crate's: valo already has the shape, and a provider of ours would only forward to it. One manager serves every program, behind a lock, since it caches its lookups (decision 35); the crate re-exports `valo_fontmgr`, so whoever provides one names the version the field holds. `grants`: an `Arc<dyn ProgramGrants>`, what the user lets the program use, which the engine reads at each check and serves `wasdk:platform/permissions` and the program's mounts from, or none, which grants nothing. `folders`: the program's own folders on the machine, `ProgramFolders`, which the engine mounts writable at `/data` and `/cache` whatever its grants, or none, which leaves it neither; whoever runs the program makes them (the store, for the WaOS app). Step 7 of the design's work order adds each other capability, one at a time, after its interface is shown to the lead, and each adds its field to `ProgramEnvironment`.

`audio`: an `Arc<dyn AudioDevices>`, the sound devices the program's graph plays on and records from, or none, which leaves the program without sound (its `get-audio` answers none). The graph is not the provider's: Web Audio is `web_audio_api`'s, the whole spec implemented in Rust, which the engine serves to the program node for node (`docs/proposals/2026-10-29-sound.md`, decision 1), and the crate is re-exported, as valo's font manager is, so a provider names the version the engine serves. What a provider decides is the devices: `new_context` makes web-audio-api's `AudioContext` on the output a sink id names, the empty string being the system's default; `outputs` lists the outputs a picker shows, each an `AudioOutput` with its id, its group and its label; `set_output` moves a context onto another; `has_microphone` says whether the devices have a microphone the program may be given, false where the app may not record sound, as an app whose bundle does not say why it does, so the engine refuses the microphone without putting its question; and `open_microphone` opens the default microphone as a `MediaStream`, `NotFound` where none is attached now. Which outputs a program may use is the engine's to decide, from what its user picked, and the microphone's question is the engine's to put: a provider asks nothing.

`machines`: the providers of the machines the program may be given, each of one kind (`Machines`), which its picker offers the user, or none, which leaves the program without machines (its `get-machines` answers none). A provider offers its machines as `MachineChoice`s, an id and a name, and answers the `Machine` an id names: what it runs (`platform`, a `Platform`, its `OperatingSystem` and `Architecture`, `Platform::of_uname` reading them from what `uname -s` and `uname -m` print, as an SSH machine's provider asks them when it connects), its user's login shell (`login_shell`, none where it has none, as on Windows), each learnt once; its files from their root (`MachineFiles`, a folder on this computer for this computer itself, `/`), and its commands, a `Command` run with pipes (`exec`, a `WithPipes` of its `Child`, its `ChildInput` and its output and errors as streams of chunks) or in a terminal of a `TerminalSize` (`exec_in_terminal`, an `InTerminal` of its `Child`, its `Terminal` and its output), which ends as an `ExitStatus`, takes a `Signal`, is ended as the program that started it ends (`Child::end`: asked to end its own way, then forced after a short grace), or fails with an `ExecError` (`docs/proposals/2026-10-29-processes.md`, decisions 2 and 5). Which machines a program holds is the user's, kept among its grants by their ids; a provider asks nothing, and what a machine runs runs as its user, outside the program's sandbox.

`ProgramGrants` is what the user lets one program use, read live (decision 7 of `docs/proposals/2026-10-23-permissions.md`): the network switch, which is the internet, and the domains beneath it, any, only some, or all but some, a domain standing for itself and every name under it (`Domain::covers`, `DomainRule::allows`); the local-network switch, this computer and the local network, which no domain rule can guard (decision 12); whether the program may read the clipboard without the user's paste, and write it; the folders of the machine mounted in the program, each at a path inside it, read-only or writable; the answer to each question put at a first use, notifications, the camera and the microphone, which `set_answer` keeps, the camera's and the microphone's also `Simulated`, allowed with devices of WaOS's own (`Answer::allows`), the simulated microphone recording what `simulated_microphone` says, a quiet tone unless silence is chosen (`SimulatedSound`); and the answer to the program opening links of a scheme of its own, any but `http`, `https` and `mailto`, asked once per scheme (`link_scheme_answer`), which `set_link_scheme_answer` keeps; and the machines the user picked for the program, by their ids (`machines`), which `keep_machine` keeps, none where nothing keeps them. A picker or a file dialog can have an answer the user set in place of asking, none where nothing keeps one: the machine for the picker of machines (`machine_answer`), the output for the picker of outputs (`audio_output_answer`), and the paths for each kind of `FileDialog`, open a file, open files, open a folder and save a file (`file_dialog_answer`). `changed` resolves at the next change the user makes. Whoever keeps the user's settings implements it: the store, for each program over its own settings and the global ones (decision 8), each of which is a `Setting`, the global value followed or the program's own. A `Domain` is a name of at least two labels, any case taken and kept lower case.
