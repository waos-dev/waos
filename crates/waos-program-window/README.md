# waos-program-window

A program's windows as its user meets them, on any desktop: each view a program asks for in an Waft window of its own, made as the program set its `window-config`, the view's canvas filling it, the pointer, the keys and the keyboard's focus going to the program, its text open to the input methods, and Edit's commands sent to it. The windows talk to their program through `ProgramLink` and `ViewLink`, so the same code serves a program whose engine runs in the same process and one whose engine runs in another (the layers of decision 4 of `docs/proposals/2026-10-29-macos-apps.md`).

- **Takes:** `waos`, for the types wasmtime generates from the WIT, which cross as they are, for the engine's own `RunningProgram` and `ProgramView`, which are the link to a program in the same process, and for the shell's `ShellCompositor` and `ShellCompositionLayer`, which a program's layers are made through; `waos-window-messages`, for a program's call on its view as a value, `ViewCall`; Waft, for the windows, its compositor, the composition layer a canvas shows and the program's own beneath it, the pointer, the keys and the text input; and on Linux Waft's winit host, whose `Linux::activate` brings a window forward with a launch's activation token, and on Apple's systems Waft's winit host, whose `SurfaceBuffer` over an `IOSurface` is how a program's hardware buffer is shown on Waft's layer, and whose `CoreVideoFrame` is how a frame a layer shows comes back, each retained through Core Foundation; and on Android Waft's Android host, whose `AndroidHardwareBuffer` over an `AHardwareBuffer` is how a program's hardware buffer is shown on Waft's layer and comes back from it.
- **Provides:** `ProgramLink`, what the windows need of a program (its name, its end, a view added for a request or the request failed, a view removed), and `ViewLink`, what a window reports of one view (its pointer, keys, focus, text input, Edit's commands, the request to close, the user's Back while the program handles it, its metrics, screen, presence and frame, whether its window is maximized, and what the system's settings say a double-click on a title bar does), under the names of `ProgramView`'s methods; their implementation for a program in the same process, `RunningProgram` and `ProgramView` themselves, and `placed_view`, a view opened in a window as the engine is handed it; `ViewWindows`, the windows of one process, which take each `WindowRequest`, with the program's name and icon as `ProgramFace`, and, where its windows are an app of their own on Windows and Linux, its `ProgramIdentity`, the app id and on Windows what a pin of a window starts, which each window of the program carries, say which window is in front (`front_window`, the focused one or else the last to arrive), bring a program's front window forward (`bring_forward`), which on Android brings its task forward, and bring it forward for a launch that asked for the program (`bring_forward_for_launch`), on Linux with the launch's activation token through Waft's `Linux::activate`, the program's next window opening with the token where it has none yet, say which of Waft's views shows a program's view (`waft_view_of`), and open a window the platform restored for the program about to start with it (`open_given`, `given_started`, `given_not_started`); `RestorableWindow` and `WindowRole`, what each window asked for carries as its initial data, the program it shows and whether it is the program's first window or an extra one, which names a restored window's program again; `PromptPlacement`, where WaOS shows a prompt, one widget on every platform, for a program until its `ShownPrompt` is dropped, `PROMPT_SIZE`, how large a prompt is in a window of its own, and `PromptWindows`, the placement in WaOS's own windows: over the program's windows, centred over a dimmed backdrop, or in a window of the prompt's own for a program with none, with the program's face, its identity among it, whose closing dismisses it; `ProgramWindows`, what goes in each program's window, with what the process puts over each (`OverWindow`), for whoever builds the process's views (`content_of`), and where a request to close one goes (`close_requested`), and `PromptWindows::content_of` and `close_requested` the same for a prompt's window of its own, which carries `PROMPT_WINDOW` as its initial data; `WindowChanges`, a widget that reports each change of the window it is drawn in, as Waft's `WindowScope` tells the widgets that read it; `ViewCalls`, the shell's side of a view's text input, and of its cursor, focus, Back and bars' style, as the engine holds them, and `WindowCalls`, of its window, its size limits where the window has them, its move from a press, maximizing and minimizing among it, which hand each call on as the `ViewCall` it is; `Canvas`, what a view's pictures are presented to from the engine's frame threads; `CanvasLayer`, the composition layer a canvas shows, made as opaque as its window's background, a `Canvas` whose hardware buffers show with the program's layers as its children, and which whoever shows the canvas places; `CanvasView`, the shell's side of a view whose canvas is in the engine's process, its hardware buffers presented to its `Canvas` and its cursor, focus, Back and bars' style sent on as `ViewCall`s; `WaftCompositor`, the shell's compositor over Waft's, whose every layer is Waft's, for the engine to hold for a program, and shows a hardware buffer the program presents on it as Waft's buffer over the platform's own, and answers what it shows now as Waft's layer answers it, case for case, as the platform's own again, a raw buffer as its surface and a lent frame as its pixel buffer, which keeps its pool from handing the frame out again while the engine reads it, and `waft_layer`, Waft's layer behind one of them, for what the program hands a layer to, such as a player; `rect_of`, a frame in Waft's terms as the program reads it, and `metrics_of`, a view's metrics so; `ShownView`, one view shown on the main thread, knowing nothing of a window, which carries out the program's calls on the view, passes its calls on a window to whatever shows it in one, tells the program the metrics and the presence whatever shows it says, holds the keyboard only while whatever shows it lets it, and keeps whether the program goes back within itself, which whatever shows it reads to send it the user's Back (`handles_back`, `pop_route`), and the style the program asks for of the system's bars over it, each field as said last, and `ProgramCanvas`, the widget a shown view's canvas fills its box in, with the program's input, its picture annotated with that style, which Waft's view samples under each bar as it samples any app's, so on Android the window showing the view, a program's task or WaOS's deck while the view's page fills it, takes it, and `ProgramPicture`, the same canvas with none of it, for a view whose program ended; and `waft_menu`, a program's menu, the WIT's flat list, as Waft's tree, each entry under the submenu it names and keeping the id the program gave it, with `waft_image`, an image in Waft's terms; and a program's file dialog in Waft's terms: what it offers (`waft_open_options`, `waft_folder_options`, `waft_save_options`), and what Waft's dialog answers as the paths on the machine the user picked, which the engine mounts, a pick without a path failing it (`picked_file_paths`, `picked_folder_path`, `PickedPaths`); and a program's notification in Waft's terms, under the program's own id and title, an action it answers by typing made through the system's replies where the system takes them (`waft_notification`), and a click on one as the program hears it (`activation_of`).
- **Used by:** the WaOS app, for the windows it shows in its own process, where a program has no app of its own (Windows and Linux for now, and its tests); `apps/waos-window`, a program's window process on macOS, whose link reaches the program through WaOS, whose dialogs of WaOS's prompts are centred on the screen of the window in front, and which shows the program's menu bar and opens its context menus at its views (`waft_menu`, `waft_view_of`) and its file dialogs on its windows (`waft_open_options`, `picked_file_paths` and the rest), and which posts its notifications under its bundle and sends the clicks on them back (`waft_notification`, `activation_of`); on macOS, the WaOS app again, which keeps the canvases of the views in its programs' apps (`CanvasLayer`, `CanvasView`); the WaOS app on every desktop for where its prompts show (`PromptPlacement`, `PromptWindows`, and on macOS its own placement in dialogs of the programs' apps, launched for a prompt when they do not run); the WaOS app for the programs' menus it shows through Waft's, their tray icons' and their context menus in its own windows (`waft_menu`, `waft_image`); and the WaOS app for the programs' file dialogs it shows through Waft's in its own windows (`waft_open_options`, `picked_file_paths` and the rest); and the WaOS app for the programs' notifications it posts through Waft's under its own name, each under its program's id and titled after its name (`waft_notification`, `activation_of`); and the WaOS app's deck on a phone, whose tabs show their programs' views with no window (`CanvasLayer`, `CanvasView`, `ShownView`, `ProgramCanvas`, `ProgramPicture`, `metrics_of`).

A window request arrives on the main thread with the program's link and its face; Waft is asked for the window (`Platform::request_view`) with the program's name where the program left it untitled, its icon, its identity as Waft's `WindowsWindowConfig` and `LinuxWindowConfig`, and as initial data what names the window for its restoring (`logic::restoration`); the window Waft makes for it gets a composition layer, which the canvas shows and the window's frames place, and the view is added through the link with its metrics, screen, presence and frame, whether the window has size limits, whether it is maximized, what the system's settings say a double-click on a title bar does, and the queue its calls arrive on (`OpenedView`). Through the in-process link the engine presents the program's hardware buffers to that layer from its frame threads (`logic::canvas_view`), with the layers the program's view held as it presented as the layer's children, beneath its picture, each Waft's own again and placed as Waft places a layer (`logic::composition`, `logic::placements`); a layer with children blends its own buffer, so they show through the room the program's picture makes whatever the window's background. A window's view arrives as every view does, through Waft's binding's observers, and the windows, which noted the request by what Waft answered it with, know it as their program's; whoever builds the process's views, a `MultiViewApp`, puts the windows' content in it, which reports each change of the window back to them (`WindowChanges`), and the windows read every window again as the app's lifecycle changes, since content builds no frames while the app draws nothing; a request to close the window goes to its program, and Waft's removal of the view takes the program's view away. A window the system restored, as Android gives a task from Recents after the process died, arrives the same way carrying no request of this process, and is opened for its program the same way, titled and iconed so, before the program starts with it as a view it was given; from then on it is followed and shown as a window asked for is. The user's Back in a window goes to the program while it handles Back, and otherwise sends the window to the background, the program running on. The program's calls on the view, its text input and its window are queued as `ViewCall`s for the window's main thread (`logic::view_calls`), as a window process's arrive from WaOS, and carried out there: the view's own and its text input's by the view, which knows nothing of a window (`state::shown_view`), and the window's by the window the view is in (`state::view_windows`). What Waft reports of the window, and what the user does in the canvas, goes to the view's link (whether the window is maximized read again only as its frame changes, since winit's answer for a window without decorations reports a move and a resize of its own; the system's setting for a double-click on a title bar at each change of its focus, as a user who changed it comes back to the window) (`ui::program_canvas`, `ui::program_text_input`, `ui::edit_commands`). A key is claimed from Waft at once and sent to the program; a key going down that the program leaves is then offered to Waft's menu bar, so a ⌘C a program's text field leaves chooses Edit's Copy. Nothing waits on the program, but a resize: a view's new metrics reach its link inside the platform's resize, before the new size shows, and a link may hold them until the program's picture at that size is shown, as a program's window process does on macOS (decision 55 of `docs/proposals/2026-10-17-the-waos-project.md`).

The code is in Waft's layers, as WaOS's is: `src/logic` is plain Rust, tested without Waft's UI (the conversions between Waft's terms and the program's, a window's configuration, its title bar, geometry, how a view stands, pointers, keys, the cursor, text input, a layer's placement, a menu, a file dialog's options and picks, a notification and a click on one; the calls a window's main thread carries out; the canvas's layer, the program's layers on Waft's compositor, and the shell's side of a view in the same process); `src/state` ties it to the application (the windows, and each view shown); `src/ui` holds the widgets. The windows are tested with real programs in the WaOS app's tests, on Waft's test platform.
