# waos-dev-protocol

What `cargo waos` and a running WaOS say to each other: the messages of one run, how they are framed on a stream, and what carries them on this machine, a Unix socket, or a named pipe on Windows. The connection is the run (the design's decision 29): `cargo waos run` connects, sends the program's id and its component, hears `Compiling` while WaOS compiles the component, which it does before it starts it, and reads what the program writes until it ends; closing the connection, by Ctrl-C or the terminal closing, stops the program, and a later run of the same id replaces it. A run is the program its id names (decision 11 of `docs/proposals/2026-10-23-permissions.md`), which WaOS runs with that program's settings and folders, installed or not. There is no stop message. `waos open <file> --program <id>` connects the same way and sends one `Open`, files to open with the program the id names, which WaOS answers `Opened` or `Refused` (decision 3 of `docs/proposals/2026-10-29-opening.md`, until programs register what opens them). `cargo waos screenshot` connects the same way and sends one `Screenshot` of the program an id names, which WaOS answers `Screenshots`, a `WindowPicture` for each of its windows, numbered from 1 in the order they opened, with the title the program gave it, its size in physical pixels, whether it is in sight (a window other windows cover is, while the run is attached: the design's decision 63), and its last picture as a PNG, none before it showed one; `cargo waos tap`, `press`, `drag`, `type`, `key` and `scroll` send one `Input` to a window of the program, by its number, a `Tap` or a `Scroll` at a point in the window's physical pixels from its top-left, a `Press` held there for a `duration`, a `Drag` from a point to another, held at the first for a `hold` and moved in `steps` equal moves over a `duration`, `Text` to commit into what it edits, or a `Key` or a chord by name (`cmd+s`), which WaOS answers `InputDone` once the window shows its next picture after it, a press's or a drag's after its time, saying whether a new one came. An `Input` is simulated by WaOS (the design's decision 64): WaOS makes its events itself and hands them to the program as it hands over the user's input, so the program hears them as a user's, while the system and the window's menu bar never see them; a key the program leaves goes nowhere, where a real one would go on to the menu bar, a gap known for now. `cargo waos resize` connects the same way and sends one `Resize`, a size in logical points for the view in a window of the program, by its number, which WaOS gives the window as the program's own `set-frame` sizes it, its top-left and what it holds around the view kept, and answers `Resized`, the view's size in physical pixels and its scale as the view reported them after, a window system's clamp included, and whether the window then showed a picture the program drew at that size; a view in no window, a tab of a phone's deck, is `Unreached(InNoWindow)`. All three are answered `Unreached` and why while no run of `cargo waos run` runs the program, for a program the library opened among them, which no tool reads or drives (the design's decision 60), and for a window the program does not have, a point outside the window, text with nothing in the window edited, and a chord naming no key; an `Input` while WaOS asks the program's user something over its windows is `Unreached(Asking)`, saying what, and not given, and each `WindowPicture` says what WaOS asks over it (`asking`). `cargo waos settings` and `set` connect the same way and send one `Settings`, for the rows of a program's settings, or `Set`, one `Row` set as its user would set it on its settings page: a question's answer, the camera's and the microphone's simulated too, a switch, what a simulated microphone records (`SimulatedSound`), the answer to opening links of a scheme, the answer to it holding a role (`Role`, `role.inspector`), or the answer set for its picker of machines, its picker of outputs or one of its four file dialogs (`FileDialog`), given in place of asking. WaOS answers `Settings`, each row a `SettingRow`, its key as the command line names it (`Row::parse` reads the same names), what holds, whether it follows the setting for every program, and for a picker's row the machines or outputs offered now (`Offered`); or `Refused`, with why a value names nothing now; or `Unreached(NeverRunByCargoWaos)` for a program no `cargo waos run` on this machine runs or has run. `cargo waos inspect` connects the same way and sends one `Inspect` of the program an id names (step 4 of `docs/proposals/2026-11-15-inspector-roles-and-compatibility.md`): its audit summary, at most `days` days of it, what it uses now (`ActiveUses`), or its live trace of the capabilities named (`TracedCapability`); WaOS answers `Inspected`, lines of JSON of `wasdk:inspect`'s values, which the protocol carries as text so that the WIT stays their one schema: once for a summary, a day a line; for what it uses, first a line of everything active, then a line per change, a `resync` of everything where the command fell behind; and for a trace an `Inspected` per event; the last two until the program ends or the command closes the connection. A summary is `Unreached(NeverRunByCargoWaos)` by the rule of the settings, and the rest `Unreached` by the rule of a screenshot. And while WaOS asks a run's program's user something, a row on Ask, the run's connection hears `Asking`, saying what (`Asked`). The socket is in the user's own folder, so the system's file permissions decide who may connect (decision 30), and on Windows the pipe's security descriptor gives the user alone access; the network transport for phones carries the same messages.

- **Takes:** a program's id, its `waos-package` `ProgramId`, and its component, from `cargo waos`; a program's id with a row of its settings to read or set, from `cargo waos`; a program's id and files to open with it, from `waos open`; a program's id with a screenshot or an input to one of its windows, or a size for one, from `cargo waos`; what the program writes and how it ends, its windows' pictures, what came of an input and the size a window took, from the WaOS app; a `tokio` runtime, on both sides.
- **Provides:** `ToWaOS` and `FromWaOS`, the messages, with `Input`, `WindowPicture` and `Unreached`; `Row`, `SettingRow`, `Offered` and `Asked`, a program's rows of settings and what WaOS asks its user, with the `Question`, `Switch`, `Answer` and `FileDialog` they name, and each row's key (`Row::parse`, `RowError`); `Connection`, which agrees on the protocol's number with the other side first (`PROTOCOL`, `agree_on_protocol`), then sends and receives them as frames over a stream, split into a half that sends and one that receives when one task writes a program's output while another watches for the close; `ClientStream` and `ServerStream`, the streams of a connection on this machine, `cargo waos`'s end and WaOS's; `listener_path`, where a WaOS listens on this machine; `Listener`, the WaOS side's end, which makes the socket's folder, replaces a socket file a WaOS that died left, refuses to start while another WaOS answers, and removes its file when dropped, or on Windows makes the pipe's first instance and refuses to start while another process has the name.
- **Used by:** `waos-cli`, for `cargo waos run`, `screenshot`, `tap`, `press`, `drag`, `type`, `key`, `scroll`, `resize`, `settings` and `set`, and the WaOS app, which serves them and is `waos open`.

The socket's path: `~/Library/Application Support/WaOS/dev.sock` on Apple's systems; `$XDG_RUNTIME_DIR/waos/dev.sock` elsewhere, or `~/.local/share/waos/dev.sock` without one. The folder is made for the user alone (`0700`), and the socket file too (`0600`). macOS allows a socket path 103 bytes long, so a user's name may be 50 bytes.

A frame: a four-byte little-endian count of the message's bytes, then the message as `postcard` encodes it, a component, a program's output and a window's PNG as strings of bytes (`serde_bytes`), which postcard writes as it writes a `Vec<u8>`, so the encoding is the one of a sequence of bytes, read in one copy. Either side refuses a frame over 256 MiB, the receiver on the count alone, before it allocates anything: a component is megabytes, a debug build tens of them, and a count beyond that is a stream that is not ours. After a frame cut short or refused, the connection is done. A variant's place and a field's place is its encoding, so a change to a message adds at the end, and anything else raises the protocol's number; the screenshot and the input, added at the end, raised it to 3 all the same, so a WaOS of an earlier build refuses a `cargo waos` that may send them by number rather than at a message it cannot read, and the press and the drag, and `Compiling`, added at the end too, raised it to 4, so a `cargo waos` of an earlier build is refused by number rather than ending its run at an answer it cannot read; and the settings, `Set` and `Asking`, added at the end, raised it to 5 for the same reason, and `Resize`, `Resized` and `InNoWindow` to 6, and a simulated answer for the camera and the microphone (`Answer::Simulate`) and what a simulated microphone records (`Row::SimulatedMicrophone`) to 7. A message's `Debug` leaves out the text typed into a program, which may be a password, and writes a component's and a PNG's sizes rather than their bytes.

The first frame each way is that number, `PROTOCOL`, outside the messages' encoding: a count of four, then the number little-endian, the one shape every build reads. Each side sends its own and reads the other's before anything else; when they differ, each ends the connection with an error naming both numbers, which `cargo waos` prints, so a `cargo waos` and a WaOS of different builds find out rather than misread each other.

On Windows the connection is a named pipe, `\\.\pipe\waos-dev-<SID>`, named after the user by their SID since Windows has no folder of the user's own for pipes (step 11 of the design's work order). Where decision 30 is silent, this crate chose:

- The pipe's security descriptor is `O:<SID>D:P(A;;GA;;;<SID>)`: the user owns it and alone has access, through a protected list that inherits nothing, so no other user may connect, and none may read what WaOS writes, which the default descriptor lets everyone do. Administrators are not listed; they can take any object anyway.
- `cargo waos` checks that the pipe it opened is owned by its user, and refuses it otherwise (`PermissionDenied`): any user may make a pipe of a name nobody holds, and one made before WaOS starts would otherwise receive the program. The client lets WaOS identify it but not act as it (`SECURITY_IDENTIFICATION`).
- A WaOS makes the pipe's first instance as the first (`FILE_FLAG_FIRST_PIPE_INSTANCE`), so it never joins a pipe another process made; a second WaOS, or a process that made a pipe of the name, is refused with `AddrInUse`. The pipe takes no client from another machine, and goes when its last instance closes, so there is no stale file to replace.
- One instance always waits: the next is made as one connects, before it is handed out; a `cargo waos` that finds every instance busy, for that moment, tries again for two seconds.
