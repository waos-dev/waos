# waos-dev-protocol

What `cargo waos` and a running WaOS say to each other: the messages of one command, how they are framed on a stream, and what carries them on this machine, a Unix socket, or a named pipe on Windows. One connection is one command. Each side says a `Hello` first — its build, the protocol's major and, from WaOS, the requests it serves — so a different major or a request WaOS does not serve is refused before anything is sent, in words naming both builds and which one to update. Then one `Request`, answered in its own terms: `ScreenshotAnswer`, `InputAnswer`, `ResizeAnswer`, `SettingsAnswer`, `InspectAnswer` or `OpenAnswer`, or, for a run, `RunEvent`s from `Compiling` to `Ended` with the program's output among them (the design's decision 29: the connection is the run).

A run, `Request::Run`: the program's id, its arguments (after `cargo waos run --`, prefixed on the server with the program's name as `argv[0]`), the variables this run alone adds to its environment (decision 68), and its component's length and SHA-256. WaOS answers `Upload` first: `Send`, and the component follows in `Component` frames of 8 MiB at most (`CHUNK_BYTES`), which WaOS assembles and checks against both, so a component larger than one frame — a debug build is hundreds of megabytes — goes over too; `Have`, when `sent_components` holds that component already, and nothing is sent; or `Refused`, when the run cannot be set up before upload. WaOS compiles it, minutes for a large debug build, unless it is the one the code cache has, and says `Compiling` before it does; then `Started`, the program's `Output` as it writes it — bounded to 1 MiB in flight through async backpressure, so a program writing faster than the connection carries waits as on a pipe — what WaOS asks its user (`Asking`), and `Ended` with how it ended. Closing the connection, by Ctrl-C or the terminal closing, stops the program, and a later run of the same id replaces it. A run is the program its id names (decision 11 of `docs/proposals/2026-10-23-permissions.md`), which WaOS runs with that program's settings and folders, installed or not. There is no stop message.

`waos open <file> --program <id>` connects the same way using `Hello::waos_open` and sends one `Request::Open`, files to open with the program the id names, which WaOS answers `OpenAnswer::Opened` or `Refused` (decision 3 of `docs/proposals/2026-10-29-opening.md`, until programs register what opens them); it names paths on this machine, so it is local only. `cargo waos screenshot` sends `Request::Screenshot`, of each window of the program or of the one `window` names, which WaOS answers `ScreenshotAnswer::Pictures`, a `WindowPicture` for each window, with the id the run gave it as it opened (minted from 1 and never reused in that run), the title the program gave it, its size in physical pixels, whether it is in sight (a window other windows cover is, while the run is attached: the design's decision 63), and its last picture as a PNG, none before it showed one. `cargo waos tap`, `press`, `drag`, `type`, `key` and `scroll` send one `Request::Input` to a window by its optional id (or the program's first open window when omitted), a `Tap` or a `Scroll` at a point in the window's physical pixels from its top-left, a `Press` held there for a `duration`, a `Drag` from a point to another, held at the first for a `hold` and moved in `steps` equal moves over a `duration`, `Text` to commit into what it edits, or a `Key` or a chord by name (`cmd+s`), which WaOS answers `InputAnswer::Done` once the window shows its next picture after it, a press's or a drag's after its time, saying whether the window was in sight when the input was given and whether a new picture came. An `Input` is simulated by WaOS (the design's decision 64): WaOS makes its events itself and hands them to the program as it hands over the user's input, so the program hears them as a user's, while the system and the window's menu bar never see them; a key the program leaves goes nowhere, where a real one would go on to the menu bar, a gap known for now. `cargo waos resize` sends one `Request::Resize`, a size in logical points for the view in a window by its optional id (or the program's first open window), which WaOS gives the window as the program's own `set-frame` sizes it, its top-left and what it holds around the view kept, and answers `ResizeAnswer::Done`, the view's size in physical pixels and its scale as the view reported them after, a window system's clamp included, and whether the window then showed a picture the program drew at that size.

What a request cannot be carried out is answered `Refused(Refusal)`: a kind an agent acts on — `NoDevRunNow`, `NeverDevRun`, `NoWindow`, `OutsideWindow`, `InNoWindow`, `Asking`, `BadInput`, `CannotLoad`, `LocalOnly`, `NotServed`, or `Failed` — and a message for a person, naming the program, window or build. A run refuses on its connection too, as `RunEvent::Refused`, for a component that does not load. `cargo waos settings` and `set` send one `Request::Settings` or `Request::Set`, a program's rows of settings to read or one to set as its user would set it on its settings page: a question's answer, the camera's and the microphone's simulated too, a switch, what a simulated microphone records (`SimulatedSound`), the answer to opening links of a scheme, the answer to it holding a role (`Role`, `role.inspector`), or the answer set for its picker of machines, its picker of outputs or one of its four file dialogs (`FileDialog`), given in place of asking. WaOS answers `SettingsAnswer::Rows`, each row a `SettingRow`, its key as the command line names it (`Row::parse` reads the same names), what holds, whether it follows the setting for every program, and for a picker's row the machines or outputs offered now (`Offered`). `cargo waos inspect` sends one `Request::Inspect` of the program an id names (step 4 of `docs/proposals/2026-11-15-inspector-roles-and-compatibility.md`): its audit summary, at most `days` days of it, what it uses now (`ActiveUses`), or its live trace of the capabilities named (`TracedCapability`); WaOS answers `InspectAnswer::Inspected`, lines of JSON of `wasdk:inspect`'s values, which the protocol carries as text so that the WIT stays their one schema: once for a summary, a day a line; for what it uses, first a line of everything active, then a line per change, a `resync` of everything where the command fell behind; and for a trace a line per event; the last two until the program ends or the command closes the connection. And while WaOS asks a run's program's user something, a row on Ask, the run's connection hears `RunEvent::Asking`, saying what (`Asked`).

- **Takes:** a program's id, its `waos-package` `ProgramId`, the variables and arguments a run gives it and its component, from `cargo waos`; a program's id with a row of its settings to read or set, from `cargo waos`; a program's id and files to open with it, from `waos open`; a program's id with a screenshot or an input to one of its windows, or a size for one, from `cargo waos`; what the program writes and how it ends, its windows' pictures, what came of an input and the size a window took, from the WaOS app; a `tokio` runtime, on both sides.
- **Provides:** `Hello`, `MAJOR` and `SERVED`, what each side says first and what a `Mismatch` says to update; `Request` with `Run`, `Input`, `Inspection` and the settings' `Row`s, and the answers `RunEvent`, `ScreenshotAnswer`, `InputAnswer`, `ResizeAnswer`, `SettingsAnswer`, `InspectAnswer`, `OpenAnswer`, and `RefusedAnswer`, with `InputDone`, `Resized`, `WindowPicture` and `WindowId`; `Refusal` and `RefusalKind`, why a request was not carried out; `Component` and `CHUNK_BYTES` with `component_digest`, a run's component in parts; `Row`, `SettingRow`, `Offered` and `Asked`, a program's rows of settings and what WaOS asks its user, with the `Question`, `Switch`, `Answer` and `FileDialog` they name, and each row's key (`Row::parse`, `RowError`); `Connection`, which says and reads the hello first (`hello`), then sends and receives messages as frames over a stream, split into a half that sends and one that receives when one task writes a program's output while another watches for the close, and which knows whether its stream stays on this machine (`Locality`); `ClientStream` and `ServerStream`, the streams of a connection on this machine, `cargo waos`'s end and WaOS's; `listener_path`, where a WaOS listens on this machine; `Listener`, the WaOS side's end, which makes the socket's folder, replaces a socket file a WaOS that died left, refuses to start while another WaOS answers, and removes its file when dropped, or on Windows makes the pipe's first instance and refuses to start while another process has the name.
- **Used by:** `waos-cli`, for `cargo waos run`, `screenshot`, `tap`, `press`, `drag`, `type`, `key`, `scroll`, `resize`, `settings` and `set`, and the WaOS app, which serves them and is `waos open`.

The socket's path: `~/Library/Application Support/WaOS/dev.sock` on Apple's systems; `$XDG_RUNTIME_DIR/waos/dev.sock` elsewhere, or `~/.local/share/waos/dev.sock` without one. The folder is made for the user alone (`0700`), and the socket file too (`0600`). macOS allows a socket path 103 bytes long, so a user's name may be 50 bytes.

A frame: a four-byte little-endian count of the message's bytes, then the message as CBOR (`ciborium`), so each variant and field is named in its encoding: every protocol enum uses `#[serde(tag = "kind", content = "data")]` with an `Unknown` variant probed generically from `ciborium::Value` via `MapDeserializer`, so a field added with `#[serde(default)]` or a variant added at any enum's end reads on the other side as `Unknown` (and an older WaOS refuses unknown request variants cleanly rather than breaking the stream); only a real break raises `MAJOR`. A component's part, a program's output and a window's PNG travel as CBOR's own byte string (`serde_bytes`), read in one copy. Either side refuses a frame over 256 MiB, the receiver on the count alone, before it allocates anything: a component's part is 8 MiB at most, a program's output and a picture are megabytes, and a count beyond that is a stream that is not ours. After a frame cut short or refused, the connection is done. The hello's shape is frozen: a field is added with `#[serde(default)]`, and a side ignores the fields it does not know. A message's `Debug` leaves out the text typed into a program, which may be a password, and writes a component's, an output's and a PNG's sizes rather than their bytes.

The first frame each way is the hello, before any request: client sends first (`hello`), server reads first and answers (`accept_hello`). A `cargo waos` checks WaOS's against its own and the request it is about to send before sending it, and recognizes the legacy 4-byte frame of WaOS 0.2 (`cargo waos` says to update WaOS from https://waos.app; new WaOS answers a legacy 4-byte frame with `11`, above every 0.2 protocol number, so an old client prints its own mismatch telling the user to update `cargo waos`).

On Windows the connection is a named pipe, `\\.\pipe\waos-dev-<SID>`, named after the user by their SID since Windows has no folder of the user's own for pipes (step 11 of the design's work order). Where decision 30 is silent, this crate chose:

- The pipe's security descriptor is `O:<SID>D:P(A;;GA;;;<SID>)`: the user owns it and alone has access, through a protected list that inherits nothing, so no other user may connect, and none may read what WaOS writes, which the default descriptor lets everyone do. Administrators are not listed; they can take any object anyway.
- `cargo waos` checks that the pipe it opened is owned by its user, and refuses it otherwise (`PermissionDenied`): any user may make a pipe of a name nobody holds, and one made before WaOS starts would otherwise receive the program. The client lets WaOS identify it but not act as it (`SECURITY_IDENTIFICATION`).
- A WaOS makes the pipe's first instance as the first (`FILE_FLAG_FIRST_PIPE_INSTANCE`), so it never joins a pipe another process made; a second WaOS, or a process that made a pipe of the name, is refused with `AddrInUse`. The pipe takes no client from another machine, and goes when its last instance closes, so there is no stale file to replace.
- One instance always waits: the next is made as one connects, before it is handed out; a `cargo waos` that finds every instance busy, for that moment, tries again for two seconds.
