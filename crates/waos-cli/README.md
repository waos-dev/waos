# waos-cli

`cargo waos`: what someone writing a program runs. It writes a new program, builds a program as a component, runs it in the WaOS on this machine, and packages it as a signed `.wapk` listed in a package source's `index.json`; and while a run of its own runs the program, it takes a screenshot of the program's windows, gives them input and sizes them, so an agent building the program sees it and uses it (the design's decision 60); and it carries WaOS's docs of its own version, which it prints and writes as an agent's skill. It gains a command when a step needs one, and has no `doctor` and no device commands: a phone is reached through the WaOS app already on it, found on the network, never by installing anything on the phone (the design's decision 21).

- **Takes:** a name and a widget kit, for `new`; a program's crate, in a cargo project, with its `[package.metadata.waos]`, whole for `package` and its id for `run`, `screenshot`, `tap`, `press`, `drag`, `type`, `key`, `scroll`, `resize`, `settings`, `set` and `inspect`, and `NAME=VALUE` variables for a `run`'s environment; the WaOS app, installed on this machine, for `run`, `settings` and `set`, running, for an `inspect` of the summary, and running the program, for the rest; the user's signing key, for `package`; the site's docs, `packages/waos-site/content`, as `cargo xtask sync-docs` copies them into `content/`, built in by `build.rs`, for `docs` and `skill install`.
- **Provides:** the `cargo-waos` binary: `cargo waos new`, `cargo waos build`, `cargo waos run`, `cargo waos package`, `cargo waos screenshot`, `cargo waos tap`, `cargo waos press`, `cargo waos drag`, `cargo waos type`, `cargo waos key`, `cargo waos scroll`, `cargo waos resize`, `cargo waos settings`, `cargo waos set`, `cargo waos inspect`, `cargo waos docs` and `cargo waos skill install`.
- **Used by:** whoever writes a program, and an agent writing one, which sees and uses it through `screenshot`, the input commands and `resize`, reads what it does with what it was allowed through `inspect`, and reads the docs through `docs` or the skill `skill install` writes. The WaOS app itself is an Waft app, built with `cargo waft`.

```sh
cargo waos new <name> [--template winui|cupertino]   # a new program at ./<name>, which run runs and package packages as it is
cargo waos build [-p <package>] [--release]   # the component, at target/waos/<profile>/<package>.wasm
cargo waos run [-p <package>] [--release] [--env NAME=VALUE]...   # builds it, and runs it in the WaOS on this machine, with variables this run alone adds
cargo waos package [-p <package>]             # its release build, signed, at target/waos/<id>-<version>.wapk, listed in target/waos/index.json
cargo waos screenshot [-p <package>] [--out <path>] [--window <n>]   # a PNG of each of its windows, as its user sees it, at target/waos/screenshots/<package>/window-<n>.png, or where --out says
cargo waos tap --at <x>,<y> [--window <n>] [-p <package>]                 # a press and release at a point
cargo waos press --at <x>,<y> [--duration <ms>] [--window <n>] [-p <package>]   # a press held at a point, a second unless --duration says otherwise
cargo waos drag --from <x>,<y> --to <x>,<y> [--steps <n>] [--duration <ms>] [--hold <ms>] [--window <n>] [-p <package>]   # down, moves, up: 10 moves over 300 ms by default
cargo waos type "<text>" [--window <n>] [-p <package>]                    # text, as typing it enters it
cargo waos key <chord> [--window <n>] [-p <package>]                      # a key or a chord: enter, escape, cmd+s
cargo waos scroll --at <x>,<y> --by <dx>,<dy> [--window <n>] [-p <package>]   # a mouse wheel's scroll at a point
cargo waos resize --to <width>x<height> [--window <n>] [-p <package>]     # the window sized so what it shows is that many points: 390x844, a phone's
cargo waos settings [-p <package>]                                        # its settings, a row each, as its settings page in WaOS shows them
cargo waos set <row> <value>... [-p <package>]                            # one row set: camera allow, save-file /tmp/out.pdf, machine this-computer, open-file ask
cargo waos inspect summary [--days <n>] [-p <package>]                    # its audit summary, a day a line as JSON, newest first, 7 days by default
cargo waos inspect active-uses [-p <package>]                             # what it uses now on one line of JSON, then each change, until Ctrl-C or its end
cargo waos inspect <capability>...|all [-p <package>]                     # its live trace of network, files, clipboard..., an event a line of JSON, until Ctrl-C or its end
cargo waos docs                                                           # the docs' map, a line a page by the name to give, in the order to read them
cargo waos docs <page>                                                    # one page as Markdown: guide/network, waft/state, network, or its address on waos.app
cargo waos docs --search <text>                                           # every line of every page that holds the text, as <page>:<line>: <text>
cargo waos skill install [--dir <skills folder>]                          # the docs as a skill, <dir>/waos, ~/.claude/skills/waos without --dir
```

`docs` carries the docs of this version, the site's pages as `packages/waos-site/content` has them: `content/` here is their copy, which `cargo xtask sync-docs` makes and xtask's `tests/docs_copy.rs` holds to the site's, and `build.rs` builds every file of it in, so the published crate has them and an agent reads them offline. A page is named as its address on waos.app names it, less `/docs/`, so a link in one page is the name of another; the playbook, `/agents.md` on the site, is `playbook`, and the reference's page for each interface, which the site makes from the WIT, is not carried: its WIT is in the `wasdk` crate's `wit/`. `skill install` writes a folder, `waos`, in a skills folder: `SKILL.md`, the playbook under front matter that says when an agent uses it, and `docs/`, every page as `docs <page>` prints it, with `docs/index.md` their map; it replaces `SKILL.md` and `docs/` whole. Without `--dir` the folder is `~/.claude/skills`, Claude Code's personal skills, which every project sees, as every app the user makes wants it; another agent, or one project alone, names its own skills folder.

`inspect` prints JSON of `wasdk:inspect`'s values, one value a line, by the WIT's own names, so a field is `dropped-before` and a case `stdout` or `{"read": {"form": "text/plain", "pasted": false}}`: a record is an object of its fields, a case its name or an object of its name holding its payload, an option `null` or its value, a list an array. A summary has a day only where the program used something WaOS guards that day while its record was on (`record`, on unless turned off), the network, files, the clipboard, a device, a machine, a link, a notification or a question; what it writes to its output is not one, so a program that only runs and writes has no days, and the command says so on stderr, printing nothing. WaOS keeps seven days, so `--days` beyond seven prints seven.

`new` writes a new program in a folder of its name in this directory, a Waft app over `wasdk-adapter-waft` in one widget kit's look, as `cargo waft new` writes a Waft app: by default WinUI's, a `WidgetsApp` in Fluent's look whose page has a text box, an Add button, the lines it adds and a clock that ticks, in a window sized for a desktop, which works on a phone too; and with `--template cupertino`, for an app meant for phones alone, the same page in Cupertino's widgets. `cargo waos run` runs it and `cargo waos package` packages it as it is written. It prints the command that runs it, `cd <name> && cargo waos run`.

```text
hello/
  Cargo.toml            wasdk, wasdk-adapter-waft, waft, waft-widgets and the kit by their crates.io versions, or the workspace's; [package.metadata.waos]
  rust-toolchain.toml   WaOS's toolchain, nightly-2026-11-15 with wasm32-wasip3, which rustup installs by itself; none in a workspace that names its own
  icon.png              a white disc on a blue square that fills it to its edges, as every icon does, 1024 pixels on a side
  src/main.rs           the app: templates/winui.rs or templates/cupertino.rs
  .gitignore            /target
```

The program's id is `dev.example.` and its name without `-` and `_`, which an id cannot hold, so `my-app` is `dev.example.myapp`; the name people see is the package's, spaced and capitalized, `My app`; its version is the package's, `0.1.0`. A name is refused unless it is lowercase ASCII letters, digits, `-` and `_`, starting with a letter, and neither a Rust keyword nor a name cargo keeps for a package with a binary (`test`, `build`, `deps`, `examples`, `incremental`); so is a folder that is there already. Nothing is written then.

Made inside a cargo workspace, the program joins it as `cargo new` joins one (cargo's `ops/cargo_new.rs`), and never writes a `[workspace]` of its own, which would stop the workspace from loading with cargo's "multiple workspace roots found". The workspace is the `[workspace]` of the nearest `Cargo.toml` above the folder, unless its `exclude` names the folder as written, when the program is made as outside any workspace. The program inherits every key of `[workspace.package]` as `<key>.workspace = true` and, for `[workspace.lints]`, `[lints] workspace = true`, as `cargo new` writes them; each of its dependencies that `[workspace.dependencies]` lists as `<name>.workspace = true`, as `cargo add` writes one, and the rest by their crates.io versions; and no `rust-toolchain.toml` when the workspace's root has one, which rustup then takes for the program's folder too. Its folder is added to `[workspace.members]`, in order when they were in order, unless one of their patterns matches it already, as `builtin-apps/*` matches `builtin-apps/hello` in WaOS's own workspace; the root manifest is edited in place, keeping its comments, and stderr says so: ``cargo waos: added `hello` as member of workspace at `<root>` ``. Then, as `cargo new` does, cargo is asked to load the workspace with the program in it, and when it cannot, as for a second package of a name the workspace has already, its error is printed as a warning; the program is written all the same. A `.gitignore` is written whatever the folder is in, where `cargo new` writes none inside a repository it finds.

The SDK's crates are named at this release's version, since the workspace versions its crates together, and Waft's at the version `wasdk-adapter-waft` is built on, so a new program builds from crates.io as it is written. `tests/new.rs` builds each template against this workspace instead, so that a change to a template, to the SDK or to Waft is tested before it is published rather than after, when building from crates.io would still build the last release: it runs `cargo waos new` in a folder of its own, patches crates.io there, in a `.cargo/config.toml` above the program, with the workspace's path of each crate the program's manifest names, gives the program the workspace's `Cargo.lock`, and runs `cargo waos build`, into a target directory under `CARGO_TARGET_TMPDIR` kept between runs. The published crate leaves the test out, since it needs the workspace.

`build` runs cargo for `wasm32-wasip3`, debug unless `--release` (a debug build carries function names and line tables, `debug = "line-tables-only"`, which is what WaOS reads of debug info: trap backtraces with file and line), and puts the component cargo made at `target/waos/<profile>/<package>.wasm`, named after the package; without `-p` the package is the one of the current directory. It prints the component's path.

`run` reads the program's id from its `[package.metadata.waos]`, the one field of the table a run needs, and refuses a package without the table, with `package`'s message, before it builds anything. It builds the program, connects to the WaOS on this machine at `waos_dev_protocol::listener_path()`, starts the installed WaOS when none answers and waits up to ten seconds for it, and sends the program with its id (the design's decision 29). WaOS compiles the component before it starts it, minutes for a large debug build, unless it is the component the last run of the id sent, unchanged, whose code WaOS keeps; and `run` says so as the compile starts (`cargo waos: WaOS is compiling <name>`), then that the program runs. WaOS runs it as the program the id names (decision 11 of `docs/proposals/2026-10-23-permissions.md`): with that program's settings and its own `/data` and `/cache`, installed or not, as Xcode's and Android Studio's runs share the app's container and permissions. It starts WaOS as `open -b dev.waos.app --stderr ~/Library/Logs/WaOS.log --args --launcher-closed`, with `--env RUST_LOG=…` before `--args` when `RUST_LOG` is set, so what WaOS logs is appended to that file, picked by the same `RUST_LOG`, and says so once with the file's path; and with `--env WAOS_NATIVE_UNWIND_INFO=…` when that is set, which at `1` has WaOS compile programs with native unwind information: set it to profile or debug a program natively, for a native profiler or debugger to walk through its frames, and not otherwise, since macOS then takes seconds to drop a large program. `--launcher-closed`, WaOS's own argument, keeps its launcher closed at launch, so the run shows only the program until the user clicks WaOS's icon in the Dock. These take effect only when the system starts the app, and a WaOS running already keeps its own. On Linux it starts WaOS as the desktop's launcher does, by its desktop entry, `dev.waos.app.desktop`, the one WaOS's package installs, found in the `applications` folder of the XDG data folders, the user's first (`desktop_entries`): the program its `Exec` names, with the entry's field codes dropped and `--launcher-closed` added, in a process group of its own so Ctrl-C here never reaches it, with this process's environment, `RUST_LOG` among it, and what it writes to standard output and standard error appended to `$XDG_STATE_HOME/waos/waos.log`, or `~/.local/state/waos/waos.log`. Not `gtk-launch dev.waos.app`, which passes an app nothing but files to open, nor a `waos` found on the `PATH`, which may be any build. On Windows it finds WaOS where its installer recorded it among the installed apps, the `InstallLocation` of `Software\Microsoft\Windows\CurrentVersion\Uninstall\WaOS`, the user's own before the machine's, as `cargo waft build nsis` installs it, and starts `waos.exe --launcher-closed` there on its own, apart from the terminal, with this process's environment, `RUST_LOG` among it, its standard error appended to `%LOCALAPPDATA%\WaOS\Logs\WaOS.log` and its standard output to nowhere, so it does not attach to the terminal's console and a Ctrl-C there ends the run, not WaOS; with none installed, the run ends saying how to install it. Elsewhere a run with no WaOS answering ends saying to start WaOS by hand. The connection is the run: what the program writes to stdout and stderr comes to this process's own, each line after the program's name (`<name>: `), as it wrote it, until the run ends; then one line on stderr says how the program ended, and the exit status is 0 for a `main` that returned success and 1 otherwise, for a run WaOS refused, and for one WaOS stopped or replaced with a later run of the same id. The name is on every line, not only when another run replaced this one, so two runs' logs read apart whatever order they arrive in, and a prompt without its newline is prefixed once, where its line began. Ctrl-C closes the connection, which stops the program in WaOS, and exits with 130. A WaOS of another build answers with another protocol number, and the run ends with a line naming both before anything is sent.

`run --env NAME=VALUE`, given any number of times, adds a variable the program reads in that run and no other, as Docker's `-e` does, so `cargo waos run --env RUST_LOG=debug` has a Rust program log at debug. Nothing of this shell's environment is passed, and installed programs never get these: only the run `cargo waos run` starts. A variable is `NAME=VALUE`, its name before the first `=`, which a value may hold more of; one with no name or no `=` is refused before anything is built. `TMPDIR`, which WaOS sets to the program's own `/tmp`, wins over a variable of that name.

`package` reads the program's id, the name people see and its icon from its `Cargo.toml`, and takes the version from the package's own `version`:

```toml
[package.metadata.waos]
id = "dev.example.triangle"   # reverse-DNS; names the program for good, and what `run` runs it as
name = "Triangle"
icon = "icon.png"             # relative to Cargo.toml: a square PNG, drawn at 1024 pixels on a side and at least 256, that fills the whole square: no rounded corners, margin, transparency or shadow of its own; WaOS shapes it on each system
```

Before it builds, it warns on stderr of an icon that breaks the rule above, saying what it found: not square, under 256 pixels on a side, or transparent pixels on its edges, its corners among them, as a rounded tile on a transparent margin has, which shows smaller than every other icon (`icon_rule`; decision 10 of `docs/proposals/2026-11-13-what-six-apps-found.md`). The warning does not stop the packaging, though `waos-package` still refuses an icon that is not square or is too small. It builds the release component, signs it with the user's signing key, writes the package at `target/waos/<id>-<version>.wapk`, prints its path, and lists it in `target/waos/index.json`, making the index when there is none: a listing of the same id at the same version is replaced, and every other is kept. `target/waos` then holds what a package source serves, the index with the packages beside it, each listed by its file name with its SHA-256; uploading the index and the packages as assets of a GitHub release makes the repository a source (the design's decision 45).

The signing key, Android's name for the private key that signs a publisher's packages, is the text of `WAOS_SIGNING_KEY` when that is set, as on CI, and otherwise the file `signing.key` in the user's configuration folder: `$XDG_CONFIG_HOME/waos/signing.key`, or else `~/.config/waos/signing.key` on macOS and Linux and `%APPDATA%\waos\signing.key` on Windows, apart from the WaOS app's own folder so removing the app never takes the key with it. Its public half, which each package carries as `publisher.key`, is the publisher's key. The first `package` with neither makes the signing key, in a file only the user may read in a folder only the user may open: by their modes, `0600` and `0700`, on Unix, and on Windows by an access list made with each, which names the user alone and inherits nothing, rather than DPAPI, whose file only this user on this machine could read back, where the key must be backed up and set as a CI secret as it is; and says where it is and the fingerprint of the publisher key its packages carry (the design's decision 47). Back it up: every update of a program must be signed with the key that signed it first, so a lost key means publishing the program again under a new id. Both hold the same text, the key's PKCS#8 PEM (`-----BEGIN PRIVATE KEY-----`), so a CI secret is set to the file's content. A key that cannot be read is an error, never a reason to make another, and so is a `WAOS_SIGNING_KEY` set but empty, which is what CI gives a secret it does not have. On CI, where `CI` is set, a key is read but never made: with no `WAOS_SIGNING_KEY` and no key file, `package` fails saying to set `WAOS_SIGNING_KEY`, rather than sign with a key thrown away with the machine.

`screenshot`, `tap`, `press`, `drag`, `type`, `key`, `scroll` and `resize` are for the program the package's id names while a run of `cargo waos run` runs it, started in another shell (the design's decision 60): each connects to the WaOS on this machine, never starting one, sends one `Screenshot`, `Input` or `Resize`, and waits for the answer. WaOS refuses a program a run of its own does not run, one the library opened among them, so no tool reads or drives an installed program; and a window the program does not have, a point outside the window, text while nothing in the window is edited and a chord naming no key: each is said on stderr, with the exit status 1. The windows are numbered from 1 in the order they opened; `--window` names one, the first unless it says otherwise. A point is in the window's pixels, the screenshot's, from its top-left, written `<x>,<y>`; either number may be negative, as a scroll's `--by` often is.

`screenshot` writes the last picture of each of the program's windows as `window-<n>.png` in `target/waos/screenshots/<package>`, first taking away the window pictures an earlier screenshot left there, and prints one line for each, its path, its window's number, title and size in pixels: `…/window-1.png  window 1 "Notes" 1600x1200`. `--out` writes them where it names instead: a folder, one that exists or is written with a `/` at its end, holds every window's picture as `window-<n>.png`, and any other path is one file for `--window`'s picture alone, the first window's without `--window`; each is made where it is missing, and where the picture went is printed as before. A picture is what the window shows, at its size: what the program drew in it over its composition layers, each as it shows now, a buffer the program presented, a player's video or a camera's picture, drawn together by WaOS (the design's decision 62); a window that has drawn nothing yet has no file, and a window out of sight, minimized or hidden, shows its last picture and draws nothing new until it is in sight, which stderr says. A window other windows cover is in sight, and draws, while `cargo waos run` is attached (the design's decision 63), so a screenshot of a run's window behind the terminal is its picture now.

The input is simulated by WaOS (the design's decision 64): WaOS makes the events itself and hands them to the program as it hands over the user's own input, so the program hears them as a user's, while the system never sees them: the real pointer does not move, no other app hears a key, and the window's menu bar is not offered a key. `tap` presses and releases the mouse's primary button at the point. `press` presses it at the point, holds it for `--duration` milliseconds, 1000 unless it says otherwise, longer than Flutter's long press waits, 500, and releases it there: XCUITest's `press(forDuration:)`, Playwright's `mouse.down`, a wait and `mouse.up`. `drag` presses it at `--from`, holds it there for `--hold` milliseconds, none unless it says otherwise, moves it with the button held to `--to` in `--steps` equal moves, 10 unless it says otherwise, one every `--duration` divided by the steps, of 300 milliseconds unless it says otherwise, and releases it at `--to`: a pointer down, moves over a time and an up, as adb's `input swipe` with its duration, adb's `input draganddrop` and XCUITest's `press(forDuration:thenDragTo:)` with a hold, and Playwright's `mouse.move` with `steps`, whose moves go a step's share of the way further each, as these do. Both points must be in the window; a drag's way between them then is too. A press and a drag take the time they say before WaOS answers. `scroll` turns a mouse wheel there by `--by`, in pixels, a positive `dy` scrolling down, towards the content's end. The mouse is one of the run's own, which stays where an input left it, so a tap reaches a control a hover reveals as a user's second click does. `type` enters the text into what the window edits, as an input method enters what it commits, in place of what is selected; with nothing edited, it is refused, and the text field is tapped first. `key` presses a key, or a chord of modifiers and a key joined by `+`, on a US keyboard: `cmd`, `ctrl`, `alt` and `shift`, then a letter, a digit, one of ``- = [ ] \ ; ' ` , . /``, or `enter`, `escape`, `tab`, `space`, `backspace`, `delete`, `up`, `down`, `left`, `right`, `home`, `end`, `pageup`, `pagedown` or `f1` to `f12`, in any case. A key the program leaves goes nowhere, where a real one would go on to the window's menu bar and choose the item it is the shortcut of, one of the program's menus or one of WaOS's (Quit, Copy, Undo): a chord that only a menu item answers does nothing, a gap known for now. Each input returns once the window has shown a picture the program drew after it, so a screenshot taken next shows what it did; when none comes within two seconds, as for an input that changed nothing, or at once for a window out of sight, minimized or hidden, it returns saying so on stderr, with the exit status 0.

`resize` sizes a window so what it shows, the view the program draws in, is `--to` logical points, the unit the program lays out in, its top-left where it is: what a test needs to see the program at a phone's width, 390x844, or in a narrow window. It is Playwright's `setViewportSize` for a program's window, and named as `tap` and `drag` are, by the plain verb for what a person does to a window. A screenshot's pixels, the points the input commands take, are these points times the window's scale, 2 on a Retina screen, so `--to 390x844` gives a screenshot of 780x1688. WaOS sizes the window as the program's own `set-frame` sizes it, keeping what the window holds around the view, its title bar, so a window in WaOS and a program's own app on macOS each take the size as they take the program's, or what their window system keeps it to, while a tab of a phone's deck is in no window, and is refused, exit status 1. It prints the size the window took, in points with its scale and in pixels (`window 1: 390x844 points at scale 2, 780x1688 pixels`), says on stderr when that is not the size asked for, and returns once the window has shown a picture the program drew at that size, or saying on stderr that none came within two seconds.

Nothing here runs a program: it runs in the WaOS app, on a thread of its own there, and this process holds only the connection.

`settings` and `set` read and set the program's settings, which WaOS keeps, as its settings page in WaOS shows them, one row each, so a run never waits for a person: a row on Ask is asked of the user when the program asks; one set is answered without asking, every run, installed or not, since a development run is the program its id names (decision 11 of `docs/proposals/2026-10-23-permissions.md`). The rows, by the names `waos-dev-protocol`'s `Row::parse` takes:

```text
camera | microphone                                          allow | deny | simulated | ask
notifications                                                allow | deny | ask
simulated-microphone                                         tone | silence | global
network | local-network | clipboard-read | clipboard-write   on | off | global
record                                                       on | off | global
link-scheme <scheme>                                         allow | deny | ask
role.inspector                                               allow | deny | ask
machine | audio-output                                       <id> | ask
open-file | open-folder | save-file                          <path> | ask
open-files                                                   <path>... | ask
```

`settings` prints each row, its key, what holds, whether it follows the setting for every program, and for `machine` and `audio-output` the ids and names offered now; `set` prints the rows after the change. `simulated` gives the program a camera or a microphone of WaOS's own, touching no device and asking the system nothing: the camera a test pattern, "WaOS test pattern", on macOS and Android so far, and the microphone a quiet beep, or silence with `simulated-microphone silence`; the program is shown using a simulated device. A question set to `ask` drops the program's own answer, so it follows the answer for every program, which is Ask unless the user set one on WaOS's page for every program, and `set` says so when it is not. A path is made whole against the current directory, as `waos open` makes its files, and WaOS refuses one the dialog could not have chosen: a file to open that does not exist, a folder that does not exist, a file to save in a folder that does not exist; and a machine or an output not offered now. `role.inspector` answers whether a program whose component imports `wasdk:inspect` may hold the inspector role, which it is asked about at its start, before anything of it runs; it has no setting for every program, and `ask` asks again at its next start. When the question comes, a set answer that no longer holds is what the picker or the dialog answers for nothing chosen: no machine, `not-found` for the output, the dialog's failure with why; never another, and never the question shown in its place. Both reach a program a run of `cargo waos run` on this machine runs or has run, or a development program the store does not have installed, whose settings are kept from before its first run; never another installed one, and start WaOS when none answers, as `run` does, since the rows are set before the run that needs them.

While a row is on Ask and WaOS asks, `run` says so on stderr, with the row that answers it ahead (`cargo waos: WaOS asks the user: may camera use the camera?; `cargo waos set camera allow|deny|simulated` answers it without asking from then on`), and `run --help` says that a question WaOS asks has a row and `cargo waos set` answers it ahead; `screenshot` says what WaOS asks over the windows, which the pictures do not show; and the input commands say WaOS is asking and give nothing, as a person's click goes to the question first.
