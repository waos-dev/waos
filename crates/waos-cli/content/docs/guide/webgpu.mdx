---
title: WebGPU
description: Draw a view with wgpu, a frame at a time.
---

A program draws on its views with WebGPU, through `wgpu` with `wasdk-wgpu` as its backend, so code written for wgpu draws unchanged. Frames are on demand: a program asks for one, and it arrives at the next refresh of the screen the view is on. The canvas is the size the program configures, whatever the view's, so a program configures it again at each `ViewEvent::Metrics`.

## With wasdk

```rust
let instance = wasdk_wgpu::instance();
let adapter = instance.request_adapter(&wgpu::RequestAdapterOptions::default()).await?;
let (device, queue) = adapter.request_device(&wgpu::DeviceDescriptor::default()).await?;
// one of views::views(), or from views::view_changes()
let view = SharedView::new(view);
let surface = instance.create_surface(view.clone())?;
let metrics = view.metrics();
let config = surface.get_default_config(&adapter, metrics.width, metrics.height).unwrap();
surface.configure(&device, &config);
// ViewEvent::Frame arrives on view.events()
view.request_frame();
// on it: draw into surface.get_current_texture()'s texture, submit, then queue.present(frame)
```

## With Waft

Waft draws every widget with WebGPU itself, through its renderer, valo, over `wasdk-wgpu`, and asks for each view's frames. It keeps its device to itself: an app that draws with WebGPU makes a device of its own, as above, and shows what it draws on a composition layer ([Compositing](/docs/guide/compositing)).

## Where it's missing

What wgpu has beyond WebGPU is not there, and panics at the call, naming the gap: among it ray tracing, mesh shaders, shaders other than WGSL, binding arrays, and a surface on anything but a view. A feature without a WebGPU name fails `request_device`.

## Interface

`wasi:webgpu/webgpu`, with the canvas and its frames in [`wasdk:platform/views`](/docs/reference/wasdk-platform/views)
