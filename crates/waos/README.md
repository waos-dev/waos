# waos

The engine: it runs programs and serves `wasdk:platform` and `wasdk:media` to them. It is organized by interface: each interface's module holds that interface's state, plain Rust tested without an engine, beside the code that serves it to a program. Beside them are the runtime (wasmtime, workers, freezing), the GPU side (WebGPU, shared hardware buffers), the shell's traits and the public API. The types wasmtime generates from the WIT are used directly; they come from the crate's own copy of the WIT, `wit/` beside `src/`, which `cargo xtask sync-wit` copies from the repository's `wit/`, the one edited. The engine reaches nothing outside itself: it makes hardware buffers, and the shell shows them.

- **Takes:** a `Shell`, the embedding app's parts, one per job (`ViewPlacement`, `VsyncWaiter`, `ShellCompositor`, the system's compositor, whose layers, `ShellCompositionLayer`s, the engine holds for a program's `composition-layer`s and never looks into but to hand one a buffer the program presents on it and to ask what it shows now, a `LayerPicture`, none for a shell without one, `Prompts`, `ShellClipboard`, `ShellMenuBar`, `ShellContextMenus`, `ShellTrayIcons`, `ShellAudioOutputPicker`, `ShellRecordingIndicator`, `ShellFileDialogs`, `ShellOpener`, `ShellNotifications`, `ShellMediaPlayers`, `ShellMediaAssets`, `ShellImageCodecs`, `ShellVideoFrameReaders`, `ShellCameras` and `ShellMachinePicker` now, the last fifteen none for a shell without them, with `NoPrompts` for a shell with nobody to ask); the machine's facts, whole, as `PlatformState` and the setters that keep it current; a `FreezePolicy`, how long a program stays hidden before it is frozen; what moves its time (`EngineTime`), which freezes, the moments a view is hidden or shown, when its spare hardware buffers go and when a program's sound is read are read from: its own thread every 100 ms (`Real`), as an app has it, or a test (`Manual`, with a `ManualTime` the test keeps and moves with `elapse`, each 100 ms tick on the way running in order); whether programs are compiled with native unwind information, for a native profiler or debugger (`native_unwind_info`, off unless asked for); where each running program's `/tmp` is made (`temporary_folders`), a folder of the app's own among its caches, on the volume of the programs' `/data`, so a file renamed from one into the other is one rename; which proxy programs' HTTP goes through (`HttpProxy`: the system's, as an app sends, on macOS read from its settings with their exceptions and beneath the environment's variables, or none, as the tests send, whatever the machine's settings); for each program, a `ProgramEnvironment`, the capabilities chosen for it (its fonts, so far), what the user lets it use (its `ProgramGrants`), its own folders (`ProgramFolders`), where its output goes and the variables whoever runs it gives it, a development run's `--env` (decision 68), and the views the shell gives it at start (`PlacedView`); and, as the program runs, the shell's reports of what happens to its views (`ProgramView`), its pointer and key events stamped on the program's clock (`ProgramView::now`), each key answering whether the program handled it (`KeyHandledFuture`: not handled when the program drops its reply unanswered or never reads the key), the user's Edit commands (`ProgramView::copy`, `cut`, `paste` and `edit`), and the user's Back, which the shell sends only while the program says it goes back within itself (`ProgramView::pop_route`, while `handles_back` answers true, the shell told each change through `ShellView::set_handles_back`, and doing its own with the press otherwise: decision 8 of `docs/proposals/2026-11-12-phone-programs-and-library.md`; the style of the system's bars a program asks for over a view goes to the shell as it says it, `ShellView::set_overlay_style`, the engine keeping no copy), each pointer event with the modifier keys the keyboard holds as it happens (`HeldModifiers`), of each screen's refresh it asked the shell's `VsyncWaiter` for, with when the refresh's picture is expected on screen (`screen_refreshed`), and of the app going to the background and coming back (`app_suspending`, `app_resumed`); what is on the platform's clipboard each time another writer changes it (`set_clipboard`); the item the user chooses in a program's menu bar (`RunningProgram::menu_chosen`); what the user opens with a program, files by their paths on the machine and links (`RunningProgram::open_requested`, an `OpenRequest`); what the user does to a program's notifications, at launch or while it runs (`RunningProgram::notification_activated`, an `Activation`); what the user does to a program's tray icon and chooses in its attached menu (`TrayIconReports`); each change of the state, the metadata and the cues of a player a program opened (`MediaPlayerReports`); and each change of the state of a capture session a program started (`CaptureSessionReports`). It answers a program's offsets from UTC (`system.utc-offset`) and what its time zone is called then (`system.time-zone-abbreviation`) for the time zone the shell names, by its IANA name in `PlatformState` and `set_time_zone`, from the system's time zone database through jiff (Android's own `tzdata`, and the copy jiff bundles on Windows), a zone the database does not hold answering none. It draws the glyphs of a program's fonts with valo's text stack (`valo-text`), plays a program's sound with web-audio-api and measures a sound file with symphonia before web-audio-api decodes it, keeps a program's paths inside its mounts with the system's calls (`rustix`), through a port of `wasmtime-wasi`'s copy of cap-std's path code, and sends a program's HTTP with hyper's client over the program's own connections, through the proxies macOS's settings name, read with `system-configuration`, in TLS with `tokio-rustls`, checking certificates with `rustls-platform-verifier`; and watches a program's folders through the system's watch of each, with notify.
- **Provides:** `WaOS`, which compiles programs into its code cache ahead of their load, loads them through it, removes a program's code from it, runs them, and freezes them out of sight; `RunningProgram`, one program as the shell adds and removes its views and lists them (`views`), reads its clock (`now`, which a shell in another process stamps the program's input from), asks it whether it may end, reads the menu bar it set last (`menu_bar`), tells it what its user opened with it (`open_requested`), what its user did to its notifications (`notification_activated`) and whether the system refuses it them (`system_notifications_refused`), keeps its views in sight though other windows cover them while a tool watches it (`watch`, held as a `Watching`, as `waos run` holds one while it is attached, decision 63), stops it and awaits its `ProgramEnd`, whose failure carries an `IncompatibleProgram` for a program built for another version of the interface and a `RoleNotGranted` for one whose user did not grant it a role it asks for, or awaits the moment it runs nothing (`idle`), is frozen (`frozen`) or stands at its freeze (`stopped_at_freeze`), what a test waits on to see the rule freeze a program and a frozen program stop; `Program`, a program loaded, which the embedder may name otherwise than by its file (`Program::named`, as the app names an installed program by its id); the shell's traits and what crosses them (`ViewPlacement`, `VsyncWaiter`, `ShellCompositor`, `ShellCompositionLayer`, `Prompts`, `ShellView`, `ShellTextInput`, `ShellWindow`, `ShellWindowSizeLimits`, `ShellClipboard`, `ShellClipboardItem`, `ShellMenuBar`, `ShellContextMenus`, `ShellTrayIcons`, `ShellTrayIcon`, `ShellAttachedMenu`, `ShellMenuAtIcon`, `ShellAudioOutputPicker`, `ShellRecordingIndicator`, `RecordingDevice`, `MenuChosenFuture`, `AudioOutputPickedFuture`, `TrayIconReports`, `ShellFileDialogs`, `FileDialogFuture`, `OpenOptions`, `FolderOptions`, `SaveOptions`, `FileType`, `ShellOpener`, `OpenFuture`, `ShellNotifications`, `ShellNotificationScheduling`, `NotificationFuture`, `ShellSystemPermission`, `SystemPermissionFuture`, `Notification`, `NotificationAction`, `ShellMachinePicker`, `MachinePickedFuture`, `MachineChoice`, `ShellMediaPlayers`, `ShellMediaPlayer`, `VideoOutput`, `MediaPlayerReports`, `ShellMediaAssets`, `ShellMediaAsset`, `MediaAssetFuture`, `ShellImageCodecs`, `ShellImageSource`, `ShellHardwareImageCodecs`, `OpenedImage`, `ImageFuture`, `ShellVideoFrameReaders`, `ShellVideoFrameReader`, `VideoFrame`, `ShellCameras`, `ShellCamera`, `ShellCaptureSession`, `OpenedCamera`, `StartedSession`, `CameraListFuture`, `CameraOpenFuture`, `CaptureStartFuture`, `PhotoFuture`, `CameraOutputs`, `CaptureSessionReports`, `PlacedView`, `ViewRequest`, `HeldModifiers`, whose keys a shell in another process sends on (`keys`), `HardwareBuffer`, `CopiedItem`, `Content` and `CopyOptions`, and `Question`, `Switch`, `Answer`, `SimulatedSound`, `FileDialog`, `AudioDevices`, `AudioOutput` and `AudioDeviceError`, re-exported from `waos-capabilities`), none of it a GPU object; `file_dialog_answer_refusal`, why a path cannot be set as a dialog's answer, which a settings page checks before it keeps one; and `Stats`, what a program costs, its workers' among it, and how many workers it runs, for the app to show; and what a tool that looks at a program's window and drives it reads of a view (the design's decision 60): what the view shows at its size, the last picture it handed the shell over what each composition layer it was handed with shows now, drawn on a GPU device of the engine's own (`ProgramView::picture`, decision 62), the moment it shows a picture the program drew after reading every event queued on it so far (`picture_after_events`), the title of its window as the program set it last (`window_title`), what its input methods edit (`editing_value`), and a size for the window it is in, so the view is that many logical points, its top-left kept, through the shell's window as the program's `set-frame` goes, which resolves with the view's metrics the shell reports next and is none for a view in no window, a phone's (`resize_window`); and the input a tool, `waos tap` or a test, gives the program as its user would, through its views as the shell reports a user's input, so the program cannot tell the two apart (decision 64): the program's own mouse (`RunningProgram::mouse`, a `Mouse`), which comes into a view before it presses there and leaves one view before it comes into another, and `Keyboard`, a US keyboard's keys and chords and text inserted as an input method commits it. What a program writes to its standard output and error goes to the `ProgramOutput` in its environment as it writes it, bytes tagged with their `OutputStream`; with none, it is `tracing` events under the `program` target, one per line, naming the program.
- **Used by:** the WaOS app, and any app that embeds the engine.

An app that embeds the engine sets `#![recursion_limit = "256"]` at its crate root: proving that a type holding a `WaOS` or a `RunningProgram` crosses threads walks into wgpu-core's registries behind the engine's GPU instance, deeper than the compiler's default limit allows, and what is a warning today (`recursion_depth_exceeding_limit`) becomes an error. The engine and its tests set the same.

Built so far, steps 4a to 4c of the design's work order: running a program, freezing it, and drawing. Programs are compiled to this machine's code with Cranelift, and on iOS, which gives an app no executable memory, to Pulley's bytecode, which wasmtime's interpreter runs and the code cache keeps as it keeps native code (`engine`'s `compile_for_this_system`). A program's `std::thread`s run as the component model's cooperative threads (`engine_config`), taking turns on the program's thread, where the program is linked with a libc that has them, as `docs/proposals/2026-11-22-cooperative-threads.md` says. `WaOS::load` compiles a component once into the code cache and maps it from there after, one file per component and engine settings, since wasmtime maps code compiled with native unwind information into an engine without it and the other way round; `compile` compiles a component into the cache ahead of its load, as an app does when it installs a program, and does nothing when the cache holds its code as the component is now, which `is_compiled` tells; `remove_compiled` removes a component's code, found by the component's path, so it is called while the component is still there, and a file written for a component removed while it compiled is removed once written; each compile writes a file under a new name and then removes the component's files compiled from it as it was before, so nothing is written over a file a program maps; Windows refuses to remove a file wasmtime maps, so there a superseded or removed file a running program maps is dated at the epoch, never mapped again, and removed by a later compile or removal once nothing maps it; nothing removes the files of another engine's settings or of an earlier wasmtime, whose names this engine never makes; a program's trap is caught by a signal handler on its own thread on every system, macOS included, not by wasmtime's Mach exception thread, which a caught signal can make end the whole process (decision 58 of `docs/proposals/2026-10-17-the-waos-project.md`), and since wasmtime installs its handler once for the process, an embedder's own wasmtime engine in the same process sets `macos_use_mach_ports(false)` too; `run` starts a program on a thread of its own, with a single-threaded tokio runtime and one store, the views given there before its code runs, and calls its `wasi:cli/run`, its code linked once for it and its workers (`running::instances`); the engine's time ticks every 100 ms (`engine_time`, `epoch`), on a thread of its own or as a test moves it, and each tick adds the fuel each of a program's stores burned since the last into its `Stats`; `stop` ends a program from any thread, its store with it, so every GPU object it held goes back to wgpu-core with the handle that held it, measured by the engine's own test (`engine`) as the experiment measured it; and `ended` resolves, any number of times, with how it ended, a `ProgramEnd`: its `main` returned, with success or failure; it failed, trapping or unable to run, the error carrying an `IncompatibleProgram` when the program was built for another version of the interface, or a `RoleNotGranted` when it asks for a role its user did not grant, which `downcast_ref` finds, a trap's backtrace naming each frame's file and line from the program's line tables, which the engine reads from the component's file only once the program failed (`source_lines`), since wasmtime's own backtrace details read the DWARF at every unwind, a stop's among them, told apart where it happens: the link, wasmtime's `Linker::instantiate_pre`, which checks every import against what the engine serves before anything of the program runs, failed, its detail wasmtime's own words; or `stop` ended it. A program's workers (`workers`, `running::worker`, decisions 10 and 11 of `docs/proposals/2026-10-17-waos-v1-interface.md` and decision 1 of `docs/proposals/2026-11-13-what-six-apps-found.md`) are other instances of its code, each in a store of its own on a thread of its own with a single-threaded tokio runtime, as the main instance runs, made from the one linked code: `start` admits the worker among the program's, starts its thread, instantiates the code and calls its `worker-entry.run`, and answers once `run` has accepted the entry or refused it; the worker then runs until everything the call started has finished, wasmtime's `poll_no_interesting_tasks`, its `Worker` is dropped, or its program ends. A stream is a handle in one store's table, so each side's is the engine's own and a bounded channel joins them: what one instance writes ends at `stream::Forwarded`, which takes each message only once the channel has room, and the other reads the channel as a stream the engine produces, so a message is copied twice, out of one memory and into the other, and a reader that stops reading stops the writer (measured: a 16 MiB message takes 0.7 ms, about 21 GiB/s). A worker's store holds the program's IO side as the main instance's does: its grants, the files handed to it, its folders, its network and HTTP, its machines, its fonts, the system's settings, the screens, media assets and image codecs, WASI, its clock, WebGPU; and none of its user's side (`running::instances::UserSide::none`): no placement, so `views` lists none, hears of none and refuses a request `unsupported`, no compositor, clipboard, menu places, sound devices, dialogs, opener, notifications, players, frame readers, cameras or machine picker, each answering as a shell without it, and the lifecycle's requests to end and to open, the main instance's alone, end at once in it. The answers its user set for the program's pickers are the program's settings, read through its grants, which every instance shares: a worker's `pick` with a machine set answers that machine, kept as the main instance's would be, and with none set answers none, as a shell without a picker does; a worker has no dialogs or sound, so their set answers never reach it. All of a program's instances share its clock, its lifecycle, so they freeze and thaw together and its GPU work waits for the thaw in each, its `Stats`, whose fuel and memory count every store and whose `workers` counts those running, its activity (`idle` once no instance is in its code), and its trace span, a worker's span `worker` beneath it. A store's limits are its own, 32 instances and 32 memories, as the main instance's; a program runs at most 64 workers at once, its workers' workers among them (`workers::WORKER_LIMIT`), and `start` answers `refused` past them. When the main instance ends, returning, trapping or stopped, the program's workers end, and `ended` resolves once every one has, its store gone; a run that replaces it starts after.

Each interface's module holds its state, plain Rust tested without an engine, beside the `host` module that serves it over the types wasmtime generates (`bindings`): `views` (the list and its changes, a request through the shell's `ViewPlacement`, every method of a view and its text input, the shell's `ShellCompositor` as `get-compositor` answers it, none where the shell has none, and the composition layers a program makes on it, and the modifier keys a program was told of, one record for all its views, caught up with the keyboard before each pointer event as Flutter's desktop embedders do, the keys it missed arriving as synthesized key events stamped with the pointer event's time), `windows` (a window through `ShellWindow`, its move from a press, maximizing and minimizing among it, its frame, whether it is maximized and what the system's settings say a double-click on a title bar does from the engine's copies of what the shell reports, its size limits through the shell's `ShellWindowSizeLimits`, none where the shell's window has none, and `window-config`'s setters into `WindowConfig`, macOS's title bar among them), `screens`, `system`, `lifecycle`, `fonts`, `permissions`, `trust` and `clipboard` (the listing the shell sets, what a program writes as the shell writes it, and its `source`; the user's copy request, which writes once whatever the write switch says, and paste, which reads whatever the read switch says until the clipboard changes, mounting each file it names read-only at its own path as its `text/uri-list` is read); `files`, served as the WASI a program's `std` imports for them; `network`, served as `wasi:sockets@0.3`, its name lookup and its TCP and UDP, and the checks of its sockets and its HTTP; and `wasi`, the rest of what its `std` imports, with its output to its environment's `ProgramOutput` or, with none, to `tracing`. `wasi:webgpu` is served by the WebGPU host, `crates/waos-webgpu-host`, the wasi-gfx runtime's, modified (its README) over one wgpu-core instance the engine makes for every program (`gpu`), whose objects live in each program's store and go with it; the types the host generates are reused through `bindings`' `with`. A view's `context` is the host's canvas context over the view's canvas (`buffers`), which every context on the view shares.

Frames are served by refresh, one frame to a view for each refresh of its screen (decisions 38, 39 and 65). A view's `request-frame` made while the view has not had the frame of the refresh its screen is in is answered at once, with that refresh's times and a frame naming the view alone, as an observer added to Chromium's `BeginFrameSource` between two ticks is sent the one it missed; the refresh a screen is in is the last the shell told of, moved on by the whole intervals passed since at the rate the system says the screen has, and is not known, so nothing is answered at once, where the system says no rate or no refresh was told yet (`views::ScreenRefreshes::current`). Otherwise `request-frame` asks for the next refresh of the screen the view is on, through the shell's `VsyncWaiter`, once per screen until that refresh comes however many views on it ask (`views::ScreenRefreshes`), and where the screen's interval is known the engine asks for the refresh after each one a view was served, so the last refresh it was told of is never one a view has had while a later one has begun. Either way a frame is served only while the view is in sight and on a screen, in sight being on screen and not occluded, which the shell reports apart (`Presence`), or on screen and occluded while a tool watches the program (`RunningProgram::watch`, decision 63), a minimized window staying out of sight: one hidden, covered and unwatched, or on no screen waits, and asks once it can be served again; a watch begun or ended counts as each view's presence changing, the program's state derived again and a frame waited for asked for, so nothing is forced and the program hears nothing of a covering a watch keeps from it. At `screen_refreshed(screen, at)` each program's views on that screen that asked, are in sight, have not had that refresh's frame and have fewer than two frames in flight each get one `frame` on their own stream, after every event before it there, the same frame for all of them, stamped with `at` on the program's clock and naming them all (`views::ProgramViews::screen_refreshed`), as Android's `Choreographer` serves every window of its thread at one vsync; each hand-over is a `tracing` event under `targets::FRAMES` naming the view and the views its refresh served. A frame is in flight from the program's `present` until it is handed to the shell after its GPU work (`views::frames_in_flight`): a view with two in flight is left out of the refresh, or of the answer at once, and asks for the next, as Flutter's `Animator` does while its `FramePipeline(2)` is full, so a program whose GPU work is slower than its screen draws at the GPU's pace while the other views on the screen are served as usual.

A view keeps the picture it shows (`views::shown_picture`): the last one handed to the shell, from the moment the shell has it, with how many of the view's events the program had read when it presented it, which the view's event queue counts as it queues them and as the program reads them, a move merged into the one before counting as that one. Its hardware buffer is held from the pool as the shell's is, until the next picture replaces it and the shell has let go of it too, without anything drawing over it, and the layers it was handed with are kept with it, weakly, so they go with the program; `picture` draws a screenshot of it (`screenshots`): each layer asked what it shows now (`ShellCompositionLayer::current_picture`), a buffer it was presented, marked in use while it is read so the layer does not give it back, or a video's frame, held as its frame so its pool does not hand it out again, sampled through a texture over its memory and drawn where its placement puts it, through its transforms, cut by its clips, hidden only at an opacity of none, since the program's picture carries the fade, a buffer stretched over its rectangle and a frame whole at its shape, turned and mirrored as its `rotation` and `flip` say, as the system shows it, centred, the bottom-most first, then the program's picture over them at its own size from the top-left, as the shell shows a canvas, into a hardware buffer of the view's size, whose pixels it reads, BGRA and premultiplied; and `picture_after_events` resolves once a picture presented after the program read every event queued at the call is shown, or with nothing once the view is gone. The engine keeps a copy of what each view's input methods edit (`views::view_text_input`): whether the program is editing, from its `set-client` to its `clear-client` or until the platform ends editing, and the value it set or an input method changed last, each side handing over the whole of it; and each window's title, as the program's request asked for it or `set-title` set it last.

Hardware buffers are the engine's (decision 3), on Apple's systems, Android, Linux and Windows: each view has a pool of `IOSurface`s, on Android of `AHardwareBuffer`s in RGBA8, on Linux of dmabufs in BGRA8 that GBM allocates linear on the first render node and exports read-write, and on Windows of D3D12 textures in BGRA8 shared by NT handle, which D3D12 makes only on a device, so the engine keeps one of its own for it, on the adapter every program gets, D3D12's at high performance whatever the program asks (`os::windows`; Waft's device is on the same, as a shared texture opens only on its own adapter), three when the program configures its canvas, at the size it set with `view.set-canvas-size`, never the view's own, and again at its next texture once it sets another, a size past its device's largest texture, zero or none at all trapping it, and each frame a wgpu texture on the program's device over the hardware buffer it is drawn into, viewed in the hardware buffers' BGRA8 (RGBA8 on Android) or, where the program's configuration names it among its view formats, in its sRGB counterpart, as WebGPU's canvas allows (`os`, the one place the system's allocation, Metal and Vulkan are named). On Android a program's device is opened through the engine's `DeviceOpener` (`os::HardwareBufferImports`), with wgpu-hal's `open_with_callback` adding `VK_ANDROID_external_memory_android_hardware_buffer` and `VK_EXT_queue_family_foreign`, as is the screenshots' device; a frame's texture is a `VkImage` imported over the buffer's memory, and the image is handed to the compositor and back (decision 8 of `docs/proposals/2026-11-11-android-pictures.md`, as amended): as the canvas hands a texture out it is acquired from `VK_QUEUE_FAMILY_FOREIGN_EXT` (`os::take_from_compositor`, skipped for a texture taken while the program is frozen, whose pixels are undefined anyway), and as the frame is presented it is moved by wgpu-core to a state its usage allows (drawn into, else copied into, sampled, copied from) and released to that queue family in that layout by a barrier recorded raw, in the submission that carries what the program wrote (`os::hand_to_compositor`); Linux does the same with a dmabuf: its device is opened with `VK_KHR_external_memory_fd`, `VK_EXT_external_memory_dma_buf`, `VK_EXT_image_drm_format_modifier`, `VK_EXT_queue_family_foreign`, a frame's texture is a `VkImage` in the dmabuf's modifier and plane layout over memory imported from a duplicate of its fd, and before a texture is acquired back the program's thread waits, up to 100 ms, for the fence the dmabuf's readers left, exported as a sync file (a semaphore imported from it crashes lavapipe's queue submit), since a compositor gives a buffer back with its read still pending now and then (a few of 187 buffers came back with a fence still pending); on Apple's systems the first does nothing and the second only submits what the program wrote; on Windows the first does nothing and the second moves the texture to D3D12's common state, from which another device's use starts. On Windows the shell copies each frame it shows into a composition swapchain of the layer's own on Waft's device and releases the hardware buffer once that copy is done, on every Windows that composes; a layer that moves or resizes shows a frame apart from the room the window's picture makes for it, a sliver along its edge while it moves, since DirectComposition applies the layers' placement a frame before the picture's swapchain shows (measured: while a layer moved, all 568 reads were a frame off), as Chromium accepts between its root swapchain and its overlays; composition textures, from Windows 11 24H2, would show the hardware buffer itself in one commit with the placements, with neither the copy nor the sliver. A frame never waits for a hardware buffer (decision 41), as Flutter's `FlutterSurfaceManager` and Firefox's `SurfacePoolCA` never wait for a surface: the canvas hands the program a free hardware buffer, or a new one when the shell holds every one. `present` submits what the program wrote on its device's queue that no submission carried, then hands the frame to a thread of the view's own, which waits for the GPU to finish that submission, after every one that drew the frame, and then calls `ShellView::present(buffer, layers, released)`, `layers` being the shell's own layer of each `composition-layer` the view holds, as the program's `set-layers` named them last, in the order named, with its placement as the program gave it, as the WIT's record, a transform that is not 16 values trapping the program as it sets them; the program's store keeps each view's layers (`views::view_layers`), so they go with the program, and a view the shell takes away lets go of its own then; a present with nothing drawn since the last hands nothing over, its layers with it, so the shell keeps showing the frame on screen with its layers; a released hardware buffer returns to the pool, which a shell over Waft's macOS host learns only at the view's next present. The program's `Stats` count its frames presented and its hardware buffers' bytes, its views' and its own. Spare hardware buffers go back once the view has drawn nothing for a second of the engine's time, at the tick that finds it so, down to three. On other systems drawing is refused with a message when the canvas is configured. On Linux a frame reaches the screen only where the compositor can read the program's dmabuf: a virtual machine whose host-side compositor reads guest memory only through virgl's blob resources, which the test VM lacks, shows nothing of it (a known limit). Where `WaOSConfig::hardware_buffers` is `HardwareBufferMode::Offscreen`, or `Auto` on a Linux machine where no `/dev/dri/renderD*` node opens (such as headless containers and CI runners under Mesa lavapipe), Linux falls back to offscreen buffers (`os::linux`): plain `wgpu` BGRA8 textures whose presented frames are copied back through a staging buffer under the freeze gate (`submit_once_thawed`) and tracked in flight, with no-op queue-family transfers and reader waits, so drawing and `ProgramView::picture` screenshots work without DRM or dmabuf extensions.

A program's own hardware buffers are apart from its views' (`hardware_buffers`, decision 35 of `docs/proposals/2026-11-02-program-media.md`): on Apple's systems `get-hardware-buffer-allocator` answers the system's allocator, and its `allocate` an `IOSurface` of the program's, in BGRA only, `rgba8` answering `unsupported`, a side past 16384, the largest 2D texture Metal makes, answering `too-large`, and a side of no pixels trapping the program; on Android an `AHardwareBuffer` with Android's usage for each the program names, in RGBA only, `bgra8` answering `unsupported`, and a side past 4096, Vulkan's guaranteed largest, answering `too-large`; on Linux a linear dmabuf, in BGRA only, a side past 4096 answering `too-large`; on Windows a shared texture, in BGRA only, a side past 16384, D3D12's largest, answering `too-large`, and `cpu-read` answering `unsupported`, as the CPU does not read a shared texture; elsewhere it answers none. A buffer answers what it can be used for, `hardware-buffer.usage`, at least what the program asked (decision 10 of `docs/proposals/2026-11-11-android-pictures.md`): on Apple's systems every flag for a buffer the program allocates, whatever it asked, and `gpu-sampled`, `composer-overlay` and `cpu-read` for a decoded image's and a video frame's; on Android what the `AHardwareBuffer` describes, `CPU_READ_RARELY` or `CPU_READ_OFTEN` as `cpu-read`; on Linux every flag, linear memory serving all (`os`). Every check reads that usage: `read-pixels` answers `unsupported` for a buffer whose usage lacks `cpu-read`, on every system. A program that reads the pixels of a buffer it allocated without `cpu-read`, which works only where the system gives the buffer more, is warned under the `program` log target, once (`hardware_buffers::unasked_read`). A buffer names no GPU API; `gpu_interop` serves `wasdk:platform/gpu-interop`, decision 36, whose `import-texture` makes a texture of a buffer on the program's device over its `IOSurface` through Metal and wgpu-hal (`os`), for what the buffer's usage allows, `gpu-sampled` as WebGPU's `texture-binding` and `gpu-color-output` as its `render-attachment` and `copy-dst`, `composer-overlay` and `cpu-read` as none, and copied from always, its pixels taken as written, and which holds the buffer through wgpu-hal's drop callback until wgpu frees it. The engine remembers the devices a buffer's textures were made on, and whatever reads the buffer outside the program's GPU work, its `read-pixels`, an encoding, a layer's present, first submits on each what the program wrote that no submission carried, its `write-buffer`s and `write-texture`s, an empty batch as wgpu advises, then waits for that submission, after every one the program made there (`SubmittedWork`), as a view's frame does before it reaches the shell. Each such reader is handed the buffer and gives it back (`ProgramHardwareBuffer::hand_out`, `take_back`): the first hands each texture the buffer keeps to the compositor's side with that submission, as a frame is (`os::hand_to_compositor`), and the last to give it back takes them back with their pixels kept (`os::take_back_from_compositor`), before a present's answer resolves; where the system hands textures over (Android and Linux), the buffer keeps each texture made of it until its next hand-out, a program drawing through one it let go of at once, and those the program no longer holds go then. A screenshot's hold on a buffer a layer shows holds back the release the engine handed the layer (`after_reads`), the engine counting the readers itself on Android, which has no use count the compositor shares, as `IOSurface`'s. The bytes of the buffers a program allocates and the hardware codecs decode for it are counted into the program's `Stats` with its views' hardware buffers (`hardware_buffers::counted_bytes`), by their rows' bytes, as each is made, and given back once its memory goes, after the program, its textures and whatever reads or shows it have let go of it. They are counted, not bounded: only the system refuses a buffer, an allocation or a decode answering `out-of-memory` where it has no memory left, as a WebGPU device's allocations fail past what the GPU has. A video frame's buffer is not counted: its decoder's pool bounds it.

A program shows a buffer it drew on a composition layer with the layer's `present` (`views::layer_presents`, decision 35): the buffer goes to a thread of the layer's own, started at its first present, which waits for what the program submitted and wrote on each device that drew into it, then hands the shell's layer the buffer as the system's own (`ShellCompositionLayer::present`), in the order the program presented, counted as the program's GPU work in flight until then; the engine holds the buffer, with the frame it is the memory of and the bytes it is counted for, until the shell says it is done with it, which resolves the present's answer, and answers it as well when the layer goes with the buffer unshown. The layer shows one source at a time, the last given it, buffers presented or a player's or a camera's picture, which the shell's layer keeps, as Waft's does.

Freezing is the engine's, by the rule in `lifecycle` (decision 25): a program hidden, by its views' presence, for the policy's `after_hidden`, where it sets one, is frozen (none by default: a program is then frozen only when the app suspends, since a hidden program's window may be one its user still reaches and closes, as a card in Android's Recents); `app_suspending` makes every program `paused` and frozen at once, and resolves once none runs, which the app awaits inside the platform's grace period; `app_resumed` puts each back in the state its views give and thaws it if shown; a program is thawed as soon as one of its views is shown, while it owes an answer to `request_exit`, since a frozen program cannot answer, and while a request to close one of its views or a view's going waits for it to handle it, since either decides whether it goes on: a swiped card in Android's Recents reaches a program frozen with the whole app. A frozen program stops inside its wasm at the next epoch tick and waits there, using no CPU, until thawed, when it goes on from where it stopped; one waiting in a host call stops as soon as it runs again; `stop` ends it where it stands. Each tick first runs what reads the engine's clock at each tick, a view's spare hardware buffers and a program's sound, since a sound starting keeps its program from a freeze, then every program's rule, so a freeze that comes due takes at that tick: no timer of its own, and nothing to cancel.

Freezing and the GPU meet in three places. A frozen view keeps only the hardware buffer on screen and the one being drawn: the rest go at the freeze, and a hardware buffer the shell releases while the program is frozen goes too, so a frozen program holds one hardware buffer or two; the pool adds what it draws into again after the thaw. A host call that would submit GPU work waits while its program is frozen: `queue.submit`, where the WebGPU host asks the engine's `SubmissionGate`, and `view.present`, a layer's `present`, `read-pixels` and an encoding of a hardware buffer, which submit the program's queued writes (`gpu::submit_once_thawed`), since a platform may refuse GPU work from the background and a program waiting in a host call when the app suspends could reach one before its first epoch check stopped it; thawed, a submission goes through under the lock a freeze takes (`Lifecycle::while_thawed`), so a freeze that comes meanwhile waits the moment the submission takes and none starts once a freeze has taken, and to the program it was a plain call. Nothing of the engine's runs on the program's thread under that lock but the submission, the program's or the engine's of its writes: a frame is handed to the shell by the view's own thread after its wait, never from a callback of wgpu-core's, which fires on whichever thread submits or polls. And `app_suspending` resolves only once no program has GPU work in flight: each program's stop (`RunningProgram::idle`, which a test also waits on to see a program has stopped) is its standing still, then a wait, on a thread of its own, for everything on every device the program opened, which the engine is told of at each `request-device` and keeps weakly, so a compute-only program's work counts as a drawing program's; the wait is counted with the frames the program presented as its work in flight until the GPU is done with it.

Fonts are the first capability the engine serves (`fonts`, the design's decisions 33 to 37): `wasdk:platform/fonts` answers from the valo `FontManager` in the program's environment, one the embedder shares among programs behind a lock, and with none every answer is empty, as on a machine with no fonts installed. Each face handed out, a typeface, gets an id of the program's own, the same however the face was matched, and the engine keeps the id's face: the file's bytes as valo shares them, the one mapping in the process, and the face's index. Ids are per program, not engine-wide: a glyph call can then draw only a face its program was handed, a program given no fonts draws none, and the files a program named are let go with it. The file a face is in has an id of the program's too (`typeface.file-id`), the same for every face in it and different for different files, and the face says its index in it (`typeface.index`), so a program that reads whole files reads each once, opening a stream only for a file it has not read: a file is the one mapping valo's manager shares among its faces, which it makes once per path on every system (CoreText's path on macOS, the font configuration's on Android, fontdb's on Windows and Linux), and the engine knows it by that mapping's address. A typeface serves its tables without the outline and colour-glyph tables (valo's `Typeface::tables`), so a program whose glyphs the engine draws never holds a font file; a program that reads fonts itself, as a typesetter does, opens a face's whole file (`typeface.open-stream`), with its length, so the program can reserve the file's size before reading, and the face's index in it, which the engine copies from that one mapping straight into the program's buffer, a megabyte at each read at most (`stream::stream_of_shared_bytes`): the file's size in each program that asks, where the interface would allow the file mapped into the program with no copy (measured on macOS: eight programs reading a 53 MiB face cost 0.2 MiB each mapped against 53.4 MiB copied), not built; a glyph call names a font, a typeface's id, a point on its axes and the fake bold and italic the program's text layout asks for (`embolden`, `skew`, valo's `FontSynthesis`), and the engine draws it with valo-text's `Rasterizer` over the face's whole file, making each font once and keeping it for the program's run: the face itself for no coordinates, or the face's named instances, the only points on its axes valo makes fonts at, so other points draw nothing. `changes` counts the manager's watch, made at the program's start, onto each stream the program opens. Each glyph call is a `tracing` event under `targets::GLYPHS`, at `trace`: which call, the typeface and glyph it named, and whether the engine drew a shape.

Permissions are served from the program's grants and the shell's `Prompts` (`permissions`, decisions 1 to 9 of `docs/proposals/2026-10-23-permissions.md`). Each getter of `wasdk:platform/permissions` hands the program a `permission` for one guarded capability, a switch (the network, the local network, reading and writing the clipboard) or a question (notifications, the camera, the microphone). Its `state` reads the program's `ProgramGrants` at each call, never a copy, so a change the user makes holds from the next call: a switch on or off is `granted` or `denied`, a question answered is the answer, and one not answered is `not-asked`; notifications the user allowed read `denied` while the system refuses them the program, as the system last said (below), the user's answer kept. `request` on a question not answered puts it to the user through `Prompts::ask`, once however often the program asks while it is put, keeps the answer through the grants' `set_answer`, and resolves to where the permission stands; on a question answered it resolves at once; for notifications the user allowed, now or before, it then puts the system's own question too, where the system keeps a permission of its own for the program (`ShellNotifications::system_permission`, `ShellSystemPermission::request`), keeps its answer as the system's refusal, and resolves to both; where the user did not allow them the system is not asked; on a switch it opens the switch's page in the program's settings through `Prompts::open_settings` and resolves once the user leaves it. `changes` hears the grants' `changed` and the system's refusal changing, and tells the state each time it is another than the last told. A program given no grants is granted nothing: every switch off and every question denied without asking. Enforcing the switches is each capability's, in its step.

A program's roles, what it may be besides a program (`roles`, decision 9 of `docs/proposals/2026-11-15-inspector-roles-and-compatibility.md`), are read from what its component imports, for an installed package and a development run alike: a component that imports an interface of `wasdk:inspect` asks for the inspector role. Before it is linked, each role it asks for is checked against its grants' answer (`ProgramGrants::role`), its own alone, since a role has no setting for every program; with none, the shell asks its user at once (`Prompts::ask_for_role`), the question put through the program's access, which is made before the program is linked so the trace and the summary tell it as any question, the answer kept (`set_role`), and a program without grants holds none. One not granted ends failed before anything of it runs, with a `RoleNotGranted` in its error, rather than wasmtime's missing import. A role's interfaces are linked only for a program that holds it. The inspector's, `wasdk:inspect`'s devices, audit and trace (`inspection::host`), serve this device alone, named as the embedder names it, and the programs on it as the embedder gives them (`WaOSConfig::inspected_programs`, an `InspectedPrograms`: the store's and the runs' for the app, none for the tests unless a test gives some, and then no device), every one the inspector among them, with each change to them and each one's icon as it is asked for, and a program started held for it (`start-held`, decisions 18 and 19), which the embedder starts and the engine holds after its access is made and before anything of it runs, its role's question included, until the inspector drops the `HeldProgram` (`WaOS::run_held`), or ended (`end`); a program's days as the audit log keeps them, today's kept first where it runs; and a running one's trace, a stream per capability, of the program the engine runs under the id asked for, its name, as the embedder names a program it runs (`Program::named`). The role is read again at each call, and each stream ends as soon as the user takes it back, so a program whose role is turned off sees no device, no program and no stream from then on.

Every guarded use a program makes is decided and told through its access (`access`, step 2 of `docs/proposals/2026-11-15-inspector-roles-and-compatibility.md`, in the model of `docs/proposals/2026-11-15-access-layer-design.md`): one per program, made as it is linked and shared by its main instance and its workers. It runs the capability's own rule against the grants, or against what was compiled from them, as the mount table is, and tells what the program asked with what the rule resolved it to, or the setting that refused it, by the key of the setting's row (`clipboard-read`, `camera`, `link-scheme`, `folders`, `network`, `domains`, `local-network`…). Every capability is decided through it: the clipboard, the cameras, the microphone, the machines, links, notifications, the questions, which are told (a question put, its answer, a switch's page opened, a pick mounted), the files, an open and a change decided by the mounts through the one function that leads a path through them, a file the program hands to the system (to open in an app, to read as media or an image, to open a dialog at, to paste elsewhere) decided as an open on its behalf, a machine's root it opens kept among its open files, a status, a symlink read and a hash only noted, a handle's first write noted once, a watch of a folder decided, and the network, each of today's checks wrapped whole: a lookup, with what it was for (the program, a request, a player), a TCP connection, an accepted one and a listener decided, each datagram noted, a request decided by its host. The access also keeps what the program uses now (`access::active_uses`, decision 11 of the inspector proposal), one registry of entries, each added as its guard, an `ActiveUse`, is made and taken away as it is dropped: each use that lasts, held by what owns the real thing from its start until it really ends (a capture session, the microphone recording, a command until its `exit_status` answers, an HTTP request until its response's body ends, a folder watch while its stream lasts), which the shell's indicator of who records reads; each file the program has open, the guard kept with its handle, shared by every copy of it and each stream reading or writing it, so the entry goes with the last, its path asked of the system only for a listener and outside the registry's lock, so a file closed before the listener reads is still named; and each of its sockets (`network::sockets::open_sockets`), a TCP connection it made or accepted or the engine made for its HTTP, a listener and a UDP socket, the guard kept with the system's socket, so the entry goes as the socket closes, with its addresses, the names they were looked up by, and the bytes it moved, read only when someone reads the entry. A listener (`RunningProgram::active_uses`) is given what is active as it subscribes and then each start and end, sent under the lock that makes them, and what each TCP connection and UDP socket moved, read by the listener's own stream on its own tick, at most once a second and only as it moved more, so a program nobody listens to pays nothing for it (decision 20); one whose 1024 changes are full is behind, sent nothing more until it is sent everything active again, so it never shows a use that ended, and the program never waits for it. With nobody listening an entry costs nothing measurable beside an open; a listener woken by each change makes an open about 3 µs slower while it listens. A command's end is watched on a thread of its own, since the program may let its handle go, and every command a program started, from any of its instances, ends with it, as a tree beneath it (`machines::StartedCommands`, `Child::end`): asked to end its own way, a hangup in a terminal and a termination with pipes, then killed after a short grace, so no command outlives the program that started it. What is told is counted in the program's audit summary (`access::summary`, step 3): per day from midnight UTC, the counts and small facts `waos-capabilities`' `AuditDay` holds, each list capped and what falls beyond counted, counted in memory under the day's lock beside the check that already ran, where a file is on the machine asked of the system before it, a datagram on an atomic, a stat not at all, into the program's day, which every run of it shares, begun from what was kept of today (`access::days`); one writer per engine, on a thread of its own, keeps each program's day through the engine's `AuditLog` (`WaOSConfig::audit`, the store for the app, none for the tests) about once a minute while it changes, as the day ends, at a program's end, and every day, waited for, as the app quits (`WaOS::keep_every_day`) or the engine is dropped, so no program waits on the store's lock or a file write and a clean quit loses nothing; an inspector, `waos inspect` and a program's settings page read today's day from memory (`WaOS::days_of`). Nothing is counted or kept while the user keeps no record of what the program does (`ProgramGrants::keeps_record`, decision 13), read again as the grants change, as the mounts are: turned off, what was counted of today is let go; the live trace and what the program uses now go on, since they keep nothing. Each thing told is also sent, as an event of `wasdk:inspect`'s `trace` (the engine's types of it in `inspection`, serializable as JSON of the WIT values by the WIT's own names, `waos-wit-serialize`), to whoever listens to its capability through `RunningProgram::trace` (`access::trace`, step 4): network, files, clipboard, camera, microphone, machines, permissions, links, notifications and output, each event naming the instance it came from; while nobody listens to a capability, a use of it costs one relaxed load and no event is made; a listener's events wait in a bounded channel, 4096, and one that falls behind loses events, the next it is sent saying how many. The days kept, what the program uses now and the trace are what `waos inspect` reads over the development connection (the app's `logic::dev_inspect`). A day is kept only once the program used something guarded on it, so a program that only writes its output has none.

The clipboard is the platform's one, which every program shares, and the shell's (`clipboard`, `docs/proposals/2026-10-25-clipboard.md`): the shell writes it, through `ShellClipboard::write`, and says what is on it, as a whole listing of items, each offered in MIME types and read one type at a time (`ShellClipboardItem`): after each write, as the write's answer, and each time another writer changes it, through `WaOS::set_clipboard`. The listing changes only by the shell's word and counts its changes, so an item a program listed reads `changed` once the count has moved, and a copy is replaced once a change is counted after it. A shell with no clipboard leaves programs none. A program sees what is on it, and its changes, only while one of its views has the focus, by its views' presence, a change made while none has it told as one gains it; its reads are the `clipboard-read` switch's and its writes the `clipboard-write` switch's, each read from its grants as it is made. A write takes what the program gives out of its store in the call, each data stream piped into a collection and each file looked up in its mounts, so a file outside them is `not-found` and the shell is given the file's path on the machine; the shell gets the bytes once every stream has ended. What the program put on the clipboard is its `source`, whose requests are the pastes of its promised forms and files, until another copy replaces it (`sources`). A paste thaws a frozen program while it owes the answer, and is answered with a stream and a `done`, which says whether the program made the content whole (`answers`): a form's paste takes the whole content, and fails unless it has it within five seconds (`PROMISE_DEADLINE`); a file's writes each chunk into the sink the shell hands it as the program streams it, so a big file is never held whole, and fails unless the program begins its answer within those five seconds; and either fails at once when the program drops the request or its `done` does not say ok. When the program flushes the clipboard, and before the engine stops it, it is asked for every form its last copy still promises, files aside, if nothing replaced it, and what it gives in time is kept, so later pastes are answered without it; a promised file ends with the program.

Menus are the shell's places for them (`menus`, `docs/proposals/2026-10-28-menus.md`): the menu bar (`ShellMenuBar`), context menus (`ShellContextMenus`) and tray icons (`ShellTrayIcons`), each none for a shell without it, and then a program's getter answers none and the program, or its framework, draws its own. A menu is a value, a flat list of entries naming their parent, given whole. The engine keeps each program's menu bar as it set it last (`RunningProgram::menu_bar`, none while it has set none) and tells the shell of each; which program's bar is shown is the app's choice, and a choice in it the shell reports with `RunningProgram::menu_chosen`, which every stream of the program's choices hears. A context menu opens at a point of one of the program's views, named by the program and the view's id, and a menu at a tray icon at the icon, each answering the id of the item chosen, or none. A tray icon is added once the shell has made it, `add` resolving to it or to why the platform did not show it, and it says which menus it offers; it is the shell's while the program holds its handle (`ShellTrayIcon`, removed when dropped): the program dropping the handle, or ending, removes it, after which its menus' handles do nothing and its streams end. What the user does to an icon, and chooses in its attached menu, the shell reports into its `TrayIconReports`; each call for an icon's events is a stream of its own, as each for a menu's choices is. A choice or an event on its way to a program thaws it until the program has handled it on each stream that carries it, read it and come back for the next or dropped the stream, as a paste of a promised form thaws it, and only one a stream will carry does: a program that reads none is not thawed for it.

File dialogs are the shell's (`file_dialogs`, `docs/proposals/2026-10-29-file-dialogs.md`): a function per kind, the options resources with setters, a dialog shown for the program as a sheet on the window of the view it names. The shell answers the paths on the machine the user chose, unless the user set the dialog's answer among the program's settings (`ProgramGrants::file_dialog_answer`), which is the answer in place of showing the dialog, each path checked as the dialog would have let it be chosen, a file to open that exists, a folder that exists, a file to save in a folder that exists, and the dialog failed with why when one does not hold, never another path (`file_dialogs::set_answers`); the engine mounts each at its own path before the program has it (`files::Picks`), read-only unless the options asked to write, and a save's target writable, whether or not it exists yet: among the program's mounts through its grants (`ProgramGrants::keep_picked`), which the store keeps in the program's own settings and mounts until the user removes it there, at once while the program runs; or, where the grants keep nothing, for the program's run alone (`HandedFiles::hand_pick`). An initial folder the program names is looked up among its mounts. A file in the program's own folders may be renamed onto a writable file mount, as one replace, copied beside the target first when the two are on different volumes, where the system refuses the rename (decision 3); the program's `TMPDIR` is `/tmp`, though Rust's `std::env::temp_dir` panics on WASI whatever `TMPDIR` says, and a program reads `TMPDIR` itself, or tells the `tempfile` crate with `tempfile::env::override_temp_dir`.

Opening is the system's, through the shell's opener (`opener`, `docs/proposals/2026-10-29-opening.md`): a link, a file, and a file shown in the system's file manager, a function for each, none for a shell without one. The engine keeps the rules (`LinkSchemes`): a link of `http`, `https` or `mailto` opens freely; a link of any other scheme, by its scheme in lower case, opens as the program's grants hold the user's answer (`ProgramGrants::link_scheme_answer`), and one not answered yet is asked through `Prompts::ask_to_open_links`, once at a time however often the program opens its links, as a permission's question is (`asking`), the answer kept through `set_link_scheme_answer`; a scheme refused, or asked with nobody answering, answers `denied` without reaching the shell, and text that is no link fails. A file the program names is looked up among its mounts and handed to the shell by its path on the machine; a path outside them fails without reaching it. A program given no grants is refused every scheme but the free ones, without asking.

Playing media is the system's, through the shell's players (`media_players`, decisions 2 and 5 of `docs/proposals/2026-11-02-program-media.md`), none for a shell without them. The engine keeps the rules (`media_sources`), as decisions 7 and 8 of `docs/proposals/2026-10-29-media.md` set them: a source that is an absolute path is looked up among the program's mounts and handed to the shell as the `file:` URL of where it is on the machine; a link of `http` or `https` is handed over once the program's own lookup of its host lets the program reach it, the network switch and its rule of domains for the internet and the local-network switch for this computer and the local network, as its HTTP's host is looked up when a proxy is in effect (decision 14 of the permissions proposal); a path outside the mounts, a host the rules refuse and any other text give a player that failed, with why, which reaches no shell. The lookup runs on a thread of tokio's for blocking work, so `open` answers at once, the player loading; what the program asks of it meanwhile waits and reaches the shell's player in order once it opens (`media_players::player`). The system's player fetches the link itself, so a second lookup of its own landing elsewhere is not seen, the blind spot a proxy has. The shell reports each player's state into its `MediaPlayerReports`, as it reports a tray icon's events; the engine keeps the newest in a `watch`, which `state` reads, and each `state-changes` stream hears the newest when the program reads it, passing over the states between, as an audio context's state changes are heard. A state change does not thaw a frozen program. A player's picture goes to the shell's own layer of the program's `composition-layer` (`VideoOutput::Layer`), or to the shell's own reader of the program's `video-frame-reader` (`VideoOutput::Frames`); the program dropping the player drops the shell's, which stops it. The program picks an audio track and a text track by their ids in the state's `tracks`, which the shell's player is asked for; the shell reports the cues of the text track shown, the user's caption settings merged in, and the media's metadata, each kept newest in a `watch` of its own: `cue-changes` hears the cues now, then each change, `metadata-changes` each change, `metadata` reads the newest.

Reading media without playing it is the system's too, through the shell's reading of media (`media_assets`, decision 32 of `docs/proposals/2026-11-02-program-media.md`), none for a shell without it. An asset's source is checked by the players' rules (`media_sources`): a path among the program's mounts is handed to the shell as its `file:` URL at once, a link once the program's own lookup of its host, on a thread of tokio's for blocking work, lets the program reach it, and anything else gives an asset that answers every question `refused`, with why, and reaches no shell. `open` answers at once; each of the asset's `async func`s waits for the shell's asset, where its link is still looked up, then for the shell's answer (`ShellMediaAsset`), off the program's store, so a program reads other things meanwhile. Its answers are the player's types, and its picture is the platform's own frame, held by the program as a reader's is (`ProgramVideoFrame`). The program dropping the asset drops the shell's once no read of it is under way.

Images are decoded and encoded by the system's codecs, through the shell's (`image_codecs`, decision 33 of `docs/proposals/2026-11-02-program-media.md`), none for a shell without them. The program's memory and GPU memory are two types, and every move between them is a call: an image decodes into a `pixel-buffer` in the program's memory and encodes from one through the shell's codecs (`ShellImageCodecs`, each image a `ShellImageSource`), and where the shell has hardware codecs (`ShellHardwareImageCodecs`, the same answer for as long as it runs), into a hardware buffer of the program's own, an `IOSurface` on Apple's systems, counted in the program's stats as an allocation is (`ProgramHardwareBuffer`, decision 35), and out of one, a buffer the program drew, a decoded image or a video frame's, handed to the shell as the system's own once the GPU has finished what the program submitted to draw into it, and held, with the frame it is the memory of, until the shell answers. The tests are one binary, `tests/all`, which links the engine and compiles the test shell once for all of them; each of its modules tests one part of the engine or one program, and names its tests, so `cargo test -p waos --test all survey::` runs survey's and `cargo test -p waos --test all <filter>` those whose names hold the filter. They run alongside each other in one process, so a test reads only what its own engine, shell and outputs record, or a program's lines in the log while it holds the program's turn (`tests/all/shell/turns.rs`). Three tests read what every engine in their process records, with nothing to tell its own from another's, and are binaries of their own: `tests/frames_in_flight.rs` and `tests/two_windows.rs` the frames the engine hands over, and `tests/waft_app.rs` the glyph calls it draws; `cargo test -p waos --test two_windows` runs one.
