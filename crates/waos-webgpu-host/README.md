# waos-webgpu-host

The WebGPU host the engine serves `wasi:webgpu` with: wasmtime's host of `wasi:webgpu@0.3.0-rc.2` over wgpu-core. It is the [wasi-gfx runtime](https://github.com/wasi-gfx/wasi-gfx-runtime)'s `wasi-webgpu-wasmtime` at revision `772bc344d3d0e24ba2d3ee29fc0033fc6ccea81d`, the one whose `wasi:webgpu` WIT is the copy in `wit/deps`, with the one helper it used from the runtime's `shared` crate folded in (`stream_pipe.rs`), and modified. It is a crate of ours because crates.io takes no Git dependency and no `[patch]` (the design's decision 57); it keeps the runtime's licence, Apache-2.0 with the LLVM exception (`LICENSE`), with a `NOTICE` saying where it came from and what changed, and each file changed saying so in its first line, as the licence asks, and the runtime's edition, so its patches can be offered upstream as they are.

- **Takes:** a wasmtime component `Linker` and a program's store, through `WasiWebGpuCtxView`; the one wgpu-core `Global` the embedder makes; the embedder's `DeviceOpener`, `SubmissionGate` and `DeviceListener`, each optional, and a `CanvasSurface` for each canvas; and its `wit/`, a world over `wasi:webgpu` whose package is a copy of the repository's `wit/deps`, made by `cargo xtask sync-wit`.
- **Provides:** `add_to_linker`, which serves `wasi:webgpu` to a program; the types bindgen generates for it (`wasi::webgpu::webgpu`); the values behind its resources (`Device`, `Texture`, `CanvasContext`, `GpuObject` and the rest), and `reexports`, the wgpu-core and wgpu-types it works with.
- **Used by:** `waos`, the engine, which links it as the crate that serves `wasi:webgpu` and reuses the types it generates (`crates/waos/src/bindings.rs`), as the design's decision 20 says.

It carries the experiment's patches, as `../wasdk`'s history under `vendor/` left them, until they land upstream:

- What the pinned revision leaves unimplemented is filled in: the canvas context (`canvas.rs`, a `CanvasSurface` the embedder supplies, so a platform that composites a view itself brings its own target), a texture's size and attributes, labels on every object (`labels.rs`), and every call a program can reach answers without a `todo!()`, a `panic!` or an `unwrap`.
- Every GPU object is given back when the resource holding it goes (`gpu_object.rs`): when the program drops its handle, or when its store is dropped with the handle still in its table, so a program ended where it stands leaks nothing.
- A lost device is reported as WebGPU reports one (`device_loss.rs`): `gpu-device.lost` resolves with the reason, `destroy()` loses the device at once, and no error is generated from a lost device.
- `request-device` refuses what WebGPU refuses, as WebGPU names it (`device_request.rs`); on an adapter below WebGPU's default limits, as the iOS simulator's Metal is, a device has the adapter's own value for each limit it falls short on, which one warning names, and a shader that needs more fails at its pipeline; and an embedder may open a program's device itself (`DeviceOpener`), for a system whose compositor needs a device made with extensions wgpu-core does not enable. Either way the device takes Vulkan's and DX12's memory in 4 MB blocks, with a block of its own for anything larger, not in wgpu's default of 128 to 256 MB.
- A program's misuse is answered as WebGPU answers it: a call on an ended pass or encoder is a validation error (`command_encoding.rs`), not a trap; a device's buffers are unmapped when it is destroyed (`buffer_mapping.rs`); a shader's compilation info is kept (`compilation_info.rs`).
- A canvas keeps its current texture until the frame is presented, as WebGPU's canvas does, so what the embedder does at present finds it whether or not the program still holds it.
- Uncaptured errors are written out, and host calls are traced.
- It runs on wasmtime 50 and wgpu-core 30, the versions the engine runs on; the pinned revision named wasmtime 47 and wgpu-core 29.

And three patches of this project's. An embedder is told of each device a program opens (`DeviceListener` in `WasiWebGpuCtx`, with `Device::downgrade` for a hold that keeps nothing alive), so it can wait for the GPU work on every device the program holds. An embedder may hold a program's submissions (`SubmissionGate` in `WasiWebGpuCtx`), for a platform that refuses GPU work from an app in the background: `queue.submit` waits on the gate, then submits inside it (`while_allowed`), so a hold that came between the wait and the submission refuses it and the wait starts again, and no submission starts once a hold has taken; the engine holds a frozen program's. And an embedder may submit what the program wrote on a device's queue that no submission carried, its `write-buffer`s and `write-texture`s, as an empty batch, as wgpu advises (`Device::submit_pending_writes`, and `WeakDevice::submit_pending_writes` from a weak hold), which answers that submission's index, after every one the program made there, so an embedder that hands a frame over once the GPU has drawn it waits for that submission on a thread of its own, the program's writes included, rather than learning the index from a `queue_on_submitted_work_done` closure, which wgpu-core fires on whichever thread submits or polls; it submits where its gate allows, as `queue.submit` does.

And made a crate of ours: renamed from `wasi-webgpu-wasmtime`, with `StreamPipeMap` and the broadcast helper it used from `wasi-gfx-runtime-shared` folded in and the rest of that crate left out, `raw-window-handle`, which nothing named, dropped, and its world's comment naming `cargo xtask sync-wit` rather than the runtime's `wit-fetch.sh`. It is formatted as the runtime formats its code, rustfmt at edition 2021, and has the runtime's lints, not the workspace's: its `unsafe` is the runtime's, a mapped buffer's range read and written.
