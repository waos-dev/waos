# Menus

**Decisions taken (2026-10-28).** The lead took these, one question at a time, starting the menus capability, which the clipboard's decision 14 (`2026-10-25-clipboard.md`) left the Edit menu's commands and the key reply to, and which v1 interface decision 6 (`2026-10-17-waos-v1-interface.md`) first sketched:

1. **A menu is a value rebuilt from state**, as Flutter's `PlatformMenuBar` is a widget: an item's checked or enabled state follows the app's state at each rebuild, and the host replaces the native menu with the new value, as Flutter's macOS embedder does. One value serves every place a menu shows, with nativeapi's breadth of places and item kinds (submenus, checkbox and radio items, shortcuts, icons), not its objects changed by hand; the WIT's menu, replaced whole (v1 interface decision 6), is the same shape, so WaOS's embedder converts a value to a value.
2. **A platform interface tells only what the system itself provides; where it provides nothing it answers `None`, and the app or the framework handles it: the host never stands in for a system.** So `Platform::menu_bar()` is `None` on Windows, Linux and phones, whose apps draw their menu bars (WinUI's `MenuBar` is drawn in XAML), and the app knows to draw its own. In this version: the menu bar (macOS), context menus (macOS and Windows; `None` on Linux, which has no system menu: GTK and Qt draw theirs in a pop-up surface, which winit offers only from 0.31, still a beta, so a framework can draw them there once Inset moves to it), tray icons (macOS, Windows, Linux's StatusNotifierItem), and the Dock icon's menu (macOS; Windows' jump lists are another thing).

```rust
pub trait MenuBar {
    /// Replaces the app's menu bar whole; a choice reaches the app as
    /// `EmbedderClient::menu_selected(id)`.
    fn set_menus(&self, menus: &[MenuEntry]);
}

pub trait PopupMenus {
    /// Answers the id of the item chosen, or none.
    fn show(&self, view: ViewId, at: Offset, menu: &[MenuEntry]) -> PopupMenuFuture;
}

// Platform::menu_bar(), popup_menus(), tray_icons(), dock_menu(): each None where the
// system has none.
```

3. **A tray icon exposes what each system allows, and its conventions are the framework's or the app's**: on Windows a right click opens a menu because the framework, hearing `ContextMenuRequested`, opens one at the icon, not because the host decided it. A menu the system opens by itself (macOS on a click, Linux when the desktop chooses) and a menu the app opens at the icon (macOS, Windows) are each `None` where the system does not offer it; the events are what the system reports. Dropping the icon's handle removes it (`NSStatusBar.removeStatusItem`, `Shell_NotifyIcon(NIM_DELETE)`, the StatusNotifierItem leaving the bus).

```rust
pub trait TrayIcons {
    fn add(&self, image: &TrayImage, tooltip: Option<&str>) -> Box<dyn TrayIcon>;
}

/// Removed when dropped.
pub trait TrayIcon {
    fn set_image(&self, image: &TrayImage); // TrayImage { rgba, size, template }
    fn set_tooltip(&self, tooltip: Option<&str>);
    /// A menu the system opens by itself, when it chooses: macOS on a click, Linux when
    /// the desktop decides. None on Windows.
    fn attached_menu(&self) -> Option<&dyn AttachedMenu>;
    /// The app opens a menu at the icon now: macOS and Windows. None on Linux.
    fn menu_at_icon(&self) -> Option<&dyn MenuAtIcon>;
}

/// As the system reports it; each system reports some of these.
pub enum TrayIconEvent {
    Activated { position: Offset },
    ContextMenuRequested { position: Offset },
    SecondaryActivated { position: Offset },
    DoubleClicked,
    Scrolled { delta: f64 },
}
```

4. **Edit's commands are items the system provides, sent to the focused view as events, and on by default**, as macOS's Edit menu sends `copy:` to whatever has the focus, the web's Edit menu and ⌘C reach the page as a `copy` event, and iOS's edit menu sends its standard edit actions to the first responder. Until an app sets a menu bar of its own, the host shows the system's standard one (the app's menu, Edit, Window), as Flutter's macOS template and Xcode's do; an app that sets its own replaces it whole, with provided items or items of its own, so a provided item is the default, never a lock. On macOS AppKit then recognises the Edit menu and adds dictation and emoji to it. For WaOS this is what the clipboard's decisions 4 and 5 need: Edit's Copy, Cut and Paste are WaOS's commands, a paste the user's.

```rust
pub enum ProvidedItem {
    // the app's
    About, Services, Hide, HideOthers, ShowAll, Quit,
    // the focused window's
    Minimize, Zoom, ToggleFullScreen, BringAllToFront,
    // the focused view's edit commands, sent to it as events
    Undo, Redo, Cut, Copy, Paste, SelectAll, Delete,
}

EmbedderClient::clipboard_event(view, ClipboardEvent::Copy(request) /* Cut, Paste */);
EmbedderClient::edit_command(view, EditCommand::Undo /* Redo, SelectAll, Delete */);
```

5. **A program gets the menu bar, context menus and tray icons**: the menu bar and context menus as v1 interface decision 6 has them, and tray icons free, as menus are and as no system asks before an app adds one, removed when the program ends; a click on a frozen program's icon thaws it to answer, as a paste of its promised form does. A program's Dock menu comes with its own Dock icon (step 10).
6. **The WIT is Inset's model in WIT's terms**: a menu is a flat list whose entries name their parent, since WIT has no recursive types, replaced whole; each place is a getter answering none where the system has none (`get-menu-bar`, `get-context-menus`, `get-tray-icons`), as `get-clipboard` does; choices come back by id. A view's events gain the key's reply (the clipboard's decision 11) and Edit's commands (`copy`, `cut`, `paste`, as the clipboard's decisions 4 and 5 have them, and `edit` for undo, redo, select-all and delete). A program's provided `quit` asks that program to end, as v1 settled; its `hide`, `minimize` and the rest act on WaOS's windows for it; a program that sets no menu bar gets the standard one.

```wit
interface menus {
  use views.{view};

  record menu-entry {
    id: u32,
    parent: option<u32>,
    kind: menu-entry-kind,
  }

  variant menu-entry-kind {
    submenu(string),
    item(menu-item),
    provided(provided-item),
    separator,
  }

  record menu-item {
    label: string,
    enabled: bool,
    check: item-check,             // plain, checkbox(on/off/mixed), radio(on/off)
    shortcut: option<shortcut>,
    icon: option<image>,
  }

  record shortcut {
    logical: u64,
    modifiers: shortcut-modifiers,
  }
  flags shortcut-modifiers { meta, control, alt, shift }

  enum provided-item {
    about, services, hide, hide-others, show-all, quit,
    minimize, zoom, toggle-full-screen, bring-all-to-front,
    undo, redo, cut, copy, paste, select-all, delete,
  }

  record image { width: u32, height: u32, rgba: list<u8>, template: bool }

  resource menu-bar {
    set: func(entries: list<menu-entry>);
    chosen: func() -> stream<u32>;
  }

  resource context-menus {
    show: async func(view: borrow<view>, x: f64, y: f64, entries: list<menu-entry>) -> option<u32>;
  }

  resource tray-icon {
    set-image: func(image: image);
    set-tooltip: func(tooltip: option<string>);
    attached-menu: func() -> option<attached-menu>;
    menu-at-icon: func() -> option<menu-at-icon>;
    events: func() -> stream<tray-icon-event>;
  }
  resource tray-icons {
    add: func(image: image, tooltip: option<string>) -> tray-icon;
  }

  get-menu-bar: func() -> option<menu-bar>;
  get-context-menus: func() -> option<context-menus>;
  get-tray-icons: func() -> option<tray-icons>;
}
```

7. **WaOS's menu bar shows the program in front's own menus**, and WaOS's while its library is in front. macOS titles the first menu with the process's name, whatever the app sets, so until step 10 gives a program a process of its own, WaOS keeps that first menu (About WaOS, Hide WaOS, Quit WaOS) and the program's own app menu follows under the program's name: `WaOS │ Notes │ File │ Edit │ View │ Window`.
8. **Inset's text fields leave Edit's command keys to a host that provides those commands**, as Flutter's text fields leave paste to the browser: the program's embedder answers that its host provides them, beside its `handles_editing_keys`, and a field then leaves ⌘C, ⌘X and ⌘V unhandled, so the key's reply says so, WaOS sends the key on to its Edit menu, and the field acts on the `copy`, `cut` or `paste` event, whose paste reads whatever the read switch says. This settles what the clipboard's decision 13 left to menus.

9. **A key a program leaves goes on to WaOS's menu bar the way Chrome sends on a key its page left** (2026-10-29): WaOS keeps the key from AppKit at once, since the main thread cannot wait for a program on its own thread, and when the program's reply says not handled it hands the key back through Inset's `MenuBar::perform_key_equivalent(&KeyEvent) -> bool`, for which Inset's macOS host keeps the `NSEvent` and calls `mainMenu.performKeyEquivalent:`, AppKit's public call, as Chrome's browser process does with the event it kept when its renderer answers not consumed. AppKit wants a key's answer before its call returns and lets no reply come later; every system that answers later claims the key, keeps it and sends it on, as Flutter's macOS embedder redispatches. Inset's own key handling stays answered at once.

10. **Edit's commands are WaOS's only where WaOS has an Edit menu** (2026-10-29): a program's embedder tells Inset that its host provides them only when the program has a menu bar (`get-menu-bar` answers one, macOS today), so its text fields leave ⌘C, ⌘X and ⌘V to WaOS there, and handle Ctrl+C, Ctrl+X and Ctrl+V themselves on Windows and Linux, as every app there does: those systems have no Edit command of their own and no notion of the user's paste, so a paste there is the program's own read, under the read switch. WaOS does not take a key the program left to act on it, which would invent a command those systems lack.
11. **A program's About shows WaOS's own About for now** (2026-10-29); a program's own About comes with its own process (step 10).

12. **Adding a tray icon resolves once the icon exists, and the icon is the capability** (2026-10-29): `TrayIcons::add` in Inset returns a future of the icon, as `PopupMenus::show` and `Clipboard::write` return futures, and the WIT's `tray-icons.add` is an `async func`; the icon's `attached-menu()` and `menu-at-icon()` then answer from the real icon, an object or none, so nothing needs to be known before an icon exists, and Inset's `menus_offered`, the WIT's `menus-offered` and the shell's matching method go. An `add` that waits can also tell of an icon that failed to appear.
13. **Inset's `PlatformTrayIcon` widget applies each system's convention**, as `PlatformMenuBar` does for the menu bar: an icon present while the widget is mounted, as SwiftUI's `MenuBarExtra` is while in its scene; its image, tooltip and menu of the same items `PlatformMenuBar` takes, and its click and double click, as Electron's `Tray` and nativeapi's `TrayIcon` have them; and its menu shown on each system's own trigger, as Electron's `setContextMenu` shows it (handed to the system where the icon offers an attached menu, opened at the icon on `ContextMenuRequested` elsewhere). An app that wants another trigger uses the icon's capabilities directly. A program in WaOS gets the same widget through its framework; the engine applies no convention.

```rust
PlatformTrayIcon::new(image)
    .tooltip("Notes")
    .menus(vec![
        PlatformMenuItem::new("Open Notes").on_selected(open),
        PlatformProvidedMenuItem::new(PlatformProvidedMenuItemType::Quit).into(),
    ])
    .on_activated(show_window)
    .on_double_clicked(show_window)
    .child(app)
```

Settled along the way, as the proposer's defaults:
- **The key order on macOS is the framework first, then the menu's key equivalents**, as AppKit offers a key equivalent to the key window's views before the main menu and Flutter's macOS embedder redispatches a key its framework left; the clipboard's decision 5 has the same order for WaOS's programs. Only macOS has a menu bar here, so the question is only its.
- **Inset's own system code**, as its macOS pasteboard is: AppKit, Win32's `TrackPopupMenu` and `Shell_NotifyIcon`, and StatusNotifierItem with its DBus menu (drawn by the desktop) over a pure-Rust DBus crate; not tauri's muda and tray-icon, which need GTK on Linux.

## Research behind it

| Place | macOS | Windows | Linux | iPad | Android |
|---|---|---|---|---|---|
| App menu bar | `NSApp.mainMenu` | none: WinUI apps draw `MenuBar` | none: GTK 4 draws in the window | iPadOS 26's, later | none |
| Context menu at a point | `NSMenu` pop-up | `TrackPopupMenu` | none: GTK and Qt draw in an `xdg_popup` | partly | partly |
| Tray or status icon | `NSStatusItem` | `Shell_NotifyIcon` | StatusNotifierItem | none | none |
| Dock icon menu | `applicationDockMenu:` | jump lists, another model | none | none | none |

| A tray icon | macOS `NSStatusItem` | Windows `Shell_NotifyIcon` | Linux StatusNotifierItem |
|---|---|---|---|
| Image | yes, a template image follows light and dark | yes | yes |
| Tooltip | yes | yes | yes |
| A menu the system opens by itself | on click; the app then hears no clicks | no | when the desktop chooses |
| The app opens a menu at the icon | yes | `TrackPopupMenu` | no |
| What the app hears | left and right clicks, double click | select, context menu, double click | activate, secondary activate, context menu, scroll |
