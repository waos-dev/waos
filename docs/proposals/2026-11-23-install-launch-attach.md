# Install, launch, attach: a run in steps, and WaOS as a platform to Waft's tools

Written 2026-11-23, as it was built on the branch `install-launch-attach`. Until now `waos run` was one route (decision 29 of `2026-10-17-the-waos-project.md`): the command sent the component over its dev-protocol connection, the connection was the run, the program's output streamed back on it, and closing it, by Ctrl-C or the terminal closing, stopped the program; nothing was installed, a development run was the program its id names, with that program's settings and folders (decision 11 of `2026-10-23-permissions.md`), and a tool's screenshot, input, size and inspection reached only a program a run of `waos run` ran (decision 60). This records the lead's decisions that replace that, and the shape built.

## The lead's decisions

1. **A run is install, launch, attach and stop, as Android's, iOS's and Flutter's are.** `waos install` builds the program and installs it; `waos launch` starts an installed program, with arguments and `--env` variables for that launch alone; `waos attach` reads what a running program writes and how it ends, and closing it detaches, the program running on; `waos stop` ends it. `waos run` is build, install, launch and attach, Ctrl-C stopping the program as before (the lead chose this), and `waos install && waos launch` is the detached form. Why: the connection as the run tied a program's life to one terminal, left nothing installed to open again from the launcher, and gave no way to read a program started any other way; every platform a developer knows separates the steps.
2. **Development installs, by a development id.** A program installed from its source is a program of its own, under its id followed by `.development` (`dev.example.notes.development`): its own folder, data, cache and settings, exactly as any installed program, so the store, the engine, the launcher and the per-program apps treat it as one. The store records where an install came from, a package with its publisher's key or the source with none; no package or source update replaces a development install, and no package may take a development id (`waos-package` refuses one). The launcher names it the program's name followed by " (Development)". The program published under the plain id keeps its data and its publisher's pin untouched. Installing again replaces the component and keeps the data and settings. Why: a development run under the plain id mixed a developer's build with the published program's data and pin, and left the published program unusable beside it.
3. **No limit on reach.** Every request that reaches into a program reaches any program running, however it was installed or started: screenshots, input, sizes, inspection, settings, attach, and service extensions, a published program as well as a development install, and the command names any program with `--id`. The lead: WaOS is open and gives power to its user, not a vendor; the dev socket is the user's alone. Why: a limit to programs a run of `waos run` started protected nothing from the user, who owns the socket, and kept the user's own tools from the programs they use every day.
4. **WaOS is a platform to Waft's tools.** A program's service extensions, named calls a development tool makes, each answered with JSON, as Flutter's `ext.flutter.*` are, are an interface of the platform (`wasdk:platform/service-extensions`, in `wasdk:platform` 2.1.0), which a Waft app's framework serves from its table of them in a debug build. Waft's CLI (`cargo waft ext`) reaches them through `waos`, which only carries the messages: `waos ext list --json` lists each program running that serves extensions in Waft's listing format, its address the command that relays to it, and `waos ext --id <id> --stdio` is that relay, one message of Waft's service protocol a line. Why: Waft's tools then reach an app on WaOS as they reach one on any of Waft's own hosts, with nothing of WaOS's to learn, and WaOS needs no copy of Waft's inspector; the relay trusts WaOS's socket rather than a token, since that socket is the user's alone.

## The shape built

**The store** (`crates/waos-store`). `InstalledProgram { manifest, origin }`, `Origin::Package { publisher }` or `Origin::Development { component_sha256 }`, the latter recorded in the install's folder as `development.sha256` in place of `publisher.key`. `install_development` installs a `DevelopmentBuild` under its development id; `holds_development` tells a build installed already, so an unchanged install changes nothing and its compiled code stays. `installed_changes` tells every change of what is installed, which the library follows.

**The dev protocol** (`crates/waos-dev-protocol`, major 3, since `Run` went). `Install` (the component's length and SHA-256, the `Upload` handshake, then `InstallAnswer::Installed` with the development id), `Launch` (`LaunchAnswer::Compiling` then `Launched`; abandoned when its connection closes while it compiles), `Attach` (`RunEvent`s: `Started`, what was written with nobody attached, its last 1 MiB, then the output with backpressure, then `Ended`), `Stop`, `Uninstall`, `Extension` (`ExtensionAnswer::Answered` with the JSON text, or refused `NotRunning`, `NotServing`, `UnknownExtension` with the names served, `InvalidParams`, `ExtensionFailed`) and `ServingPrograms` (each program's id, name and WaOS's process id).

**WaOS** (`apps/waos`). Every run, from the library, the launcher, files opened with it, a program's app, an inspector, or `waos launch`, writes to one kept output (`launch_outputs`) that goes to WaOS's log and to every attach, so any running program is attached to. The dev server's requests reach programs through the runs alone, never through who started them.

**The engine and the adapter** (`crates/waos`, `sdk/wasdk-adapter-waft`). `RunningProgram::service_extensions` hands a call to the program's stream of calls opened last, keeps the program thawed until it answers, and answers `unknown` at once when none is open; `serves` tells whether one is. The adapter, in a debug build alone, merges the calls into its event loop and hands each to `EmbedderClient::service_extension_call`. A program built against `wasdk:platform` 2.0.0 still runs: the engine serves 2.1.0, which wasmtime links 2.0.0's imports to by semver's rule.

**The command** (`crates/waos-cli`). `waos install`, `launch`, `attach`, `stop`, `uninstall`, `run` as their sum, `ext --stdio` and `ext list [--json]`; every command that reaches a program takes `--id <id>`, and with none, in a program's project, names the project's development id.

## Not in this change

The network transport for phones, which `waos` reaches not yet; an inspector's own use of service extensions inside WaOS; and a way for a source's listing of a development id to be hidden in the library rather than refused when chosen.
