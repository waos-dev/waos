# Opening, and being opened

**Decisions taken (2026-10-29).** The lead took these, one question at a time, starting step 7's opening, which v1 interface decision 8 (`2026-10-17-waos-v1-interface.md`) first sketched; v1 also settled that `http`, `https` and `mailto` open freely and any other scheme asks once per program and scheme, and permissions decision 4 that opening needs no permission. The rule throughout: a capability common to apps lives in Inset, and WaOS is a thin wrapper over it.

1. **Opening is a call for each kind, as Electron's `shell` and Tauri's opener plugin have them**: a link (`shell.openExternal`, `openUrl`), a file (`shell.openPath`, `openPath`), and a file shown in the system's file manager (`shell.showItemInFolder`, `revealItemInDir`); not one call taking a URI, as Flutter's `url_launcher` has it, whose `file://` would hide that phones share a file through the system (Android's `FileProvider`, iOS's `UIDocumentInteractionController`), that a WaOS program names a file by its path inside the program, and that only a file can be revealed.

```rust
pub trait Opener {
    fn open_link(&self, link: &str) -> OpenFuture;
    fn open_file(&self, path: &Path) -> OpenFuture;
    fn reveal_file(&self, path: &Path) -> OpenFuture;
    /// Whether some app on this system opens `link`; none where the system won't say.
    fn can_open_link(&self, link: &str) -> Option<bool>;
}
// Platform::opener(), none where the system has none; OpenFuture answers Result<(), OpenError>.
```

2. **Inset asks whether a link can be opened where the system answers it, and the WIT does not, for now**: macOS (`NSWorkspace.urlForApplication(toOpen:)`) and Windows answer freely, iOS only for schemes the app declared (`LSApplicationQueriesSchemes`), Android only for intents in its manifest's `<queries>`, and Linux's portal not at all; Apple and Google limit it because asking about many schemes tells which apps the user has, which identifies them. A program learns that nothing opens a link when opening it fails with `no-app`.
3. **Being opened: hearing it now on every system, with WaOS's open requests to programs; registering what opens a program with step 10**, on every system together, since macOS reads a program's types from its own bundle's `Info.plist`, which comes with apps of their own. Inset hears macOS's `application:openURLs:` for links as well as files, Windows' and Linux's launch arguments, iOS's `openURLContexts`, and Android's intent at launch and `onNewIntent`, through the Java activity of the file dialogs' decision 6. A program is opened through WaOS's command line until then.
4. **Keeping one instance is an opt-in crate of Inset's, `inset-single-instance`, not a platform interface**: Windows only starts a second process with the file as its argument, and keeping one instance is the app's own pattern, as Electron's `requestSingleInstanceLock` and Tauri's single-instance plugin are; Linux's D-Bus activation (`DBusActivatable`, `org.freedesktop.Application.Open`) is its way there, a named mutex and a pipe Windows', and macOS keeps one instance itself. A second launch's files reach the first through the crate, which the app hears as it hears the platform's open requests.
5. **A file a program is opened with is mounted writable**: the user chose to open it in this program. A role per file type, as macOS's `CFBundleTypeRole` (Editor, Viewer) gives, rarely helps in practice; a setting can come later if one is needed.
6. **The shapes** (2026-10-29): Inset's `Opener` (`open_link`, `open_file`, `reveal_file`, `can_open_link`) answers `OpenError` (`NoApp`, `Failed`); being opened reaches the app as `EmbedderClient::open_requested(OpenRequest { files, links })`, whose files are the file dialogs' `PickedFile`, since Android hands an opened file over as a `content://` URI and the web's `launchQueue` as a file handle, as their pickers do. The WIT's `opener` adds `denied` for a scheme the user refused, and `lifecycle` gains `open-requests`, each file mounted writable at its own path; a request thaws a frozen program until it has read it, and one for a program that is not running starts it and waits until it listens, as v1 settled for a notification's click.

```wit
interface opener {
  variant open-error {
    denied,
    no-app,
    failed(string),
  }

  resource opener {
    open-link: async func(link: string) -> result<_, open-error>;
    open-file: async func(path: string) -> result<_, open-error>;
    reveal-file: async func(path: string) -> result<_, open-error>;
  }

  get-opener: func() -> option<opener>;
}

// lifecycle gains:
record open-request {
  files: list<string>,
  links: list<string>,
}
// resource lifecycle: open-requests: func() -> stream<open-request>;
```
