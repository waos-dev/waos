# WaOS on Windows and Linux

Written 2026-11-13, after a survey of Waft and WaOS on a Windows 11 and an Ubuntu 26.04 virtual machine (both ARM64, neither with a real GPU): Waft built and ran on both; WaOS did not build on Windows, and on Linux ran programs that do not draw but opened no program's window. This records what the lead decided for the two systems, and the order of the work. What was planned on this date, not what is.

## The lead's decisions

1. **Both systems go forward at once**, each in its own virtual machine, with small fixes first and a design note before each large piece.

2. **Small fixes, as recommended**: on Linux, every window named after the app's identifier (the Wayland app id and the X11 class) with a desktop entry of the same name; an app's own file types registered through shared-mime-info, `.wapk` as `application/x-wapk`; `cargo waos run` starting the installed WaOS from its desktop entry; and a new view always drawn once, which on Wayland is what shows a window at all. On Windows: Waft apps as GUI programs that still write to the terminal they were run from; the app's icon in its executable; the dev connection over a named pipe that only the user can open; the signing key readable by the user alone; and `cargo waos run` starting the installed WaOS from what its installer registered.

3. **Programs draw on Linux through dmabuf buffers shown in Wayland subsurfaces**, as the design note proposed after Chromium, Firefox and GTK: buffers made with GBM, or `udmabuf` where there is no GPU; each composition layer a subsurface beneath the window's own picture; releases through `linux-drm-syncobj` where the compositor offers it; X11 refused with its reason for now. An experiment in the VM comes first (`../experiments/2026-11-13-linux-dmabuf-subsurfaces`), and the build after the lead reads it.

4. **A program's files on Windows are cap-primitives' Windows half, copied as the Unix half was**, with WaOS's own checks of each path component and folder changes made on the parent folder's handle; a single `NtCreateFile` open waits for an experiment that shows it pays. A machine's root shows Windows drives as `/c/…`, as Git's shell does. A command ended by Ctrl-C reads as the signal `INT`. Terminals are WaOS's own ConPTY start, with each command in a job object given at its creation: portable-pty can neither give the job at creation nor end the whole tree, and Microsoft documents the whole sequence.

5. **On Linux a program's layers go to the compositor as GTK 4 hands them, with no fallback** (2026-11-13, amending 3): a layer is a synchronized subsurface whenever the compositor has the protocols and making its buffer does not fail, as GTK's graphics offload does, which compares no devices and draws nothing itself in their place; X11 is refused with its reason. The experiment found a virtual machine whose compositor accepts such a buffer and shows nothing of it, because the guest's buffer is one the host-side compositor cannot read without virgl's blob resources: programs show nothing there, a known limit, and Waft drawing the layers itself where the compositor cannot, as Chromium does by allocating on the compositor's device, is later work. The lead weighed that fallback now: it brings a device rule and a second way of drawing layers for what is unusual on a real machine.

6. **The app's identity at run time is a setting of each system that reads it from the process, named as that system names it** (2026-11-13): Linux's `app_id` (Wayland's, and X11's class), and Windows' AppUserModelID, each filled from the app's one identifier at build time; macOS, iOS and Android read theirs from the bundle or the package the CLI writes from the same identifier. The lead weighed one generic identifier set on every system, which does nothing on most of them.

7. **Programs draw on Windows 10 and later, not only on the newest Windows 11** (2026-11-13): Windows has composed layers since Windows 8, but takes a picture an app drew elsewhere as a layer, with no copy, only since Windows 11 24H2 (composition textures), which the design note first proposed to require, refusing elsewhere. The lead found that too new. So a program's frame is copied on the GPU into a surface the compositor owns, one copy a frame, which works on every Windows that composes; showing the frame with no copy where the system can is later work.

8. **On Windows a program's picture may land one frame after the window around it while it moves or resizes, and that is accepted** (2026-11-13): the experiment (`../experiments/2026-11-13-windows-composition`) found DirectComposition applying a layer's new place a frame before the window's own picture, presented through a swapchain, shows; a picture that stays where it is shows no such thing. Chromium has the same between a page and its overlays. The lead weighed drawing the whole window through DirectComposition surfaces, which lands everything together at the cost of a second copy of the whole window each frame and a second graphics API, and committing each placement a frame late, which rests on a guess about the present queue. It goes away with the later work of decision 7: composition textures put the picture and the layers in one commit.
