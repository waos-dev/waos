# Bevy on WaOS: research

Research for the lead, 2026-11-05: what it would take to run Bevy programs on WaOS, and what WaOS lacks that games commonly need. Nothing was built or run; every claim is read from source unless marked *inferred* or *unverified*.

## The answer

- Bevy 0.20.1 can run on WaOS with a backend crate of its own, a `bevy_waos` plugin in place of `bevy_winit`, and no change to Bevy's engine logic; but not unpatched.
- **Blocker 1:** five Bevy crates assume every `wasm32` build is a browser and switch on Bevy's `web` paths, which on `wasm32-wasip2` panic at the first task spawned, and break the build when audio is on. A `[patch]` that drops the features they force and narrows a few `cfg`s to `target_os = "unknown"` fixes it, and could go upstream: Bevy's own manifests mark the assumption as a TODO.
- **Blocker 2:** Bevy draws only on `wgpu::Surface`s made from raw window handles, and `wasdk-wgpu` has no surfaces. Either `wasdk-wgpu` implements wgpu's surface over a view's canvas, or Bevy renders to textures by hand and loses its window targets.
- **Blocker 3:** a `.wapk` carries no files beside the component, so a game's `assets/` folder cannot ship. Embedding the assets in the component works, but every byte then lives in linear memory.
- **Gaps that degrade, most common first:** no threads, so one core runs everything; no pointer lock or raw mouse motion; no gamepads; no fullscreen a program can set; no sound backend for `bevy_audio`; frames paced only at the screen's refresh.

## What games need, and what WaOS has

| Need | How common in games | What WaOS has | What is missing |
|---|---|---|---|
| A loop driven by frames and input | Every game | `views.request-frame` and the `frame` event, with `time` and `display-time` (`views.wit`); every input on the view's `events` stream | Nothing for the loop itself. Bevy's runner is synchronous and the streams are async, so the program's `#[wasdk::main]` drives `App::update` (porting notes) |
| Drawing with wgpu | Every game | `wasi:webgpu` through `wasdk-wgpu`, with wgpu 30.0.1, the version `bevy_render` uses (`waos/Cargo.lock`; `bevy_render/Cargo.toml`) | Surfaces: `wasdk-wgpu`'s `create_surface` and `Queue::present` are gaps (`sdk/wasdk-wgpu/src/instance.rs`, `queue.rs`). Blocker 2 |
| Shipping assets | Every game with an `assets/` folder | `std::fs` over the program's files: `/data`, `/cache`, folders the user mounts (`sdk/wasdk/README.md`) | A package holds `manifest.toml`, `program.wasm`, `icon.png` and the signature, and other entries are not unpacked (`crates/waos-package/README.md`; the test in `package.rs` that drops `assets/splash.png`). Blocker 3 |
| Threads | Every Bevy game; `default_platform` turns `multi_threaded` on (`bevy/Cargo.toml`) | One thread per program. Workers are planned: separate instances that share no memory (v1 interface decision 10, `2026-10-17-waos-v1-interface.md`), not built: `program.wit` imports no `workers` | Shared-memory threads. Bevy then runs every system, the render world and all async tasks on one core, as on the web; workers cannot carry Bevy's ECS, which needs shared memory |
| Pointer lock and raw mouse motion | Common: first-person and third-person cameras, Bevy's own `FreeCamera` (`bevy_camera_controller/src/free_camera.rs`: `AccumulatedMouseMotion`, `CursorGrabMode::Locked`) | `pointer-event` with absolute `x`, `y` in the view (`views.wit`); `set-cursor(none)` hides the cursor | Locking the pointer and motion deltas unbounded by the screen's edge: Bevy's `MouseMotion` comes from winit's `DeviceEvent::MouseMotion` (`bevy_winit/src/state.rs`, `device_event`) |
| Cursor grab (confined) | Common: strategy and top-down games keep the cursor in the window | None | `CursorGrabMode::Confined` (`bevy_window/src/window.rs`) |
| Gamepads | Common: most action games, every couch game | Only `key-device.gamepad` and `joystick`, for keys a gamepad sends as keys (`views.wit`) | An interface for gamepads: buttons, axes, connection, rumble. The first version left gamepads for the formal version (`2026-10-16-waos-v1.md`). Bevy needs no fork for it: a plugin writes `RawGamepadEvent` and `GamepadConnectionEvent` (`bevy_input/src/gamepad.rs`), as `bevy_gilrs` does |
| Fullscreen | Common: most PC games offer it, many start in it | The menu's `provided-item.toggle-full-screen` (`menus.wit`), which the user picks; a size change arrives as `metrics` | A way for the program to enter or leave fullscreen, or to know it is fullscreen; exclusive modes with a video mode (`WindowMode::Fullscreen(_, VideoModeSelection)`, `bevy_window/src/window.rs`) |
| Frame pacing and vsync control | Common: a vsync toggle, frame caps, uncapped modes for benchmarks | Frames at the screen's refresh only; at most two frames in flight per view (`crates/waos/src/views/frames_in_flight.rs`); `screen.refresh-rate` (`screens.wit`) | `PresentMode` beyond `Fifo`, `desired_maximum_frame_latency`, a rate other than the screen's. Bevy falls back to `Fifo` when the surface offers only it (`bevy_render/src/view/window/mod.rs`, `present_mode`) |
| High-rate input | Occasional: rhythm and fighting games, drawing | Every event stamped (`pointer-event.time`, `key-event.time`); "while the program is behind, a pointer's consecutive moves are merged into the latest" (`views.wit`, `events`) | Little for Bevy: its input messages carry no time stamps and it reads input once per frame (`bevy_input/src/keyboard.rs`, `KeyboardInput`), so merged moves lose nothing it reads. Sub-frame positions are lost |
| Audio with low latency | Every game plays sound | Web Audio's graph, played on WaOS's own thread, with `latency-hint` and `base-latency`/`output-latency`; `stream-input-node` for samples pushed ahead, a tenth of a second ahead by default (`audio.wit`; `sdk/wasdk/README.md`) | A backend for `bevy_audio`, which is bound to rodio's default device (`bevy_audio/src/audio_output.rs`, `DeviceSinkBuilder::open_default_sink`). Samples pushed from the frame loop would add the stream's lead to every sound (*inferred*, unmeasured) |
| Asset loading speed | Every game, most at start and between levels | `std::fs`, each read crossing into WaOS | Parallel decoding: images, glTF and audio decode on the one thread between frames, as on the web. Unmeasured |
| Large memory | Large 3D games | `wasm32`: up to 4 GiB of linear memory; WaOS caps instances and memories, not their size (`crates/waos/src/running/store.rs`, `StoreLimitsBuilder`) | More than 4 GiB (`memory64`); GPU memory is the host's and does not count |
| Save files | Every game that keeps progress | `/data`, kept, and `/cache` (`sdk/wasdk/README.md`); `lifecycle-state.hidden` as the moment to save (`lifecycle.wit`) | Nothing, but a game finds its folder by path: `bevy_platform::dirs::preferences_dir` answers none off the desktops (`bevy_platform/src/dirs/mod.rs`), and `bevy_settings` uses the browser's `localStorage` on every `wasm32` (`bevy_settings/src/store_wasm.rs`) |
| Networking with UDP | Multiplayer games | WASI 0.2's UDP, linked (`crates/waos/src/wasi/mod.rs`), under the network permission; over SSH, UDP answers `not-supported` (`2026-10-17-waos-v1-interface.md`) | Nothing on this computer. Whether `std::net::UdpSocket` works on `wasm32-wasip2`, and which netcode crates build for it, is *unverified* |
| IME in text fields | Occasional in games: names, chat; common in tools | `text-input`, Flutter's model: the program holds the text and the platform sends the whole edited value (`views.wit`) | A shape Bevy reads: `bevy_window::Ime` is winit's `Preedit`/`Commit` (`bevy_window/src/event.rs`), which `bevy_ui_widgets`' text input consumes (`text_input.rs`, `on_ime_input`). A backend can derive them by diffing values (*inferred*) |
| Multiple windows | Rare in games; common in editors | `views.request-view` with a `window-config` (`views.wit`, `windows.wit`) | Little: decorations, level and transparency are set only when the window is made, and Bevy may change them later (`bevy_window/src/window.rs`) |
| Accessibility | Rare in games | None in the WIT | An accessibility tree: Bevy's goes through AccessKit in `bevy_winit` (`bevy_winit/src/accessibility.rs`) |

## Porting notes

Bevy was read at `v0.20.1`, commit `a0577b5c6a7b`, its current release (`cargo info bevy`), cloned sparsely into the session's scratchpad. Paths below are Bevy's crates unless they start with WaOS's folders.

### Bevy's web support is the precedent, and the first obstacle

On the web, Bevy runs without threads, without blocking, and without files, and WaOS needs all three:

- **No threads.** `multi_threaded` is a feature, off on the web; the task pools are then `single_threaded_task_pool.rs`, and pipelined rendering is compiled out on `wasm32` (`bevy_render/src/lib.rs`, `#[cfg(not(target_arch = "wasm32"))] pub mod pipelined_rendering`).
- **No blocking on wgpu.** The browser's WebGPU is asynchronous, so Bevy never blocks on a wgpu future: shader errors are read with `now_or_never` (`bevy_render/src/render_resource/pipeline_cache.rs`, `load_module`), the renderer is made in a task spawned on `wasm32` rather than with `block_on` (`bevy_render/src/settings.rs`, `RenderCreation::create_render`), and shaders are handed to wgpu as WGSL text (`ShaderCacheSource::Wgsl`). `wasdk-wgpu` has the same constraint, since its callbacks fire only when the program yields (`sdk/wasdk-wgpu/src/lib.rs`), so this part of Bevy fits as it is.
- **The loop.** `winit_runner` calls `spawn_app` on `wasm32` and returns at once, the browser driving each turn (`bevy_winit/src/state.rs`); `App::run` "will never return on iOS and Web" (`bevy_app/src/app.rs`).
- **Assets.** The default reader on `wasm32` is `HttpWasmAssetReader`, a `fetch` (`bevy_asset/src/io/source.rs`, `get_default_reader`); `FileAssetReader` is compiled out on `wasm32` (`bevy_asset/src/io/mod.rs`); `file_watcher` is a `compile_error!` on `wasm32`; there is no default writer, so no asset processing.

The obstacle: Bevy's browser paths are chosen by `cfg(all(target_arch = "wasm32", feature = "web"))` (`bevy_platform/src/cfg.rs`), which is right, but five crates switch `web` on for every `wasm32`, each under the comment "TODO: Assuming all wasm builds are for the browser": `bevy_asset`, `bevy_render`, `bevy_log`, `bevy_audio` and `bevy_winit` (their `Cargo.toml`, `[target.'cfg(target_arch = "wasm32")'.dependencies]`, each enabling `bevy_app/web` and the like). Cargo cannot turn a feature off, and `bevy_render` needs `bevy_asset`, so any Bevy that draws runs its browser paths on `wasm32-wasip2`. What that does there:

- `TaskPool::spawn` calls `web_task::spawn_local` (`bevy_tasks/src/single_threaded_task_pool.rs`), which queues through JavaScript's `queueMicrotask` (web-task 1.1.3, `src/queue.rs`). On `target_os = "wasi"`, wasm-bindgen compiles every JavaScript import to a stub that panics (wasm-bindgen-macro-support 0.2.130, `codegen.rs`). So the first asset load panics (*inferred* from the two sources; not run). The build itself links, since the stubs import nothing.
- `LogPlugin` installs `tracing_wasm::WASMLayer`, the browser's console (`bevy_log/src/lib.rs`); the panic hook is `console_error_panic_hook` (`bevy_app/src/panic_handler.rs`); `ScheduleRunnerPlugin` waits with `setTimeout` (`bevy_app/src/schedule_runner.rs`). Each panics on its first use (*inferred*).
- `bevy_platform::time` becomes `web_time`, which re-exports `std::time` off `target_os = "unknown"` (web-time 1.1.0, `src/lib.rs`): harmless.
- `bevy_audio` forces rodio's `wasm-bindgen`, which switches on cpal's Web Audio host on any `wasm32` while cpal declares `wasm-bindgen` and `web-sys` only for `target_os = "unknown"` (cpal 0.17.1, `Cargo.toml` and `src/platform/mod.rs`). So `bevy_audio` should fail to build for `wasm32-wasip2` (*inferred* from cpal 0.17.1's manifest; rodio 0.22.2 took cpal 0.17.3 in a local lockfile; not built).

The fix is a `[patch.crates-io]` of Bevy, small and not of its engine logic: drop the `web` features those five manifests force, since the browser crates themselves build on WASI, each JavaScript call a panicking stub; and narrow to `all(target_arch = "wasm32", target_os = "unknown")` the paths that pick the browser by `target_arch` alone and run whatever the game does: the default reader and `FileAssetReader` (`bevy_asset/src/io/mod.rs`, `source.rs`), the console subscriber (`bevy_log/src/lib.rs`), and rodio's `wasm-bindgen` (`bevy_audio/Cargo.toml`). Bevy's own "TODO" says it wants the assumption gone, so the patch could go upstream; its exact size is *inferred*, since nothing was built. What remains on the browser's side only panics when used: saving a screenshot to a download (`bevy_render/src/view/window/screenshot.rs`), `bevy_settings`' `localStorage`, `bevy_clipboard`'s `web-sys`, and `bevy_ui_widgets`' `mac_host`, which asks `web_sys::window()` on `wasm32` (`text_input.rs`, `on_focused_keyboard_input`) at the first key pressed in a focused text field, so Bevy's text fields need that `cfg` narrowed too (*inferred*). `uuid`'s forced `js` is harmless: its dependencies are gated to `target_os = "unknown"` (uuid 1.29.0, `Cargo.toml`).

### Where a WaOS backend plugs in, and whether Bevy allows it

A crate of WaOS's, `bevy_waos`, over `wasdk` and `wasdk-wgpu`, as `sdk/inset-embedder-wasdk` is for Inset. Bevy allows each part without a fork, once the patch above is in:

- **Features.** A game takes `bevy` without `default_platform` (`bevy_winit`, `bevy_gilrs`, `multi_threaded`, `webgl2`, `x11`, `wayland`, `sysinfo_plugin`, `custom_cursor`, `bevy/Cargo.toml`) and without `audio`, keeping `default_app`, `2d_bevy_render` or `3d_bevy_render`, `ui_api`, `ui_bevy_render`, `std` and `default_font`. Without `webgl2` Bevy's WebGL workarounds are off, each `cfg(all(feature = "webgl", target_arch = "wasm32", not(feature = "webgpu")))` (`bevy_pbr/src/deferred/mod.rs`, `bevy_render/src/settings.rs`), and it draws as on any WebGPU device. `DefaultPlugins` then has no `WinitPlugin`, and `LogPlugin` is disabled for a subscriber writing to standard error, which WaOS sends to its log (`crates/waos/src/wasi/mod.rs`).
- **The runner.** `App::update`, `finish`, `cleanup` and `plugins_state` are public, "useful for situations where you want to use `App::update`" (`bevy_app/src/app.rs`). `bevy_waos::run(app)` is the body of `#[wasdk::main] async fn main`: it awaits the views, ticks the task pools and yields until `plugins_state` is `Ready`, calls `finish` and `cleanup`, then for each `frame` event writes what arrived since into Bevy's messages, calls `app.update()`, and asks for the next frame unless the app is idle (`WinitSettings`' `UpdateMode::Reactive`, `bevy_winit/src/state.rs`, maps onto `request-frame` asked only on input or `RequestRedraw`). It must await between readiness checks: Bevy's own runners spin on `plugins_state` without yielding (`bevy_app/src/app.rs`, `run_once`), which would never let a WaOS call finish (*inferred*). A game's `App::new()...run()` can stay as it is, as on the web: `set_runner` (`bevy_app/src/app.rs`) takes a runner that hands the `App` to the async `main` and returns, as `spawn_app` hands it to the browser; only `main` itself gains a macro of `bevy_waos`'s.
- **The renderer.** `RenderCreation::Manual(RenderResources(device, queue, adapter_info, adapter, instance))` (`bevy_render/src/settings.rs`) takes the adapter and device `main` awaited from `wasdk_wgpu::instance()`, so Bevy never calls `wgpu::Instance::new` (`bevy_render/src/renderer/mod.rs`, `initialize_renderer`), which on `wasm32` with wgpu's `webgpu` feature, on for `wasdk-wgpu`, would reach for the browser's `navigator.gpu` (*inferred*), nor passes `compatible_surface`, a gap in `wasdk-wgpu` (`sdk/wasdk-wgpu/src/instance.rs`).
- **Windows.** `bevy_waos` keeps one `Window` entity per view, made for a `Window` the game spawns with `views.request-view`, and turns each `view-event` into Bevy's messages, as `bevy_winit`'s `forward_bevy_events` does from winit's (`bevy_winit/src/state.rs`): `metrics` into `WindowResized` and `WindowScaleFactorChanged`; `pointer` into `CursorMoved`, `CursorEntered`, `CursorLeft`, `MouseButtonInput`, `MouseWheel`, `TouchInput` and the pan and pinch gestures; `key` into `KeyboardInput`, through a table from the USB HID usage to `KeyCode` and from Flutter's logical id to `Key`, which Inset never needed since its keys are Flutter's (`sdk/inset-embedder-wasdk/src/keys.rs`); `focus` into `WindowFocused`; `close-requested` into `WindowCloseRequested`; `lifecycle.state-changes` into `AppLifecycle` and `WindowOccluded`. Changes the game makes to a `Window` go to `windows.window` (`set-title`, `set-frame`, `show`, `hide`) and `view.set-cursor`, as `bevy_winit`'s `changed_windows` does (`bevy_winit/src/system.rs`). Bevy's `CursorIcon`s are CSS's names, as `cursor` is; custom cursor images have no counterpart.
- **Surfaces: blocker 2.** `create_surfaces` makes each window's surface from its `RawHandleWrapper` with `create_surface_unsafe(SurfaceTargetUnsafe::RawHandle { .. })`, and `ExtractedWindow::present` presents its `SurfaceTexture` (`bevy_render/src/view/window/mod.rs`). `wasdk-wgpu` panics at both, by design: "The program draws on a `wasdk:platform/views` view" (`sdk/wasdk-wgpu/src/lib.rs`). Two ways, a decision for the lead:
  1. *Recommended:* `wasdk-wgpu` implements wgpu's custom surface (`InstanceInterface::create_surface` takes the `SurfaceTargetUnsafe`) over a view's canvas: a raw window handle that names the view, as raw-window-handle's web handles name a canvas; `configure` as `configure_canvas`, `get_current_texture` as the canvas's, and `present` as `view.present` with no layers; capabilities offering `Fifo` only. Bevy is unchanged, and so is any other wgpu program that draws on a surface. It widens what `wasdk-wgpu` promises; a raw handle carrying a view follows wgpu's browser backend, which finds a canvas by the number in a `RawWindowHandle::Web` (`wgpu-30.0.1/src/backend/webgpu.rs`). [The UI frameworks research](2026-11-05-rust-ui-frameworks-on-waos-research.md) asks the same question and recommends rendering to textures for now.
  2. Bevy renders each camera to `RenderTarget::TextureView`, with the canvas's texture put in `ManualTextureViews` before each update and `view.present` after it. No change to `wasdk-wgpu`, but cameras no longer target windows, and what assumes a window target breaks: a mouse's pointer is on a window (`bevy_picking/src/input.rs`, `mouse_pick_events`), and a pointer outside its camera's target picks nothing (`bevy_picking/src/pointer.rs`, `Location::is_in_viewport`); UI laid out on a window is likely the same (*inferred*).
- **Assets.** `app.register_asset_source(AssetSourceId::Default, ..)` before `AssetPlugin` replaces the default reader; with the patch, `FileAssetReader` over `std::fs` reads a folder the program reaches. Blocker 3 is where that folder comes from: assets embedded with `embedded_asset!`, read from linear memory and counted in it, with `cargo waos run` refusing a component over 256 MiB (`crates/waos-dev/README.md`); downloaded into `/cache` on first run; or a folder the user mounts. No hot reload: `file_watcher` needs `multi_threaded` and `notify` (`bevy_asset/Cargo.toml`).
- **Tasks.** With `web` off, the single-threaded pool runs a spawned task at once until it waits (`TaskPool::spawn`), and `TaskPoolPlugin` ticks the rest once per update (`bevy_app/src/task_pool_plugin.rs`). A task awaiting a WaOS call then advances only between updates, which is when `main` yields (*inferred*).
- **Audio.** `bevy_audio` is rodio's, opening the default device itself (`bevy_audio/src/audio_output.rs`), with no seam for another output. With the patch, cpal falls back to its null host off the browser (cpal 0.17.1, `src/platform/mod.rs`), and `bevy_audio` warns "No audio device found" and plays nothing: games run silent (*inferred*). Sound needs either cpal's custom host (`cpal::platform::CustomHost`, feature `custom`) over a `stream-input-node`, plus a change to `bevy_audio` to open it; or an audio plugin of WaOS's over the Web Audio graph, each sound an `audio-buffer-source-node` from `decode-audio-data`, scheduled on WaOS's audio thread, which is the better fit but means games use its API instead of `bevy_audio`'s.
- **Gamepads.** Once WaOS has an interface, a plugin of `bevy_waos`'s writes `RawGamepadEvent`s; nothing in Bevy changes (`bevy_input/src/gamepad.rs`, `bevy_gilrs/src/lib.rs`).
- **The rest of the platform.** The clipboard is `bevy_clipboard`'s, over `arboard` on Windows and Unix and `web-sys` on `wasm32` (`bevy_clipboard/Cargo.toml`), and needs a backend over `clipboard.wit`; system fonts are `parley`'s `system` feature, behind `system_font_discovery` (`bevy_text/Cargo.toml`), with no backend over `fonts.wit`, which games rarely miss since they ship their fonts; `sysinfo_plugin` goes with `default_platform`, and `bevy_remote` is built only off wasm (`bevy_internal/Cargo.toml`).
- **Time.** `Time<Real>` reads `Instant`, `std`'s on WASI, which WaOS serves from the program's own clock (`crates/waos/src/wasi/mod.rs`). A program stopped while hidden resumes with its clock gone on (`lifecycle.wit`); `Time<Virtual>` clamps the step after it to `max_delta`, 250 ms by default (`bevy_time/src/virt.rs`, `DEFAULT_MAX_DELTA`). With no frames while hidden, a game's update stops there, as in a browser's background tab; what must go on, a multiplayer connection, cannot (*inferred*).

### Blockers and gaps

What stops a typical Bevy game from running at all, each with its way out:

1. Bevy's browser paths on every `wasm32` (five manifests): a patch of Bevy's, which upstream marks as wanted.
2. No surface in `wasdk-wgpu`: surfaces over view canvases in `wasdk-wgpu`, or render targets by hand.
3. No backend: `bevy_waos`, the runner, windows, input, the renderer made by hand, the asset source, logging.
4. No assets beside the component: embedding, a download, or packages that carry files.
5. `bevy_audio` does not build (*inferred*): the patch makes it build and play nothing.

What only degrades it, the most common first: one core for everything (threads); no pointer lock or raw mouse motion, so mouse-look cameras stop at the screen's edge; no gamepads; no fullscreen of the program's own; silence until an audio backend exists, and then a frame loop's latency if samples are pushed; vsync only, no frame caps or uncapped modes; asset decoding on the frame thread; 4 GiB of memory; no confined cursor; updates stopping while hidden; no custom cursors or accessibility tree; IME through a translation from Flutter's model to winit's.

### Unverified, to settle by building

- Whether `wasdk-wgpu` builds with wgpu's `fragile-send-sync-non-atomic-wasm`, which `bevy_render` switches on (`bevy_render/Cargo.toml`) and which makes wgpu's custom backend require `Send + Sync` types on `wasm32` (wgpu 30.0.1, `build.rs`, `send_sync`); no WaOS crate turns it on today.
- Whether `inventory`, behind `reflect_auto_register`, runs its constructors in a component entered through the async `run` export; its docs say it works on every wasm target, constructors called again being harmless (inventory 0.3.21, `src/lib.rs`). `reflect_auto_register_static` is the fallback.
- What WebGPU features Bevy's 3D path asks for that `wasi:webgpu` lacks: `wasdk-wgpu` panics at `PolygonMode::Line`, binding arrays and `clear_texture` (`sdk/wasdk-wgpu/src/lib.rs`); Bevy gates the fast wireframe, bindless and `clear_texture` on features or on WebGL (`bevy_pbr/src/wireframe.rs`, `bevy_core_pipeline/src/deferred/node.rs`), so they should be skipped, but nothing has run.
- What each wgpu call costs across the component boundary, for a Bevy frame of thousands of calls; and how long asset decoding stalls frames on one thread.
