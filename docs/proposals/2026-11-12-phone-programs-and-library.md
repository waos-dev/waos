# Programs on a phone, and the library's home

Written 2026-11-12, after WaOS first ran on a phone (a Pixel 2 XL, Android 15) with the deck of `2026-11-11-android-pictures.md`: a bottom bar naming what is in sight and a list of tabs, and the library as one scrolling page with three text buttons on every program's row. Both were ad hoc. This records what the lead decided in their place, and the order of the work. What was planned on this date, not what is.

## The lead's decisions

1. **On Android a program opens as a task of its own**, even when it is opened from WaOS: its own card in Recents with its name and icon, moved between by the system's back, home and recents gestures, with nothing of WaOS drawn over it. A program on a phone is an app of the phone, as on a desktop it is an app with its own Dock icon. A program already running is brought forward rather than started again, and its card swiped away in Recents ends it, so WaOS needs no close and no switcher of its own there. This amends decision 4 of `2026-11-11-android-pictures.md`: tasks are not only later, they are Android's default.

2. **A program is shown inside WaOS only where the system gives it no identity of its own, which is iPhone, and on Android where the user turns that on in the settings.** Every program still runs in WaOS's one process either way: where Android ends WaOS in the background, every program goes with it, and a card opened again from Recents starts its program fresh.

3. **Inside WaOS, programs are tabs as Safari's pages are on iPhone**: a bottom bar with a pill naming the page; a sideways drag on the bar moves between programs; an upward drag shrinks the page into an overview of cards, where tabs close; the library's home is the new-tab page. The lead built this once, in the frozen experiment (`../wasdk/waos/src/phone`), whose gestures had bugs: it is rebuilt from that intent, not copied. The bar and the tab list built on 2026-11-11 go. Settled with the lead on the drawing of its four states: the home is the new-tab page, so there is no fixed library page, and a tab is the home until it opens a program, which it then becomes; there is one home at most, which the overview's plus and a swipe past the last tab go to where it exists; on the home the bar's pill is a search field that filters the grid, where Safari has its address; a program that ended keeps its last picture in its tab, with how it ended, until the tab is closed; in the overview nothing has the input focus and a card shows its program's last frame; a page is never resized or faded as it shrinks, only moved, scaled and clipped; and a gesture that starts while something moves takes over from where it is, nothing waiting for an animation to end.

4. **The library's main screen is a home of program icons** (the draft named L1), on a phone and in the desktop's panel alike, as a phone's home screen and the Start menu's pinned apps are: a tap opens a program, a running one is marked, one with an update is badged, and whoever uses the microphone or the camera is said above the grid. Holding an icon, or a right click on a desktop, offers its settings, closing it while it runs, and removing it, which still asks. Adding programs, the sources with what each lists and the field that adds one, is a page of its own behind a plus; every program's settings are behind a gear. The question whether to install a package is a sheet over whatever shows. The settings pages keep what they hold.

5. **The order: the library's home, then the deck, then tasks**, with what running several activities in one process asks of Waft's Android host looked into alongside, so the design of tasks is ready when the deck is. Until tasks land, Android shows programs inside WaOS; then its default becomes tasks and the deck moves behind the setting.

6. **Where Waft or its Cupertino widgets lack something a design asks for, the lead is told, and it is ported, not worked around.** `CupertinoSwitch` is ported from Flutter for the settings pages, which stood an On/Off segmented control in its place. `CupertinoContextMenu`, the menu a home screen shows on a held icon, is not ported yet: the held icon's actions are a `CupertinoActionSheet`, an established pattern of its own, until it is.

7. **A phone learns of the files WaOS opens from the same `file_associations` the desktop bundles are written from** (`[package.metadata.waft]`): Waft's CLI writes them into the Android manifest, which it left out, with no key of Android's own. Android has no way for an app to teach it a new extension, so a `.wapk` may reach WaOS as an untyped file; what the manifest must claim for that is settled by what the phone's Files app does.

8. **A program says in advance whether it goes back within itself, and hears the user's Back only while it does** (2026-11-12): `view.set-handles-back(handles)` and the view event `pop-route`, Flutter's `SystemNavigator.setFrameworkHandlesBack` and `popRoute`. While a program does not handle Back, the platform does its own with the press: in the deck it closes the overview where that is open, leaves a program for the home, the program keeping its tab and running on, and on the home is Android's own; with programs as tasks it is Android's default for the task. Why in advance: a program runs on a thread of its own behind the interface and cannot answer a press on the spot, as Waft's `pop_route() -> bool` answers its host; Android itself has an app register for Back only while it wants it, since Android 13, and sends a launcher's root to the background rather than finishing it, since Android 12. The lead weighed the event alone, a program with nothing to go back to ending itself: smaller, but a program that never thought of Back would have a dead Back, and leaving a program would end it. A program built with Waft declares from its navigators' state with no code of its own, which asks Waft for Flutter's `setFrameworkHandlesBack` on its platform, ported as decision 6 says.

9. **A program's task is a Waft window, reached through `request_view`** (2026-11-12), with the program's id as the view's initial data: WaOS asks Waft for a view as it does for a window on a desktop, Waft's Android host starts a document activity in a task of its own, and the activity arrives as the view. A card Android brings back by itself arrives as a view the platform gave, carrying the same data, which is how WaOS knows which program to start. The lead weighed an activity of WaOS's own beside Waft's: it would put Android's tasks in WaOS where every app on Waft with several windows needs them. Waft's three branches toward this (`android-app-outlives-activities`, `android-task-per-view`, `android-pinned-shortcuts`) were never approved by the lead: they are a draft to learn from, and their design is reviewed with the lead before anything is carried over.

10. **Every view a program asks for is a task** (2026-11-12), as on a desktop every view is a window: a program's `request-view` makes another card in Recents, titled as its window. The lead weighed one task for each program, `request-view` answering `unsupported` as in the deck: simpler and what nearly every Android app does, but it hides what the platform can do, whose document tasks are made for this. An extra view's card that outlives the process has no program state behind it and is removed; only the program's main card starts it fresh.

11. **A program's code is compiled when it is installed** (2026-11-12), as Android compiles its own apps at install, and when it is updated; its icon says so until the code is ready. The first open compiled it, which on a phone is long enough to notice, and wasmtime reports no progress to show (`precompile_component` is one call). An open while the code compiles waits for it. After an update of WaOS that changes its engine the first open compiles again and the icon shows the same; nothing compiles every installed program at startup.

12. **Waft's app lives on a thread of its own, which no activity owns, and Waft receives Android's calls itself** (2026-11-12). Android calls every activity's callbacks on the process's one main thread; the crate Waft's host is built on, android-activity, starts a thread for each activity and runs the app on it, so the app ends with its activity, and a second activity would be a second app. With several activities in one WaOS, each activity is a view of the one app: its callbacks hand their events from Android's main thread straight to the app's thread, its input queue is attached to the app's thread, and Android's main thread waits for the app only where Android asks it to, when a window is taken away. No thread stands for an activity. The lead weighed keeping android-activity, each activity's thread only forwarding to the app's: the cheapest, but a forwarding layer over the very model being left, with a thread idle for every open program. Flutter's embedding has this shape, an activity's callbacks going from the main thread into the engine, though with one activity to an engine.

13. **An activity Android destroys to make again keeps its view** (2026-11-12): Android destroys an activity without finishing it when a setting changes that the app does not handle itself, and under the developer option "Don't keep activities". The activity saves which view it was, with a value made fresh in each process, where Android keeps an activity's saved state; the activity Android makes in its place gets it back and attaches to the same view, which was without a window meanwhile, as it is whenever the app is in the background, so the program runs on. Flutter keeps its engine and attaches again the same way. The lead asked for this only if it is simple and without risk, so it was measured first (`../experiments/2026-11-12-android-task-per-program`, the section added the same day, on the emulator, API 37): the saved state came back every time, in the same task and process, 8 ms after the destroy for a change of font scale; a card left by a process that died brings the old process's saved state, which the fresh value tells apart; and the risk looked for, a card swiped away while its activity is destroyed, so that nothing hears it and its program runs on with no card, does not arise there, since Android killed the whole process at that swipe, as it did when an app's last card was swiped, with no callback in either case. So a view ends when its activity is destroyed finishing, and everything ends with the process, which is what decision 2 says. Not measured: the same swipe while something else keeps the process alive, a foreground service, which WaOS has none of; Android's callback for that is the service's `onTaskRemoved`.

14. **Back at a program's first screen sends its task to the background, and the program runs on** (2026-11-12), its card staying in Recents until it is swiped away. This amends decision 8, which left it to "Android's default for the task": for a document task that default finishes the activity and removes its card, which would end the program at one Back too many, where an app's own launcher screen, since Android 12, goes to the background and keeps running. Both are Android's own, for two kinds of task; a program is an app to its user, so it gets the app's.

15. **In the deck, touches follow where a page is going, not where it is drawn** (2026-11-12): while a page flies to fill the screen with no finger on it, as after a tapped card, a touch on it goes to its program, at the place it will have once it lands, and does not catch the flight; the bar's upward drag still takes the page over from where it is. This amends decision 3's "a gesture that starts while something moves takes over from where it is" for a page flying open, which caught the program's first touch when the flight looked done. Why: it is iOS's own rule, Core Animation hit-testing a view's model layer, its final frame, rather than what is drawn mid-animation; in Waft, Flutter's `Transform` with `transformHitTests: false`.

16. **On a desktop WaOS has no window the user has to care about** (2026-11-13): programs are the apps; WaOS is a launcher summoned when a program is to be found or opened, and gone once it is, as macOS's Spotlight shows its apps. It is one floating card, a search field as its top row over the grid of programs (the draft named L2): typing filters, Enter or a click opens, Escape or a click outside dismisses, a running program is marked and one with an update badged, and the sources and the settings are behind its "…". It replaces the library's panel above the Dock icon on every desktop. The lead weighed a search pill floating apart from the grid (L1), which they showed as an idea rather than a look, and a pill alone until something is typed (L3). It is summoned by WaOS's icon in the Dock or the taskbar by default; a setting leaves only an icon in the menu bar or the tray. A global shortcut and categories of programs are for later.

17. **On Windows and Linux, dismissing the launcher minimizes it while WaOS keeps its place in the taskbar or dock** (2026-11-13): those desktops show a running app there only through its windows, so a launcher that hid itself would leave nothing to click; a minimized one keeps its button, and a click on it restores the launcher, as either desktop restores any app. The setting of decision 16 reads the same on every desktop: kept in the Dock or the taskbar, the default, or only an icon in the menu bar or the tray. The lead weighed the tray icon alone on these desktops, which is not always a good experience there.

18. **A window the system restores is a view it gives, and the app decides what goes in it from the view's initial data** (2026-11-13), as iOS restores scenes and macOS windows, and Android a task from Recents: in WaOS a restored card builds the program its initial data names, or closes where that names an extra view; Waft tells the binding's observers of every view's window changes, so a restored view's window is followed as a requested one's is. The lead weighed a controller adopting a given view (`WindowController::of_given_view`). The "show programs inside WaOS" switch is a preference of WaOS's own, kept in a file of its own, not among the grants the store keeps.

19. **In Waft a view shows what its data says, and that is the whole of what an app uses for views and windows** (2026-11-13, replacing how decisions 9 and 18 were first built): the app declares once what each view shows from its initial data, for first, asked-for and restored views alike (`MultiViewApp`); it asks the system for another with `request_view` and holds nothing, the view arriving where every view does; and a view's content reaches its own window from inside (`WindowScope`), for its title, its closing and whether it is in sight. This is SwiftUI's scenes (`WindowGroup(for:)`, `openWindow(value:)`), and how Android and iOS hand an app its activities and scenes. Waft's port of Flutter's experimental windowing (`WindowController`, `WindowingOwner`, the `Window` widget) goes: Flutter has two mechanisms it never joined, a web page giving views and a desktop app making windows through controllers, and nothing for a view the system makes or restores, so every shape built over both was glue between them (requests that held views, windows held or given, a controller taking on a given view, an observer waiting for the window it had asked for). What it costs: desktop code holds no window before its content exists. In WaOS, which program waits for an arriving view is WaOS's own question, and a program's window reports whether it is in sight from inside its content.

## Known gaps when this was written

- Waft's Android host had no text input, so no source could be typed on a phone; and no file types in its manifest, so a package reached WaOS on a phone only by `adb`. Both were being built.
- In the Android library some text and the programs' icons drew blank.
- Nothing tells a program where WaOS draws over it; with tasks as Android's default nothing does, and inside WaOS the bar is beneath the page, not over it.

20. **Six apps are written on WaOS as an outside developer would write them, to find what it lacks** (2026-11-13): a terminal on `alacritty_terminal`, a live document on `typst`, a 3D model viewer on wgpu and egui with no Waft, a synthesizer on `fundsp`, a camera with shader filters, and a feed reader; with Notes and the Video Player they touch every interface WaOS has. Each is built from the public documentation and `cargo waos` alone where it can be, by an agent that keeps a log of every place the interface, the SDK, the tools or the documentation failed it, which is the work's first product; the apps are its second, each finished enough to be among the first programs a new user sees, and showing real Rust crates at work in a program. They live in `builtin-apps/` for now, and reach users through WaOS's default source, not inside its installer. A scene in Bevy, which needs a backend of WaOS's for Bevy's windows and input, waits as the riskiest.
