# A process per WaOS program on macOS: Chrome's app shims, and what WaOS should build

Research for v1 decision 3 (`waos/docs/proposals/2026-10-16-waos-v1.md`) and decision 51 of `2026-10-17-the-waos-project.md`: on macOS each running program becomes an app of its own, through a small window process per running program. Written 2026-10-29.

**How claims are marked.** **[read]** means read in the source or page named beside it; **[inferred]** means my reasoning from what was read, not checked by running anything. Nothing here was run or measured: no PWA is installed on this Mac (`~/Applications/Chrome Apps.localized` is empty), and the brief allowed writing only this file.

**Sources.** Chromium at revision `e211e2d52491adbb55c4b6a7e722de3e16a2d435` (main, 2026-10-29), fetched from `chromium.googlesource.com/chromium/src/+/<rev>/<path>`; paths below are at that revision unless marked *(GitHub mirror, main, 2026-10-29)*, used after googlesource began answering with a bot check (the log endpoint was skipped then; commit messages were read from the `chromium/chromium` GitHub mirror instead). Apple's documentation and the macOS SDK headers in Xcode on this Mac. WaOS's repository and a local checkout of Inset (github.com/waos-dev/waft) at 2026-10-29, read as they were that day.

## 1. How Chrome makes a shim bundle

| | what Chrome does | source |
|---|---|---|
| When | at install, and again whenever a launch fails (see "updates" below) | [read] `chrome/browser/web_applications/os_integration/mac/web_app_shortcut_creator.mm` (`CreateShortcuts`, `UpdateShortcuts`), `app_shim_launch.mm` |
| Where | `~/Applications/Chrome Apps.localized/<Name>.app`; the user may move or rename it, and Chrome finds it again by bundle id through Launch Services | [read] `os_integration/mac/README.md`; `BundleInfoPlist::SearchForBundlesById` in `web_app_shortcut_creator.mm` |
| Executable | a copy of one generic loader, `Contents/MacOS/app_mode_loader`, taken from `Google Chrome Framework.framework/Helpers/app_mode_loader`; the loader `dlopen`s the Chrome framework and calls a versioned entry point (`ChromeAppModeStart_v<N>`), so the shim runs Chrome's own code | [read] `BuildShortcut` in `web_app_shortcut_creator.mm`; `chrome/app_shim/app_mode_loader_mac.mm`; `chrome/app_shim/chrome_main_app_mode_mac.mm` |
| `Info.plist` | a template, `app_mode-Info.plist`, filled in: `CFBundleIdentifier` = `<chrome bundle id>.app.<app id>` (with the profile in it for single-profile apps), `CFBundleName`, `CFBundleShortVersionString` (the app's display version), `CrAppModeShortcutID/Name/URL`, `CrBundleIdentifier` (which browser made it), `CrAppModeUserDataDir`, `CrAppModeIsAdhocSigned`, `LSHasLocalizedDisplayName`, `NSHighResolutionCapable`, `LSEnvironment` `MallocNanoZone=0`, and `CFBundleDocumentTypes` / `CFBundleURLTypes` from the app's file and protocol handlers. | Name | the bundle's file name, plus `<lang>.lproj/InfoPlist.strings` with `CFBundleDisplayName`; Finder uses the localized name only while the file name equals `CFBundleName` | [read] `UpdateDisplayName`; `os_integration/mac/README.md` |
| Icon | `Resources/app.icns`, written by Chrome's own `IcnsEncoder` from the manifest's icons, masked to Apple's shape where the OS does not mask | [read] `UpdateIcon` in `web_app_shortcut_creator.mm` |
| Signing, before 2023 (still the fallback where policy disables ad-hoc signing) | none of its own: the shim is built by "copying an executable out of the browser's app bundle", so "the app shim's code signature is not valid and … every app shim has the same identity from the operating system's point of view". The browser accepted a shim whose process met a requirement derived from the Chrome framework's designated requirement, so the copied loader carries Chrome's own signature [inferred from that check] | [read] commit `f09879c953` message (GitHub mirror); `IsAcceptablyCodeSignedLegacy` in `app_shim_manager_mac.cc`; `UseAdHocSigningForWebAppShims` (feature, then enterprise policy) in `web_app_shortcut_mac.mm` |
| Signing, now | **ad hoc**, by Chrome at creation, through `SecCodeSignerCreate` with no identity, flags `restrict | kill | runtime` (hardened runtime) and one entitlement, `com.apple.security.cs.disable-library-validation`, since the ad-hoc shim loads Google-signed Chrome framework code. Chrome keeps the shim's code-directory hash (cdhash) in `AppShimRegistry`, under an HMAC key kept in prefs | [read] `UpdateSignature`, `AppShimEntitlements` in `web_app_shortcut_creator.mm`; commits `f09879c953` (2023-10, behind `UseAdHocSigningForWebAppShims`), `f8cccb4ead` (HMAC key cache) |
| Writing to disk | through a separate helper, `web_app_shortcut_copier`, so binary-authorization tools such as Santa can trust shims "transitively" without trusting every file Chrome writes; the helper accepts only a caller signed with the same identity as Chrome | [read] `web_app_shortcut_copier_mac.mm`; `CopyStagingBundleToDestination`; commit `531642ad9f` |
| Gatekeeper | Chrome removes the quarantine attribute from the bundle and the loader, then calls `LSRegisterURL`. Nothing is notarized: a locally made, ad-hoc-signed, unquarantined bundle is not assessed by Gatekeeper the way a downloaded one is [inferred from the quarantine removal; not tested] | [read] `CreateShortcutsAt` |
| Who may connect | the browser checks each connecting shim by its Mach audit token: `SecCodeCheckValidity`, then its cdhash against the one saved at signing; a shim that fails is refused (`kFailedValidation`) and Chrome rebuilds it | [read] `IsAcceptablyAdHocCodeSigned`, `VerifyCodeDirectoryHash`, and the connection path near "The attaching app shim's code signature is invalid" in `chrome/browser/apps/app_shim/app_shim_manager_mac.cc` |
| Updates | shims are not updated in place. A launch that fails, or a shim that exits before connecting, makes Chrome rebuild every copy (`kRecreateUnconditionally`) and launch again once; a second failure gives up. Because the shim `dlopen`s the running Chrome's framework version (read from a `RunningChromeVersion` symlink in the user data dir), most Chrome updates need no rebuild; the entry point's name is versioned to force one when the ABI changes. Since 2026-08, Chrome also rebuilds and re-signs all shims when the macOS version changes, because "Upgrading the macOS operating system causes Gatekeeper to treat pre-existing ad-hoc signatures as unverified on first launch" | [read] `AppShimHost::OnShimProcessTerminated` in `app_shim_host_mac.cc`; `LaunchShimOnFileThread` in `app_shim_launch.mm`; `AppShimListener::InitOnBackgroundThread`; `chrome_main_app_mode_mac.mm`; commit `91dc901582` |
| Uninstall | Chrome deletes the bundles it finds by bundle id (`DeletePlatformShortcuts`, `DeleteMultiProfileShortcutsForApp`), with `DeletePathRecursively`, not to the Trash | [read] `web_app_shortcut_mac.mm` |

What follows for WaOS [inferred]: everything above is plain file work plus one Security.framework call. The only parts that need Chrome's own identity are the copier (a Santa concession) and the cdhash check; neither needs a Developer ID per program, and none of it needs notarization.

## 2. What runs in the shim, and what stays in the browser

The shim is a full Chrome process type (`--type=app_shim`, `content::ContentMain`) [read: `chrome_main_app_mode_mac.mm`], acting as a "remote cocoa" host: the browser keeps the UI framework (Views) and the web contents, and the shim holds the AppKit objects. `components/remote_cocoa/README.md` [read]: Remote Cocoa "bridges Cocoa objects with their Chromium C++ counterparts, which can be either in-process (the browser) or out-of-process (PWA app shims)".

| Concern | In the shim | In the browser (and GPU/renderer processes) | source |
|---|---|---|---|
| App identity | `NSApplication`, its bundle id, Dock tile and badge (`SetBadgeLabel`), bouncing (`SetUserAttention`), ⌘-Tab | decides badge and attention | [read] `app_shim_controller.mm`, `app_shim.mojom` |
| Windows | each `NSWindow` and its content `NSView`s, created on request through `remote_cocoa.mojom.Application` and driven by `NativeWidgetNSWindow` (frame, title, show, fullscreen, key status) | the Views `Widget`, layout and all decisions (`NativeWidgetMacNSWindowHost`) | [read] `components/remote_cocoa/common/native_widget_ns_window.mojom`, `.../app_shim/native_widget_ns_window_bridge.mm` |
| Pictures | a `ui::DisplayCALayerTree` under each window: a `CALayerHost` showing the GPU process's `CAContext` by id (`ca_context_id`), or, for software compositing or with remote layers disabled, a plain `CALayer` whose contents is an IOSurface looked up from a Mach port (`IOSurfaceLookupFromMachPort`). The browser forwards each frame's `CALayerParams` with `SetCALayerParams`; the shim drops frames of a size the window no longer has and swaps contents inside the window's resize transaction, holding the context's fence port until then | the GPU process draws the window's compositor output, Views and web contents together [inferred: not read in viz], into a `CAContext`; the browser only relays the id | [read] `ui/accelerated_widget_mac/display_ca_layer_tree.mm`, `NativeWidgetNSWindowBridge::SetCALayerParams`, `NativeWidgetMacNSWindowHost::AcceleratedWidgetCALayerParamsUpdated`, `ui/base/cocoa/remote_layer_api.{h,mm}` |
| Input | the `NSView`s receive every event: Views' `BridgedContentView`, and for web contents `RenderWidgetHostViewCocoa` | events are routed and handled; Views' keys go through `DispatchKeyEventRemote`, a **synchronous** call from the shim's main thread to the browser | [read] `native_widget_ns_window_host.mojom` (`[Sync] DispatchKeyEventRemote`, `[Sync] DispatchMonitorEvent`, `[Sync] GetHitTestResult`…) |
| Text input | the `NSView` is the `NSTextInputClient`: `interpretKeyEvents:` runs in the shim, marked text and commits are forwarded (`ImeSetComposition`, `ImeCommitText`); `firstRectForCharacterRange:` and `characterIndexForPoint:` are **synchronous** calls to the browser, which answers from a cache of the renderer's composition bounds and, on a miss, blocks on the renderer | composition state, caret rects | [read] `content/app_shim_remote_cocoa/render_widget_host_view_cocoa.mm` (`firstRectForCharacterRange:` → `SyncGetFirstRectForRange`), `content/browser/renderer_host/render_widget_host_view_mac.mm`, `content/common/render_widget_host_ns_view.mojom`, `components/remote_cocoa/common/text_input_host.mojom` (Views' text fields: every query `[Sync]`) |
| Keys a page leaves | the web view forwards the key asynchronously (`ForwardKeyboardEventWithCommands`) and claims it from AppKit at once (`performKeyEquivalent:` returns `YES`); when the renderer answers "not consumed", the browser sends the serialized `NSEvent` back with `RedispatchKeyEvent`, and the shim runs it through its window's `CommandDispatcher`, which reaches the main menu | the renderer decides | [read] `RenderWidgetHostViewCocoa performKeyEquivalent:`, `NativeWidgetMacNSWindowHost::RedispatchKeyEvent` ("If the target window is out of process then always report the event as handled"), `NativeWidgetNSWindowBridge::RedispatchKeyEvent` |
| Menu bar | built in the shim by Chrome's own `chrome::BuildMainMenu(…, is_pwa=true)`; items act through the window's command dispatcher, which asks the browser synchronously (`[Sync] ValidateUserInterfaceItem`, `[Sync] ExecuteCommand`); the profile menu is sent as values (`UpdateProfileMenu`) | commands | [read] `AppShimController::SetUpMenu`, `CreateCommandDispatcherForWidget`; `native_widget_ns_window_host.mojom`; `chrome/browser/ui/cocoa/main_menu_builder.mm` *(GitHub mirror)* |

| Dock menu | `applicationDockMenu:` builds an `NSMenu` from items the browser sent as values (`UpdateApplicationDockMenu`); a choice goes back as `OpenAppWithOverrideUrl` | the items (the manifest's shortcuts) | [read] `AppShimController::GetApplicationDockMenu`, `CommandFromDock` |
| About | the PWA's app menu keeps About, with AppKit's `orderFrontStandardAboutPanel:`, so it shows the shim bundle's name, icon and version | — | [read] `main_menu_builder.mm` *(GitHub mirror)* lines around `IDS_ABOUT_MAC` |
| Dock click, ⌘-Tab, reopen | `applicationWillBecomeActive:` → `FocusApp`; `applicationShouldHandleReopen:` → `ReopenApp` | opens or focuses windows | [read] `chrome/app_shim/app_shim_delegate.mm` |

| Accessibility | the shim exchanges remote accessibility tokens so VoiceOver sees the browser's tree inside the shim's window, and tells the browser when assistive technology appears | the tree | [read] `SetRemoteAccessibilityTokens` in `native_widget_ns_window_bridge.mm`; `AppShimApplication accessibilitySetValue:` in `app_shim_application.mm` |

Two things stand out [inferred]: Chrome allows synchronous calls only from the shim to the browser ("No synchronous communication is allowed in this direction", browser → shim, `render_widget_host_ns_view.mojom` [read]), and it uses them heavily for Views; and the shim never draws. It shows the GPU process's layers through a private API (`CAContext` / `CALayerHost`, declared by hand in `remote_layer_api.h`), with the IOSurface path kept as a fallback.

## 3. The connection: Mojo over Mach

| Step | What happens | source |
|---|---|---|
| Browser listens | at startup the browser checks in a Mach service with launchd's bootstrap server, named `<browser bundle id>.apps.<SHA-256 of the user data dir>`, with `bootstrap_check_in`; it also writes a `RunningChromeVersion` symlink (framework version, IPC flavour) and a `ChromeFeatureState` file into the user data dir | [read] `AppShimListener::InitOnBackgroundThread`, `MachBootstrapAcceptor::Start`, `mojo/public/cpp/platform/named_platform_channel_mac.cc` *(GitHub mirror)* |
| Shim finds the browser | launched by Chrome: the command line carries Chrome's pid and framework path, and the shim connects only to that pid. Launched by the user, the Dock or Finder: it reads the pid from the browser's `SingletonLock` symlink and checks that process's bundle id; with no browser running it launches one (`--user-data-dir`, and `--no-startup-window` behind `AppShimLaunchChromeSilently`) with `NSWorkspace`, then polls `bootstrap_look_up` every 100 ms for up to 60 s | [read] `AppShimController::FindOrLaunchChrome`, `FindChromeFromSingletonLock`, `PollForChromeReady` (`kPollPeriodMsec`, `kPollTimeoutSeconds`) |
| Handshake | the shim makes a channel and sends its send end to the browser's port in a raw Mach message (`msgh_id = 'apps'`); the browser reads the sender's **audit token** from the message trailer, checks the code signature (§1), and binds a Mojo `IsolatedConnection`. The shim sends `OnShimConnected(AppShimInfo)`: app id, profile, launch type (`kNormal`, `kRegisterOnly` when Chrome launched it, `kNotificationAction`), files and URLs it was opened with, login-item state, and a notification action handler; the reply carries the result, the browser's feature state and the `AppShim` interface | [read] `AppShimController::ConnectToBrowser`, `SendBootstrapOnShimConnected`; `MachBootstrapAcceptor::HandleRequest`; `chrome/common/mac/app_shim.mojom` |
| Failure | any result but success, or the bootstrap pipe closing first, terminates the shim; a shim launched by Chrome that cannot load the framework simply exits, so that Chrome rebuilds and relaunches it; a shim launched alone that cannot load it starts Chrome with `--app-id` and exits | [read] `OnShimConnectedResponse`, `BootstrapChannelError`, `app_mode_loader_mac.mm` |
| Launch by Chrome | `NSWorkspace openApplicationAtURL:` with `activates` per launch mode; a background launch (for notifications) sets `hides`, `addsToRecentItems = NO` and the private `_kLSOpenOptionBackgroundLaunchKey` | [read] `LaunchTheFirstShimThatWorksOnFileThread` in `app_shim_launch.mm`; `base/mac/launch_application.mm` *(GitHub mirror)* |
| Feature state | a shim launched alone guesses Chrome's feature flags from the file, allows only an explicit list of features before connecting, and replaces its feature state with the browser's once connected | [read] `chrome/app_shim/README.md`, `AppShimController::PreInitFeatureState`, `FinalizeFeatureState` |

Why Mach and not a Unix socket [inferred]: the shim is launched by Launch Services, so it is launchd's child, not Chrome's, and cannot inherit a channel; Mach ports (an IOSurface's, a fence) cannot cross a Unix socket; and a Mach message gives the receiver the sender's audit token, which is what the code-signature check needs. `bootstrap_check_in` works for a name no launchd plist declares only outside the App Sandbox, which both Chrome and WaOS are.

## 6. How a program's picture reaches its window process

Today [read: `apps/waos/src/logic/canvas_view.rs`, `inset-embedder/src/composition.rs`, `inset-embedder-winit/src/os/apple/composition/mod.rs`]: the engine draws into an IOSurface from the view's pool and calls `ShellView::present(picture, released)` from the view's frame thread; WaOS's canvas presents it to Inset's native surface (`Surface::present(SurfaceFrame::new(picture), released)`), which sets it as a layer's contents in an explicit `CATransaction` off the main thread and calls `released` once `IOSurfaceIsInUse` answers false at a later present. A child surface (a player's video, media decision 3) is a layer beneath the picture's buffer layer in the same tree; Inset already keeps a slot for "a layer the system draws into" inside each surface.

The three ways a layer or a buffer crosses processes on macOS:

| | IOSurface by Mach port | `CARemoteLayerClient` / `CARemoteLayerServer` | `CAContext` + `CALayerHost` |
|---|---|---|---|
| Status | public; Apple's recommended way: "`IOSurfaceCreateMachPort(_:)` and `IOSurfaceCreateXPCObject(_:)` … offer an improved way to perform cross-process rendering" [read: [CARemoteLayerServer docs](https://developer.apple.com/documentation/quartzcore/caremotelayerserver)] | public since macOS 10.7, in the SDK headers with no deprecation macro, but Apple calls it "a legacy class for cross-process rendering" [read: same page; `QuartzCore.framework/Headers/CARemoteLayer{Client,Server}.h` in this Mac's SDK] | private, declared by hand [read: `ui/base/cocoa/remote_layer_api.h`] |
| Who uses it | Chrome's fallback and software path [read: `display_ca_layer_tree.mm`]; Firefox's remote native layers send a batch of layer commands with each changed surface as an `IOSurfacePort` [read: `gfx/layers/NativeLayerRootRemoteMacParent.h` on searchfox; the port type not checked] | the JDK's old browser plugin [inferred from JDK-7141393's title "CARemoteLayer code refactoring"; not read] | Chrome for every window [read]; WebKit to show the GPU process's video layer in the web process [read: WebKit bug 206043 summary] |
| What crosses | a buffer; the receiving process builds and owns the layer tree | a whole layer tree: the server (the window process) sends its `serverPort`, the client (WaOS) makes `CARemoteLayerClient(initWithServerPort:)`, sets its `layer`, sends back `clientId`, and the server hangs `+[CALayer layerWithRemoteClientId:]` in its view [read: the headers] | a whole layer tree, by a `uint32` context id |
| Per frame | one small message per present (which picture, where its children go) and one per release; each picture's port once, then an id | nothing: WaOS commits its own transactions | nothing, but Chrome sends a fence port to keep contents and window size in step |
| Releases | the window process sees when Core Animation lets go; `IOSurfaceIsInUse` is system-wide ("in use by any process in the system" [read: Apple's `IOSurfaceIsInUse` reference via search]), so Inset's present-time check still works there | unchanged, in WaOS | unchanged, in WaOS |
| Resize | the window process can apply a new picture in the same transaction as its window's resize, as Chrome's `SetCALayerParams` does | no public way to tie WaOS's commit to the window's resize [inferred: no fence API in the header] | fences, private |
| A child `AVPlayerLayer` | must be in the window process: a player layer shows only a player in its own process [inferred from AVFoundation's object model], so the player runs there, or WaOS reads frames out (`AVPlayerItemVideoOutput`'s IOSurface-backed buffers) and sends those, which loses FairPlay-protected video and leaves pacing to WaOS | stays in WaOS, inside the hosted tree; whether protected and HDR video survive a remote layer is unknown | stays in WaOS; WebKit does exactly this for video [read: WebKit bug 206043 summary] |

**Answer.** Send the program's pictures as IOSurfaces: the picture already is one, the receiving side can be Inset's own surface with its release rule unchanged, the API is the one Apple recommends, and the per-frame cost is two small Mach messages. The video child is the hard case: with buffers only, the player must live in the window process (§11, decision 3). A middle way keeps players in WaOS and hosts only their layer in the window process through `CARemoteLayerClient`, hung in Inset's existing system-layer slot of the child surface; it rests on a legacy API and needs an experiment for HDR, protected content and resizing before anyone relies on it [inferred].

## 7. Input and text input across the processes

The window process's `NSView` must receive the events and be the `NSTextInputClient`, because AppKit and the input methods talk to the process that owns the key window [inferred from AppKit's model; Chrome's shim does it this way, read in §2].

**Keys and the reply (clipboard decision 11, menus decision 9).** WaOS already does, across threads, what Chrome does across processes for web contents [read: `apps/waos/src/ui/program_canvas.rs`, `deliver_key` and `offer_to_menu_bar_if_left`]. Across processes it becomes:

1. AppKit gives the window process a key (`keyDown:` or `performKeyEquivalent:`); its canvas claims it at once (`KeyEventResult::Handled`, AppKit's `YES`), since AppKit wants the answer before the call returns, and keeps the key (Inset's host keeps the `NSEvent` for `perform_key_equivalent`, menus decision 9).
2. It sends `Key { view, event, reply: n }` to WaOS; WaOS hands the engine the key, the engine gives the program its `key-input` with a `key-reply`.
3. The program answers, or drops the reply (not handled). WaOS sends `KeyReplied { n, handled }`.
4. On a key going down that the program left, the window process calls its own `MenuBar::perform_key_equivalent`, so ⌘C reaches *its* Edit ▸ Copy, which sends `Edit(copy)` to WaOS, which gives the program its `copy` event with the write handle. This is Chrome's `RedispatchKeyEvent` [read §2], and no call waits on the other process.

**Composition.** The input method calls the window process's view: `setMarkedText:`, `insertText:`, `unmarkText`; Inset's text input turns them into editing deltas, which the window process sends to WaOS for the program. Every question the input method asks synchronously (`firstRectForCharacterRange:`, `selectedRange`, `attributedSubstringForProposedRange:`) is answered in the window process from state the program pushed ahead: `ShellTextInput::set_editing_state`, `set_caret_rect` and `set_composing_rect` already push it [read: `ShellTextInput` in `2026-10-17-the-waos-project.md`], and winit answers the candidate window's position from the rect last pushed [inferred from winit's `set_ime_cursor_area` model]. So unlike Chrome, which asks the browser synchronously and, on a cache miss, blocks on the renderer [read §2], WaOS needs no synchronous call; the price is that the candidate window may sit at the caret of one keystroke before until the program's next push arrives, one more hop than today [inferred].

**Pointer, scroll, gestures, cursor, focus.** Events go one way, already in Flutter's shapes (`pointer-event`); `set_cursor` and `request_focus_change` come back as values; the window's focus, occlusion, minimizing, frame, screen and scale are reported as `ProgramView` reports are today, from the window process.

**The clipboard** stays in WaOS: `NSPasteboard` is system-wide, and WaOS's promised forms are served from WaOS's process [inferred]. One change: WaOS looks at the pasteboard's `changeCount` when it is activated or one of its windows gains focus [read: `apps/waos/README.md`], and with programs as their own apps WaOS is seldom active, so a window process must tell WaOS when it becomes active or its window becomes key.

## 8. Menus, Dock, About, notifications, the files per program, and launching

**What moves into the window process, and what that settles** [inferred unless marked]:

| | in the window process | settles |

| Menu bar | the program's menus, set by value (Inset's `MenuBar::set_menus`), with the program's own app menu first: macOS titles it with the process's name, now the program's | menus decision 7's workaround (`WaOS │ Notes │ File …`) goes; the bar is the program's alone |
| Edit's commands | provided items in the window process; a choice goes to WaOS as the view's `copy`, `cut`, `paste` or `edit` event; WaOS trusts it as the user's because only WaOS's own window process can send it (checked at connection, as Chrome checks the audit token) | clipboard decisions 4 and 5 unchanged |
| About | AppKit's standard About panel in the window process, showing the bundle's name, icon and `CFBundleShortVersionString`; the publisher's key fingerprint can go in its credits | menus decision 11 ("comes with its own process") |
| Dock icon and Dock menu | the bundle's icon; `applicationDockMenu:` built from the program's menu value, as Chrome's shim builds its Dock menu from values [read §2] | menus decision 5 ("A program's Dock menu comes with its own Dock icon") |

| Context menus, tray icons, file dialogs | in the window process: a context menu must open in the process that owns the window, and a file dialog as a sheet on the program's window (Chrome's shim hosts `menu.mojom` and `select_file_dialog.mojom` [read]); a tray icon there belongs to the program's app | |
| Notifications | posted by the window process through Inset's `Notifications`, whose center is the process's own (`UNUserNotificationCenter::currentNotificationCenter` [read: `inset-embedder-winit/src/os/apple/notifications/mod.rs`]), so under the generated bundle id, with its name and icon; a click reaches the window process, which forwards the activation; with nothing running, macOS launches the bundle, which starts WaOS and connects saying it was launched by a notification, and WaOS delivers the click once the program listens, as Chrome does [read §4] and as notifications decision 3 already requires | the `<program id>/<id>` prefix and the `Notes: …` title go; needs the bundle validly signed (§1) |
| Opening files and links with the program | the generated `Info.plist` declares the program's document types and link schemes; Finder's Open With and Apple Events reach the window process, which forwards them | opening decision 3's "until programs register what opens them with the system" |
| Quitting | `applicationShouldTerminate:` answers `NSTerminateLater`, asks WaOS to ask the program (`request_exit`), and replies with its answer; logout and restart ask each program the same way. Chrome's shim terminates at once [read §2], which WaOS's quit rule forbids | the quit flow, per program |

**What stays in WaOS:** the engine and every program's code and GPU work, the store and settings, the clipboard, files, network, processes, sound, the library, `cargo waos`, and the prompts (§11, decision 8).

**The files per program, made at install from the package** [inferred; Chrome's equivalents read in §1]:

```text
~/Applications/WaOS Programs/Notes.app/       the folder name is the program's name
  Contents/Info.plist                         CFBundleIdentifier dev.waos.program.<id>, CFBundleName, CFBundleShortVersionString
                                              (the manifest's version), CFBundleIconFile, CFBundleDocumentTypes and
                                              CFBundleURLTypes (what the program opens), WaOSProgramId, WaOSAppBundleId
  Contents/MacOS/<loader>                     a copy of WaOS's small loader
  Contents/Resources/program.icns             from the package's icon.png (inset-cli already builds icns from one PNG,
                                              `inset-cli/src/desktop.rs` [read])
  Contents/_CodeSignature/                    ad hoc, made by `codesign --sign - -o runtime --entitlements …`
```

- The bundle id must be namespaced, never the program's id itself: `waos-package`'s `ProgramId` is a reverse-DNS id that "both an Apple bundle id and an Android application id accept" [read: `crates/waos-package/README.md`], so a publisher could name a program `com.apple.Safari`; Chrome likewise uses `<browser id>.app.<app id>` [read].
- Settings, data and permissions stay in WaOS's store; the bundle holds nothing that changes while the program runs.
- Like Chrome, WaOS keeps the cdhash it signed, checks each connecting window process by its audit token, rebuilds a bundle that fails to launch or connect, re-signs every bundle when macOS's version changes, and deletes the bundle on removal.

**Launching.**
- From WaOS (the library, an opened file, `cargo waos run`): WaOS opens the program's bundle through Launch Services, which activates it as any app's launch does (project decision 32), passing WaOS's pid; the window process connects to that WaOS only, as Chrome's shim connects to the Chrome that launched it [read §3].
- From the Dock, Finder, Spotlight, a notification or a file: the window process finds WaOS by a bootstrap name derived from WaOS's data folder (Chrome hashes its user data dir [read]); with no WaOS answering it opens WaOS.app with `--panel-closed`, hidden, as `cargo waos run` starts it, and polls for the name; WaOS's single-instance guard settles two at once. It then says which program it is, why it was launched, and the files or links it carries; WaOS runs the program as the library opens it.
- A development run of a program that is not installed has no bundle; §11, decision 6.

## 9. What Inset needs

The question is where the cut goes. The engine's shell traits are already the narrow, value-shaped boundary between the program's engine and "what needs the platform" (`ShellView`, `ShellWindow`, `ShellTextInput`, `ViewPlacement`, menu bars, notifications and the rest, all callable from any thread, every request with one answer) [read: `2026-10-17-the-waos-project.md`, decisions 22 to 24]. Three cuts are possible:

| | A. WaOS's per-program shell in a small Inset app | B. A remote host in Inset (Chrome's remote cocoa) | C. A plain AppKit window process |
|---|---|---|---|
| The window process | an Inset app built from WaOS's workspace (Inset's macOS host and framework), showing one program's windows: the canvas (`SurfaceView`), its input, text input, menus, Dock menu, About, notifications, context menus, tray icons, file dialogs | Inset's macOS host only, serving windows for an Inset app that runs in another process | hand-written `NSApplication`, `NSWindow`, an `NSTextInputClient` view, menus from values, `UNUserNotificationCenter`… |
| What crosses | the engine's shell calls and the program's identity-bound capabilities, as values; pictures as IOSurfaces | Inset's whole embedder API: every `Platform` call and `EmbedderClient` event, the framework's own pictures as IOSurfaces, the native surface tree | the same as A |
| Inset changes | none needed to show a picture: `SurfaceFrame.buffer` is already an IOSurface and `released` already exists [read]; possibly a way to keep an app light (no GPU device or fonts until it paints), found by measuring | large: a serializable embedder API, offscreen views rendered into IOSurfaces, and Inset's own keys and text queries, answered at once in-process today, made either synchronous across processes, as Chrome's Views are [read §2], or redesigned | none |
| WaOS changes | the program canvas, its key and text-input code, the edit commands and per-program menus move from `apps/waos` into the window app nearly as they are (they already talk to the engine asynchronously); WaOS gains a per-program proxy of the shell traits | WaOS unchanged above Inset | as A, plus a second implementation of what Inset's macOS host already does |
| Cost per program | an Inset framework and a GPU device per process, unmeasured | the lightest window process | light |
| Who else needs it | WaOS only | any Inset app wanting windows in a helper process: in practice only hosts of apps, which is WaOS | — |

**Answer.** Cut A is the smallest natural split: it is WaOS-specific code, it puts the cut where the code's contract already is, the per-frame path stays a pass-through of `present` and `released`, and Inset gains nothing it has no other use for. B is Chrome's shape because Chrome's UI framework draws the whole window, the tabs and toolbar included; a WaOS program draws its own window, so the framework in WaOS has nothing to draw there but the canvas [inferred]. C duplicates Inset's host. If A's memory per process measures too high, B is the fallback that removes the framework from every window process. One Inset capability might be worth adding later, for the middle way of §6: a surface that shows another process's layer tree (on Android, `SurfaceControlViewHost`'s `SurfacePackage` [inferred, not read here]), which would matter to Android's task per program too.

## 10. The alternatives to a window process

| | One WaOS process faking each identity | A window process per program (recommended) | A full process per program, each with its own engine |
|---|---|---|---|
| How | change `NSApp.applicationIconImage` and the menus as the front program changes | §8 | each program's bundle runs the engine, wasmtime and WebGPU for its one program; WaOS keeps the store and library |
| Dock and ⌘-Tab | one icon and one ⌘-Tab entry for all programs: a process is one app to Launch Services and the Dock, so per-program entries are impossible, and renaming the app menu at run time needs private calls [inferred] | one each | one each |
| Notifications, About | WaOS's | the program's | the program's |
| Frames | in-process, as today | IOSurface per present, two small messages | in-process |
| Memory | lowest | an Inset app per program (§11, experiment 1) | an engine, a wasmtime store, a GPU device and the capability providers per program [inferred: the heaviest] |
| Crash isolation | none | a window process crashing loses windows, not the program [inferred] | a program crashing takes only itself |
| Shared state | all in one place | the engine's grouping of every view on one screen into one refresh (decision 39), freezing, quit, the dev server and the clipboard stay global | each of those becomes per process, or IPC to WaOS |
| Fits the lead's decisions | contradicts v1 decision 3 | is v1 decision 3 ("a small window process per running program") | contradicts it, and programs running as threads of one WaOS |
| Verdict | fragile and incomplete | recommended | heavier; worth keeping in mind only if one engine for every program proves a liability |

## 11. Recommended architecture for WaOS, and the decisions it needs

### The shape

```text
Notes.app (generated, ad hoc signed)               WaOS.app (Developer ID, notarized)
  loader ── dlopen ──▶ WaOS's window library         engine: every program on its own thread, its GPU work,
  one process per running program, an Inset app:       its IOSurface pool; store, library, clipboard, files,
    NSApplication: Dock icon, menu bar, About,          network, sound, cameras, dev server, prompts
    Dock menu, ⌘-Tab, notifications (its bundle id)
    windows: canvas = Inset SurfaceView             per program: a proxy of the shell traits
    NSTextInputClient, keys, pointer, cursor            (ShellView, ShellWindow, ShellTextInput, menus,
    context menus, tray icons, file dialogs              notifications, dialogs, players?)
            ▲                                                   │
            └──── Mach messages, found by a bootstrap name, ────┘
                  checked by audit token and cdhash:
                  ⇢ events, key and edit commands, IME deltas, window reports, opened files, clicks
                  ⇠ present(picture id, children), each picture's IOSurface port once, cursor, menus,
                    window calls, text-input state, notifications
                  ⇢ released(picture id)
```

1. **Each installed program gets a generated bundle** at install, in `~/Applications/WaOS Programs/`, from its manifest and icon: a namespaced bundle id, the program's name, version and icon, what it opens; a copy of one small loader that loads WaOS's window library from WaOS.app (Chrome's loader and framework [read §1]), so a WaOS update updates every program's window code without rewriting bundles; signed ad hoc, its cdhash kept and checked at each connection; rebuilt when a launch fails and when macOS's version changes; deleted with the program.
2. **One window process per running program**, launched through Launch Services, an Inset app showing that program's windows, menus, Dock menu, About and notifications, and nothing of WaOS's own UI.
3. **The engine stays in WaOS.** The cut is the engine's shell traits and the program's identity-bound capabilities, sent as the values they already are. Pictures cross as IOSurfaces, each picture's Mach port once, then by id; the window process presents to Inset's surface and reports releases.
4. **Keys and text input never wait across processes**: the key reply and the edit commands as Chrome's web contents do them (§7), the input method answered from pushed state.
5. **Launch from anywhere**: a window process launched alone starts WaOS hidden and connects; WaOS runs the program as the library opens it.

### Experiments before the design is fixed

1. **A window process's cost**: memory (`footprint`, `vmmap --summary`) and time from launch to first picture of an Inset app showing one `SurfaceView` fed IOSurfaces by another process; with and without a GPU device and fonts. Decides 1.
2. **`CARemoteLayerClient` on today's macOS**: an IOSurface layer and an `AVPlayerLayer` (SDR, HDR, and FairPlay where a test stream allows) made in one process and shown in another's window; live resize; hit-testing. Decides 3.
3. **The present loop over Mach**: IOSurface ports once and ids per frame at 120 Hz, releases by `IOSurfaceIsInUse` in the window process; latency added per frame.
4. **A generated ad-hoc-signed bundle**: its Dock icon, ⌘-Tab, About, `UNUserNotificationCenter` permission and delivery under its own id, a click launching it with nothing running, Gatekeeper with and without quarantine, and whether notification permission and a camera grant survive re-signing. Decides 4, 5 and 9.

### Risks

- **Ad-hoc signatures**: Gatekeeper distrusts them after a macOS upgrade (Chrome rebuilds every shim then [read]); endpoint-security tools such as Santa may block bundles WaOS writes (Chrome writes through a trusted helper [read]); TCC grants are probably tied to the cdhash [inferred].
- **Lifetime races**, the source of Chrome's recent use-after-free fixes [read §5]: two launches of one program, a window process outliving its program or WaOS, a notification click racing a launch.
- **Synchronous calls**: none are needed in this design; adding any later invites Chrome's drag deadlock [read §5].
- **Accessibility** (a known gap in v1) will need the program's accessibility tree served from the window process; Chrome does it with private remote accessibility tokens [read §2]. It shapes the window protocol when it comes.
- **Memory per program**: unmeasured, here and in Chrome's case.
- **Drag and drop** starts and ends in the window process, so dragged data and promised files must cross, the case where Chrome deadlocked.
- **Live resize**: the program draws at the new size on its own thread, so a window can show a stretched or clipped picture for a frame or two; WaOS's rule that a frame never waits forbids holding the resize as Chrome does [inferred].
- **The pasteboard**: WaOS must hear from window processes when to look at `changeCount` (§7).
- **Private or legacy APIs**: none in the recommended path; decision 3's option b rests on a legacy class Apple may remove.
