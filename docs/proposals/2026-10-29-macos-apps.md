# Programs as apps of their own on macOS

**Decisions taken (2026-10-29).** The lead took these, one question at a time, after project decision 51 (`2026-10-17-the-waos-project.md`) put apps of their own on macOS and Android next, side by side; v1 decision 3 (`2026-10-16-waos-v1.md`) had settled a small window process per running program. The research behind them, Chrome's app shims and what WaOS should build, is `2026-10-29-macos-app-shims-research.md`.

1. **The cut is WaOS's shell traits: each running program's windows are a small Inset app of its own, and the engine stays in WaOS.** The window process shows the program's canvas and holds what macOS gives an app: its Dock icon, menu bar, About, notifications, text input, context menus and file dialogs. The engine's shell calls and the program's identity-bound capabilities cross as the values they already are, and pictures as IOSurfaces. Not a remote host inside Inset, as Chrome's remote cocoa is: Chrome's framework draws the whole window, while a program draws its own, so WaOS's framework has nothing to draw there but the canvas. Not a hand-written AppKit process, which would repeat Inset's macOS host. The research's four experiments (a window process's cost, `CARemoteLayerClient` for video, the present loop over Mach, a generated ad-hoc-signed bundle) run before the decisions that wait on them.
2. **The rest follows Chrome's app shims, not a design of WaOS's own**, except where an earlier decision differs. As Chrome: a bundle per program generated at install with a namespaced id (`dev.waos.program.<id>`), whose small loader loads WaOS's window library, signed ad hoc with the library-validation exemption, its code hash checked at each connection; the connection a Mach port found by a bootstrap name and checked by the sender's audit token; the window process holding the windows, input, menus, Dock menu, About, context menus, file dialogs and notifications, and asking the system for its own notification permission; cameras and the microphone staying in WaOS; WaOS's prompts shown in the program's window. By earlier decisions: no call waits on the other process, the input method being answered from state the program pushed ahead (Flutter's way, where Chrome asks synchronously), and quitting asks the program (WaOS's quit flow, where Chrome's shim ends at once). The experiments' lead steps were dropped as too long.
3. **Pictures reach the window through Chrome's private `CAContext` and `CALayerHost`, being simpler**: WaOS puts the program's layers, its picture and any player's layer, in a `CAContext`, whose id the window process hosts in a `CALayerHost`; nothing crosses per frame, players stay in WaOS with their HDR and protected video, and a resize lands in one frame on both sides through the context's fence port. Not IOSurfaces sent per frame, Chrome's fallback, which copies video out and loses protected video; not the public `CARemoteLayerClient`, which, measured (`../experiments/2026-10-29-remote-layer/`), lost HDR and dropped frames as if the layer were off screen; and not players moved into the window process, which no one does. The API's stability, read on 2026-10-29: Chrome has used it since 2014 (on by default since October 2014), its only version check ever, OS X 10.9 or later, was removed in 2016, and today it checks at run time only that the classes and methods exist (`ui/base/cocoa/remote_layer_api.mm`); WebKit's macOS path uses the same `contextWithCGSConnection:options:` and fence port (`LayerHostingContext.mm`); Apple made a public form only on iOS, BrowserEngineKit's `BELayerHierarchy` (iOS 17.4), marked unavailable on macOS; every class and method Chrome checks is present on macOS 27.0.1.

   **No fallback route**: a second way that hardly anyone runs needs maintaining and tends to break. On macOS a program's windows are its own app's, through this API only.
4. **The hosting is WaOS's code, over two small hooks of Inset's macOS host, and the code keeps three layers apart**: what belongs to WaOS anyway (the engine, its pictures, players and prompts, all drawn in WaOS), what a program's window in a process of its own needs on any desktop (the window process's windows, input, menus and the messages between the two processes), and what is macOS's alone (the bundle, Mach, `CAContext` and `CALayerHost`, declared by WaOS as Chrome declares them), so that the code says what each part is and stays easy to keep. Inset gains, on macOS only and reached by downcasting to its compositor, a surface root no view shows, whose layer the app places itself, and the hook that shows a system layer on a surface, made public; nothing private enters Inset. Not a general "show another process's surfaces" capability in Inset, which nothing but WaOS needs.
5. **Two fixes in Inset**: a window process must never draw, since macOS 27's graphics driver gives a process about 230–280 MB the first time it draws anything (found 2026-10-29: a plain Metal app clearing once gets it too), so Inset's macOS host makes its GPU device and draws only once a view paints something of its own; and an app is not forced to the front at launch, so a program's app that WaOS starts in the background, to post a notification or at login, does not take the user's focus. Nothing calls the first: a frame that only places surfaces, which is all a window process's frames do, has nothing to draw, so the host moves the surfaces' layers and makes no device; the check costs nothing per frame, and an ordinary app's first frame draws at once. The second leaves activation to macOS, which brings forward what is launched as an app (the Dock, Finder, a notification's click, WaOS opening it) and leaves behind what is launched in the background: winit's forcing goes, with no special case, and a bare executable run from a terminal opens behind it.
6. **WaOS.app carries the program loader and the window library through Inset's CLI**: an app declares the other targets of its workspace it carries (`[package.metadata.inset.macos]` `helpers` and `libraries`), and the CLI builds them with the app, puts a helper in `Contents/Helpers`, where Chrome keeps its loader, and a library in `Contents/Frameworks`, and signs them before the bundle. Cargo cannot build another package's library as a dependency without an unstable feature. cargo-packager, which the CLI packaged desktop apps with, signs and makes the disk image before anything can be added, and neither it nor any planned version puts files in `Contents/Helpers`, so Inset's CLI builds macOS packages itself, the `.app`, its signing, the `.dmg` and notarization by Apple's own tools, as it already builds Android's and iOS's, and keeps cargo-packager for Windows' and Linux's installers. A development run finds them beside WaOS's executable, where `cargo build` leaves them; when they are missing, WaOS refuses programs' windows with an error saying what to build, and shows none itself.
7. **Each program app's record of its code hash is protected as Chrome protects its shims'**, provided it is clear, easy and its code lives in the right layer: the record carries an HMAC of the hash under a key WaOS keeps in the macOS Keychain, as Chrome's `cdhash_hmac` rests on a key the Keychain guards, so a process running as the user cannot swap in a window process of its own by rewriting a bundle and its record, which would see what the program shows and type into it as the user. The record exists only on macOS, so the Keychain's code is in WaOS's `os/macos`; a development build may meet the Keychain's question once per rebuild, as Chrome's developers do, with no second path around it.
8. **WaOS's prompts for a program are one Inset widget everywhere, shown where each platform puts a sheet: on macOS, drawn by WaOS into an Inset windowless view and shown as a sheet of the program's app** (2026-11-03), as Chrome's browser draws an app shim's permission bubbles and the shim shows them through its remote layers. The prompt's content is WaOS's on every platform; a placement per platform shows it (on Windows and Linux, where a program's windows are WaOS's own, a WaOS dialog window owned by the program's window). On macOS WaOS adds an ordinary Inset view on a composition layer of its own (native-surfaces decision 33: `add_view`, `set_view_metrics`, `remove_view`, its input through the framework's own entry points); WaOS places that layer in a `CAContext`, and the program's app hosts it in a `CALayerHost` on a sheet of the program's window, forwarding the sheet's input to WaOS, so the window process still draws nothing (decision 5). This brings back for WaOS's own UI the view in no window native-surfaces decision 20 removed when a program's picture stopped needing it. A view on a layer is a generic capability of Inset's, none where a host has none: Android's `SurfaceControlViewHost` and the Windows App SDK's content islands are the same idea; only sending the layer to another process is macOS's alone, and WaOS's. On macOS every view, a window's too, draws into a composition layer of its own (native-surfaces decision 34), so views keep one drawing path. Not a WaOS window over the program's window, which belongs to another app; not the window process drawing a native alert, which decision 5 rules out.
9. **A prompt is a dialog window of its own in the program's app, not a sheet on one of its windows** (2026-11-04), amending decision 8 after the lead saw it run: a program may have several windows, or none, so a prompt attached to one window has to pick one and is lost when that window closes. The dialog is centred on the screen of the program's front window, or the main screen when it has none; its content stays WaOS's view on a layer, hosted in a `CALayerHost`, so the window process still draws nothing; showing it bounces the Dock icon of an app in the background rather than activating it. Asking stays the engine's `Prompts` interface, which a graphical or a command-line shell implements, since not every program has a window; a program whose app is not running yet keeps WaOS's own window for its prompt until the app can be launched in the background (plan step 5). Inset's input and view value types become serde-capable behind a feature, so the messages carry Inset's own types instead of WaOS's copies of them.
10. **A program's menu bar and context menus are its app's, shown by the window process through its own Inset host** (2026-11-05, plan step 5): macOS shows the menu bar of the app in front, which is the program's app while its window is, and a context menu opens at a point of a window the window process holds. WaOS forwards the program's menus as the values they are, whole, and the window process answers each choice by its id. The items the platform provides that act on windows (hide, minimize, zoom, full screen, bring all to front) are carried out by the window process on its own windows, which are the program's, and Edit's commands reach its focused view, whose edit events already cross; a program that sets no menu bar gets the standard one. Tray icons stay in WaOS, belonging to no window. Not WaOS's own menu bar, which shows only while WaOS is in front.
11. **About is macOS's standard panel in the program's app**, reading the name, version and icon WaOS writes into the program's bundle at install; nothing crosses (2026-11-05).
12. **Quitting a program's app asks the program, through WaOS** (2026-11-05), as decision 2 has it: the window process, asked by macOS to quit (its Quit, the Dock's, logging out), answers later, asks WaOS, which asks the program with the lifecycle's exit request as its own Quit does, and answers with the program's answer: an agreeing program ends and its app quits, a refusing one keeps everything open. At logout macOS asks WaOS and each app at once, so a program is asked twice, each answer standing on its own, as WaOS's quit flow allows a second Quit.
13. **A program's file dialogs are opened by its window process, a sheet on the parent view's window, and WaOS mounts the paths it answers** (2026-11-05): the window process is WaOS's own code, its code hash and every connection's sender checked (decisions 2 and 7), and the program only asks, naming no path, as Chrome's browser takes the paths a web app's shim answers (remote cocoa's `SelectFileDialogBridge`). Not the panel in WaOS, which could not be a sheet on the program's window and would bring WaOS to the front.
14. **A program's notifications are posted by its window process under its bundle, WaOS asking first and macOS second; a refusal by either is the program's denial** (2026-11-05), as decision 2 and the notifications proposal put the posting in the program's own process on macOS: they show under the program's name and icon, and the system holds scheduled ones under its bundle. WaOS's question stays, since WaOS decides what a program may do on every system; the system's per-app prompt follows it, as Chrome has shown its own prompt before the system's since 2026-10-22. The program reads one state, granted only while both allow: a refusal by macOS, at its prompt or later in System Settings, reads as `denied`, WaOS's own switch staying as the user set it, and WaOS's settings sending the user to System Settings, since macOS asks once. A click while the program is not running launches its app, which says hello with it, and WaOS starts the program and delivers it. Not the system's prompt alone, which would leave WaOS's grant to macOS.
15. **A program's app is reached through one getter: launched the first time something needs it, never brought forward by the launch** (2026-11-05), so each route is a line on top of it rather than logic of its own: a window, a file dialog, a prompt and a notification ask for the app, which is launched, without a window, when it is not running, and shared by everything that asks while it launches, failing with why if it never comes; a context menu, which opens at a view the app already shows, and the menu bar, which is sent as the app connects, take the app only when it runs. What the user must see brings the app forward as it shows (a window taking the focus, a dialog), so a notification's launch stays in the background with no special case. This amends decision 13, a file dialog of a program whose app is not running launching the app as a window does, and ends decision 9's interim window of WaOS's own for a prompt of a program whose app is not running. Not each route launching and waiting for the app its own way.
