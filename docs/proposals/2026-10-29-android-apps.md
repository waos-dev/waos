# Programs as apps of their own on Android

**Decisions taken (2026-10-29).** The lead took these, one question at a time, after project decision 51 (`2026-10-17-the-waos-project.md`) put apps of their own on macOS and Android next, side by side, and asked for each program's own identity on Android too. The research behind them is `2026-10-29-android-identity-research.md`.

1. **A task per program in WaOS's own app, as Firefox's web apps are.** Each running program is a document task of WaOS's program activity, found again by the program's id (`FLAG_ACTIVITY_NEW_DOCUMENT`), and its task description carries the program's name, icon and colours, so it has its own card in Recents; a pinned shortcut is its icon on the home screen, and its notifications are a channel group of their own. App info, Settings › Apps, the app drawer, the desktop window's header and the notification header still say WaOS: Android names those after the package, and lends no other identity to an app's task. Not a generated shell app per program, as Chrome's WebAPKs are: Play forbids installing apps for this, from 2027 certified devices block apps nobody registered, and each program would ask through the system's install dialog; only Google and Samsung, who sign the shells, build them. Not a shell owning the program's window: it needs API 35, and the user would still answer camera and microphone prompts twice.
2. **Both the tasks and the deck: a task per program by default, WaOS's deck of tabs only when the user switches it on.** By default, Android's Recents is the switcher between programs, and WaOS's own card is the library. A setting keeps programs as tabs in WaOS's one task instead, the phone design's deck (`../wasdk/docs/proposals/2026-09-26-waos-mobile.md`). iOS gives an app one card in its switcher, so on iPhone WaOS keeps the deck for now.
3. **On Android, a task is Inset's window, provided it is natural there and no hack.** `Platform::request_view` starts a task of its own, Android's way of opening a new window (`FLAG_ACTIVITY_NEW_DOCUMENT`); the view arrives through `view_added` with its `initial_data`, here the program's id. Its `window()` answers: `set_title` names the Recents card, `close` ends the task, and a new `HostWindow::set_icon(Option<IconImage>)` sets the card's icon, as it sets a window's icon on Windows and Linux; macOS has none and leaves it unset, as `WindowConfig` leaves an option a system lacks. A task Android brings back by itself, from a shortcut or from Recents after the process was killed, arrives as a view the platform gave, carrying the data it was started with. WaOS's window per program then runs on Android as it does on a desktop. Not a WaOS-only activity outside Inset, which would break the rule that a common capability is Inset's.

   *The proposer's notes.* A task's colours are left out until a program can declare one. Today Inset's app runs inside its one activity's loop, and keeps that activity through every configuration change because a second loop cannot be made; the natural shape is Android's own, a process that outlives its activities, as Flutter's engine outlives a `FlutterActivity`: Inset's app gets one loop for the process, and each activity instance, which `android-activity` already runs on a thread of its own with only application-wide state shared, attaches to it as a view and leaves when it is destroyed. That reshaping comes first, in its own change; several activities at once on a device is still to be checked.
4. **A program's home-screen icon is offered when it is installed**: WaOS asks the launcher to pin the program's shortcut, and the launcher asks the user, as Play adds an installed app's icon and Chrome's "Install app" pins a web app's. Recent programs on WaOS's own icon's menu change nothing in the architecture and wait for the formal version.
5. **A program's notifications are a channel group of its own, holding Inset's sound and silent channels**, so the program has its own section and switch in WaOS's notification settings, as Gmail has one per account, and still posts either kind; this is v1's "a channel per program" made exact. Not one channel per program, which on Android 8 to 11 could not post silently, silence being the channel's; not WaOS's two channels for every program with the program's name in the text, which no switch could turn off per program. Inset gains this on its Android host (decision 6).
6. **What only Android has stays behind Inset's Android host, reached by downcasting the platform, not in Inset's main API**, as WaOS reaches what only macOS has through `WinitPlatform::macos()`; not a helper crate either, since a shortcut must open Inset's own activity with data in the form its host reads back. `AndroidPlatform::pinned_shortcuts()` (`request_pin`, `update`, and `disable`, Android letting no app remove one; `request_pin`'s future finishes once the launcher has the request, never waiting for the user's answer, since Android reports only a pin and never a decline, and the call may take seconds off the main thread) and `AndroidPlatform::notification_channel_groups()` (`set(id, name)`, `remove(id)`, and `notifications(id)`, the same `Notifications` as everywhere, posting in that section's channels), so the cross-platform `Notification` gains no field and WaOS hands each program a `Notifications`: its section's on Android, the platform's elsewhere. `HostWindow::set_icon` stays in the main API, since Android, Windows and X11 all have a window's icon.
