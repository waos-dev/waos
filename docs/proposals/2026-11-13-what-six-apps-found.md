# What six apps found

Written 2026-11-13, after six apps were written on WaOS as an outside developer would write them (decision 20 of `2026-11-12-phone-programs-and-library.md`): a terminal, a live Typst document, a 3D model viewer on wgpu and egui with no Waft, a synthesizer, a camera and a feed reader, each with a log of every place the interface, the SDK, the tools or the documentation failed it. This records what the lead decided about the gaps in the interface, and the order of the work that follows. What was planned on this date, not what is.

## The order of the work

As the lead took it: first what breaks today (programs that end WaOS on Android, the engine faults the logs name, the phone's safe area and status bar); then what lets an app be tested without a person (a development run's permissions, `cargo waos new` inside a workspace, a line said while a run compiles, test tools that drag, hold and resize); then the launcher of decision 16 of `2026-11-12-phone-programs-and-library.md`; then the interface's gaps below, each designed with the lead; then programs as apps of their own on Windows and Linux and the release flow; then the documentation's pages.

## The lead's decisions

1. **Workers are built now.** Three of the six apps froze their window during heavy work (a Typst compile, a model's import, a synthesizer's graph), and a program has one thread. The design is the one of 2026-10-17 (decisions 10 and 11 of `2026-10-17-waos-v1-interface.md`): instances of the program's own code that share nothing and exchange messages, as the web's workers do, with the IO side and WebGPU and without the user's side. Wasm's own threads cannot do it: a component cannot share its memory, wasmtime 50 calls its support of the component model's threads very incomplete, and the cooperative threads that come with WASI 0.3 run one at a time. The experiment that decision asked for comes first (measured: two workers halve a one-second job and four quarter it, and a busy worker leaves the main instance's timing unchanged), then the WIT and its Rust face shown to the lead, then the build. This replaces the wait of decision 51 of `2026-10-17-the-waos-project.md`. Code that must run in time with a sound's output (the web's AudioWorklet) is a separate question, taken later.

2. **HTTP and sockets move to WASI 0.3.** A program's `main` is async, and WASI 0.2's HTTP answers with a pollable that nothing in a program can await, so the feed reader polled every 10 ms. WASI 0.3's client is `send: async func(request) -> result<response, error-code>`, wasmtime 50 serves it, and clocks, the command line and random numbers are already on 0.3.

3. **The time zone is in `system`, in WASI's shape, with a change.** `time-zone: func() -> option<string>`, the IANA name; `utc-offset: func(when: instant) -> option<s64>`, in nanoseconds; and `time-zone(option<string>)` among `system-change`'s cases. WASI 0.3's own `timezone` interface has the two functions and no change, is marked unstable, and wasmtime 50 does not serve it, so importing it would bind the interface to something that may still move. Amended 2026-11-16: `time-zone-abbreviation: func(when: instant) -> option<string>` joins them, the zone's abbreviation at a moment ("CET", "PDT"), which Dart's `DateTime.timeZoneName` gives and WASI's interface lacks; with `utc-offset`, a Waft program's local `DateTime` reads its fields and zone through Waft's `Platform` as Dart reads them through its VM. The lead kept our own interface for it, since it needs more than WASI's; serving WASI's alongside stays open.

4. **A typeface can be opened as its font file**, as Skia's `SkTypeface::openStream` opens one: `open-stream: func() -> tuple<stream<u8>, u32>` on `typeface`, the file whole and the face's index in it. Typst and egui need a font's bytes, and could use no font of the system's. Decision 18 of `2026-10-17-the-waos-project.md` kept font files in the engine because a copy costs the file's size in each program; that cost stays, for the program that asks, and a Waft program, whose glyphs the engine draws, never asks. Measured, the engine can serve such a stream without a copy on macOS (0.2 MiB a program against 53.4 MiB copied, for a 53 MiB face); the interface is the same either way.

5. **Modifier keys and key codes need nothing in the interface.** A view's key events are Flutter's `KeyData`, and a program keeps which modifiers are down from the keys it is sent, as the terminal and the model viewer both did. What was missing is the names: the SDK gains named constants for the logical and physical keys, since a number written wrong fails silently.

6. **The terminal keeps `vt100`**, which is small and does the job, rather than vendoring Alacritty's emulator.

7. **Documents keeps its fonts in the repository until decision 4 is built**, then keeps only what the system cannot offer (the maths face).

8. **The model viewer ships egui's own fonts**, as every egui app does, and lists their licences (the Ubuntu Font Licence, the OFL and MIT).

9. **The three Windows test failures that look like WaOS's own** (a `*.localhost` name, no system font, the certificate check) wait until the apps work.

10. **A package's icon fills its whole square, and WaOS shapes it on each system.** Two of the six drew a Mac app's icon, a rounded tile with a margin, and showed smaller than the rest in the library, which rounds the whole picture itself. Apple's shape helps only in the Dock: Android and iOS cut their own shape from a full square, Windows wants no tile, and a full square can be made into every system's shape while a tile cannot be made back into a square. So the icon is 1024 pixels on a side with no rounded corners, margin, transparency or shadow; WaOS adds Apple's tile and margin when it makes a program's Mac app; `cargo waos package` says so when an icon's corners are transparent; and the page agents read (`agents.md` of the site) says how to draw one.

11. **The Fluent kit gets WinUI's `Page`, which keeps an app's content out from under the system's bars.** Documents and the terminal drew under a phone's status bar, as every app on the kit would: WaOS tells a program where the bars are, and in WinUI it is `Page` that uses it, which the port lacked. `Page` also shrinks its content for the keyboard, as Flutter's `Scaffold` does, recorded as a difference from WinUI, whose own way (scrolling the focused field into view) is a larger port. More of WinUI is ported as it is convenient, so later apps have it.

12. **A view says the style of the system's bars over it**: `set-overlay-style: func(style: overlay-style)` on `view`, beside `set-handles-back`, with `status-bar-icons` and `navigation-bar-icons`, each an optional `brightness`, and `status-bar-contrast-enforced` and `navigation-bar-contrast-enforced`, each an optional `bool`: Flutter's `SystemUiOverlayStyle` without the bars' colours, which Android 15 ignores and iOS never had. A Waft program already works its style out from what it draws under the bars; the interface had nothing to carry it, so the gallery's light page had white status-bar text.

13. **While a program says nothing, the bars follow the system's light or dark mode**, where they were white always. The fix is in Waft's Android app, since a native Waft app with no navigation bar has the same fault.

14. **Workers' interface, after the experiment** (measured: two workers halve a one-second job and four quarter it, the main instance's timing is unchanged while a worker computes, sixteen mebibytes are handed back in 0.7 ms, and a worker runs 0.09 ms after it is asked for). The sketch of 2026-10-17 stands with three corrections: `worker-entry`'s `run` answers `result<stream<list<u8>>, worker-error>`, so `start`, which waits for it, really says `unknown-entry`; `finished` also says of a worker that it trapped; and a program's instances share one clock. A worker may start workers, dropping a `worker` ends it, and messages are bytes only for now. In Rust a worker is `#[wasdk::worker] async fn name(inbox: StreamReader<Vec<u8>>, outbox: StreamWriter<Vec<u8>>)`, started by its name.

15. **`cargo waft` takes an app's Android libraries.** HTTPS does not work in WaOS on Android: the system's certificate check needs a small library of its own in the APK and a call at start, and a Waft app could add nothing to its APK's Java side. The need is general (an AndroidX library for a game activity, Kotlin for a web view, a manifest's permissions for location), and Android's name for it is a library dependency: an app lists `.aar` and `.jar` files as `dependencies` under `[package.metadata.waft.android]`, and `cargo waft` merges each as Gradle does, its classes, its manifest's entries, its resources and its native libraries, refusing what it cannot merge rather than dropping it. Naming a library by its Maven coordinates, and a crate declaring its own, can come later under the same key.

16. **The Fluent kit's list is Waft's list with WinUI's rows.** Waft's `ListView` already scrolls and builds what is in sight; what the feed reader built by hand is the row that lights under the pointer, shows pressed and selected, takes the focus and moves with the arrow keys, and the selection of one or several. So the port is WinUI's `ItemContainer` and the selection of its `ItemsView`, over Waft's list, without WinUI's own virtualizing. A multi-line text box that does not wrap keeps its base in Waft, which gains laying text out at its own width, with the horizontal scroll in the kit's `TextBox` as WinUI's `TextWrapping="NoWrap"` has it; Flutter has none to port. After these: `CommandBar`, `Frame`, `AutoSuggestBox`, links in text.

17. **Smaller ones, as recommended:** `Page` keeps WinUI's name beside Waft's navigator `Page`; `AcceptsTab`, which is WPF's and not WinUI's, is not added; the bars follow the system's mode while the app runs too; Waft's Apple host keeps learning of a released buffer at the layer's next present.

18. **Every question WaOS asks has a row in the program's settings, and a row can hold a set answer.** A development run stopped at WaOS's own prompts with nobody to answer them, and the tools could not see why. The permission questions already have a row, ask, allow or don't allow; the pickers and the file dialogs get one each, ask or answer with a named machine, a named output, the paths given. The rows are set on the settings page or by `cargo waos set`, and are the program's settings like any other, shown there, since a development run is the installed program (decision 11 of `2026-10-23-permissions.md`): no second layer of grants for a run. While a row asks, the run says on its terminal what WaOS is asking. After that, the camera and the microphone gain a fourth value, simulated: a test-pattern camera and a silent microphone from WaOS itself, with no system dialog and no hardware, as Chrome's fake devices, since the system's own question for a camera cannot be answered by any tool and a build machine has none.

19. **Documents keeps Typst's default faces and adds the system's fonts on top**, replacing decision 7. A document that names no font is set in Libertinus Serif, which no system has installed, so dropping it would change every plain document, differently on each system and from Typst everywhere else. Typst's own command-line tool does the same: its faces embedded, the system's beside them.

20. **`localhost` and any name ending in `.localhost` are this computer, answered by WaOS itself on every system**, as browsers answer them without asking the system. macOS answers such names and Windows and Android do not, so a program using one worked on some systems only. They stay under the switch for this computer and the local network, as `127.0.0.1` is.

21. **A typeface's font file says its length**: `open-stream` answers a `font-file` record, the stream, the file's `length` and the face's `index`, as Skia's stream for a font file has a length. Without it a program's buffer grew by doubling as it read: after a few lines of Chinese, Documents held 583 MiB where Typst's own tool held 248 (measured), and the cause was that, not the file being copied where it could be mapped, which Typst's tool does too.

22. **Simulated is a fourth value of the camera's and the microphone's rows**, on a program's page and on the page for every program; the recording indicator says that it is simulated; and what the simulated microphone gives is the user's choice, a quiet tone by default, since silence cannot be told from a microphone that does not work, or silence.

23. **Waft's Android host gets image codecs**, on Android's own decoder. It had none of any kind, so a program on Android decoded no picture.

24. **On Windows and Linux a program is an app of its own by its windows' identity, inside WaOS's process**: its own taskbar or dock button with its icon and name, pinned and started from its pin with WaOS closed, found by name in the Start menu or the app grid. macOS needed a process per program because identity there is the process's; on these two it is the window's. A process per program would add a row in the task manager, notifications under the program's name on GNOME and a crash kept to one program, for far more work. Notifications on GNOME stay under WaOS's name for now.

25. **The engine keeps its fuel count and its yield.** Doing all three of their jobs with the epoch check would make a computing program about a fifth faster, but the network work WaOS does for a program runs on the program's thread and moves only when the program yields: with the epoch alone it would wait up to some 200 ms while the program computes, where it waits a third of a millisecond now. Taking a program's network off its thread would remove that and allow the change; it is a design of its own, for later.

26. **The built-in apps' icons are one family**, each one thing drawn with care, light from above, a quiet tile and few colours, as Apple's own are made, each kept as an SVG beside its PNG; and the page agents read says what a good icon is in those terms and points to them, rather than giving a recipe.

27. **Notes and Video Player take built-in apps' ids**, `dev.waos.notes` and `dev.waos.videoplayer`, in place of examples' ids, before anything under them is published.

28. **What programs print is in WaOS's log by default**, so a program can be debugged on a phone, where no environment can change the log's filter.

29. **The Fluent kit's text box that does not wrap is built from what Flutter already has**: the editor in a horizontal scroll view, laid out at its own text's width, with no change to Waft's port of Flutter's editor. Where Flutter's pieces are not enough, the lead hears of it before anything in Waft's port changes. Line numbers follow what WinUI's `TextBox` and Flutter's editor already expose, found before anything is built.

30. **Window identities on Windows and Linux, the Waft side** (after the measurement: one process showed two windows as two apps on GNOME 50 and Windows 11, each pinned and started from its pin): a process-wide AppUserModelID filled from the app's identifier; per-window blocks for Windows (its AppUserModelID and relaunch command, name and optional icon, which must be one Windows can load or the whole relaunch is dropped) and for Linux (its app id and an activation token); each identity's notifications on Windows with their own click handler; an open window brought forward on Linux through a Linux-only call. GNOME files a notification by its process, not by the app it names, so WaOS's notifications there land under whichever of its windows GNOME finds first; accepted for now, since only a process per program would change it.

31. **Cameras on Android are built**, on Android's own camera API in Waft's Android host; **the website shows the built-in icons**, linked from the page agents read; **the code that reads a photo's details is shared** between Waft's Apple and Android hosts.

32. **Waft's custom shaders are WGSL**, written as Valo's runtime effects are, under Flutter's names (`FragmentProgram`, `FragmentShader`, `ImageFilter::shader`); one program serves as a paint and as a filter, by Flutter's filter convention; a shader is built into the code that uses it; a uniform looked up once is kept; a picture is drawn into an image by a call on the platform. Flutter's shaders are ported by hand.

33. **Waft ports Flutter's Material next**, from the `material_ui` package where Flutter now develops it, and moves its Cupertino's reference to `cupertino_ui` likewise; the reference checkout is `../flutter-packages`. Theme fields come with their component; Material's colour library is ported; until shaders land, Android's ink is the ripple; `Canvas.drawShadow` joins Waft's drawing interface; English first; third-party notices in a file of their own. The WinUI kit stays the default for WaOS's apps and `cargo waos new` until the lead judges Material good enough; Liquid Glass waits for Flutter to merge it into `cupertino_ui`.

34. **A camera's frames say how they are turned**, as the web's `VideoFrame` does, a rotation and a flip on `video-frame`, so a picture taken with a phone held upright is shown upright; on Android a second program joining a camera takes photos at the first one's size, or none, which is Android's limit and is documented as such.

35. **Valo's runtime effects, for Waft's shaders**: a filter's input is the effect's first image left empty, as in Flutter, and a host can prepare an effect for its screen's format when it loads it, so a shader does not stutter the first time it shows.

36. **Three choices of Waft's Material port**: a border or a text style that depends on a widget's state carries a resolver as Waft's colours already do; an object's identity, for `ObjectKey` and `GlobalObjectKey`, is its handle; and callbacks that are the same tear-off in Dart get a stable identity by Waft's existing pattern, so a sheet stacked on another is shown as Flutter shows it.
