# Sound

**Decisions taken (2026-10-29).** The lead took these, one question at a time, starting step 7's sound. Already settled (v1 interface decision 4 and its notes, `2026-10-17-waos-v1-interface.md`): a program builds Web Audio's graph and schedules changes on the audio clock; WaOS plays it on its own audio thread and mixes the programs, since a program cannot answer the system's real-time callback in time, so none of its code runs there; sound gets in through inputs of WaOS's own, samples the program pushes ahead, a player's sound and the microphone; a frozen program's scheduled sound plays out, and a program is not frozen while it is audible or recording; the microphone asks at first use, and WaOS shows which program records. Playing sound is no UI framework's job, so sound is WaOS's alone, through its `local-audio` capability.

1. **WaOS plays a program's graph with `web-audio-api`, a Rust implementation of the W3C Web Audio API, and offers every node of the spec but AudioWorklet**: the crate (MIT) is what IRCAM's `node-web-audio-api` builds Node.js's Web Audio on, renders on its own thread through cpal (Core Audio, WASAPI, ALSA, PipeWire) and decodes the common formats. v1 kept to a strict subset to keep an engine of WaOS's own small; with the whole spec implemented, each further node (delay, compressor, convolver, oscillator, wave shaper, channel splitter and merger, and the rest) costs only its WIT binding, and a program written against the web's Web Audio moves over node for node. AudioWorklet stays out, since it runs the program's own code on the audio thread. *This revises v1 decision 4's strict subset.*
2. **The WIT names Web Audio one for one, each kind of node a resource that hands out the `audio-node` it is** (2026-10-29), since WIT has no inheritance and Web Audio's interfaces do (every node an `AudioNode`, `connect` taking any): `audio-param` with its automation, a resource per node (`gain-node`, `oscillator-node`, `delay-node`, `biquad-filter-node`, `dynamics-compressor-node`, `convolver-node`, `wave-shaper-node`, `stereo-panner-node`, `panner-node`, `analyser-node`, `channel-splitter-node`, `channel-merger-node`, `constant-source-node`, `iir-filter-node`, `audio-buffer-source-node`), and `audio-context` making them with its `create-*` methods, as the spec's factories are. WaOS's own inputs, where the web has none: `stream-input-node`, samples the program pushes ahead, and `microphone-node`, asking at first use, in place of the web's `getUserMedia`; a player's sound comes with media. One context per program by default, more if it makes them. The output device is chosen as the web chooses it, by `selectAudioOutput`, a picker WaOS shows, and the context's `set-sink-id`, so a program sees no list of the user's devices, as the machines' and the photo pickers' grants go. The program-side SDK names its Rust types as the web does (`GainNode`, `create_gain`). Where the binding runs into something awkward while it is written, it is raised rather than worked around.
3. **A mistake the spec throws for traps the program** (2026-10-29), as an uncaught exception ends a script on the web: `web-audio-api` reports the spec's exceptions by panicking with the exception's name ("InvalidStateError - Cannot call `start` twice"), which WaOS catches at each call; a misuse is a programming error, a panic in Rust as an index out of bounds is. Returning them as `result`s, as IRCAM's Node binding turns the same panics into JavaScript exceptions, would make nearly every call return a result nobody handles, and would read the crate's panic text. Failures outside the program's hands (devices, the user, decoding) answer `audio-error`.

Settled along the way, as the proposer's defaults, from what building it met:
- **Audible is sound playing now, read at each tick of the engine** against the context's clock, since the crate reads no output level: a source scheduled far ahead does not keep its program thawed until it starts, and a frozen program's scheduled sound plays out because rendering is on a thread of its own.
- **The system mixes the programs**: each program's context is an output stream of its own, since the crate keeps its backends private. *This revises v1's "WaOS mixes the programs"*; a volume per program is a context's.
- **`OfflineAudioContext` is offered, through a base context both kinds hand out**, decision 1 taking every node of the spec; `ScriptProcessorNode` stays out for AudioWorklet's reason, and the media stream nodes wait for media.
- **Decoding is capped as a buffer's size is**, so a small file cannot expand until it aborts all of WaOS.
- **Recording waits for what shows it**: the app's picker of outputs and its indicator of who records, and the microphone's usage description in WaOS.app's bundle, which inset-cli cannot yet add; until then `open-microphone` answers `not-supported` without asking.
