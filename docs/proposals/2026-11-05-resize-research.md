Research for the lead, 2026-11-05: how real platforms resize windows and keep an app's drawing in step with the size. No decisions are taken here.

Marks: *(unverified)* = not confirmed in a primary source I could read; *(inferred)* = my conclusion from sources. Apple's `developer.apple.com` pages were read through its JSON mirror (`/tutorials/data/documentation/...json`); Wayland through `xdg-shell.xml` at gitlab.freedesktop.org (`wayland/wayland-protocols`, `stable/xdg-shell/xdg-shell.xml`).

## In short

- **Everywhere the window's size is decided outside the app** (user drag, window manager, compositor, rotation, layout); the app is told, and the app's own request is only a request. Only Wayland, Android and Chrome's compositor have a protocol in which the app's frame is tied to a specific size change; macOS, Windows, X11 and the web have none by default.
- **Notification is almost always after the fact and asynchronous**: the window already has the new size, and the app learns by event/callback. The exceptions that ask first are macOS `windowWillResize:toSize:`, Windows `WM_SIZING` and `WM_GETMINMAXINFO`, and the Wayland `configure`, which is a suggestion the client answers with a commit.
- **Refusal comes in two forms, and every platform has the first**: constraints declared ahead (min/max, aspect ratio, increments) and a veto on each step (macOS, Windows). Constraints are hints in places: Wayland says the client "should not rely on the compositor to obey the minimum size". Nothing lets an app refuse a *forced* size (maximized, fullscreen, tiled, split view, rotation): there the app must draw to the size given (Wayland: maximized geometry "must be obeyed", else a protocol error).
- **The GPU surface's size is the app's job on desktop and mobile** (create or resize the swapchain/drawable/canvas buffer to match the window); the window system never resizes it for you, it only scales or rejects a mismatch. Vulkan says so per platform: Win32, Xcb and Xlib "currentExtent must always equal the window size"; Wayland returns the special value `0xFFFFFFFF` and the swapchain *sets* the window size; Android scales a mismatch.
- **When the app is late, what is shown depends on the platform, not on the app**: the old frame stretched (Windows default, macOS `CAMetalLayer`, web canvas, Android scaling mismatch), the old frame anchored with the gap in a background color (Windows `DXGI_SCALING_NONE`, Android `windowBackground`, Chrome's gutter color), the old buffer kept until the new one is committed (Wayland), or the whole window frozen (macOS Flutter blocks the resize up to 1 s).
- **Only a few systems make the window wait for the app**: Wayland (`ack_configure` + commit), X11 with `_NET_WM_SYNC_REQUEST` (WM paces itself by a counter the client bumps), Android (`syncSeqId` + BLAST + `SurfaceSyncGroup`, 1 s timeout), Chrome (`LocalSurfaceId` + deadline, but 0 for the top-level window on desktop), Flutter macOS (blocks the platform thread, 1 s timeout). Everything that waits also has a timeout; none waits forever.
- **The two ways to hide lateness**: block the size change until a frame arrives (Flutter macOS, Android BLAST, `presentsWithTransaction`), or let the size change and fill with a known color/old content (Chrome desktop, Windows, X11). The first costs responsiveness of the window; the second costs visible artifacts.
- **Content that cannot be late is decided by pixel sizes**: rotation, fullscreen and Split View are a size change like any other, plus an animation that covers it (screenshot on Android, a transition coordinator on iOS).

## Special cases

- **iOS/iPadOS rotation.** `viewWillTransition(to:with:)` gives the new size and a coordinator; animations added with `animate(alongsideTransition:)` run in the same group as the system's. Rotation is a size change on the view controller ([UIViewController](https://developer.apple.com/documentation/uikit/uiviewcontroller)). Whether the system shows a snapshot of the old content while an app draws late: *(unverified)*.
- **iPadOS Stage Manager / Split View.** Windows are `UIWindowScene`s; the system changes the size, the app observes `effectiveGeometry`, may ask with `requestGeometryUpdate` and limits with `sizeRestrictions` ([sizeRestrictions](https://developer.apple.com/documentation/uikit/uiwindowscene/sizerestrictions)). Snapshot during resize: *(unverified)*.
- **Android rotation.** Default: a configuration change destroys and recreates the Activity ([runtime changes](https://developer.android.com/guide/topics/resources/runtime-changes)); `configChanges="orientation|screenSize|..."` makes the system call the app instead, which is also what Vulkan pre-rotation needs ([prerotation](https://developer.android.com/games/optimize/vulkan-prerotation)). In `ScreenRotationAnimation` a screenshot of the whole screen "prior the change of orientation is taken to hide the element resizing", then rotated and cross-faded; "seamless" rotation instead transforms the window's surface back to the old rotation (`SeamlessRotator`) until the app draws once at the new size, and orientation updates are frozen meanwhile (`DisplayRotation.mSeamlessRotationCount`). [ScreenRotationAnimation.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/wm/ScreenRotationAnimation.java), [SeamlessRotator.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/wm/SeamlessRotator.java), [DisplayRotation.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/wm/DisplayRotation.java). The app opts in per window with `ROTATION_ANIMATION_SEAMLESS` (same file).
- **Android freeform / multi-window / foldables.** Same mechanism as rotation: a configuration change with new dimensions on every user resize or fold; the app may take it (`configChanges`) or be recreated; `resizeableActivity="false"` puts the app in compatibility mode ([multi-window](https://developer.android.com/develop/ui/views/layout/support-multi-window-mode)). Details of per-device resize limits: *(unverified)*.
- **macOS fullscreen / snapping.** `window(_:willUseFullScreenContentSize:)` lets the delegate change the size the content will have ([doc](https://developer.apple.com/documentation/appkit/nswindowdelegate/window(_:willusefullscreencontentsize:))); `windowWillEnterFullScreen` precedes it; Tiling/snap uses the same `windowWillResize` path *(unverified)*. Live resize has explicit start and end hooks (`viewWillStartLiveResize`, `inLiveResize`) for cheaper drawing ([doc](https://developer.apple.com/documentation/appkit/nsview/viewwillstartliveresize())).
- **Windows fullscreen / maximize / snap.** Maximize size may be overridden in `WM_GETMINMAXINFO`. On the flip model the app must call `ResizeBuffers` to realize a fullscreen/windowed transition, "otherwise, your next call to `Present` fails" ([ResizeBuffers](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-resizebuffers)). Snap is an ordinary resize *(unverified)*.
- **Wayland fullscreen / tiled.** Sent as states in the same configure; fullscreen geometry is a maximum, maximized must be obeyed, tiled edges say to draw without shadow ([xdg-shell.xml](https://gitlab.freedesktop.org/wayland/wayland-protocols/-/raw/main/stable/xdg-shell/xdg-shell.xml)).

## Across processes

- **Chrome.** Each frame's surface is named by a `SurfaceId` = `FrameSinkId` + `LocalSurfaceId`; the `LocalSurfaceId` has a `parent_sequence_number` "incremented by the embedder" (the browser, on resize) and a `child_sequence_number` "incremented by the client itself", plus an `embed_token` ([local_surface_id.h](https://chromium.googlesource.com/chromium/src/+/main/components/viz/common/surfaces/local_surface_id.h)). The browser embeds the new id with a deadline policy (`kUseDefaultDeadline`, `kUseSpecifiedDeadline(frames)`, `kUseInfiniteDeadline`) and a *fallback* surface to show until a frame for the new id exists ([delegated_frame_host.cc](https://chromium.googlesource.com/chromium/src/+/main/content/browser/renderer_host/delegated_frame_host.cc): `SetShowSurface`, `SetOldestAcceptableFallback`, `SetFallbackBackgroundColor`). On Windows, Linux and macOS the top-level renderer is *not* blocked: "we would like to produce new content as soon as possible or the OS will create an additional black gutter", so a resize uses `GetResizeDeadlinePolicy()` (0 frames by default) and the gutter shows `GetGutterColor()`. Hidden tabs resized get a blank fallback "preferred to showing contents of old size". A macOS-specific `kThrottleResizeIpc` feature throttles resize IPCs during window resize ([render_widget_host_view_mac.mm](https://chromium.googlesource.com/chromium/src/+/main/content/browser/renderer_host/render_widget_host_view_mac.mm)). Live resize on macOS is therefore: the NSView changes size at once, the browser allocates a new `LocalSurfaceId`, tells the renderer, and shows old frame plus gutter color until the renderer's frame for it arrives. What a late frame looks like beyond that (stretch or crop): *(unverified)*.
- **Flutter macOS.** `FlutterView.setFrameSize:` calls `[_resizeSynchronizer beginResizeForSize:scaledSize notify:^{ [_viewDelegate viewDidReshape:self]; } onTimeout:^{ logError "Resize timed out" }]` ([FlutterView.mm](https://github.com/flutter/flutter/blob/main/engine/src/flutter/shell/platform/darwin/macos/framework/Source/FlutterView.mm)). `ResizeSynchronizer` (Swift, class `FlutterResizeSynchronizer`; the older name in Objective-C was `FlutterResizeSynchronizer.mm`, now gone from main) marks "in resize", calls `notify` (which sends the new metrics to the engine), then loops on the platform thread "for up to 1 second", pumping engine messages with `pollFlutterMessagesOnce()`, until the raster thread's `performCommit(forSize:afterDelay:notify:)` reports a frame whose size equals the target; it exits early on shutdown, and does nothing before the first frame ([ResizeSynchronizer.swift](https://github.com/flutter/flutter/blob/main/engine/src/flutter/shell/platform/darwin/macos/framework/Source/ResizeSynchronizer.swift)). Its own comment lists the problems it avoids: content at the old size in the new bounds, black letterboxing, a perception of lag. Here the platform thread is the one that must wait: the window's resize completes only with the frame.
- **winit** (contrast). One `WindowEvent::Resized(PhysicalSize)` after the size changed, no acknowledgement and no way to hold the resize; `request_inner_size` returns `Some(size)` when applied at once and `None` when "the actual size will be delivered later with `Resized`"; `set_resize_increments` is "a niche constraint hint" (macOS only; "Wayland: Not implemented"; unsupported on iOS, Android, Web) ([WindowEvent](https://docs.rs/winit/0.30.13/winit/event/enum.WindowEvent.html), [Window](https://docs.rs/winit/0.30.12/winit/window/struct.Window.html)). `pre_present_notify` tells the window system a present is coming, to schedule. A winit app resizes its swapchain after the event; anything late is shown as the platform does (table). Any internal pacing on Wayland: *(unverified, source not read)*.

## What an interface would need to say

A size change is one of these, and the program's answer differs:

- **A size the program may answer.** User drag on desktop, program-requested, layout-driven: the platform has a requested size, and the program may keep it, pick another within constraints, or (Wayland `0`) choose its own. On this kind the platform, not the program, still decides the final size ("should not rely on the compositor to obey").
- **A size the program must take.** Maximized, fullscreen (a maximum), tiled, split view, rotation, fold: drawing to another size is a protocol error (Wayland) or ignored. The interface should say which kind each change is.
- **Constraints declared ahead, as facts the platform may or may not honour:** min size, max size, aspect ratio, increments with base size (X11 `WM_NORMAL_HINTS`, macOS `resizeIncrements`/`contentAspectRatio`, Wayland min/max only). Terminals need increments; not every platform has them.
- **The size itself:** in physical pixels and the scale factor; logical size is derived. Window geometry versus buffer size differ where there is decoration or shadow (Wayland `set_window_geometry`).
- **An identifier tying a frame to the change it answers** (Wayland `serial`, Android `syncSeqId`, Chrome `LocalSurfaceId`, X11 update number), and what a frame of any other size means: scaled, rejected, or stale.
- **Whether the platform waits for the frame** (Wayland, Android, Flutter macOS) **or does not** (Windows, X11 default, Chrome desktop top level), and a **deadline** at which it stops waiting (Android 1000 ms, Flutter 1 s, Chrome per policy).
- **What is shown while the program is late**, which is a platform property the program can only choose among: the previous content (stretched, anchored, or clipped), a background color, a snapshot of the old content, or a frozen window. A background color is something the program can set ahead (Android `windowBackground`, DXGI background color, Chrome gutter color).
- **Back-pressure:** a burst of changes may be collapsed so that only the last needs an answer (Wayland: "free to discard all but the last"; X11 sync counter takes the last number).
- **The first size**, before any change (Wayland `0,0` means "program decides"; `currentExtent = 0xFFFFFFFF` means the swapchain sets it) and sizes that do not fit in the GPU (WebGPU texture limit, Vulkan `minImageExtent`/`maxImageExtent`).
- **Animation attached to a transition** (iOS coordinator, Android rotation screenshot): a program may be asked to draw into both sizes during it.
