# A machine's facts, file watching and a per-program `/tmp`

Written 2026-11-15, after building them. Three gaps the Zed-on-WaOS experiment found (its report's "Proposed interfaces for WaOS's gaps"): Zed asks what the machine runs and which shell its user logs in to, watches its worktree, and makes temporary files through `std::env::temp_dir()`. This records the lead's decisions, what was built from them, and the choices made while building that the decisions did not settle.

## The lead's decisions

1. **Two facts on a machine** (`wasdk:platform/machines`, the `machine` resource): `platform`, what the machine runs, a `platform` record of an `operating-system` (`macos`, `linux`, `windows`, `other(string)`) and an `architecture` (`aarch64`, `x86-64`, `other(string)`), as `uname(2)` says on Unix; and `login-shell`, the user's login shell, the user database's shell on Unix, the one SSH starts, none on Windows. No `find-program` and no `environment`: a program does those with `exec`, as Zed does over SSH. Every kind of machine WaOS has answers them; a remote machine learns both once as it connects, running `uname -sm` and reading the shell SSH starts.
2. **File watching**, an interface of its own beside `wasi:filesystem`: `watch(folder, recursive, latency-ms)` over a descriptor the program holds, answering a stream of batches of `change`s (`created`, `modified`, `removed`, `renamed`, `other`, `rescan`), paths relative to the folder, never a path outside the folders the program holds. The engine side over each system's own API, the way the `notify` crate maps them, notify itself allowed if its licence and maintenance fit. Batches by `latency-ms`; an overflow becomes `rescan`; dropping the stream stops the watch. In the `program-base` world and in wasdk.
3. **A per-program `/tmp`**: WaOS preopens a temporary folder of the program's own at `/tmp`, emptied when the program ends, a crash among the ends, and sets `TMPDIR=/tmp`. No new interface. The docs say that `std::env::temp_dir()` panics on WASI whatever `TMPDIR` says, a gap of `std`'s, and that the `tempfile` crate takes `tempfile::env::override_temp_dir("/tmp")`.
4. **The `/tmp` folders are under WaOS's own cache folder**, on the volume of the programs' `/data`, so a file renamed from one into the other is one rename. (Built first under the system's temporary folder, as the first decision said; on Linux `/tmp` is often a volume of its own, where a rename from it into `/data`, or into a file inside a picked folder, fails.)
5. **A machine's commands and its `login-shell` both take the shell from the user database**, as SSH does, whatever `SHELL` WaOS was started with.
6. **`watch` is an `async func`**: inotify watches each folder beneath a recursive watch apart, which takes a while for a large tree, and the program's other tasks go on meanwhile.
7. **One end of a rename the system did not pair is `moved(path)`** (2026-11-17): something was moved to or from the path, and the system did not say which or from or to where; the program looks at the path to see what is there now. macOS's FSEvents reports each end of a rename on its own with `ItemRenamed`, which WaOS had turned into `other`, dropping that it was a rename; Zed's port (the experiment's milestone 4) then lost git's updates, which rename a `.lock` file into place. Linux and Windows keep the paired `renamed(from, to)`. The lead chose the plain name over `renamed-end`.

## What was built

- **`machines`.** `platform` and `login-shell` on `machine`, and on `waos-capabilities`' `Machine` trait, with `Platform::of_uname` reading `uname -s` and `uname -m`'s names, for this computer now and an SSH machine's provider later. This computer reads both once as `LocalMachines` is made: `uname(2)` through rustix, Android reading as Linux as its `uname` does; and `getpwuid_r`'s `pw_shell`, `/bin/sh` for an empty one, which the login environment its commands run in uses too. On Windows the processor is `IsWow64Process2`'s native machine, and there is no login shell.
- **`file-watching`.** The engine watches the path the system gives of the folder's handle (`F_GETPATH`, `/proc/self/fd`, `GetFinalPathNameByHandleW`), only while that path leads to the same folder, checked by its identity before and after the system starts watching, so a rename or a symlink cannot make a watch of a mount's folder tell names outside it. notify's watcher of each system: FSEvents, inotify with notify watching each folder beneath, `ReadDirectoryChangesW`; symlinks never followed. A rename's ends are paired where the system pairs them (inotify by its cookie, Windows by order); FSEvents' come as `other` each; an end nothing pairs is a removal or a creation. A batch is taken its latency after its first change; a rescan of the whole folder is its batch alone, and a batch past 4096 changes becomes one. A folder above the mounts, the root among them, and on Windows the drives, are `unsupported`; a file is `not-directory`.
- **`/tmp`.** Every program has one, whatever else it was given, beside `/data` and `/cache`, writable, at `WaOSConfig::temporary_folders` (the app's `caches/tmp`: `~/Library/Caches/WaOS/tmp`, `%LOCALAPPDATA%\WaOS\Cache\tmp`, `$XDG_CACHE_HOME/waos/tmp`, Android's cache folder's `tmp`). It is removed once the program and its workers have ended, before the end is told. Each folder is held by a lock on a file beside it, so an engine starting removes what a crash of WaOS left and leaves what another engine holds. `TMPDIR` was `/cache`; it is `/tmp` now, and a file in `/tmp` may be renamed onto a picked file as one in `/data` may.
- `examples/file-watching` and the engine's tests of it; `examples/machines` says both facts; the site's guide has a page for file watching, and the processes, file dialogs and concepts pages say the rest.

## Choices made while building

- **`wasi:filesystem/preopens` is imported in `program-base`**, and wasdk re-exports it as `wasdk::preopens`: a program's own folders and its mounts have no descriptor otherwise, `std` keeping its own, so nothing but a machine's root could be watched.
- **notify is pinned at `=9.0.0-rc.8`.** 8.2.2, its last release, gives no rescan for Windows' overflow, which the decision asks for, and panics at an FSEvents flag it does not know. The pin moves to 9.0 once it is released.
- **Windows' native processor is `IsWow64Process2`'s, not `GetNativeSystemInfo`'s**, which answers x64 to an x64 WaOS emulated on ARM64; the Windows VM on ARM64 answered `0xaa64`.
- **An SSH machine's files cannot be watched yet**: WaOS reaches no SSH machine. Its provider will bring a watch of its own, polling over SFTP or running `inotifywait` or `fswatch` through `exec`.
