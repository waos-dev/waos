## Summary

These are the details a "keep the decoder's picture and hand out its planes" interface most often gets wrong. Each is expanded, with sources, below.

1. An app cannot always reach the planes of a hardware-decoded frame on Android. The path Chromium and mpv actually use asks the codec for `AIMAGE_FORMAT_PRIVATE`. That image reports zero planes, and the layout is up to the device, including a vendor layout (a bug report names Qualcomm UBWC, Samsung SBWC and Arm AFBC; that list was not checked against a vendor document). Vulkan then reports `format = VK_FORMAT_UNDEFINED` and a non-zero `externalFormat`. For that image the only legal view is `VK_IMAGE_ASPECT_COLOR_BIT` plus a `VkSamplerYcbcrConversion` created with the same external format. Plane aspects are forbidden. The GL equivalent is `samplerExternalOES` / `GL_TEXTURE_EXTERNAL_OES`, which also does not expose planes. Sampling through that conversion is the only zero-copy read. An identity YCbCr model returns reconstructed components, still not the planes.
2. Forcing a known planar format is a different contract, and it gives up the decoder's own picture. `AIMAGE_FORMAT_YUV_420_888` (`0x23`, the same value as `AHARDWAREBUFFER_FORMAT_Y8Cb8Cr8_420`) promises three CPU planes and even width and height. `AIMAGE_FORMAT_PRIVATE` (`0x22`) says the layout is up to the device and the bytes are not directly accessible. ImageReader says each format is compatible only with itself. A hardware decoder that only produces a vendor layout will not write that layout into a `YUV_420_888` reader; the connection fails or something converts. `KEY_COLOR_FORMAT` is set by the user for encoders and is only readable on a decoder's output format.
3. Even when Vulkan does report a real multi-planar format (`G8_B8R8_2PLANE_420_UNORM` for `Y8Cb8Cr8_420`, `G10X6_B10X6R10X6_2PLANE_420_UNORM_3PACK16` for P010), a plane view needs `VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT` and `VK_IMAGE_ASPECT_PLANE_n_BIT`. A colour-aspect view of the same image still requires a YCbCr conversion. Chromium's Android importer does not take the plane-view path: any buffer whose Vulkan format is not a single-plane RGB format is imported as an external format.
4. The conversion's `suggestedYcbcrModel`, `suggestedYcbcrRange`, and chroma offsets are suggestions for the sampler, and they are a different object from the stream's CICP colour. Using the suggested model makes the sampler return RGB. Using identity makes it return components, in the order given by `samplerYcbcrConversionComponents` (Vulkan's external-format sampling is Cb, Y, Cr in Dawn's comment, which then swizzles back). Doing both is a double conversion.
5. wgpu 30.0.2 cannot represent that Android image. `ExternalTextureFormat` is `Rgba`, `Nv12`, or `Yu12`, all ordinary filterable planes. The Vulkan backend maps `NV12`/`P010` to the two multi-planar formats and to `PLANE_0`/`PLANE_1`, and it never creates a `VkSamplerYcbcrConversion`. It also never chains `samplerYcbcrConversion` into `VkDeviceCreateInfo` (the enable call is commented out, and `add_to_device_create` does not push the struct). Metal and GLES report no capabilities for `NV12` or `P010`. The DMA-buf importer is documented as single-plane only. D3D12 is the backend that actually has a plane-slice path, including `Texture::with_plane_slice` for wrapping one DXGI plane as `R8Unorm` or `Rg8Unorm`.
6. WebGPU's public `GPUExternalTexture` is not a plane API. The descriptor is a video source plus `colorSpace` (`"srgb"` or `"display-p3"`). The sample is already in that colour space, may be outside `[0, 1]`, and is read only with `textureSampleBaseClampToEdge` or `textureLoad`. An `HTMLVideoElement` import expires on the automatic-expiry task; a `VideoFrame` import expires when the frame is closed, and holding the texture holds the frame, which can stall the decoder.
7. Dawn's native external texture is the plane API, plus one opaque exception. It takes `plane0` and optional `plane1`, a 12-float YUV-to-RGB matrix, gamut and transfer parameters, crop origin and size, rotation, and a mirror flag. `TextureFormat::OpaqueYCbCrAndroid` is the exception: one plane, no second plane, and the shader undoes Vulkan's component order before the matrix. That format still is not plane access.
8. Where planes do exist, the 10-bit packing is the high 10 bits of a 16-bit word, not a 10-bit texel. Apple `'x420'` / `'xf20'`: "each 10 bits in the MSBs of 16bits". Android `COLOR_FormatYUVP010` (54, `0x36`, the same value as `AHARDWAREBUFFER_FORMAT_YCbCr_P010`): 10 MSBs, low 6 unused, little-endian. wgpu's `P010` plane views are `R16Unorm` and `Rg16Unorm`, so a shader that treats the word as a full 16-bit value is off by a factor of 64 unless it shifts. Apple's lossless and lossy packed 10-bit formats (`'&xv0'`, `'-xv0'`) have no padding and no planar info struct; they are not those 16-bit planes.
9. The visible rectangle and the half-size chroma plane do not share a grid. Crop is in luma pixels and is applied before rotation. An odd crop origin or an odd visible size means the chroma sample that covers the first visible luma is not at chroma `(0, 0)` of a plane that was cropped the same way, and the last chroma sample covers one visible luma and one coded luma. Android's `Y8Cb8Cr8_420` and P010 require even width and height for the buffer, which does not make the visible rect even. 4:2:0 chroma siting (left, center, top-left) changes which luma the chroma sample is co-sited with.
10. A buffer stays eligible for a hardware overlay only if it is still the decoder's buffer, with the usage and format the display accepts. On Android that usage is `AHARDWAREBUFFER_USAGE_COMPOSER_OVERLAY`, which Chromium sets only for its SurfaceControl image-reader modes; the comment says the framework adds it itself except for `ASurfaceTransaction_setBuffer`. Importing into Vulkan as sampled-only, or drawing the frame into an RGB texture, is a different buffer. Apple can enqueue the same `CVPixelBuffer` to `AVSampleBufferDisplayLayer`. A Metal render into an RGB drawable is no longer that layer. Compressed Apple pixel formats and protected Android buffers are the cases that drop out of one of the two paths (sample, or scan out) even when the other still works.

## 1. Android: the decoder's output, and the only zero-copy sample

### What comes out of a hardware decoder

**verified.** Two ImageReader formats are different promises. `AIMAGE_FORMAT_PRIVATE` (`0x22`): "The choices of the actual format and pixel data layout are entirely up to the device-specific and framework internal implementations, and may vary depending on use cases even for the same device. Also note that the contents of these buffers are not directly accessible to the application." `AImage_getNumberOfPlanes` on that format "will return zero." `AIMAGE_FORMAT_YUV_420_888` (`0x23`): plane 0 is Y with pixel stride 1, planes 1 and 2 are U and V with the same row stride and the same pixel stride, so interleaved NV12 is pixel stride 2 and planar I420 is pixel stride 1. The comment's example producer is a camera, and "this format is always supported as an output format for the android Camera2 NDK API." It does not say a video decoder always produces it. Source: NDK `NdkImage.h`, `AIMAGE_FORMAT_YUV_420_888`, `AIMAGE_FORMAT_PRIVATE`.

**verified.** `AHARDWAREBUFFER_FORMAT_Y8Cb8Cr8_420` is the same numeric value, `0x23`. "Must have an even width and height. Can be accessed in OpenGL shaders through an external sampler. Does not support mip-maps, cube-maps or multi-layered textures." The same sentence is on `AHARDWAREBUFFER_FORMAT_YCbCr_P010` (`0x36`) and `AHARDWAREBUFFER_FORMAT_YCbCr_P210` (`0x3c`). The access named by the header is an external sampler, not a pair of `R8`/`RG8` textures. Source: NDK `hardware_buffer.h`.

**verified.** CPU plane lock is a third view, and it is not the GPU view. `AHardwareBuffer_lockPlanes` "can lock multi-planar formats" and "YUV formats are always represented by three separate planes," Y then Cb then Cr, with row stride and pixel stride. The usage flags must be `AHARDWAREBUFFER_USAGE_CPU_*`. "In case the buffer cannot be locked, `outPlanes` will contain zero planes." Source: `AHardwareBuffer_lockPlanes`.

**verified.** The video path that keeps the decoder's buffer asks for private, not for `0x23`. Chromium's `ImageReaderGLOwner` constructor: "Set the width, height and format to some default value. This parameters are/maybe overriden by the producer sending buffers to this imageReader's Surface." It calls `AImageReader_newWithUsage(1, 1, AIMAGE_FORMAT_PRIVATE, usage, ...)`. The usage is `AHARDWAREBUFFER_USAGE_GPU_SAMPLED_IMAGE`, or `AHARDWAREBUFFER_USAGE_PROTECTED_CONTENT` for the secure mode, and `AHARDWAREBUFFER_USAGE_COMPOSER_OVERLAY` when the mode is a SurfaceControl mode. Source: `image_reader_gl_owner.cc`, `ImageReaderGLOwner::ImageReaderGLOwner`.

**verified.** mpv does the same. `hwdec_aimagereader.c` `init`: "dummy dimensions, AImageReader only transports hardware buffers", then `AImageReader_newWithUsage(16, 16, AIMAGE_FORMAT_PRIVATE, AHARDWAREBUFFER_USAGE_GPU_SAMPLED_IMAGE, 5, &reader)`. The window is turned into a Java `Surface` and stored on FFmpeg's `AVMediaCodecDeviceContext.surface`. The GL mapper requires `EGL_ANDROID_image_native_buffer` and either `GL_OES_EGL_image_external` or `GL_OES_EGL_image_external_essl3`, imports with `eglGetNativeClientBufferANDROID` / `eglCreateImageKHR` / `glEGLImageTargetTexture2DOES`, and sets the mapped format to `IMGFMT_RGB0`. The author of the change wrote "the texture is always RGB0" and "can't fix". Source: mpv `video/out/hwdec/hwdec_aimagereader.c`; mpv PR 9324, sfan5, 2021-10-18.

**verified.** ImageReader will not quietly treat one format as another. "Some color formats may be overridden by the producer sending buffers to this ImageReader's Surface if the default color format allows. ImageReader guarantees that all Images acquired from ImageReader will have a 'compatible' format to what was specified. As of now, each format is only compatible to itself." `PRIVATE` images "are not directly accessible by the application." Source: Android `ImageReader` reference, `getImageFormat` and `newInstance` with usage.

**verified.** A decoder's colour format cannot be selected with `KEY_COLOR_FORMAT`. MediaFormat: "`KEY_COLOR_FORMAT` — set by the user for encoders, readable in the output format of decoders." fadden, 2014, on the same question: "No, there is currently no way to specify the color format for the decoder output. This is especially annoying on devices that use undocumented proprietary buffer layouts. Directing the output to a Surface results in more consistent and portable behavior." Source: Android `MediaFormat`; Stack Overflow 25236174.

**verified.** `COLOR_FormatYUVP010` is 54 (`0x36`), the same value as `AHARDWAREBUFFER_FORMAT_YCbCr_P010`. "P010 is 10-bit-per component 4:2:0 YCbCr semiplanar format. This format uses 24 allocated bits per pixel with 15 bits of data per pixel. … Each chroma and luma component has 16 allocated bits in little-endian configuration with 10 MSB of actual data." The diagram shows the low 6 bits unused. "Use this format with Image. This format corresponds to `ImageFormat.YCBCR_P010`." Source: Android `MediaCodecInfo.CodecCapabilities`.

What I could not settle by reading a decoder on a device: which fraction of current hardware decoders, given `AIMAGE_FORMAT_PRIVATE`, return `0x23` versus a vendor code. The projects that ship this path treat the result as opaque. A closed issue that names the vendor codes (Qualcomm `YCbCr_420_SP_VENUS_UBWC` `0x7FA30C06`, `YCbCr_420_TP10_UBWC` `0x7FA30C09`, `YCbCr_420_P010_VENUS` `0x7FA30C0A`, and the same claim for Samsung SBWC, Arm AFBC, MediaTek) is a bug report, not a vendor document. **verified** as what that report says; not verified as an exhaustive device survey. Source: lumina-video issue 9.

HDR on this path is metadata beside that opaque buffer, not a promise of linear P010. The earlier report already verified `KEY_HDR_STATIC_INFO` and the colour keys on `INFO_OUTPUT_FORMAT_CHANGED`. mpv PR 9324 records that a Pixel 6 did 10-bit HEVC and VP9 hardware decode with HDR through this AImageReader path and "got visually acceptable results." That is one device, and the texture was still the external-OES sample.

### Vulkan import: format versus externalFormat, and why plane views stop

**verified.** `vkGetAndroidHardwareBufferPropertiesANDROID` fills `VkAndroidHardwareBufferFormatPropertiesANDROID`: `format`, `externalFormat`, `formatFeatures`, `samplerYcbcrConversionComponents`, `suggestedYcbcrModel`, `suggestedYcbcrRange`, `suggestedXChromaOffset`, `suggestedYChromaOffset`. "`format` is the Vulkan format corresponding to the Android hardware buffer's format, or `VK_FORMAT_UNDEFINED` if there is not an equivalent Vulkan format." "`externalFormat` is an implementation-defined external format identifier for use with `VkExternalFormatANDROID`. It must not be zero." "If the Android hardware buffer has one of the formats listed in the Format Equivalence table, then `format` must have the equivalent Vulkan format listed in the table. Otherwise, `format` may be `VK_FORMAT_UNDEFINED`, indicating the Android hardware buffer can only be used with an external format." The equivalence that matters here is `AHARDWAREBUFFER_FORMAT_Y8Cb8Cr8_420` → `VK_FORMAT_G8_B8R8_2PLANE_420_UNORM` and `AHARDWAREBUFFER_FORMAT_YCbCr_P010` → `VK_FORMAT_G10X6_B10X6R10X6_2PLANE_420_UNORM_3PACK16`. A vendor code is not in that table, so `VK_FORMAT_UNDEFINED` is allowed. Source: Vulkan ref page `VkAndroidHardwareBufferFormatPropertiesANDROID`; the struct itself in NDK `vulkan_android.h`. The equivalence rows are the extension's table as stated on that page; I did not re-read the PDF table cell by cell this session, so the two rows above are **verified** against the NDK format comments plus the ref page's rule, and the exact table cell text is the ref page's.

**verified.** "`formatFeatures` must include `VK_FORMAT_FEATURE_SAMPLED_IMAGE_BIT` and at least one of `VK_FORMAT_FEATURE_MIDPOINT_CHROMA_SAMPLES_BIT` or `VK_FORMAT_FEATURE_COSITED_CHROMA_SAMPLES_BIT`." Those features "only indicate the features available when using an external-format image." A non-undefined format has a separate set of features from `vkGetPhysicalDeviceFormatProperties2`, and "the external format will support sampler YCbCr conversion even if the non-external format does not, and rendering directly to the external format will not be supported even if the non-external format does." Source: the same ref page.

**verified.** An image created with a non-zero `VkExternalFormatANDROID` has `format = VK_FORMAT_UNDEFINED`. "If `externalFormat` is zero, the effect is as if the `VkExternalFormatANDROID` structure was not present." For the view: "If `image` has an Android external format, `format` must be `VK_FORMAT_UNDEFINED`" (VUID-VkImageViewCreateInfo-image-02399). "If `image` has an Android external format, the `pNext` chain must include a `VkSamplerYcbcrConversionInfo` structure with a `conversion` object created with the same external format as `image`" (VUID-VkImageViewCreateInfo-image-02400). "If `image` has an Android external format, all members of `components` must be the identity swizzle" (VUID-VkImageViewCreateInfo-image-02401). "When creating a `VkImageView`, if `image` was created with an Android hardware buffer external format, then `aspectMask` must equal `VK_IMAGE_ASPECT_COLOR_BIT`." Source: Vulkan ref pages `VkImageViewCreateInfo`, `VkImageSubresourceRange`.

**verified.** Plane views are a different image, one that was created with a real multi-planar `VkFormat`. "If `subresourceRange.aspectMask` is one of the multi-planar aspect mask bits, a single-plane image view will be created. The `image` of a single-plane view must have been created with a multi-planar format and the `VK_IMAGE_CREATE_MUTABLE_FORMAT_BIT` create flag." "`VK_IMAGE_ASPECT_PLANE_0_BIT` specifies plane 0 of a multi-planar image format." A colour-aspect view of a multi-planar format is a multi-plane view and still needs the YCbCr conversion. Source: `VkImageViewCreateInfo`, `VkImageAspectFlagBits`.

**verified.** The conversion object is `VkSamplerYcbcrConversionCreateInfo`: `format` (or the external format in the `pNext` chain), `ycbcrModel`, `ycbcrRange`, `components`, `xChromaOffset`, `yChromaOffset`, `chromaFilter`, `forceExplicitReconstruction`. The Android struct's `suggested*` members and `samplerYcbcrConversionComponents` are what the spec tells the application to put there. They are named "suggested" in the member list. Source: NDK `vulkan_core.h` `VkSamplerYcbcrConversionCreateInfo`; `vulkan_android.h`.

What that suggestion means for an interface, **verified** as the semantics of the fields and **from the Dawn comment** for the component order:

- `suggestedYcbcrModel` selects the matrix the sampler applies (`VK_SAMPLER_YCBCR_MODEL_CONVERSION_YCBCR_709`, `_601`, `_2020`, or `_YCBCR_IDENTITY` / `_RGB_IDENTITY`). Identity does not apply a matrix. It still reconstructs chroma at the sample position. It is not a plane load.
- `suggestedYcbcrRange` is narrow or full. It is the sampler's range, not a second copy of the container's CICP range, and the two can disagree. The stream's range is the one an app needs if it converts itself; the suggestion is the one that matches how this particular buffer was written.
- `suggestedXChromaOffset` / `suggestedYChromaOffset` are `VK_CHROMA_LOCATION_COSITED_EVEN` or `VK_CHROMA_LOCATION_MIDPOINT`. They are the reconstruction offsets, which is chroma siting for this buffer. Whether the implementation honours a location it did not suggest is a format-feature question (`MIDPOINT_CHROMA_SAMPLES` versus `COSITED_CHROMA_SAMPLES`), not a field the app can assume is free.
- `samplerYcbcrConversionComponents` is the swizzle the sampler expects. Dawn's comment, in `ComputeExternalTextureParams`: "Vulkan's YCbCr sampling returns components in Cb, Y, Cr, 1 order while yMat expect Y, Cb, Cr, 1." Dawn multiplies by a swizzle that puts them back. An interface that exposes "the sample" has to say which order, or the app's matrix is applied to the wrong channels.

**verified.** Chromium never tries the plane view for these buffers. `VulkanImage::InitializeFromGpuMemoryBufferHandle` queries the format properties, then `should_use_external_format = !IsSinglePlaneRGBVulkanAHBFormat(ahb_format_props.format)`. The RGB list is `R8G8B8A8_UNORM`, `R8G8B8_UNORM`, `R5G6B5_UNORM_PACK16`, `R16G16B16A16_SFLOAT`, `A2B10G10R10_UNORM_PACK32`. Everything else, including a real multi-planar format, takes the external-format path: `externalFormat` is copied, the image is created as `VK_FORMAT_UNDEFINED`, usage is reduced to `VK_IMAGE_USAGE_SAMPLED_BIT` ("We never use image as attachment"), and `ycbcr_info_` is filled from the suggested model, range, and offsets. Source: `vulkan_image_android.cc`.

**verified.** The video shared image does not proceed without an external format. `AndroidVideoImageBacking::GetYcbcrInfo`, Dawn branch: if `ycbcr_info.externalFormat` is 0 it logs "Failed to get the ycbcr info" and returns nothing. The comment: "VulkanYCbCrInfo requires that the format be UNDEFINED if the external format is non-zero." Source: `android_video_image_backing.cc`.

**verified.** `VK_ANDROID_external_format_resolve` is the exception that lets an external format be a colour attachment, and only as a resolve. Chromium's comment: "VUID-VkImageCreateInfo-pNext-02397 was requiring only `VK_IMAGE_USAGE_SAMPLED_BIT`. With `VK_ANDROID_external_format_resolve` condition got relaxed to support input/color attachments, but it requires `externalFormatResolve` feature to be enabled. We never use image as attachment." The resolve properties include `externalFormatResolveChromaOffsetX/Y`, so the resolve also has a chroma siting. Source: `vulkan_android.h` `VkPhysicalDeviceExternalFormatResolvePropertiesANDROID`; `vulkan_image_android.cc`.

### What the other Android projects do

**verified.** Media3's effect pipeline does not read planes. `ExternalTextureManager` "forwards frames from a `SurfaceTexture` backed by an external oes texture (`GL_TEXTURE_EXTERNAL_OES`)." `GlShaderProgram` then samples 2D textures. The zero-copy step is the external sampler; the effect chain's own outputs are ordinary 2D textures, which is a GPU copy into RGB. Source: Media3 `libraries/effect/.../ExternalTextureManager.java` as indexed by the project docs; `GlShaderProgram` reference.

**verified.** GStreamer's `amcviddec` with a surface sets source caps to `video/x-raw(memory:GLMemory), format=RGBA, texture-target=external-oes`, allocates `GST_GL_TEXTURE_TARGET_EXTERNAL_OES`, and attaches that one memory to the output buffer. The non-surface config is the byte-buffer path, appended only when `gl_output_only` is false. Source: `gst-plugins-bad` `sys/androidmedia/gstamcvideodec.c`, `gst_amc_video_dec_base_init`, `gst_amc_video_dec_set_src_caps`.

**verified.** FFmpeg's MediaCodec device context is a surface, not a format. `AVMediaCodecDeviceContext.surface` is "android/view/Surface handle, to be filled by the user. This is the default surface used by decoders on this device." `native_window` is the alternative. The hwcontext's only pixel format is `AV_PIX_FMT_MEDIACODEC`. Without a surface, a caller gets `AV_PIX_FMT_NV12` instead, which is the byte-buffer output. Source: FFmpeg `libavutil/hwcontext_mediacodec.h` (9.0); `hwcontext_mediacodec.c` `pix_fmts`; Stack Overflow 75610292, the accepted answer, which points at that header.

**verified.** mpv's two names are the two contracts. `--vo=mediacodec_embed` "renders `IMGFMT_MEDIACODEC` frames directly to an `android.view.Surface`" and "many of mpv's features (subtitle rendering, OSD/OSC, video filters, etc) are not available." `--hwdec=mediacodec` with `--vo=gpu` is the AImageReader path above. The interface-changes note says mpv 0.28 renamed the old `--hwdec=mediacodec` to `mediacodec-copy` "to reflect conventions followed by other hardware video decoding APIs." `mediacodec-copy` is the copy-back. Source: mpv `DOCS/man/vo.rst`; `DOCS/interface-changes.rst`.

libplacebo's own Android mapper was not read this session. **from memory**, libplacebo samples the imported `AHardwareBuffer` with a YCbCr conversion when the format is external, and can bind multi-planar Vulkan formats as planes when the driver reports one. I am not using that as evidence.

## 2. How WebGPU implementations expose YUV

### The spec the apps see

**verified.** `GPUExternalTextureDescriptor` has `source` (`HTMLVideoElement` or `VideoFrame`) and `colorSpace` (`PredefinedColorSpace`, default `"srgb"`). There is no plane, no matrix, no crop, no rotation. `importExternalTexture` step 4: "Let data be the result of converting the current image contents of source into the color space `descriptor.colorSpace` with unpremultiplied alpha. This may result in values outside of the range [0, 1]. If clamping is desired, it may be performed after sampling." The note: "This is described like a copy, but may be implemented as a reference to read-only underlying data plus appropriate metadata to perform conversion later." Source: WebGPU TR, §6.4.1, fetched this session.

**verified.** Lifetime. An `HTMLVideoElement` import "expires (is destroyed) automatically in a task after it is imported." The task sets `[[expired]]` to true. A `VideoFrame` import "expires when, and only when, the source `VideoFrame` is closed." "If an imported `VideoFrame` is dropped without being closed, the imported `GPUExternalTexture` object will keep it alive until it is also dropped. … this may still stall the video decoder." The user agent may un-expire and return the same object when the source image is unchanged. Source: the same section.

**verified.** Sampling. "External textures are represented in WGSL with `texture_external` and may be read using `textureLoad` and `textureSampleBaseClampToEdge`." "When the binding resource type is a `GPUExternalTexture`, the result is in the color space set by `colorSpace`. It is implementation-dependent whether, for any given external texture, the sampler (and filtering) is applied before or after conversion from underlying values into the specified color space." "If the internal representation is an RGBA plane, sampling behaves as on a regular 2D texture. If there are several underlying planes (e.g. Y+UV), the sampler is used to sample each underlying texture separately, prior to conversion from YUV to the specified color space." A `GPUTexture` bound at an `externalTexture` binding "is like a `GPUExternalTexture` with a single RGBA plane and no crop, rotation, or color conversion." Source: WebGPU TR §6.5.

The colour space of the result is the descriptor's `colorSpace`, not the video's. `"srgb"` and `"display-p3"` are the `PredefinedColorSpace` values named by MDN for this call. The spec text fetched this session says `PredefinedColorSpace` and does not, in the paragraph I read, list HDR transfers. A PQ frame sampled into `"srgb"` is a conversion into that encoding; the spec does not say the conversion is a tone map.

### Dawn's native external texture

**verified** against `src/dawn/native/ExternalTexture.cpp` at `b4a6a2d38b2bc1e1103912f9fa18a4b2ccc4bf79`, which is the implementation the validator and the param builder share. I did not read `include/dawn/webgpu.h`'s C struct this session; the fields below are the ones this file reads.

- `plane0` is required. `plane1` optional. There is no third plane in this validator: "Y + UV" checks plane 0 for 1 component and plane 1 for 2. `Yu12` is not this structure.
- If `plane1` is set, `yuvToRgbConversionMatrix` must be non-null. The comment: "YUV-to-RGB conversion is performed by multiplying the source YUV values with a 3x4 matrix on the right. This is to use 36 bytes of uniform buffer instead of 48." The 12 floats are row-major. A missing matrix becomes identity `{{1,0,0},{0,1,0},{0,0,1},{0,0,0}}` only in the one-plane case, and a TODO says the matrix should become required.
- `gamutConversionMatrix`, `srcTransferFunctionParameters`, and `dstTransferFunctionParameters` must be non-null.
- `doYuvToRgbConversionOnly` skips the gamma and gamut steps. The MSL expectation for `textureLoad` shows the order: sample planes, multiply by the matrix, and unless that flag is set, gamma-decode, gamut-multiply, gamma-encode.
- `cropOrigin` and `cropSize` are in plane-0 texels. Both crop dimensions must be non-zero and the rectangle must lie inside plane 0. `apparentSize` is a second size, also non-zero and within `maxTextureDimension2D`; a 90° or 270° rotation swaps its width and height for the load bounds. The comment on the transform: "The video frame metadata both rotation and mirroring information. The rotation happens before the mirroring when processing the video frame, so do the inverse order when converting UV coordinates." The crop scale and translation are applied after that.
- `TextureFormat::OpaqueYCbCrAndroid` is a one-plane format. It requires `OpaqueYCbCrAndroidForExternalTexture`. The validator rejects the plane when `HasYCbCrDescriptor()` is set: "`%s` was created with a `YCbCrVkDescriptor`." For this format the matrix is pre-multiplied by a swizzle that turns Cb,Y,Cr,1 into Y,Cb,Cr,1. There is also `Unorm16FormatsForExternalTexture`, which lets `R16Unorm` and `RG16Unorm` planes through even though they are not filterable float, described in the file as "a hack to allow YUV HDR `SharedTextureMemory`."

`ExternalTextureParams.cpp` in the same tree builds the 12-float matrix from enums: range `Identity`, `Narrow`, `Full`, and matrix `Identity`, `Rec601`, `Rec709`, `Rec2020`. That is Dawn's built-in set. A `BT.2020` constant-luminance matrix, or a custom one, has to come in as the 12 floats.

Sampling of the multi-plane case in the MSL snapshot: luma `plane0.read(coord)`, chroma `plane1.read(coord >> 1)`, then the matrix. Chroma is point-sampled at half the luma coordinate in that `textureLoad` expansion. `textureSampleBaseClampToEdge` is what applies the sampler's filter to each plane before the matrix, matching the spec note.

## 4. What a frame must say so the app can convert it

The earlier report has the precedence fight (WebCodecs config overrides the bitstream; Chromium's H.264 parser prefers the SPS; containers disagree with the bitstream). This is the set that changes the pixels, once the planes are in hand.

**verified.** Apple attaches all of it to the buffer, as separate keys, not as one colour space:

- `kCVImageBufferYCbCrMatrixKey` (matrix), `kCVImageBufferColorPrimariesKey`, `kCVImageBufferTransferFunctionKey`.
- Transfer values that matter for HDR: `kCVImageBufferTransferFunction_SMPTE_ST_2084_PQ`, `kCVImageBufferTransferFunction_ITU_R_2100_HLG`, `kCVImageBufferTransferFunction_ITU_R_2020` ("note: `kCVImageBufferTransferFunction_ITU_R_709_2` is equivalent, and preferred"), `kCVImageBufferTransferFunction_Linear`, `kCVImageBufferTransferFunction_sRGB`.
- Primaries include `kCVImageBufferColorPrimaries_ITU_R_2020`.
- Chroma siting is its own key. "For progressive images, only the TopField value is used." Values: `Left` ("horizontally co-sited with the left column of luma samples, but centered vertically"), `Center` ("fully centered"), `TopLeft` ("co-sited with the top-left luma sample"), `Top`, `BottomLeft`, `Bottom`, `DV420`.

Source: `CVImageBuffer.h`.

**verified.** Android's sampler suggestions are the same four facts, in Vulkan's enums, and they describe the buffer the driver imported, not the container. See section 1. Dawn's built-in matrices are identity, Rec.601, Rec.709, Rec.2020, and identity / narrow / full range (`ExternalTextureParams.cpp`). That is a smaller set than H.273. A frame that only says "BT.709" has not said whether the range is narrow, and the narrow and full matrices differ by the scale and the chroma midpoint.

**verified.** Bit depth and where the bits sit, for the formats a hardware decoder actually writes:

- 8-bit biplanar: every bit of the byte is the sample. Apple `'420v'` / `'420f'`. Vulkan `G8_B8R8_2PLANE_420_UNORM`. wgpu `R8Unorm` / `Rg8Unorm`.
- 10-bit in 16: the sample is the top 10 bits. Apple `'x420'` / `'xf20'` say "MSBs of 16bits". Android `COLOR_FormatYUVP010` draws the low 6 bits as unused, little-endian. Vulkan's `G10X6` name is the same layout (10 bits, then 6 unused). wgpu's view is `R16Unorm`, so the shader sees `sample / 65535`, which is `value_10bit / 1023 * (1023/65535)` unless the unused bits are zero and the shader shifts. Treating the word as a full-range 16-bit value is wrong by that factor. Video range is a further scale: Apple's 10-bit video range is luma `[64, 940]` and chroma `[64, 960]`, in the 10-bit units, not in the 16-bit word.
- Packed compressed 10-bit (Apple `'&xv0'`, `'-xv0'`) has "no padding bits between pixels" and no planar info. It is not this 16-bit layout.

**verified.** Visible rectangle versus chroma. Android, from the earlier report and still the rule: the crop is inclusive (`KEY_CROP_LEFT/TOP/RIGHT/BOTTOM`, right and bottom are the last valid column and row), "understood in the context of the output frame before applying any rotation," and it is not the buffer size. The buffer's `Y8Cb8Cr8_420` requirement is even width and height, so the coded buffer is even and the crop may still be odd. Dawn's crop is a rectangle in plane-0 texels and must lie inside plane 0; the chroma coordinate in the `textureLoad` expansion is `coord >> 1`, so an odd crop origin selects a chroma texel whose left (or top) luma is outside the crop. WebGPU's external texture has no crop in the public descriptor; the browser is supposed to have applied the visible rect before the sample, and `textureSampleBaseClampToEdge` exists so a filter cannot read past that rect. wgpu's `width`/`height` plus `sample_transform` are the same idea: the size the shader sees can be the visible size while the planes are the coded size, and the transform maps the unit square onto the visible part of the plane.

Chroma siting then moves the sample by half a luma pixel. `Left` / cosited-even and `Center` / midpoint are the two Vulkan locations. Apple's `TopLeft` is both. An interface that stores one "chroma location" enum has to say whether it is horizontal, vertical, or both, because Apple stores them as one 2D value and Vulkan stores them as two.

## 5. The explicit conversion to RGB

What each platform offers, and what it does not promise.

**verified.** Apple: `VTPixelTransferSession` (the header was seen; the property list is `VTPixelTransferProperties.h`). Destination keys: `kVTPixelTransferPropertyKey_DestinationColorPrimaries`, `DestinationTransferFunction`, `DestinationYCbCrMatrix`, `DestinationICCProfile`, `DestinationCleanAperture`, `DestinationPixelAspectRatio`, `ScalingMode`, `DownsamplingMode`. The session can retarget primaries, transfer, and matrix, and can crop and scale. I did not read a sentence that says a PQ-to-709 transfer is a tone map rather than a clip. The destination pixel format is chosen by the destination buffer the caller passes; a 10-bit or float destination is how HDR survives, and that choice is the caller's. Source: `VTPixelTransferProperties.h`.

**verified.** Android, on the zero-copy path, the conversion is the sampler. `VkSamplerYcbcrConversion` or `samplerExternalOES` writes RGB (or identity-model components) as the sample. There is no second "convert this buffer" call that keeps the result in the same `AHardwareBuffer`. `VK_ANDROID_external_format_resolve` can resolve into a colour attachment, which is a GPU write to a different image. Media3's effect pipeline samples the external texture and produces 2D textures. A byte-buffer `COLOR_FormatYUV420Flexible` / `YUV_420_888` output is the CPU image, which `AImage` then exposes as planes; that is the copy out of the decoder's layout, and it is the path `KEY_COLOR_FORMAT` only reports, not the path the app selects.

**from memory**, and only at this granularity: a D3D11 video processor (`ID3D11VideoProcessor`, `VideoProcessorBlt`) can take `NV12` or `P010` and write `B8G8R8A8` or `R10G10B10A2`, with a colour space on the stream and on the output. Tone mapping is a separate processor feature and is not implied by the colour-space fields. I did not open `d3d11.h` this session.

**from memory**: VA-API post-processing is a context created with the video-processing entrypoint, and it is optional per driver. `va_vpp.h` was not in the Firefox `mozva` tree that was searched, and it was not read.

**from memory**: libyuv converts CPU planes, including `P010` to `I010` and to 8-bit, and it does not tone-map. It is the portable fallback when the GPU cannot see the planes. Cost is a full-frame read and write on the CPU, which also drops the buffer out of any overlay path.

HDR, the part that is common to all of them: the conversion has two outputs that must not be collapsed. One is RGB in the source encoding (PQ or HLG, 10-bit or float), which a display can still tone-map. The other is SDR, which has already thrown the highlights away. Apple's transfer-function key and Dawn's `doYuvToRgbConversionOnly` are the switches that keep the first. A `colorSpace: "srgb"` external texture, in the WebGPU sense, is the second.

## 6. Staying eligible for the compositor

**verified.** Android. `AHARDWAREBUFFER_USAGE_COMPOSER_OVERLAY`: "The buffer will be used as a composer HAL overlay layer. This flag is currently only needed when using `ASurfaceTransaction_setBuffer` to set a buffer. **verified.** Apple. `AVSampleBufferDisplayLayer` "is a subclass of `CALayer` that can decompress and display compressed or uncompressed video frames." `enqueueSampleBuffer:` takes a `CMSampleBuffer`, which for a decoded frame carries the `CVPixelBuffer`. `outputObscuredDueToInsufficientExternalProtection` is the protected-content failure. **from memory**: a Wayland compositor can scan out a dmabuf subsurface whose format and modifier were advertised for scanout. ## 7. The three claims

### AV1's two bitstream forms

**verified.** The spec defines both, and says containers must choose. "This specification defines a low-overhead bitstream format as a sequence of the OBU syntactical elements defined in this section. When using this format, `obu_has_size_field` must be equal to 1. For applications requiring a format where it is easier to skip through frames or temporal units, a length-delimited bitstream format is defined in Annex B. Derived specifications, such as container formats … should indicate which of these formats they rely on." Source: AV1 spec §5.2, the markdown in `AOMediaCodec/av1-spec` `06.bitstream.syntax.md`.

**verified.** MP4 / ISOBMFF uses the low-overhead form, with one exception on the last OBU. "Each OBU SHALL follow the `open_bitstream_unit` Low Overhead Bitstream Format syntax. Each OBU SHALL have `obu_has_size_field` set to 1 except for the last OBU in the sample, for which `obu_has_size_field` MAY be set to 0, in which case it is assumed to fill the remainder of the sample." The note says a parser "MAY need to either set `obu_has_size_field` to 1 … or use the length-delimited bitstream format as defined in Annex B" before handing the sample to a decoder that wants the other form. `configOBUs` in the `av1C` "follow the open_bitstream_unit Low Overhead Bitstream Format" and "SHALL" have the size field set. Source: AV1 ISOBMFF binding v1.3.0, §2.4 and §2.3.4.

**verified.** WebCodecs uses the low-overhead form. "`EncodedVideoChunk` `[[internal data]]` is expected to be a sequence of OBUs compliant to the low-overhead bitstream format (Section 5.2 of AV1) forming a single temporal unit, except that the initial `OBU_TEMPORAL_DELIMITER` OBU may be omitted." "`description` is not used for this codec." A key chunk contains an `OBU_SEQUENCE_HEADER` before the first frame header. Source: WebCodecs AV1 registration, `av1_codec_registration.src.html`.

**verified.** VideoToolbox, in Chromium, is configured with an `av1C`. `VideoToolboxAV1Accelerator::ProcessFormat` builds the box with `libgav1::ObuParser::GetAV1CodecConfigurationBox` and passes it as the format extensions to `CMVideoFormatDescriptionCreate` with `kCMVideoCodecType_AV1`. The sample data is the OBUs the accelerator was given (`SubmitDecode` takes `base::span<const uint8_t> data` plus tile buffers). Source: Chromium `media/gpu/mac/video_toolbox_av1_accelerator.cc`. I did not read a VideoToolbox header sentence that names Annex B; the path that was read feeds an `av1C` and OBUs.

**verified** as VLC's reading of WebM and Matroska, not as the Matroska RFC text, which was not opened. `modules/codec/dav1d.c`: "in ISOBMFF/WebM/Matroska the first 4 bytes are from the `AV1CodecConfigurationRecord` and then one or more OBU." The codec-private data is an `av1C` plus OBUs, which is the low-overhead form. Annex B is not what that parser skips four bytes and then parses.

MediaCodec's AV1 sample layout was not re-read on the Android codec-specific-data page this session. The earlier report verified that AV1 codec-private data is optional. Given the ISOBMFF binding and the WebCodecs registration, the samples those containers hand a decoder are low-overhead OBUs; I am not claiming a MediaCodec header says "Annex B is rejected."

dav1d's decoder API was not read this session. **from memory**: `dav1d_send_data` takes low-overhead OBUs, and Annex B is a separate input demuxer in dav1d's tools, not a mode of the library. That matches VLC's parser, which extracts OBUs and feeds dav1d, but the library call itself was not opened.

Chromium's decoder, apart from the VideoToolbox path above, was not re-read for a second bitstream switch. The VA-API encoder delegate sets `obu_has_size_field = 1` on the tile-group header it writes (`av1_vaapi_video_encoder_delegate.cc`), which is the low-overhead form on the encode side.

### VA-API maximum size and formats

**verified.** Read from `media/mozva/va/va.h`:

- `VAConfigAttribRTFormat = 0`. Value is the `VA_RT_FORMAT_*` bits in section 3. This is the format question.
- `VAConfigAttribMaxPictureWidth = 18`. "This attribute determines the maximum picture width the driver supports for a given configuration." Read-only.
- `VAConfigAttribMaxPictureHeight = 19`. The same sentence for height.
- `VAConfigAttribMaxFrameSize = 38` is not the pixel size. `VAConfigAttribValMaxFrameSize` is a bitfield whose `max_frame_size` bit means the encoder can take a max-frame-size misc parameter. It is an encode rate-control attribute.

The width and height attributes are per configuration, so they are asked after `vaCreateConfig` (profile and entrypoint already chosen), via `vaGetConfigAttributes`. They are not a device-wide maximum and they are not on `vaQueryConfigProfiles`.

### Vulkan Video decode

**verified.** Read from NDK `vulkan_core.h` and `vulkan_video_codec_h264std_decode.h`. It is a session plus parsed parameters, not a bytestream decoder.

Up front:

- `VkVideoProfileInfoKHR`: `videoCodecOperation`, `chromaSubsampling`, `lumaBitDepth`, `chromaBitDepth`.
- `VkVideoCapabilitiesKHR`: bitstream buffer alignment, `minCodedExtent`, `maxCodedExtent`, `maxDpbSlots`, `maxActiveReferencePictures`, and the codec std-header version. `vkGetPhysicalDeviceVideoCapabilitiesKHR`.
- `vkGetPhysicalDeviceVideoFormatPropertiesKHR` returns the `VkFormat`s that can be used for the given image usage (decode DPB, decode output, and so on).
- `VkVideoSessionCreateInfoKHR`: queue family, profile, `pictureFormat`, `maxCodedExtent`, `referencePictureFormat`, `maxDpbSlots`, `maxActiveReferencePictures`, std-header version. Then `vkGetVideoSessionMemoryRequirementsKHR` and `vkBindVideoSessionMemoryKHR`. The session has memory of its own, separate from the picture images.
- H.264 session parameters: `VkVideoDecodeH264SessionParametersCreateInfoKHR` holds `maxStdSPSCount`, `maxStdPPSCount`, and optional `VkVideoDecodeH264SessionParametersAddInfoKHR` with `StdVideoH264SequenceParameterSet` and `StdVideoH264PictureParameterSet` arrays. Updates go through `vkUpdateVideoSessionParametersKHR`.

Per picture:

- `vkCmdBeginVideoCodingKHR` with `VkVideoBeginCodingInfoKHR`: the session, the parameters object, and the current DPB slots (`VkVideoReferenceSlotInfoKHR`, each pointing at a `VkVideoPictureResourceInfoKHR`).
- `VkVideoDecodeInfoKHR`: `srcBuffer` plus offset and range (the bytes), `dstPictureResource`, an optional setup reference slot, and the reference slots. `vkCmdDecodeVideoKHR`.
- H.264 picture info, chained on that decode info: `VkVideoDecodeH264PictureInfoKHR` is `pStdPictureInfo`, `sliceCount`, `pSliceOffsets`. `StdVideoDecodeH264PictureInfo` is flags (`field_pic_flag`, `is_intra`, `IdrPicFlag`, `bottom_field_flag`, `is_reference`), `seq_parameter_set_id`, `pic_parameter_set_id`, `frame_num`, `idr_pic_id`, `PicOrderCnt[2]`. The slice bytes sit in `srcBuffer`; the offsets say where each slice starts. The SPS and PPS are not re-sent as bytes; they are looked up by id in the session parameters.
- `VkVideoDecodeCapabilityFlagBitsKHR` has `DPB_AND_OUTPUT_COINCIDE_BIT` and `DPB_AND_OUTPUT_DISTINCT_BIT`. The output image and the DPB image may be required to be the same image, or required to be different, depending on the bit the implementation sets.

The output is a `VkImageView` inside `VkVideoPictureResourceInfoKHR` (`codedOffset`, `codedExtent`, `baseArrayLayer`, `imageViewBinding`). It is an ordinary Vulkan image created with the format the video-format query returned, with decode usage. It is shared with the graphics queue by being a `VkImage` on the same device: if the video queue family and the graphics queue family differ, that is a queue-family ownership transfer of that image, not a new buffer type. Nothing in these structs exports a dmabuf or an `IOSurface`. Export, if wanted, is the usual external-memory create flags on that image, and the format query has to have returned a format that can carry those flags. I did not read a sentence that guarantees the decode output format is `G8_B8R8_2PLANE_420_UNORM`; the query is the answer, per device.
