## Summary

These are the details an encoder interface most often gets wrong or leaves out. Each is expanded, with sources, below.

1. Rate control is several different contracts, and some of them cannot be combined. Average bitrate is a soft target. A data-rate window is a hard cap. Constant bitrate, variable bitrate, constant quality and a per-frame quantiser are separate modes. Apple documents the first four as mutually exclusive with each other in various pairs, and a per-frame QP turns the bitrate properties off.
2. Bitrate, frame rate and “make a key frame now” can change while the encoder is running. Resolution, profile, bit depth, whether B-frames exist, and the rate-control mode generally cannot. Changing those means a new encoder, usually after a drain so the old one finishes the pictures it already accepted.
3. The encoder may change the size it was asked for. VideoToolbox says so at creation. V4L2 `S_FMT` adjusts width and height to the driver’s alignment. Android reports a stride and slice height, and Chromium then recreates the codec at a 16-pixel alignment because `setParameters` does not do that reliably. The visible rectangle is a second size, so the padding is not encoded.
4. Zero-copy input is a buffer the encoder allocated or a surface created for it: VideoToolbox’s pixel-buffer pool, an Android input `Surface`, a D3D texture, a VA surface, a V4L2 dmabuf, a Vulkan image created with encode-source usage. A frame from the same system’s decoder or camera is that buffer only when it was created with the encoder’s format and usage. Otherwise something copies, and RGB is the usual thing that gets copied.
5. Length-prefixed samples plus an `avcC`/`hvcC`, and Annex B start codes, are both real encoder outputs. VideoToolbox’s sample carries a format description. Android and V4L2 emit start codes, and parameter sets come out as their own buffer or are prepended to a key frame, depending on a flag. VA-API packs SPS, PPS and slices only when the driver says it can. Who converts has to be explicit.
6. With B-frames, the encoder emits in decode order and the timestamps stay presentation timestamps. VideoToolbox’s callback is documented as decode order, and each presentation timestamp passed in must be greater than the previous one. V4L2 copies the input timestamp onto the output and says those timestamps will not stay in order. A muxer needs both the presentation time and the decode order. Live encoders usually turn B-frames off instead of exposing this.
7. Parameter sets are not a single header at the start. They are emitted before the first picture, again on each key frame if asked, and they change when the size or profile changes. Android’s codec-config buffers have no meaningful timestamp, and a flush before the first output can drop them so they must be sent again.
8. “Is this a hardware encoder, and can it do this?” is often answered only by creating a session. The list APIs name the codec, a profile, a maximum size and whether a session is scarce. Rate-control mode, 10-bit and the real alignment show up when the session is configured, or not at all until the first frame. Android can reclaim the encoder. VideoToolbox returns “not available now” when the hardware is busy. NVIDIA’s consumer-GPU session cap is a per-system number the vendor has changed.
9. Temporal layers, long-term references, intra refresh and a screen-versus-camera hint are separate knobs, not one scalability name. Apple’s long-term reference is a token the receiver must acknowledge before the encoder may use that frame again. Intra refresh is a period of intra macroblocks, and it is used instead of a key frame.
10. HDR encode is a profile, a 10-bit picture, a colour description, and static metadata (mastering display, content light level) that the encoder writes into the stream. Android says a 10-bit or HDR input must be configured with a suitable profile or the default 8-bit 4:2:0 profile is what you get. Dynamic metadata is a separate switch.
11. WebCodecs `VideoEncoder` has constant, variable and quantizer modes, and Chromium, having no peak in the API, stores variable mode as a peak of ten times the target. The Chromium implementation rejects alpha. There is no encoder id, no intra refresh, no long-term-reference acknowledgement, no B-frame count and no buffer size. Manual reference control is still an open spec issue.
12. Back pressure is the pool. The encoder holds input frames as references and will not produce output until the caller takes it. Drain emits what is left. Reset drops it. On Android, `flush` of an encoder is documented as undefined.

## 1. What the encoder is told to start, and what can change while it runs

### VideoToolbox

**verified.** `VTCompressionSessionCreate` takes width, height, a codec type (`CMVideoCodecType`), an encoder-specification dictionary, and source pixel-buffer attributes. “If the video encoder cannot support the provided width and height it may change them.” The specification can name an encoder id, allow or require hardware, pin a GPU registry id, and enable low-latency rate control. Source: `VTCompressionSession.h` `VTCompressionSessionCreate`; `VTCompressionProperties.h` `kVTVideoEncoderSpecification_EnableHardwareAcceleratedVideoEncoder`, `RequireHardwareAcceleratedVideoEncoder`, `EnableLowLatencyRateControl`.

**verified.** The header’s own recommended configurations are the split that matters:

- Live capture: `RealTime` true, and `ExpectedFrameRate` set to the real-time rate.
- Offline, user waiting: `RealTime` false, `MaximizePowerEfficiency` false.
- Background: `RealTime` false, `MaximizePowerEfficiency` true. If `RealTime` is true, the encoder may act as though power efficiency were false.
- Ultra-low latency: `EnableLowLatencyRateControl`, `RealTime`, `ExpectedFrameRate`, `PrioritizeEncodingSpeedOverQuality`.

Low-latency rate control “enforces” an infinite GOP, no frame reordering and no lookahead, high profiles only, and a temporal-layer structure. It is incompatible with `VariableBitRate`, `VBVMaxBitRate`, `VBVBufferDuration` and `VBVInitialDelayPercentage`. Source: the recommendations block and `kVTVideoEncoderSpecification_EnableLowLatencyRateControl`.

**verified.** Rate control, and which keys exclude which:

- `AverageBitRate`: “not a hard limit; the bit rate may peak above this.” Default 0 means the encoder chooses. “Bit rate settings only have an effect when timing information is provided for source frames.”
- `DataRateLimits`: hard caps, each a byte count and a duration in seconds. Recommended together with `AverageBitRate`.
- `ConstantBitRate`: needs `ExpectedFrameRate`. “Not compatible with” `DataRateLimits`, `AverageBitRate` and `VariableBitRate`. “The encoder will pad the frame.” “Not intended for general streaming.” Unsupported encoders return `kVTPropertyNotSupportedErr` (-12900).
- `VariableBitRate` (macOS 26 / iOS 26): the desired variable bitrate. Not compatible with average, constant, data-rate limits, or low-latency rate control. `VBVMaxBitRate` is the peak that may enter the VBV model.
- `Quality` (0.0–1.0): “for some formats, this property will direct encoder to use a fixed quantization parameter.”
- `ConstantQualityFactor` (macOS 27): “in contrast to cases where `Quality` will cause the quantization parameter to adhere to a fixed value,” this one “is designed for consistent visual quality with or without bitrate limit constraints.”

Source: `VTCompressionProperties.h`, those keys.

**verified.** Frame structure is its own set, all read/write on the session: `MaxKeyFrameInterval` (0 lets the encoder choose; 1 means every frame is a key frame), `MaxKeyFrameIntervalDuration` (both limits apply, “whichever comes first”), `AllowTemporalCompression` (false forces key-frame-only; default true), `AllowFrameReordering` (false prevents B-frames; default true), `AllowOpenGOP`, `MaxFrameDelayCount` (`kVTUnlimitedFrameDelayCount` is -1), `BaseLayerFrameRate` and `BaseLayerFrameRateFraction` / `BaseLayerBitRateFraction` for hierarchical temporal layers. `ReferenceBufferCount` fails if it exceeds the profile/level. Source: the same header.

**verified.** Per frame, `VTCompressionSessionEncodeFrame` takes a `CVImageBuffer`, a presentation timestamp that “must be greater than the previous one,” a duration (`kCMTimeInvalid` if unknown), and a frame-properties dictionary. “Some session properties may also be changed between frames. Such changes have effect on subsequently encoded frames.” `kVTEncodeFrameOptionKey_ForceKeyFrame` forces a key frame, with “it may not be possible for the encoder to accomodate all requests.” `kVTEncodeFrameOptionKey_BaseFrameQP` “turns off standard rate control” and ignores data-rate limits, average bitrate, base-layer fraction, quality, and min/max QP. It must be set for every frame, and only if `kVTCompressionPropertyKey_SupportsBaseFrameQP` is true; otherwise it is ignored. Source: `VTCompressionSession.h` `VTCompressionSessionEncodeFrame`; the two frame-option keys.

**verified.** Long-term references are a protocol, not a GOP number. `EnableLTR` makes the encoder attach `kVTSampleAttachmentKey_RequireLTRAcknowledgementToken` on an LTR frame. The client reports which tokens have reached the receiver with `kVTEncodeFrameOptionKey_AcknowledgedLTRTokens`. `ForceLTRRefresh` encodes a P frame from an acknowledged LTR, or an IDR if none has been acknowledged. Source: those four keys.

What needs a new session, **verified** as what is fixed at `VTCompressionSessionCreate` and not listed as a between-frames property: width and height (the encoder may adjust them once, at creation), the codec type, and the encoder specification (hardware required, low-latency rate control, encoder id, GPU). Profile, colour and bitrate are session properties and the encode call says some of them may change between frames; the supported-property dictionary (`VTSessionCopySupportedPropertyDictionary`, and `VTCopySupportedPropertyDictionaryForEncoder` given width, height, codec and specification) is how you find out which this encoder will accept, and a read-only one returns `kVTPropertyReadOnlyErr` (-12901). I did not find a per-key table of “legal after the first frame.”

### Android MediaCodec

**verified.** An encoder is configured with a `MediaFormat` and `CONFIGURE_FLAG_ENCODE`, then `start`. The keys Chromium sets in `CreateVideoFormat` are mime, profile and level (H.264), width, height, frame rate, `i-frame-interval` in seconds, colour format, and for low delay `latency` = 1 (skipped for H.264 baseline, because “some devices will fail configure”) and `priority` = 0. Bitrate mode is `bitrate-mode` 2 for constant and 1 for variable, then `bitrate`. Temporal layers add `max-bframes` = 0, a `temporal-layering` schema string, and optionally a temporal-layer id and a bitrate-layering string. Source: `ndk_video_encode_accelerator.cc` `CreateVideoFormat`; NDK `AMEDIAFORMAT_KEY_BIT_RATE`, `BITRATE_MODE`, `I_FRAME_INTERVAL`, `LATENCY`.

**verified.** From the `MediaFormat` reference:

- `KEY_I_FRAME_INTERVAL` (“i-frame-interval”): seconds between key frames. Negative means no key frames after the first. Zero means all key frames. “Most encoders will convert this value [to] the number of non-key-frames between key-frames, using the frame rate,” so if frames are dropped or the rate changes, the time interval will not be what was configured. A float is accepted since API 25.
- `KEY_BITRATE_MODE` (“bitrate-mode”): constants live on `MediaCodecInfo.EncoderCapabilities`. Chromium’s values match the long-standing constants VBR = 1, CBR = 2. I did not re-read the `EncoderCapabilities` page this session; constant-quality is the remaining mode those constants are known for (**from memory**: `BITRATE_MODE_CQ` = 0 and `BITRATE_MODE_CBR_FD` = 3). `KEY_QUALITY` applies only in constant-quality mode, and the range comes from `getQualityRange()`.
- `KEY_LATENCY` (“latency”): desired latency in frames. “This key is ignored if the video encoder does not support the latency feature. Use the output format to verify.”
- `KEY_MAX_B_FRAMES` (“max-bframes”): default 0, “which means that no B frames are allowed. Note that non-zero value does not guarantee B frames.”
- `KEY_PRIORITY`: 0 realtime, 1 best effort. “Performance is not guaranteed.”
- `KEY_OPERATING_RATE`: the rate the codec must keep up with, distinct from `KEY_FRAME_RATE`. `KEY_FRAME_RATE` “represents the desired operating frame rate if `KEY_OPERATING_RATE` is not present and `KEY_PRIORITY` is 0. Otherwise, this is just informational.”
- `KEY_INTRA_REFRESH_PERIOD`: if `FEATURE_IntraRefresh` is supported, “the whole frame is completely refreshed after the specified period” by intra-coding a subset of macroblocks each frame, “which leads to more constant bitrate than inserting a key frame.” Ignored if unsupported; check the output format.
- `KEY_TEMPORAL_LAYERING`: schema string. `KEY_TEMPORAL_LAYER_ID` is then present on every output buffer “only if `KEY_TEMPORAL_LAYERING` is `webrtc.svc.*`” and the id key was set at configure.
- `KEY_PREPEND_HEADER_TO_SYNC_FRAMES` (“prepend-sps-pps-to-idr-frames”): 1 prepends SPS and PPS to every sync frame. “A video encoder may not support this feature; the component will fail to configure.” Default 0.
- `KEY_VIDEO_QP_I_MIN` / `I_MAX` / `P_*` / `B_*` / `MIN` / `MAX`: QP clamps. `KEY_VIDEO_QP_AVERAGE` is reported per output frame.
- `KEY_COMPLEXITY`: encoding complexity. `KEY_MAX_FPS_TO_ENCODER`: in surface mode, drop source frames so the encoder’s input rate stays under this.

**verified.** While running, `setParameters` takes:

- `PARAMETER_KEY_VIDEO_BITRATE` (“video-bitrate”, API 19): “Change a video encoder’s target bitrate on the fly.”
- `PARAMETER_KEY_REQUEST_SYNC_FRAME` (“request-sync”): “Request that the encoder produce a sync frame ‘soon’. Provide an Integer with the value 0.”
- Also present on the class, not read in full this session: `PARAMETER_KEY_SUSPEND`, `SUSPEND_TIME`, `OFFSET_TIME`, `QP_OFFSET_MAP`, `QP_OFFSET_RECTS`, `HDR10_PLUS_INFO`, `LOW_LATENCY`.

Chromium’s `RequestEncodingParametersChange` writes frame rate and `"video-bitrate"` through `AMediaCodec_setParameters`. A requested size is rejected: “Update output frame size is not supported.” The NDK constant `AMEDIACODEC_KEY_REQUEST_SYNC_FRAME` exists from API 31; Chromium passes the string `"request-sync"` and comments that `BUFFER_FLAG_KEY_FRAME` “has no effect” on input. Source: `ndk_video_encode_accelerator.cc`; `MediaCodec` reference `PARAMETER_KEY_VIDEO_BITRATE`, `PARAMETER_KEY_REQUEST_SYNC_FRAME`.

**verified.** Profile is “a hint.” “When configuring profile, encoder configuration may fail if other parameters are not compatible… but it may also fail silently (where the encoder ends up using a different, compatible profile).” “When configuring video encoders, profile (if set) must be set together with level.” If no profile is set, the default “always supports 8-bit YUV 4:2:0” and, in Surface mode, “the default 8-bit RGBA color format.” “Applications that want to encode 4:2:2, 4:4:4, 10+ bit or HDR video input MUST configure a suitable profile.” Source: `MediaCodec` “Encoder Profiles”; `MediaFormat` `KEY_PROFILE`.

`KEY_MAX_WIDTH` / `KEY_MAX_HEIGHT` are documented as decoder adaptive-playback hints. They are not the encoder’s way to change resolution.

### Windows Media Foundation and D3D12 video encode

**verified.** Chromium’s Media Foundation accelerator finds a hardware MFT, then sets input and output types. Output type is set before input type. It sets `MF_MT_FRAME_SIZE`, `MF_MT_FRAME_RATE`, and input subtype `MFVideoFormat_NV12`. Through `ICodecAPI` it sets `CODECAPI_AVEncCommonRateControlMode` to `eAVEncCommonRateControlMode_CBR`, `PeakConstrainedVBR`, or `Quality`; `CODECAPI_AVEncCommonMeanBitRate`; `CODECAPI_AVEncCommonMaxBitRate`; `CODECAPI_AVEncMPVGOPSize` (default GOP length 3000); `CODECAPI_AVLowLatencyMode` when modifiable; `CODECAPI_AVEncVideoTemporalLayerCount`; `CODECAPI_AVEncVideoMaxNumRefFrame` down to 1 when modifiable; `CODECAPI_AVEncAdaptiveMode`; `CODECAPI_AVScenarioInfo` for display content; and `CODECAPI_AVEncMPVDefaultBPictureCount`. Per frame it can set `CODECAPI_AVEncVideoSelectLayer`, `CODECAPI_AVEncVideoEncodeQP`, and `MFSampleExtension_VideoEncodeQP`. Source: `media_foundation_video_encode_accelerator_win.cc` around the `SetValue` calls and `SetInputType` / `SetOutputType`.

**verified.** The VEA contract Chromium implements: “The bitrate mode cannot be changed using [RequestEncodingParametersChange] and attempting to do so will result in an error. Instead, re-create a VideoEncodeAccelerator.” Frame size may be requested “only when there is no pending frame.” Source: `video_encode_accelerator.h` `RequestEncodingParametersChange`.

**verified.** Microsoft’s inbox H.264 encoder (`Mfh264enc.dll`) input subtypes are `MFVideoFormat_I420`, `IYUV`, `NV12`, `YUY2`, `YV12`. Output subtype is `MFVideoFormat_H264`. Output type must be set before input type, or `SetInputType` returns `MF_E_TRANSFORM_TYPE_NOT_SET`. Profiles: Baseline, Main, High (High requires Windows 8). Level default −1 means the encoder selects it. `CODECAPI_AVLowLatencyMode` = false switches from slice parallelism to multi-frame parallelism and adds latency. `CODECAPI_AVEncNumWorkerThreads` sets the thread count. Source: Microsoft Learn, “H.264 Video Encoder.”

**verified.** FFmpeg’s `mfenc.c` `venc_opts` exposes the rate-control enum the codec API actually has: `cbr`, `pc_vbr` (peak-constrained VBR), `u_vbr` (unconstrained VBR), `quality`, and, requiring Windows 8, `ld_vbr`, `g_vbr`, `gld_vbr`. Scenario values include `display_remoting`, `video_conference`, `archive`, `live_streaming`, `camera_record`. `quality` is −1..100 and is set as `CODECAPI_AVEncCommonQuality`. A comment says setting scenario to `camera_record` puts the encoder in constant-frame-rate mode. Source: FFmpeg `libavcodec/mfenc.c` `venc_opts`, and the `ICodecAPI_SetValue` calls above it.

**verified.** D3D12 encode is queried before it is created. `ID3D12VideoDevice3::CheckFeatureSupport` with `D3D12_FEATURE_VIDEO_ENCODER_CODEC`, `OUTPUT_RESOLUTION` (minimum, maximum, and a list of resolution ratios), and `RATE_CONTROL_MODE` for CBR, VBR and CQP. Chromium maps CBR to constant bitrate, VBR to variable (target and peak), and CQP to external per-frame QP. If VBR is not supported it logs “falling back to CBR.” GOP length is `D3D12_VIDEO_ENCODER_SEQUENCE_GOP_STRUCTURE.GOPLength`, default 3000. Codecs Chromium constructs delegates for: H.264, HEVC, AV1. There is no VP8 or VP9 delegate. Source: `d3d12_video_encode_delegate.cc` `GetSupportedProfiles`, `D3D12VideoEncoderRateControl::Create`; `d3d12_video_encode_accelerator.cc` codec list.

Rate control on D3D12 is updated with `UpdateRateControl` without recreating the device. I did not read a D3D12 call that changes the encode resolution in place. AV1’s Vulkan-side analogue (frame-size override) is a capability bit; I did not find the same sentence in the D3D12 delegate.

### Linux VA-API, V4L2, Vulkan Video

**verified.** VA-API rate control is chosen when the config is created, not afterwards. Chromium passes `VAConfigAttribRateControl` as `VA_RC_CBR`, `VA_RC_CQP`, or `VA_RC_VBR` depending on the encode mode. For H.264 it also asks `VAConfigAttribEncPackedHeaders` and, only if sequence, picture and slice are all supported, requests those packed headers; otherwise `VA_ENC_PACKED_HEADER_NONE`. Variable bitrate in Chromium’s VA encoder is H.264 only and behind `kChromeOSHWVBREncoding`. On ChromeOS, H.264 CBR with temporal layers can bypass the driver’s rate control and use a software bitrate controller (`H264RateControlWrapper`); that path is disabled on Mesa Gallium (`crbug.com/365106092`). Source: `vaapi_wrapper.cc` around the rate-control attributes; `vaapi_video_encode_accelerator.cc`; `h264_vaapi_video_encoder_delegate.cc` `UseSoftwareRateController`.

**verified.** FFmpeg’s `vaapi_encode_rc_modes` is the fuller set the API has grown: CQP (`VA_RC_CQP`, quality, no bitrate), CBR (`VA_RC_CBR`, bitrate and HRD, no separate max rate), VBR (`VA_RC_VBR`, bitrate and max rate and HRD), ICQ (`VA_RC_ICQ`, since libva 1.1), QVBR (`VA_RC_QVBR`, bitrate, max rate and quality, since 1.3), AVBR (`VA_RC_AVBR`, compiled but `supported` flag 0 in that table). The mode is picked from what `vaGetConfigAttributes` reports, then frozen as `ctx->va_rc_mode`. Surface alignment comes from `VASurfaceAttribAlignmentSize` via `vaQuerySurfaceAttributes`. Source: FFmpeg `libavcodec/vaapi_encode.c` `vaapi_encode_rc_modes`.

Bitrate inside a chosen mode is a per-picture misc parameter (`VAEncMiscParameterTypeRateControl` in Chromium’s `CreateVAEncRateControlParams`). Changing the mode means a new `vaCreateConfig`. I did not read a VA encode path that changes resolution without new surfaces.

**verified.** V4L2’s stateful encoder “takes raw video frames in display order and encodes them into a bytestream. It generates complete chunks of the bytestream, including all metadata, headers, etc. The resulting bytestream does not require any further post-processing by the client.” Initialization is the reverse of the decoder: coded format on `CAPTURE`, raw format on `OUTPUT`. `VIDIOC_S_FMT` on `OUTPUT` “may be adjusted to match encoder minimums, maximums and alignment requirements.” `VIDIOC_S_PARM` sets the frame interval, “just a hint” for scheduling, and also “the framerate that the encoder uses to encode the video.” `VIDIOC_ENUM_FRAMESIZES` and, optionally, `VIDIOC_ENUM_FRAMEINTERVALS` answer before a frame is encoded. Source: kernel `dev-encoder.html`.

**verified.** Controls, from the codec-control reference: `V4L2_CID_MPEG_VIDEO_BITRATE_MODE` is VBR, CBR or CQ. CQ uses `V4L2_CID_MPEG_VIDEO_CONSTANT_QUALITY`, “1 to 100 where 1 indicates lowest quality.” `BITRATE` is the average in bits per second. `BITRATE_PEAK` “must be larger or equal to the average” and “is ignored if the video bitrate mode is set to constant bitrate.” `GOP_SIZE` (default 12). `FORCE_KEY_FRAME` is a button: “Force a key frame for the next queued buffer.” `HEADER_MODE` is `SEPARATE` (header in the first buffer) or `JOINED_WITH_1ST_FRAME`. `REPEAT_SEQ_HEADER`. `INTRA_REFRESH_PERIOD` and `CYCLIC_INTRA_REFRESH_MB` (the period control wins when non-zero). Per-type QP: `H264_I_FRAME_QP`, `H264_B_FRAME_QP`, and the min/max variants. Profiles exist as enums for H.264, HEVC, VP8, VP9. Source: `ext-ctrls-codec.html`.

**verified.** “The client is allowed to use `VIDIOC_S_CTRL()` to change encoder parameters at any time. … The client may attempt to set a control during encoding and if the operation fails with the -EBUSY error code, the `CAPTURE` queue needs to be stopped … follow the Drain sequence to avoid losing the already queued/encoded frames.” So bitrate and a forced key frame are the controls that usually work live, and a control that returns `EBUSY` needs a drain, not a silent retry. Chromium sets CBR or VBR, GOP (0 “to disable periodic key frames”), `B_FRAMES` 0, the H.264 profile and level, `HEADER_MODE_JOINED_WITH_1ST_FRAME`, and `PREPEND_SPSPPS_TO_IDR` when the control exists, and requests a key frame with `FORCE_KEY_FRAME`. Source: `dev-encoder.html` “Dynamic parameters”; `v4l2_video_encode_accelerator.cc`.

**verified.** Vulkan encode (`VK_KHR_video_encode_queue`) is H.264, HEVC and AV1. There is no VP8 or VP9 encode operation in the proposal I read. Rate-control modes are `DEFAULT` (implementation-defined, and the mode a new session starts in), `DISABLED` (the application passes a per-picture QP: H.264 `constantQp`, HEVC `constantQp`, AV1 `constantQIndex`), `CBR`, and `VBR`. They are changed with `vkCmdControlVideoCodingKHR` and `VK_VIDEO_CODING_CONTROL_ENCODE_RATE_CONTROL_BIT_KHR`, including after a session reset, which restores the implementation default. CBR requires `averageBitrate == maxBitrate`. Each layer has its own average, max, and frame rate, plus a VBV size in milliseconds (`virtualBufferSizeInMs`, `initialVirtualBufferSizeInMs`). “The exact behavior of rate control is implementation-specific.” Quality level is a separate control and can be changed on the session; it is not mutually exclusive with rate control (proposal question 5.14 is answered in that direction; I read the section headings and the rate-control text, not every answer paragraph). Source: `VK_KHR_video_encode_queue` proposal §§ on rate control and session parameters; `VkVideoEncodeRateControlModeFlagBitsKHR`.

Codec-specific sequence and picture parameters live in video session parameter objects. Changing them is a new parameters object. The proposal’s AV1 capabilities include `maxTemporalLayers`, `maxSpatialLayers`, `minQIndex`/`maxQIndex`, and `FRAME_SIZE_OVERRIDE` so a picture can be smaller than the session’s max size. GOP remaining-frame counts are optional or required per `prefersGopRemainingFrames` / `requiresGopRemainingFrames`. Source: `VK_KHR_video_encode_av1` proposal, `VkVideoEncodeAV1CapabilitiesKHR`.

## 2. Input frames

**verified.** VideoToolbox takes a `CVImageBuffer`. The session builds a pixel-buffer pool from the encoder’s attributes and any attributes the caller passed. “If the source pixel buffer attributes and the compressor pixel buffer attributes cannot be reconciled, the pool is based on the source pixel buffer attributes and the Video Toolbox converts each CVImageBuffer internally.” “Using pixel buffers not allocated by the Video Toolbox may increase the chance that it will be necessary to copy image data.” `GetPixelBufferPool` can return a different pool if a property change alters the encoder’s attributes. `kVTCompressionPropertyKey_PixelTransferProperties` configures that conversion. Chromium, for HEVC Main10, sets the source attributes to `kCVPixelFormatType_420YpCbCr10BiPlanarFullRange` or `VideoRange` and tells the session the size; for 8-bit it passes no attributes. GPU frames it accepts are `PIXEL_FORMAT_NV12`, or `P010LE` for Main10. Source: `VTCompressionSession.h` `VTCompressionSessionGetPixelBufferPool`; `vt_video_encode_accelerator_mac.mm` `CreateSourceImageBufferAttributes`, `GpuSupportedPixelFormatsForProfile`.

A decoder `CVPixelBuffer` or a screen-capture `IOSurface` wrapped as a `CVPixelBuffer` is the zero-copy input when its pixel format and size match the pool. Otherwise VideoToolbox converts, including from BGRA. I did not find a key that says the caller must pre-convert RGB.

**verified.** Android has three input kinds. “Native raw video format” is `COLOR_FormatSurface`, used with `createInputSurface` after `configure` and before `start`. “The Surface must be rendered with a hardware-accelerated API, such as OpenGL ES. `Surface.lockCanvas` may fail or produce unexpected results.” Flexible YUV 4:2:0 “can be used with an input/output Surface, as well as in ByteBuffer mode,” and “all video codecs support flexible YUV 4:2:0 buffers since” API 22. Specific layouts are “normally only supported in ByteBuffer mode” and some are vendor-specific. Chromium configures `COLOR_FORMAT_YUV420_SEMIPLANAR`, then reads `AMEDIAFORMAT_KEY_STRIDE` and `SLICE_HEIGHT`. If the codec’s aligned size differs, it sets `requested_resolution_alignment` to 16 and recreates the codec: “setParameters() doesn’t work consistently across devices.” Source: `MediaCodec` “Raw Video Buffers” and `createInputSurface`; `ndk_video_encode_accelerator.cc` the configure loop.

The zero-copy path is the input `Surface`: camera, a GL render, or a compositor can write it. A decoder’s private `AHardwareBuffer` is not an encoder input buffer. Getting it into the encoder without a CPU copy means rendering that image into the encoder’s `Surface` (a GPU sample, which the earlier frames report already found is an external-sampler sample, not a plane load). Byte-buffer mode copies into the codec’s input buffers, at the codec’s stride.

**verified.** Media Foundation in Chromium accepts `PIXEL_FORMAT_NV12` and sets `MFVideoFormat_NV12`, with `requested_resolution_alignment` of 2. The inbox software encoder’s documented inputs are the five YUV subtypes above, not BGRA. A hardware MFT’s zero-copy input is a D3D11 texture via the DXGI device manager; I did not re-read that setup in the MF file this session. D3D12 encode input is a texture: `DXGI_FORMAT_NV12` for 8-bit, `DXGI_FORMAT_P010` for H.264 High 10, HEVC Main 10, and AV1 Main when the source is P010, and `DXGI_FORMAT_AYUV` for AV1 High. Chromium’s accelerator copies a CPU frame in with `CopyBufferToNV12Texture` and reports alignment 2. A decoder texture on the same device is the zero-copy input when the format matches. Source: `d3d12_video_encode_delegate.cc` `GetDxgiInputFormat`; `d3d12_video_encode_accelerator.cc`.

**verified.** VA-API encode in Chromium creates surfaces as `VA_RT_FORMAT_YUV420` and requires `PIXEL_FORMAT_NV12` even for “native” input. FFmpeg queries `VASurfaceAttribAlignmentSize` and shifts the low nibbles into width and height alignment. A decoded VA surface is reusable as an encode source when it was allocated with a format and usage the encode context accepts; Chromium’s encode path allocates its own surfaces and uploads. Source: `vaapi_video_encode_accelerator.cc` `kVaSurfaceFormat`; FFmpeg `vaapi_encode.c` alignment query.

**verified.** V4L2 `OUTPUT` is the raw queue. `S_FMT` returns the size after alignment. The selection target `V4L2_SEL_TGT_CROP` (the document’s “visible resolution”) is how 1920×1080 is encoded from a 1920×1088 buffer “for codecs with 16×16 macroblock size. To avoid encoding the padding, the client needs to explicitly configure this selection target.” Dmabuf is the zero-copy import when the driver accepts it; Chromium tries NV12. Source: `dev-encoder.html` steps on `S_FMT` and selection.

**verified.** Vulkan encode input is an image created with `VK_IMAGE_USAGE_VIDEO_ENCODE_SRC_BIT_KHR`, and the image’s format is whatever `vkGetPhysicalDeviceVideoFormatPropertiesKHR` returns for that profile. The proposal does not fix the format at NV12. A decode-output image is a different usage; it is an encode input only if it was created with the encode usage and a format the encode profile accepts. Source: `VK_KHR_video_encode_queue` proposal, the input-format discussion in the search extract and the bitstream-buffer section I read.

## 3. Output

**verified.** VideoToolbox delivers a `CMSampleBuffer` to a callback that “will be called in decode order (which is not necessarily the same as display order).” The presentation timestamp on the sample is the one the caller passed in. There is no separate decode timestamp in the encode call; the callback order is the decode order. `kVTEncodeInfo_FrameDropped` means the frame was dropped and the sample is NULL. A key frame is the absence of `kCMSampleAttachmentKey_NotSync` (Chromium: `keyframe = !not_sync`). `kCMSampleAttachmentKey_IsDependedOnByOthers` is how Chromium decides the temporal layer, and it says that for HEVC this is not enough to fill reference and refresh flags. Chromium then runs `CopySampleBufferToAnnexBBuffer`, so the bytes the accelerator returns are Annex B, not the length-prefixed sample VideoToolbox produced. The format description on the sample is where the `avcC`/`hvcC` lives; Chromium also synthesizes an HDR SEI NAL on a PQ key frame. `VTCompressionSessionCompleteFrames` emits every pending frame up to a timestamp, or all of them if the timestamp is not numeric. `NumberOfPendingFrames` is the back-pressure gauge. Source: `VTCompressionSession.h` the callback and `CompleteFrames`; `vt_video_encode_accelerator_mac.mm` `ReturnBitstreamBuffer`.

**verified.** Android: “Encoders (or codecs that generate compressed data) will create and return the codec specific data before any valid output buffer in output buffers marked with the codec-config flag. Buffers containing codec-specific-data have no meaningful timestamps.” The CSD layout, which “must start with a start code of `\x00\x00\x00\x01`,” is H.264 SPS in `csd-0` and PPS in `csd-1`, and HEVC VPS+SPS+PPS in one `csd-0`. VP9 and AV1 codec-private data are optional. VP8 has none. Chromium’s comment matches: AVC and HEVC config buffers “need to be preserved and appended at the beginning of the bitstream”; AV1 and VP9 extra data “is not expected by decoders”; “Vp8 doesn’t produce configuration buffers.” A key frame is `BUFFER_FLAG_KEY_FRAME` on the output (value 1 in Chromium). Temporal layer id is read back from the output format when it was requested. End of stream on a Surface is `signalEndOfInputStream`. “Going back to Flushed state is only supported for decoders, and may not work for encoders (the behavior is undefined).” Source: `MediaCodec` codec-specific-data section and the flush note; `ndk_video_encode_accelerator.cc` `ProfileNeedsConfigDataInBitstream`.

**verified.** V4L2 output is a complete bytestream. The client sets `timestamp` on the `OUTPUT` buffer and “the `CAPTURE` buffer(s) which resulted from encoding that `OUTPUT` buffer will have their `timestamp` field set to the same value.” “One `OUTPUT` buffer generates multiple `CAPTURE` buffers” in some codecs, and “the encoding order differs from the presentation order … `CAPTURE` timestamps will not retain the order of `OUTPUT` timestamps.” Frame type is a flag on the dequeued buffer. Drain is `VIDIOC_ENCODER_CMD` with `V4L2_ENC_CMD_STOP`, then dequeue until `V4L2_BUF_FLAG_LAST`. After that, further `DQBUF` returns `-EPIPE`. A too-small capture buffer is returned with `V4L2_BUF_FLAG_ERROR`. Headers must be produced again after a stream restart: “any headers that must be included in a standalone stream must be produced again, e.g. SPS and PPS.” Source: `dev-encoder.html` encoding, drain, and the header note.

**verified.** VA-API does not have one bitstream shape. When the driver advertises sequence, picture and slice packed headers, Chromium submits `VAEncPackedHeaderSequence`, `Picture` and `Slice`, so the buffer it reads back already contains those NAL units. When the driver does not, the config is `VA_ENC_PACKED_HEADER_NONE` and the client has to supply the headers itself. That is the same split FFmpeg’s vaapi encoder handles by querying the attribute. Source: `vaapi_wrapper.cc`; `h264_vaapi_video_encoder_delegate.cc` `submit_packed_headers_`.

**verified.** D3D12 writes the compressed picture into a buffer the encoder created (`bitstream_buffer_`), and a resolved metadata buffer reports per-subregion layout. For AV1 that metadata includes tile layout and `D3D12_VIDEO_ENCODER_AV1_POST_ENCODE_VALUES`. Chromium’s picture parameters carry the GOP position (`PictureOrderCountNumber` / `FrameDecodingOrderNumber` reset when `GOPLength` is reached). The application, not the runtime, decides which previously encoded textures are references. I did not read a flag that says the driver always writes SPS/PPS into that buffer. Source: `d3d12_video_encoder_wrapper.cc` `Initialize`; `d3d12_video_encode_h264_delegate.cc` GOP counter.

**verified.** Vulkan writes one compressed picture into a buffer created with `VK_BUFFER_USAGE_VIDEO_ENCODE_DST_BIT_KHR`. A `VK_QUERY_TYPE_VIDEO_ENCODE_FEEDBACK_KHR` query returns the offset and size. If the implementation overrides codec parameters, `vkGetEncodedVideoSessionParametersKHR` tells the application what it actually wrote, because “it is common for applications to encode the codec-specific parameters stored in video session parameters on their own.” `precedingExternallyEncodedBytes` exists so rate control can count headers the application prepended. There is no presentation timestamp in the encode command; order is the order of the encode operations, and the application keeps the timestamps. Source: `VK_KHR_video_encode_queue` proposal, bitstream buffer, feedback query, and session-parameter feedback.

Back pressure, across these: VideoToolbox exposes `NumberOfPendingFrames` and will not release a `CVImageBuffer` until it is done with it (“the client should not modify the pixel data after making this call”). Android’s buffer rule is the one the decoder report already verified: holding a buffer can stall the codec. V4L2 stalls when either queue runs out of buffers. Vulkan and D3D12 stall on the number of in-flight encode operations the session was created with, which is a creation parameter, not a runtime surprise. Chromium’s VEA `RequireBitstreamBuffers` tells the client how many input frames the encoder may hold “since the encoder may need to hold onto some subset of inputs as reference pictures,” and how large an output buffer must be.

## 4. What can be known before trying

**verified.** VideoToolbox: `VTCopyVideoEncoderList` returns, per encoder, codec type, encoder id, a display name, an optional GPU registry id, performance and quality ratings, `InstanceLimit` (“a global instance limit cap,” “a scarce resource which may potentially be unavailable”), `IsHardwareAccelerated`, and `SupportsFrameReordering` (absent means assumed true). `VTCopySupportedPropertyDictionaryForEncoder` takes width, height, codec type and an encoder specification and returns the property dictionary without encoding a frame. `kVTCompressionPropertyKey_UsingHardwareAcceleratedVideoEncoder` is readable after the session exists. `SupportsBaseFrameQP` is readable and defaults to false. Low-latency hardware encoders are a special case Chromium documents: neither the UsingHardware property nor `IsHardwareAccelerated` is set for `com.apple.videotoolbox.videoencoder.h264.rtvc` and `hevc.rtvc`, so Chromium matches the encoder id. Hardware encode of a profile is probed by actually calling `VTCompressionSessionCreate` with `RequireHardwareAcceleratedVideoEncoder` (`CanCreateHardwareCompressionSession`). Maximum sizes in Chromium are measured, not queried: H.264 4096×2304 in real time on the machines they tested, HEVC 8192×4352 on Apple silicon in real time, smaller on Intel, and they deliberately keep the conservative number. Source: `VTVideoEncoderList.h`; `vt_video_encode_accelerator_mac.mm` `IsHardwareEncoder`, `GetMaxResolution`, `CanCreateHardwareCompressionSession`.

**verified.** Android: `MediaCodecList` plus `MediaCodecInfo`. `isSoftwareOnly()`, `isHardwareAccelerated()` and `isVendor()` exist since API 29. `getCapabilitiesForType` gives profiles, levels, colour formats, a video-capabilities range of sizes and frame rates, and `EncoderCapabilities` bitrate modes and a quality range. Chromium caches, per profile, min and max size, max frame rate, whether CBR and VBR are advertised, a software flag, and a temporal-layer count, and it notes: “We don’t check bitrate mode here since codecs don’t always specify the bitrate mode. Per code inspection, VBR support is announced if a codec doesn’t specify anything.” Alignment, whether `latency` was honoured, and whether intra refresh stuck are visible only on the output format after `configure`. Source: Android “Media codecs” performance page; `video_accelerator_util.cc`; `MediaFormat` “use the output format to verify.”

**verified.** D3D12 answers, without encoding, codec support, min and max resolution, resolution ratios, and which of CBR, VBR and CQP exist. Input format is a function of profile and bit depth in Chromium’s table, checked against the device’s reported input format in the unit tests (`support->InputFormat == DXGI_FORMAT_P010`). It does not answer how many sessions the GPU will allow. Source: `d3d12_video_encode_delegate.cc`.

**verified.** Media Foundation’s inbox encoder documents its profiles and input subtypes. Hardware MFT presence is “enumerate and activate,” which is a try. Chromium treats failure to find or activate one as “Failed finding a hardware encoder MFT.” FFmpeg’s scenario and rate-control lists are the property ranges; whether a given MFT implements one is `ICodecAPI::IsModifiable` / `IsSupported`, which Chromium checks before each `SetValue`. Source: Microsoft Learn H.264 encoder page; `media_foundation_video_encode_accelerator_win.cc`.

**verified.** VA-API: `vaGetConfigAttributes` on `VAConfigAttribRateControl` and `VAConfigAttribEncPackedHeaders` before `vaCreateConfig`. `vaQuerySurfaceAttributes` for alignment. Entrypoints are `VAEntrypointEncSlice` and the low-power variant; I did not re-read `va.h` this session, so the entrypoint names are **from memory** of the API Chromium’s encode mode selects, confirmed only by Chromium calling `vaGetConfigAttributes` with an entrypoint. Max resolution is driver-specific; Chromium checks the profile’s `max_resolution` that it has already queried.

**verified.** V4L2: `ENUM_FRAMESIZES`, `ENUM_FRAMEINTERVALS` (optional), and `QUERYCTRL` / `QUERY_EXT_CTRL` for which of the MPEG controls exist. What a control will accept while streaming is not known until `S_CTRL` returns `EBUSY`.

**verified.** Vulkan: `vkGetPhysicalDeviceVideoCapabilitiesKHR` with `VkVideoEncodeCapabilitiesKHR` (`rateControlModes`, `maxRateControlLayers`), then codec-specific capabilities (AV1’s max layers, Q index range, frame-size override), and `vkGetPhysicalDeviceVideoFormatPropertiesKHR` for the input format. Quality-level properties are a further query and can change the recommended rate-control settings. Source: the encode-queue proposal, “Check support and query the capabilities.”

**verified.** NVIDIA’s concurrent-session cap is not a Vulkan or D3D12 query. The Video Codec SDK 12.0 application note (November 2022) says non-qualified GPUs, which is the GeForce class, are limited to 3 concurrent encode sessions per system, summed across those GPUs, while qualified GPUs are limited by capacity. A July 2024 reply on NVIDIA’s forum, citing the 12.1 and 12.2 application notes, says the non-qualified cap became 5 (Windows driver 531.61, Linux 530.41.03) and then 8 (Windows driver 551.76, Linux 550.54.14). I read the 3 in the 12.0 text returned by search. I did not open the 12.2 PDF, so 5 and 8 are what that reply says. An application that wants “as many as the GPU can bear” cannot read the cap from D3D12 feature support; it finds out when session creation fails.

## 5. Failure, loss, and software fallback

**verified.** VideoToolbox errors that name an encoder outcome: `kVTPropertyNotSupportedErr` (-12900), `kVTPropertyReadOnlyErr` (-12901), `kVTInvalidSessionErr` (-12903), `kVTCouldNotFindVideoEncoderErr` (-12908), `kVTVideoEncoderMalfunctionErr` (-12912), `kVTVideoEncoderNotAvailableNowErr` (-12915), `kVTVideoEncoderAuthorizationErr` (-12211), `kVTVideoEncoderNeedsRosettaErr` (-17693), `kVTInsufficientSourceColorDataErr` (-12917), `kVTLogTransferFunctionMismatchErr` (-19513). The hardware-required key fails session creation when the machine has no such encoder, the configuration is unsupported, or “the hardware encoding resources on the machine are busy.” I did not find, in these headers, a documented teardown when the app backgrounds. What is documented is `MaximizePowerEfficiency` for a background client, and “not available now” when the resource cannot be taken. Source: `VTErrors.h`; `kVTVideoEncoderSpecification_RequireHardwareAcceleratedVideoEncoder`.

**verified.** Android `CodecException`: recoverable (`stop`/`configure`/`start`), transient (retry), or fatal (release). The decoder report already verified `ERROR_RECLAIMED` (“the resource manager reclaimed the media resource… the codec must be released”) and `ERROR_INSUFFICIENT_RESOURCE`. Chromium maps a start failure of `AMEDIACODEC_ERROR_INSUFFICIENT_RESOURCE` to `kOutOfPlatformEncoders` (“No more encoders available”). `isSoftwareOnly()` is how a fallback target is identified; it “makes no guarantees about rendering performance.” Source: `MediaCodec` error section; `ndk_video_encode_accelerator.cc` start; Android “Media codecs” page.

**verified.** Software encoders that ship with the platform, as far as a source read this session shows:

- Android AVC: `c2.android.avc.encoder` is `C2SoftAvcEnc` in AOSP. `isSoftwareOnly()` is the general test, so a device can also ship software HEVC, VP8, VP9 or AV1 under `c2.android.*` without this report having opened those files. I did not open `C2SoftHevcEnc`, `C2SoftVp8Enc`, `C2SoftVp9Enc` or `C2SoftAv1Enc` this session.
- Windows: the inbox H.264 encoder is `Mfh264enc.dll`, a CPU encoder with slice or multi-frame threading. I did not find, in the page I read, an inbox HEVC, VP8, VP9 or AV1 software encoder. Hardware HEVC and AV1 exist as vendor MFTs and as D3D12 encode codecs. **from memory**, Windows has no inbox VP8/VP9/AV1 encoder, and the AV1 Video Extension is a decoder.
- Apple: hardware can be required or forbidden, so a software encoder is a real VideoToolbox object. FFmpeg’s `allow_sw` and `require_sw` select it. Chromium assumes the low-latency rate-control encoders are hardware and treats anything else that does not set `UsingHardwareAcceleratedVideoEncoder` as software. The profile constants in `VTCompressionProperties.h` cover H.264, HEVC (Main, Main 10, Main 4:2:2 10, monochrome), MPEG-4 and H.263. I found no VP8, VP9 or AV1 profile constant in that list. I did not call `VTCopyVideoEncoderList` on this machine, so which of H.264 and HEVC have a software implementation on the current OS is the list’s answer, not a number I measured.
- Linux: VA-API, V4L2 and Vulkan encode are hardware. Chromium’s software encoders beside them are its own OpenH264, libvpx and libaom (`openh264_video_encoder.cc`, `vpx_video_encoder.cc`, `av1_video_encoder.cc`). The kernel encoder document says software header generation inside the driver is “strongly discouraged.”

Falling back is the caller’s job on every platform. VideoToolbox’s require-hardware key exists “for clients that have their own software encode implementation.” WebRTC’s `HardwareVideoEncoder.initEncodeInternal` returns `VideoCodecStatus.FALLBACK_SOFTWARE` when `createByCodecName` throws or `configure` throws `IllegalStateException`. Chromium’s VEA `required_encoder_type` is hardware, software, or no preference, and the Android finder returns a software codec only when hardware was not required and none was found.

## 6. What real projects end up needing

The settings that show up in all of them: a size, a frame rate, a bitrate or a quality/QP, a key-frame interval, a profile (and, where the codec has one, a level), whether B-frames are allowed, a real-time versus quality latency hint, and a way to force a key frame. The ones only some of them bother to plumb, and then have to: a peak beside the average, a VBV/HRD window, per-layer bitrates, a content hint, intra refresh, and reference-frame control.

**verified.** Chromium’s own encoder, which is the union of the platform ones, takes `Bitrate` (constant, variable with a peak, or external QP), frame rate, frame size, key-frame interval, latency (`Realtime` or `Quality`), an SVC mode, a content hint (`Camera` or `Screen`), chroma and bit depth, `produce_annexb` for H.264 and HEVC, and `manual_reference_buffer_control`. Per frame: `key_frame`, an optional quantizer “only when encoder configured with `kExternal`,” and reference-buffer ids. The accelerator config adds GOP length, an optional H.264 level, per-spatial-layer width/height/bitrate/frame rate/max QP/temporal-layer count, a drop-frame threshold, and low delay. Output metadata carries a key-frame flag, timestamp, QP, temporal and spatial index, an encoded size “if the platform adjusted it,” and an encoded colour space. Source: `video_encoder.h` `Options`, `EncodeOptions`; `video_encode_accelerator.h` `Config`, `BitstreamBufferMetadata`.

**verified.** FFmpeg `h264_videotoolbox` options (`videotoolboxenc.c` `h264_options` and `COMMON_OPTIONS`): `profile` (baseline, constrained_baseline, main, high, constrained_high, extended), `level` (1.3 through 5.2), `coder` (`cavlc` or `cabac`), `constant_bit_rate` (“Require constant bit rate (macOS 13 or newer)”), `max_slice_bytes`, `allow_sw`, `require_sw`, `realtime`, `frames_before`, `frames_after`, `prio_speed`, `power_efficient`, `spatial_aq`, `max_ref_frames` (“only has an effect when the value is less than the maximum allowed by the profile/level”). `get_vt_h264_profile_level` forces constrained baseline and constrained high to AutoLevel and logs that “the output may be encoded with a different level.” HEVC has the same `constant_bit_rate` switch. Pixel formats the encoder advertises include `AV_PIX_FMT_BGRA` as well as the VideoToolbox biplanar formats (the pixfmt list sits just above `COMMON_OPTIONS`).

**verified.** FFmpeg `vaapi_encode.c` selects CQP, CBR, VBR, ICQ, QVBR or AVBR from the driver’s `VAConfigAttribRateControl`, and refuses a mode the driver did not advertise. `mediacodecenc.c` has `bitrate_mode`, `operating_rate`, per-picture `qp_i_min`/`qp_p_min`/`qp_b_min` and the max counterparts, and writes them as `video-qp-i-min` and so on. `mfenc.c` has the rate-control and scenario enums in section 1.

**verified.** FFmpeg NVENC, from `nvenc.c`: a forced I frame is `NV_ENC_PIC_FLAG_FORCEIDR` or `NV_ENC_PIC_FLAG_FORCEINTRA` depending on `forced_idr`. I did not extract the full `AVOption` table (it is not in the first screen of `nvenc.c`). OBS’s `obs-ffmpeg-nvenc.c` shows how that encoder is actually driven: CQP sets `global_quality` and bitrate 0; lossless sets tune `lossless`; anything that is not VBR defaults to CBR by setting the private `cbr` option and setting `rc_max_rate` and `rc_min_rate` equal to the target. Source: the `obs-ffmpeg-nvenc.c` excerpt returned by the fetch of that file; `nvenc.c` `forced_idr`.

**verified.** OBS VA-API (`obs-ffmpeg-vaapi.c`) offers CBR (bitrate, and max rate forced equal to it), CQP (QP, no bitrate), VBR (bitrate and max rate) and QVBR (QP, bitrate and max rate). The comment points at FFmpeg’s `vaapi_encode_rc_modes`. HEVC Main with a P010 input is forced to Main 10: “Forcing Main10 for P010.” Keyframe distance is `keyint_sec`. `max_b_frames` is set on the context. Source: that file, `RC_MODES` and the profile adjustment.

**verified.** WebRTC’s Android `HardwareVideoEncoder` always sets `bitrate-mode` to `VIDEO_ControlRateConstant`, `KEY_BIT_RATE` to an adjusted bitrate, `KEY_FRAME_RATE` from the adjuster, `KEY_I_FRAME_INTERVAL`, and a colour format. Surface mode uses `createInputSurface`. H.264 constrained high sets profile and level; constrained baseline sets neither. A key frame cannot be requested with the buffer flag: “Ideally MediaCodec would honor `BUFFER_FLAG_SYNC_FRAME` … but sadly that flag is ignored. Instead, we request a key frame ‘soon’” via `PARAMETER_KEY_REQUEST_SYNC_FRAME`. Bitrate changes go through `PARAMETER_KEY_VIDEO_BITRATE`. `DynamicBitrateAdjuster` exists because hardware codecs “deviate from the target bitrate by unacceptable margins”: it measures frame sizes and scales the requested bitrate by up to 4×, and it changes the request at most every three seconds. Resolution or surface-mode changes call `initEncodeInternal` again, which creates a new codec. Configure failure returns `FALLBACK_SOFTWARE`. Source: `HardwareVideoEncoder.java` `initEncodeInternal`, `requestKeyFrame`, `updateBitrate`; `DynamicBitrateAdjuster.java`.

GStreamer element sources and HandBrake’s encoder plugins were not opened this session. **from memory**, GStreamer’s `x264enc`, `vah264enc` / `vaapih264enc`, `v4l2h264enc` and `vtenc_h264` expose the same set (bitrate, keyframe interval, rate-control mode, profile, b-frames, a realtime property on the VideoToolbox element) and pass driver-specific controls through `extra-controls` on the V4L2 element. I am not using remembered property names as evidence.

The quirks they keep working around, all verified above: VideoToolbox’s average bitrate is soft, so CBR is a different property and it is not always supported. Android ignores the sync-frame buffer flag and may ignore the key-frame interval, so everyone also sends `request-sync`. Android’s bitrate wanders, so WebRTC lies to it. VA-API’s packed-header support is not universal, so the client must be ready to write SPS and PPS. V4L2 and VideoToolbox both change the size. MF and D3D12 will not change bitrate mode without a new encoder. NVIDIA’s session cap is outside the encode API.

## 7. Where WebCodecs `VideoEncoder` is known to be limiting

**verified.** The Chromium IDL (`video_encoder_config.idl`) is the API as implemented there: `bitrateMode` is `"constant"`, `"variable"` or `"quantizer"`; `hardwareAcceleration` is a preference, default `"no-preference"`; `alpha` defaults to `"discard"`; `latencyMode` defaults to `"quality"`; `scalabilityMode` is a DOMString; `contentHint` is a DOMString. Per-frame quantizer exists, separately, for AVC, HEVC, VP9 and AV1 (`video_encoder_encode_options_for_avc.idl` and the hevc, vp9 and av1 siblings).

**verified.** What that implementation does with it (`video_encoder.cc`):

- `alpha: "keep"` is rejected: “Alpha encoding is not currently supported.”
- `bitrateMode: "quantizer"` becomes `Bitrate::ExternalRateControl()`, with no numeric QP in the config. The QP arrives per frame.
- `"constant"` becomes `ConstantBitrate(bps)`. `"variable"` becomes `VariableBitrate(bps, 10 * bps)`, and the comment says why: “Currently webcodecs doesn’t expose peak bitrate (assuming unconstrained VBR), here we just set peak as 10 times target.”
- `contentHint` `"detail"` or `"text"` becomes `ContentHint::Screen`; `"motion"` becomes `Camera`.

**verified.** The spec history says the same gaps in public:

- Per-frame QP was issue 270, closed March 2023 by codec-specific quantizer fields (pull 633), after the working group preferred that to one shared QP. Dale Curtis, on the related issue 56: “It’ll be harder to get H.264 QP support since it varies by platform / api.” Dan Sanders, 2020, on the same issue: Android can be queried for CBR, CQ and VBR, and “I’m not quite sure how an app achieves a target bitrate using [per-frame QP], especially on Android where it cannot be controlled per-frame.”
- Reference control is issue 285, still open. The last update in the issue data returned this session is 2025-04-24. The proposed shape is encoder buffers the application updates and references, which is how long-term references and non-standard temporal structures would be expressed. The September 2024 WebCodecs minutes record that B-frames can be approximated with those buffers and that a spec-compliant B-frame “would need an extension,” and that the group was “going CQP route” because a target bitrate “is much more complex with time, timestamps, etc.”
- SVC, as the earlier report already verified from issue 40: hardware encoders “have not had very good support for SVC (particularly more exotic modes like spatial scalability or K-SVC).”

Not in this API, and present on the platforms in sections 1 and 3: a peak distinct from the average, a VBV window in bytes and seconds, intra refresh, a long-term-reference acknowledgement, a B-frame count, an encoder id, a slice-size limit, a screen-content tool that is not a hint string, and a choice of Annex B versus length-prefixed output that is independent of the codec string. The AVC registration’s `format` (`avc` versus `annexb`) is the one place the bitstream form is chosen; the earlier report already verified that, and it is the encoder-side mirror of the decoder’s `description`.

## 8. HDR and 10-bit encode

**verified.** VideoToolbox. `kVTProfileLevel_HEVC_Main10_AutoLevel` and `Main42210` are the 10-bit profiles (Main 10 since macOS 10.13, 4:2:2 10 since macOS 12.3). `OutputBitDepth` “requires the encoder to output bitstream with the requested bit depth, if supported by the configured profile”; if unset, the encoder uses the highest bit depth the profile allows. Colour is `ColorPrimaries`, `TransferFunction`, `YCbCrMatrix`, and an optional `ICCProfile`; “if this property and any of the previous three are all set, they should be set to consistent values, or undefined behavior may occur.” Some encoders make these read-only. `MasteringDisplayColorVolume` is “24 bytes containing a big-endian structure as defined in ISO/IEC 23008-2 … D.2.28,” written onto the format description “and incorporated into the appropriate SEI NAL unit where supported.” `ContentLightLevelInfo` is 4 bytes, the same way. `HDRMetadataInsertionMode` is `None`, `Auto` (the default), or `RequestSDRRangePreservation` (macOS 26, only when the transfer is PQ, primaries are BT.2020 and the matrix is BT.2020). “This property has no effect if the output color space is not HDR, or if there is currently no underlying support for the HDR format.” `PreserveDynamicHDRMetadata` keeps dynamic metadata that arrived on the input pixel buffer; if false, and insertion is not `None`, the session may generate it. `LogTransferFunction` (macOS 27) fails the encode unless the source buffer carries exactly that log curve (`kVTLogTransferFunctionMismatchErr`). Chromium sets mastering display and content light only when the session lists the property, sets insertion mode to `Auto`, and for Main 10 forces a 10-bit biplanar source so VideoToolbox does not assume 8-bit. Source: `VTCompressionProperties.h` those keys; `vt_video_encode_accelerator_mac.mm` `ConfigureVtSessionForHdrMetadata`, `CreateSourceImageBufferAttributes`.

**verified.** Android. Static metadata is `KEY_HDR_STATIC_INFO`. Colour is `KEY_COLOR_STANDARD`, `KEY_COLOR_TRANSFER`, `KEY_COLOR_RANGE`; Chromium sets all three from the frame’s colour space. The 10-bit and HDR profile constants Chromium knows include `HEVCProfileMain10HDR10`, `HEVCProfileMain10HDR10Plus`, `VP9Profile2HDR`, `AV1ProfileMain10HDR10` and the HDR10+ variants. `MediaCodec` says a 10-bit or HDR input “MUST” be configured with a suitable profile, and the default profile is 8-bit 4:2:0. `COLOR_FormatYUVP010` is the 10-bit flexible layout the decoder report already verified (10 bits in the high bits of a little-endian 16-bit word). Whether a given encoder accepts it is a colour format in its capabilities, not a promise of the API. `PARAMETER_KEY_HDR10_PLUS_INFO` is how dynamic metadata is passed per frame; I did not read its byte layout this session. Source: `MediaFormat` `KEY_HDR_STATIC_INFO`; `MediaCodec` encoder-profiles note; `ndk_video_encode_accelerator.cc` the profile constants and `SetFormatColorSpace`.

**verified.** D3D12. 10-bit encode input is `DXGI_FORMAT_P010` for H.264 High 10, HEVC Main 10, and AV1 Main when the source is P010. AV1 High is `DXGI_FORMAT_AYUV`, which is 8-bit 4:4:4, not 10-bit. Chromium does not set mastering-display metadata in the portion of the delegate I read. Source: `GetDxgiInputFormat`.

**verified.** VA-API in Chromium’s encode accelerator is `VA_RT_FORMAT_YUV420` only, and native input must be NV12. The 10-bit render target `VA_RT_FORMAT_YUV420_10BPP` appears in that file for VP9 decode profiles, not for the encode attribute Chromium requests. So this tree’s VA encode path is 8-bit. A driver can still advertise a 10-bit encode config; FFmpeg discovers surface attributes per config, and OBS forces HEVC Main 10 when the input is P010. I did not read a VA encode sample that sets mastering-display SEI.

**verified.** V4L2 and Vulkan. I did not find, in the stateful-encoder document, a control for mastering display or content light level. The codec controls I read cover bit depth only indirectly, through the coded pixel format and the profile enum. Vulkan’s encode input format is queried; a 10-bit format is supported when the implementation returns one for that profile. The AV1 encode proposal I read does not mention HDR metadata. **from memory**, both can carry HDR once the bitstream is packed with the right SEI or OBU metadata, and neither has a first-class mastering-display field in the base encode structure. I am not stating that as a searched negative beyond the documents I opened.

**verified.** WebCodecs, in Chromium’s encoder, has no HDR metadata field on `VideoEncoderConfig`. Colour and HDR travel on the `VideoFrame` the application submits. Whether they reach the bitstream is the platform encoder’s behaviour above, and Chromium’s VideoToolbox path is the one I saw copy them into the session. The alpha path, which is the other thing a 4:4:4 or dual-plane encode would need, is rejected outright.
