# Video codec interface: what platforms actually take and give

Read this session, and cited below: Chromium at `chromium` (media base, `media/gpu` for VideoToolbox, MediaCodec, D3D11/D3D12, VA-API, V4L2, Blink WebCodecs), Firefox sources in a gecko-dev checkout (FFmpeg 6.1 headers, `MediaChangeMonitor`, `VideoInfo`, WMF), Apple SDK headers (VideoToolbox, CoreMedia), and the published texts of WebCodecs, the AVC registration, Media Capabilities, Android `MediaCodec` / `CodecException`, the Linux V4L2 stateful-decoder document, FFmpeg's bitstream-filter manual, GStreamer `h264parse`, and the mpv manual. GitHub issues were read as the issue pages returned by search.

Not read this session, so nothing below is taken from them: OBS, VLC, Kdenlive, MLT, Shotcut, Olive, HandBrake, LosslessCut, WebKit's decoder, current Media3/ExoPlayer sources, a Vulkan Video header, and a VA-API `va.h`. Where a claim would have come only from those, it is either omitted or marked **from memory**.

The existing `wasdk:media` `video-frames` interface was read only as context. It already treats a decoded picture as lent pool memory, with rotation and a horizontal flip stored beside the buffer. It does not carry coded size, visible rectangle, aspect, pixel format, colour, HDR, alpha, or timestamps.

---

## Summary

These are the details a chunk-in, frame-out interface most often drops. Each is expanded, with sources, in the sections below.

1. The decoder is configured from codec-private bytes (SPS/PPS/VPS, or `avcC`/`hvcC`/`av1C`), not from a profile enum. Profile, level, bit depth and chroma are parsed out of those bytes, and a typed copy of them can disagree with the bytes.
2. Length-prefixed samples (AVCC/HVCC, length field of 1, 2 or 4 bytes) and Annex B start codes are different contracts. The same browser converts one way for one backend and the opposite way for another. Who converts has to be explicit.
3. Parameter sets live out of band, in band, or both. A mid-stream SPS change is a new format on VideoToolbox, a source-change plus buffer reallocation on V4L2, and either forbidden or a special key-frame packet on MediaCodec, depending on adaptive playback.
4. A picture has three sizes: coded (padded), visible (crop), and display (aspect, then rotation). Rotation and flip are not applied to the pixels. A quarter turn swaps the displayed width and height.
5. Colour is four CICP values plus range, and the bitstream and the container disagree often enough that each project has a precedence rule. WebCodecs' config overrides the bitstream; Chromium's H.264 parser prefers the SPS.
6. HDR static metadata (mastering display, content light level) is per stream or per frame and must be reordered with the frame, because it arrives in decode order and pictures leave in presentation order. Dynamic metadata (HDR10+, Dolby Vision RPU) is a different object and is easy to drop.
7. The output buffer is borrowed from a small pool (decoder picture buffer plus a few extra). Holding it stalls decode. Android says this outright; D3D11, V4L2 and mpv size the pool for it.
8. Output order is presentation order on the stateful decoders, and the app or a parser reorders for the stateless ones (DXVA, VA-API). VideoToolbox's callback is not promised to be in display order. Timestamps have to survive that reorder; Android also rejects two inputs with the same timestamp.
9. After `flush` or `reset`, the next input must be a key frame, and on Android a flush can discard the codec-specific data so it has to be sent again. `flush` is not `reset`: flush emits remaining pictures, reset drops them.
10. "Can this device decode this?" is not one question. Apple's hardware query takes only a codec type. D3D11 checks a profile GUID at a size and format. V4L2 often cannot know the real output format until it has parsed the stream. WebCodecs' hardware preference is a hint a browser may ignore. Several platforms only answer by trying, and all of them cap how many hardware decoders exist at once. Android can reclaim one out from under you.

## 1. Naming a codec and its parameters

### What each decoder is told before the first chunk

**verified.** VideoToolbox's `VTDecompressionSessionCreate` takes a `CMVideoFormatDescriptionRef` that "describes the source video frames", an optional decoder specification, and optional destination pixel-buffer attributes. For H.264, `CMVideoFormatDescriptionCreateFromH264ParameterSets` builds that description from raw parameter-set NAL units: "At least one sequence parameter set and one picture parameter set must be provided." The NAL unit header length passed in is 1, 2 or 4. HEVC requires VPS, SPS and PPS. The function parses dimensions from the parameter sets. Source: `VTDecompressionSession.h` `VTDecompressionSessionCreate`; `CMFormatDescription.h` `CMVideoFormatDescriptionCreateFromH264ParameterSets`, `CMVideoFormatDescriptionCreateFromHEVCParameterSets`.

**verified.** Android `MediaCodec.configure` takes a `MediaFormat`. For H.264, H.265, AAC and MPEG-4 the codec needs setup data, either as `csd-0`, `csd-1`, … in that format, or as buffers flagged `BUFFER_FLAG_CODEC_CONFIG` after `start()` and before frame data. The documented layout is H.264 SPS in `csd-0` and PPS in `csd-1`, each parameter set starting with the start code `00 00 00 01`; HEVC is VPS+SPS+PPS in one `csd-0`; VP9 and AV1 codec-private data are optional. Width and height are also keys. Chromium's `MediaFormatBuilder.createVideoDecoderFormat` sets mime, width, height, those CSD buffers, colour standard/transfer/range, HDR metadata, max width/height when adaptive playback is allowed, and a Dolby Vision profile. It then pulls SPS and PPS out of an `avcC` and re-prefixes them with `00 00 00 01`. Sources: Android `MediaCodec` "Codec-specific Data"; `MediaFormatBuilder.java` `createVideoDecoderFormat`; `extract_sps_and_pps.h` `ExtractSpsAndPps`; `media_codec_video_decoder.cc` around the `ExtractSpsAndPps` call.

**verified.** Chromium's D3D11 decoder does not hand the SPS to Direct3D as codec-private bytes at configuration time. `D3D11DecoderConfigurator::Create` maps `VideoCodecProfile` plus bit depth plus chroma sampling to a decoder GUID (`D3D11_DECODER_PROFILE_H264_VLD_NOFGT`, HEVC Main/Main10, AV1 profile 0/1/2, VP9 profile 0 and 10-bit profile 2) and a `DXGI_FORMAT`, then checks `ID3D11VideoDevice::GetVideoDecoderProfile`. The coded size goes into the decoder descriptor. The actual slice data is submitted later by the H.264/HEVC/VP9/AV1 accelerators, which have already parsed the bitstream. `GetD3D11DecoderGUID` returns an empty GUID for an unknown profile and the decoder is not created. Sources: `d3d11_decoder_configurator.cc` `GetD3D11DecoderGUID`, `D3D11DecoderConfigurator::Create`, `SupportsDevice`.

**verified.** VA-API in Chromium is the same shape: a `VAProfile` chosen from `VideoCodecProfile` (`H264PROFILE_BASELINE` maps to `VAProfileH264ConstrainedBaseline`, and so on), then `vaCreateConfig`. The bitstream is parsed in software and submitted as slice data (`VASliceDataBufferType` in `H264VaapiVideoDecoderDelegate::SubmitSlice`). Source: `vaapi_wrapper.cc` profile map and `vaCreateConfig`; `h264_vaapi_video_decoder_delegate.cc` `SubmitSlice`.

**verified.** V4L2's stateful decoder "takes complete chunks of the bytestream (e.g. Annex-B H.264/HEVC stream, raw VP8/9 stream)" and "is expected not to require any additional information from the client to process these buffers." The client sets a coded pixel format on the `OUTPUT` queue. Width and height are required only if the coded format cannot be parsed from the stream; otherwise they are a placeholder "that will likely change as soon as it can parse the actual coded resolution." Chromium sets the fourcc from the profile (`VideoCodecProfileToV4L2PixFmt`) and waits for `V4L2_EVENT_SOURCE_CHANGE` before configuring the capture queue. Sources: Linux `dev-decoder.html` opening paragraphs and initialization step 1; `v4l2_stateful_video_decoder.cc` `Initialize`.

**verified.** FFmpeg's `AVCodecParameters` is the container-facing description: `codec_id`, `codec_tag`, `extradata` / `extradata_size` ("Extra binary data needed for initializing the decoder, codec-dependent"), `profile`, `level`, `width`, `height`, `sample_aspect_ratio`, `framerate`, `field_order`, colour range/primaries/transfer/matrix, `chroma_location`, `video_delay`. `AVCodecContext.extradata` repeats the same idea and names examples (MJPEG Huffman tables, MPEG-4 global headers, "they can be in the bitstream or here"). Decoding: the user sets extradata. Sources: `codec_par.h` `AVCodecParameters`; `avcodec.h` `AVCodecContext.extradata`.

**verified.** Chromium's own `VideoDecoderConfig` is codec enum, profile, level, alpha mode, colour, transformation (rotation and mirror), coded size, visible rect, natural size, aspect ratio, `extra_data`, encryption scheme, HDR metadata, spatial format. The comment on `extra_data` is the telling one: "Optional video decoder initialization data, such as H.264 AVCC." And: "FFmpegVideoDecoder assumes that H.264 is in AVC format if there is `extra_data`, and in Annex B format if there is not. We should probably add explicit signaling of encoded format." The older video-decode accelerator is looser: profile, optional Annex-B-framed SPS and PPS, "Not all clients populate these fields, so they should be parsed from the bitstream instead, if required." Sources: `video_decoder_config.h` `VideoDecoderConfig`; `video_decode_accelerator.h` `Config`.

**verified.** Firefox's `VideoInfo` keeps display size, image size, extra data, rotation, colour range, and an optional image crop rect. Its H.264 change monitor will not instantiate a decoder until an SPS is in hand, from the extra data or from a sample. Source: `MediaInfo.h` `VideoInfo`; `MediaChangeMonitor.cpp` `H264ChangeMonitor`.

What the stream itself can carry, so a decoder can discover it after the first key frame: resolution, profile, level, bit depth, chroma, colour (VUI), crop, DPB size, and new parameter sets. V4L2 is specified to work that way. VideoToolbox and MediaCodec can accept in-band parameter sets, but both still want a format or CSD up front when the container has one. D3D11 and VA-API in Chromium do not discover the profile themselves; Chromium's parser does, and refuses to start without a profile it can map to a GUID or `VAProfile`.

What you need in order to answer "can this device decode it, in hardware?" is not the same set. See section 5. Short version: a codec family plus a profile, a bit depth, a chroma format, and a size. Level and frame rate are only sometimes part of the query. The SPS bytes are what you decode; the typed fields are what you ask about.

### Shape A — RFC 6381 codec string plus setup bytes

**verified.** WebCodecs `VideoDecoderConfig.codec` is "a codec string describing the codec." `description` is "a sequence of codec specific bytes, commonly known as extradata." The AVC registration says the string begins with `avc1.` or `avc3.` and a 6-character suffix as in RFC 6381 and ISO 14496-15. If `description` is present it is an `AVCDecoderConfigurationRecord` and the samples are length-prefixed `avc`. If it is absent, the samples are Annex B. A `key` chunk in `avc` is an IDR; a `key` chunk in Annex B is an IDR plus every parameter set needed for that chunk. Sources: WebCodecs §7.6; AVC WebCodecs registration §§1–4.

**verified.** Chromium's IDL still has the open question: "Should we accept `avc1` when `description` is provided?" and "Define what happens if the parsed description differs from the metadata below." The implementation parses the string into `VideoCodec` and `VideoCodecProfile` (`ParseCodecString`), and if `description` is non-empty for H.264/HEVC it parses it as `avcC`/`hvcC`. The string's profile and the box's profile are two copies of the same fact. Sources: `video_decoder_config.idl`; `video_decoder.cc` `MakeMediaVideoDecoderConfigInternal`.

Lost or said twice:

- Said twice: profile, constraints and level (in `avc1.PPCCLL` and again in the `avcC`), and for VP9/AV1 also colour, when the string's optional colour fields and the bitstream VUI both exist. WebCodecs then adds a third copy, `colorSpace`, which overrides the bitstream (section 3).
- Lost if you keep only the string: the SPS and PPS themselves (scaling lists, VUI crop, `max_num_ref_frames`, SEI), alpha, HDR metadata, rotation, encryption, and the length-field size. `avc1` versus `avc3` signals whether parameter sets are in band, but the registration also uses presence of `description` for that, so the two signals can conflict. Chromium's IDL records that this is unresolved.
- Lost if the string is treated as complete: H.264's string does not carry colour or bit depth. High 10 is a profile, but range, primaries and crop are not in `avc1.640028`.
- A string is a poor hardware query. `VTIsHardwareDecodeSupported` takes a codec type, not a string. D3D11 takes a GUID derived from a profile enum. You end up parsing the string back into the enum the platforms already use.

### Shape B — codec family plus setup bytes, profile read from the bytes

**verified.** This is what VideoToolbox, MediaCodec (when given CSD), V4L2 and FFmpeg actually decode with: a family (`kCMVideoCodecType_H264`, mime `video/avc`, V4L2 fourcc, `AVCodecID`) and the bytes. Chromium's H.264 parser then derives profile, bit depth and chroma from the SPS (`ProfileIDCToVideoCodecProfile`, `ParseBitDepth`, `GetChromaSampling`) and will reject a bit depth that does not match the profile. Source: `h264_decoder.cc` around the profile and bit-depth checks.

Lost or said twice:

- Profile is not said twice, until a capability query wants it without parsing. Every "is this supported?" API in section 5 wants the parsed profile, so the host parses once and holds the result. That parsed result is shape C, cached.
- Lost if the family is wrong: the bytes are not self-describing across families. An `avcC` and an `hvcC` are different parsers. The family enum (or the mime, or the fourcc) is load-bearing.
- Lost relative to shape A: the `avc1`/`avc3` distinction, unless a separate "parameter sets in band" bit exists, or the host sniffs Annex B versus AVCC. Chromium currently sniffs "non-empty `extra_data` means AVCC" and the authors wrote that this should be explicit (`video_decoder_config.h`).
- Gained: nothing in the SPS is dropped on the floor. Dolby Vision still does not fall out of an HEVC family tag. Chromium has `VideoCodec::kDolbyVision` and separate profiles 5, 7, 8, 9, 10, 20 (`video_codecs.h`), and on Android sets `KEY_PROFILE` only for that mime (`MediaFormatBuilder.addProfileInfoToFormat`).

### Shape C — family plus typed profile, level, bit depth, chroma

**verified.** This is Chromium's `VideoDecoderConfig` and FFmpeg's `AVCodecParameters` fields `profile`, `level`, `format`, `width`, `height`, colour enums, with `extradata` still present beside them. D3D11 and VA-API configuration use the typed profile, bit depth and chroma, not the string. `GetOutputDXGIFormat` is a table from bit depth and chroma to `DXGI_FORMAT_NV12`, `P010`, `YUY2`, `Y210`, `AYUV`, `Y410`, `P016`, and others (`supported_profile_helpers.cc`).

Lost or said twice:

- Said twice, and dangerously: every typed field is a claim about the bytes. WebCodecs leaves the disagreement unspecified (`video_decoder_config.idl` TODO). Chromium's parser overwrites its config from the SPS when the SPS colour is specified, and special-cases a VUI matrix of RGB on a 4:2:0 stream as a lie (`h264_decoder.cc`, "prefer the frame color space over the config", `crbug.com/341266991`).
- Lost if the bytes are omitted: PPS, scaling lists, cropping rectangle, DPB size, SEI, alpha layer, Dolby RPU. A profile of "high" and 8-bit 4:2:0 does not reconstruct an `avcC`. VideoToolbox cannot create a format description from those fields alone; it parses NAL units.
- Lost if the fields are a closed enum: HEVC range extensions, high-throughput profiles, and Dolby profiles keep getting added. Chromium's `VideoCodecProfile` already has `HEVCPROFILE_REXT`, `HEVCPROFILE_HIGH_THROUGHPUT`, `HEVCPROFILE_SCREEN_EXTENDED`, and several Dolby profiles (`video_codecs.h`). A new profile means a new GUID on Windows (`GetHEVCRangeExtensionGUID`).

### How Chromium and FFmpeg carry it, and why

**verified.** Both carry family, typed restrictions, and the bytes.

Chromium does this because the two consumers differ. The hardware decoders that parse in software (D3D11, VA-API, VideoToolbox's Chromium path) need a profile to pick a GUID or a `VAProfile` before the first slice, and then need the parameter sets to build a format or a picture description. The container demuxer has the `avcC` before any sample, which is `extra_data`. The decoder is allowed to replace colour and crop from the SPS. Level is optional (`kNoVideoCodecLevel` means "not available"). Source: `video_decoder_config.h`; `h264_decoder.cc`; `d3d11_decoder_configurator.cc`.

FFmpeg does this because `extradata` is the decoder's initialization (global headers), while `profile` and `level` are "bitstream restrictions that the stream conforms to" and are useful without opening the decoder. `codec_tag` is a fourth name, the AVI FourCC, because the same `codec_id` arrives under more than one tag. Colour and sample aspect live on the parameters so a decoder that never sees a VUI still has the container's values. Source: `codec_par.h`.

Firefox's practical rule, **verified** in `H264ChangeMonitor`: do not create the platform decoder until an SPS exists; keep the extra data; if the sample's NAL length size is not 4, rewrite it. The bytes win, and the decoder is not started on a promise of them.

## 2. Bitstream form

**verified.** Two packagings of the same NAL units:

- Annex B: each NAL starts with a start code. FFmpeg's `h264_mp4toannexb` "converts an H.264 bitstream from length prefixed mode to start code prefixed mode (as defined in the Annex B of the ITU-T H.264 specification)." `hevc_mp4toannexb` does the same for HEVC. `extract_extradata` exists because "long-term headers (e.g. MPEG-2 sequence headers, or H.264/HEVC (VPS/)SPS/PPS)" may be "in-band" or "out of band"; the out-of-band form is FFmpeg's `extradata`.
- Length-prefixed: each NAL is preceded by a 1-, 2- or 4-byte length. ISO calls this the `avc` sample format. The `avcC` records `lengthSizeMinusOne`. GStreamer `h264parse` src caps are `stream-format: { avc, avc3, byte-stream }` and `alignment: { au, nal }`. `avc3` is the in-band-parameter-set variant of the ISO format. `config-interval` "sends SPS and PPS insertion interval in seconds" and `-1` means "send with every IDR."

Sources: FFmpeg bitstream-filter manual §§2.11, 2.15, 2.18; GStreamer `h264parse` pad template and `config-interval`.

**verified.** Who converts, in the trees that were read:

- Chromium WebCodecs, when `description` is present for H.264 or HEVC, parses the `avcC`/`hvcC` and then converts each chunk to Annex B before the media decoder. It clears `extra_data` on the config it hands down: "The description should not be provided to the decoder because the stream will be converted to Annex B format." If the conversion fails, the error is `kMalformedBitstream` ("Unable to convert NALU to byte stream"). Source: `video_decoder.cc` `MakeMediaVideoDecoderConfigInternal`, `MakeInput`.
- Chromium's FFmpeg demuxer path converts the other way at the packet: `FFmpegH264ToAnnexBBitstreamConverter` "converts H.264 bitstream based FFmpeg packets into H.264 Annex B", prepending the AVC decoder configuration on the first packet. Source: `ffmpeg_h264_to_annex_b_bitstream_converter.h`.
- Chromium's VideoToolbox H.264 accelerator does the reverse of that on the way into VideoToolbox. The parser feeds it Annex B NAL units; `SubmitDecode` writes each NAL with a 4-byte big-endian length (`kNALUHeaderLength`). The format description was built by `CMVideoFormatDescriptionCreateFromH264ParameterSets` with that same length. Source: `video_toolbox_h264_accelerator.cc` `SubmitFrameMetadata`, `SubmitDecode`.
- Chromium's Android path parses the `avcC` and produces start-code-prefixed SPS and PPS as `csd-0` and `csd-1`. Source: `extract_sps_and_pps.cc`.
- Chromium's D3D11 and VA-API paths do not want a raw bytestream. The software parser (`H264Decoder`) splits NAL units and the accelerator submits slices. `H264Accelerator::SetStream` documents its input as "data in annex B format, which may include SPS and PPS NALUs when there is a configuration change. The first frame must contain the SPS and PPS NALUs. SPS and PPS NALUs may not be encrypted." Source: `h264_decoder.h` `SetStream`.
- Firefox converts to 4-byte AVCC before some decoders (`AnnexB::ConvertSampleToAVCC` in `H264ChangeMonitor`) and converts to Annex B for WMF: `WMFVideoMFTManager::NeedsConversion` returns `kNeedAnnexB` for H.264 and HEVC. Source: `MediaChangeMonitor.cpp`; `WMFVideoMFTManager.h` `NeedsConversion`.
- V4L2's documented input is Annex B. Source: `dev-decoder.html` first paragraph.
- An encoder has to choose. Chromium's `VideoEncoder::AvcOptions` and `HevcOptions` are `produce_annexb`. WebCodecs' AVC encoder registration defaults to `"avc"` and allows `"annexb"`. In `avc`, parameter sets "are not included in the bitstream and are instead emitted via the output callback as the `VideoDecoderConfig.description`." Sources: `video_encoder.h` `AvcOptions`; AVC registration §5.

**verified.** In-band versus out-of-band, and a mid-stream change:

- WebCodecs, Dan Sanders on issue 72: for Annex B he expected the implementation to "detect and handle configuration changes silently," with the warning that "not all of Chrome's decoders can change to a previously unknown PPS mid-GOP." For `avcC`, "apps must reconfigure, but they do not need to flush or wait. Configuration changes are simply queued along with chunks." Chris Cunningham: decoding format is chosen by including or omitting the `avcC` in `description`.
- VideoToolbox in Chromium: if the active SPS bytes change, or the PPS changes on an IDR, it drops the format description and builds a new one. A PPS-only change on a non-IDR is stuffed in band and does not create a new format. If the new format is not acceptable to the current session, the session is drained and destroyed before a new one is created. Source: `video_toolbox_h264_accelerator.cc` `SubmitFrameMetadata`; `video_toolbox_decompression_session_manager.mm` `Process` format-change branch.
- Android, non-adaptive, or not decoding to a `Surface`: "`flush()` does not support format discontinuities; for that, a full `stop()`–`configure()`–`start()` cycle is necessary." Adaptive playback "is only activated if you configure the codec to decode onto a `Surface`." For H.264, H.265, VP8 and VP9 you may change picture size by packaging "the entire new codec-specific configuration data together with the key frame into a single buffer (including any start codes)." You then get `INFO_OUTPUT_FORMAT_CHANGED` "just after the picture-size change takes place and before any frames with the new size have been returned." A flush before that confirmation loses the size change. Source: Android `MediaCodec`, "Seeking & Adaptive Playback Support."
- V4L2: a resolution change is `V4L2_EVENT_SOURCE_CHANGE` with `V4L2_EVENT_SRC_CH_RESOLUTION`. It "triggers an implicit decoder drain." Capture buffers are reallocated. The event also fires when "the minimum number of buffers needed for decoding" changes, or bit depth changes, or colours change in a way that does not reallocate. The last buffer before the change is flagged `V4L2_BUF_FLAG_LAST`. Source: `dev-decoder.html` §§ on dynamic resolution change and drain; Chromium `v4l2_stateful_video_decoder.cc` subscribes to that event before it even has a capture queue.
- Chromium's software H.264 parser, on a new picture size, DPB size, profile, bit depth, or (behind a feature) colour space, flushes before continuing. Source: `h264_decoder.cc` after `ParseBitDepth`.

`alignment=nal` versus `alignment=au` (GStreamer) is the other axis: one NAL unit is not one picture. WebCodecs requires an access unit, "exactly one primary coded picture" (AVC registration §2). Platforms that take a bytestream (V4L2, Annex B MediaCodec) will accept a buffer that is one access unit; stateless accelerators want slices.

## 3. What a decoded frame carries

**verified.** Chromium's `VideoDecoderConfig` and `VideoFrame` keep all of the following, and the comments say why they are different:

- Coded size: "width and height of video frame immediately post-decode. Not all pixels in this region are valid." Marked deprecated in the config, still on the frame.
- Visible rect: "region of `coded_size()` that contains image data, also known as the clean aperture. Usually, but not always, origin-aligned."
- Natural size: visible size with aspect applied. Deprecated on the config in favour of `aspect_ratio()`.
- Aspect: `VideoAspectRatio::PAR` is the pixel shape ("an anamorphic video has rectangular pixels with a 2:1 PAR"). `DAR` is the shape of the rendered picture. The comment warns that "sample aspect ratio" and "storage aspect ratio" are both called SAR.
- Rotation and mirror: `VideoTransformation`, "usually calculated from a rotation matrix from a demuxer, and we only support 90 degree rotation increments." "Rotation should be applied after scaling to natural size." WebCodecs: `rotation` is clockwise degrees, `flip` is horizontal after rotation. `displayWidth` / `displayHeight` are "display aspect ratio of visible rect, after accounting for rotation." The existing `video-frames` WIT says the same: the buffer is not turned.

Sources: `video_decoder_config.h`; `video_aspect_ratio.h`; `video_transformation.h`; `video_frame.idl`; `video-frames.wit`.

**verified.** Android's crop is a separate rectangle from the output buffer: `KEY_CROP_LEFT/TOP/RIGHT/BOTTOM`, and "the right and bottom coordinates can be understood as the coordinates of the right-most valid column/bottom-most valid row" (so they are inclusive, unlike a typical exclusive rect). "The crop rectangle is understood in the context of the output frame before applying any rotation." When decoding to a `Surface`, crop, rotation and scaling are applied for you, with a documented exception, and "`VIDEO_SCALING_MODE_SCALE_TO_FIT_WITH_CROPPING` may not work correctly for videos rotated by 90 or 270 degrees" as of Android N. Pixel aspect is not applied to the `Surface`; the app places the surface. Source: Android `MediaCodec` crop table and scaling notes.

**verified.** V4L2 defines coded resolution ("typically visible resolution rounded up to full macroblocks") and visible resolution ("must be smaller or equal to coded resolution"). Source: `dev-decoder.html` glossary.

**verified.** Pixel formats Chromium enumerates include `PIXEL_FORMAT_NV12`, `NV21`, `I420`, `I422`, `I444`, `YUV420P10`, `P010LE`, `P210LE`, `P410LE`, `NV12A`, `I420A`, `I444A`, and 12-bit planar variants (`video_types.h`). Hardware output is narrower:

- VideoToolbox: Chromium asks for a biplanar video-range format from chroma and bit depth: 8-bit 4:2:0 → `kCVPixelFormatType_420YpCbCr8BiPlanarVideoRange` (`420v`), 10-bit 4:2:0 → `420YpCbCr10BiPlanarVideoRange`, and the 4:2:2 and 4:4:4 equivalents. Alpha forces `kCVPixelFormatType_420YpCbCr8VideoRange_8A_TriPlanar`. The comment lists formats VideoToolbox has actually produced when no attributes are set, including 12-bit `'tv20'`, `'tv22'`, `'tv44'` and 10-bit `'p420'`, and says there is "no definitive list." Compressed pixel formats exist from macOS 12 / iOS 15 (`kCVPixelFormatType_Lossless_420YpCbCr8BiPlanarVideoRange` and packed 10-bit variants). Source: `video_toolbox_decompression_session_manager.mm` `CreateSession`.
- D3D11: `GetOutputDXGIFormat`, table in section 1. NV12 and P010 are the 4:2:0 cases. AV1 profile 1 forces `DXGI_FORMAT_AYUV` or `Y410`. NVIDIA HEVC 12-bit 4:2:0 is special-cased to P010. Output is a `ID3D11Texture2D` array, one slice per picture, or one texture per picture. Shared-handle flags (`D3D11_RESOURCE_MISC_SHARED` and `SHARED_NTHANDLE`) are how another device imports it. Decode swap chains cannot be shared. Source: `d3d11_decoder_configurator.cc` `CreateOutputTexture`; `d3d11_video_decoder.cc` `CreatePictureBuffers`.
- VA-API: surfaces exported as dma-buf via `NativePixmap` (`vaapi_wrapper.cc` dma-buf size and `VASurfaceAttribExternalBuffers`). Chromium `VideoFrame` storage `STORAGE_DMABUFS`, "each plane is stored into a DmaBuf."
- V4L2: the capture queue's pixel format is enumerated only after the coded format is set, and only the formats supported for that coded format. Chromium notes some drivers enumerate both a high bit depth and a low bit depth and that it would rather keep the higher one. Buffers are MMAP (or the driver's dma-buf). Source: `dev-decoder.html` enumeration steps; `v4l2_stateful_video_decoder.cc` `GetNumberOfReferenceFrames` and capture candidates.
- Android: decode to a `Surface`. Chromium's frame factory uses `AImageReader` modes, including a secure one (`video_frame_factory_impl.cc`). `VideoFrameMetadata.copy_required` records that a `SurfaceTexture` image "can't be shared between contexts of different share group and hence this frame must be copied." Output format change also carries colour keys (`KEY_COLOR_STANDARD`, `KEY_COLOR_RANGE` in `MediaCodecBridge.java`).

**verified.** Colour. `VideoColorSpace` follows ISO 23001-8 / H.273 tables: primaries, transfer (including `SMPTEST2084` PQ and `ARIB_STD_B67` HLG), matrix (including `BT2020_NCL`; `BT2020_CL` "is no longer supported"). Range is `gfx::ColorSpace::RangeID`. FFmpeg has the same four fields plus `chroma_location` on `AVCodecParameters`. GStreamer's raw-video caps have `colorimetry` and `chroma-site` (the video-raw design page). WebCodecs `VideoColorSpace` on the frame is "the color space of the data produced by `copyTo()`."

Precedence, and the sources disagree:

- WebCodecs: "If `colorSpace` exists, the provided values will override any in-band values from the bitstream." The output algorithm also says detection is "best-effort" and "authors can override." A 2026 issue (w3c/webcodecs#940) says partial overrides are not implemented consistently: Chrome and Firefox agree when the whole space is set, and disagree when only transfer is set. **verified** (spec text and the issue page).
- Chromium H.264: "prefer the frame color space over the config" when the SPS colour is specified; otherwise the container colour. A matrix of RGB on 4:2:0 is replaced with Rec.709. Source: `h264_decoder.cc`.
- D3D11, if neither the bitstream nor the config yields a valid space, defaults multi-planar to Rec.709 and single-planar to sRGB. Source: `d3d11_video_decoder.cc` `CreatePictureBuffers`.

**verified.** HDR. `gfx::HDRMetadata` holds SMPTE ST 2086 mastering display (`SetMDCV`), CTA 861.3 content light level (`SetCLLI`), an adaptive global tone map, a nominal diffuse white, and an extended-range headroom. `HdrMetadataType` names `kSmpteSt2086`, `kSmpteSt2094_10`, `kSmpteSt2094_40`. `GetContentMaxLuminance` uses CLLI, then ST 2086 max, then 1000 nits. Android: `HdrMetadata.addMetadataToFormat` sets `KEY_HDR_STATIC_INFO`. Chromium's MediaCodec path keeps a `HdrMetadataReorderingMap` because "decoders receive metadata in decode order but produce frames in presentation order." If the codec does not report HDR metadata on the output buffer, the config's metadata is used. Sources: `hdr_metadata.h`; `hdr_metadata_reordering_map.h`; `media_codec_video_decoder.cc` `GetColorSpaceAndHdrMetadata`.

**verified.** Alpha. `VideoDecoderConfig::AlphaMode` is `kHasAlpha` or `kIsOpaque`. VideoToolbox has a distinct codec type `kCMVideoCodecType_HEVCWithAlpha`, "HEVC format with alpha support defined in Annex-F" (`CMFormatDescription.h`). Chromium's HEVC accelerator tracks alpha from the VPS id and passes `has_alpha` into the session; H.264 and VP9 pass `has_alpha=false`. VP8/VP9 alpha in WebM is a second bitstream: WebCodecs issue 377, Dan Sanders: "the alpha is conventionally encoded as a separate stream, and the decoder takes the alpha stream as side data on each packet. WebCodecs doesn't have side data on `EncodedVideoChunk`." Dale Curtis, 2023: "There's no way to zip hardware decoded opaque data with hardware/software decoded alpha data with the current API, so you'll need to use `copyTo()`." Issue still open as of the 2025-07-15 comment: "Chrome still doesn't support this natively."

**verified.** Timestamps and duration. WebCodecs `VideoFrame.timestamp` is a presentation timestamp in microseconds; `duration` is optional. VideoToolbox's output callback receives `presentationTimeStamp` and `presentationDuration`, either of which may be `kCMTimeInvalid`, taken from the sample buffer. The callback "will not necessarily be called in display order." Android: "Do not submit multiple input buffers with the same timestamp (unless it is codec-specific data)." Output `BufferInfo.presentationTimeUs` is how Chromium matches HDR metadata back up. Chromium `VideoFrameMetadata.frame_duration` is "the amount of time between the media timestamp of this frame and the next" and "can vary unpredictably." FFmpeg: container timestamps override codec-header frame rate; `AVCodecParameters.framerate` "should thus be used only as a last resort."

**verified.** Lifetime. Android: "holding onto input and/or output buffers may stall the codec, and this behavior is device dependent. Specifically, it is possible that a codec may hold off on generating output buffers until all outstanding buffers have been released." VideoToolbox: "the video decompressor may still be referencing the pixelBuffers" unless `kVTDecodeInfo_ImageBufferModifiable` is set. D3D11 allocates `GetRequiredNumOfPictures() + 1` picture buffers; the reference-frame list is sized to the codec DPB max plus `limits::kMaxVideoFrames` (4) plus 2 (`d3d12_helpers.h` `kMaxSize`). V4L2: the client must allocate at least `V4L2_CID_MIN_BUFFERS_FOR_CAPTURE` plus pipeline depth; Chromium treats 18 as the largest reference-frame count it has seen. mpv `--hwdec-extra-frames` is "the number of extra GPU frames hardware decoding should preallocate, on top of what the codec itself requires," and "is used only for hardware decoding APIs which require preallocating surfaces (known examples include d3d11va and vaapi)."

## 4. Flow and failure

**verified.** Order. V4L2: "`CAPTURE` buffers must be returned by the decoder in display order"; the client queues `OUTPUT` in decode order. Chromium's stateless H.264 parser calls `OutputPicture` in the order pictures should be displayed, and "guarantees that all pictures will be outputted in the same order as this method was called." That is how DXVA and VA-API get display order: the parser, not the hardware, reorders. VideoToolbox's callback is explicitly not in display order; `VideoToolboxOutputQueue` "handles frame reordering" and `SchedulePicture` means "next in presentation order." Pictures may be fulfilled before they are scheduled. FFmpeg's `has_b_frames` is "the size of the frame reordering buffer in the decoder." The encoder reconstruction flag documents the opposite case: those frames "are returned in coded order rather than presentation order." `AV_CODEC_FLAG_LOW_DELAY` exists. Chromium's `VideoDecoder::Initialize` `low_delay` means "the decoder is not allowed to queue frames, except for out-of-order frames."

**verified.** Back pressure. WebCodecs `decodeQueueSize` "does not include requests that have been sent to the underlying codec," and the IDL says "consider adding a predicted output count or other backpressure mechanism that considers the state of the underlying codec." `GetMaxDecodeRequests` on Chromium's D3D11 decoder returns 4. V4L2 Chromium reports `min(4, num_input_buffers)` and allocates 16 input buffers for H.264 and 2 for VPx. Android's stall-if-you-hold-a-buffer rule is the real back pressure, and it is device dependent.

**verified.** Flush, reset, drain.

- WebCodecs: `flush()` resolves after all output for earlier decode requests has been emitted, and "the next decode request must be a key frame." `reset()` discards pending requests, and the next decode must also be a key frame. `close()` is not recoverable. The IDL notes that a `reset` racing a `flush` can still fulfil the flush. Chromium maps a missing key frame to `DecoderStatus::kKeyFrameRequired`, "A key frame is required after configure() or flush()."
- Chromium `VideoDecoder::Decode`: an end-of-stream buffer means flush, "`output_cb` must be called for each frame pending in the queue." Re-`Initialize` "drops all internal buffered frames."
- Android: after `start()` or `flush()` "the first frame must be a key frame." The table of what counts is codec-specific: H.264 IDR, HEVC IDR or CRA, VP8/VP9 "a suitable intraframe where no subsequent frames refer to frames prior to this frame." `flush()` revokes outstanding output buffers. In asynchronous mode, `start()` must be called again after `flush()`. A flush before the first output or format change drops the CSD, which "must" be resubmitted with `BUFFER_FLAG_CODEC_CONFIG`.
- V4L2 drain is `VIDIOC_DECODER_CMD` / stop command, ending with a capture buffer flagged `V4L2_BUF_FLAG_LAST`. Seek is `STREAMOFF`/`STREAMON` on the output queue and does not by itself reconfigure capture. A source change implies a drain.
- VideoToolbox: Chromium drains the session before destroying it on a format change (`draining_` in the session manager). `VideoToolboxOutputQueue::Flush` waits until scheduled pictures are fulfilled; `Reset` discards them and completes a pending flush with the given status.

**verified.** Latency. WebCodecs `optimizeForLatency` "hint that the selected decoder should be configured to minimize the number of `EncodedVideoChunk`s that have to be decoded before a `VideoFrame` is output," with the note that some bitstreams require a minimum anyway. Chromium passes it through as `low_delay`. Android codecs are classified `LowLatencyCapability`: `kNone`, `kAny`, or `kRequired` ("decoder only supports low latency playback"). Chromium skips a required-low-latency codec when the caller did not ask, and skips a no-low-latency codec when it did. VideoToolbox `kVTDecompressionPropertyKey_RealTime` defaults to true; `kVTDecompressionPropertyKey_MaximizePowerEfficiency` is the background hint, and "setting both … is unsupported and results in undefined behavior."

**verified.** How many hardware decoders. Chromium returns `kTooManyDecoders` from VA-API (default cap 16 while `kLimitConcurrentDecoderInstances` is on, 10 on AMD Stoney Ridge), from V4L2 (checked before opening the device, because "some drivers (e.g. Qualcomm Venus on SC7180) would not allow for opening the device fd"), and from the mojo decoder service. VideoToolbox: `kVTVideoDecoderSpecification_RequireHardwareAcceleratedVideoDecoder` fails session creation when hardware cannot be allocated, and the header lists "the hardware decode resources on the machine are busy" as a reason. There is no portable number.

**verified.** Losing the decoder. Android `CodecException.ERROR_RECLAIMED`: "the resource manager reclaimed the media resource used by the codec. With this exception, the codec must be released, as it has moved to terminal state." `ERROR_INSUFFICIENT_RESOURCE`: "required resource was not able to be allocated." Chromium maps those to `MediaCodecStatus.RECLAIMED` and `INSUFFICIENT_RESOURCE` (`MediaCodecBridge.convertCodecException`). A destroyed Android overlay calls `OnSurfaceDestroyed` and `ReleaseCodec`. I did not find, in the VideoToolbox headers read this session, a documented automatic teardown when the app backgrounds. What is documented is `kVTDecompressionPropertyKey_MaximizePowerEfficiency` for a background client, and `kVTInvalidSessionErr` (`-12903`) as an invalid-session error. Claiming "iOS always kills the hardware decoder in the background" would be **from memory**; it is not stated in the headers that were read.

**verified.** Software fallback. mpv: "If hardware decoding is not possible, mpv will fall back on software decoding." Hardware decode "is not enabled by default." `hwdec=auto` "will limit itself to choosing from hwdecs that are actively supported." VideoToolbox: `EnableHardwareAcceleratedVideoDecoder` allows hardware; `RequireHardware…` "return[s] an error if that isn't possible" and "is useful for clients that have their own software decode implementation." On macOS, Chromium sets both, and sets Require to false when `allow_software_decoding` is set. On iOS the decoder-specification dictionary Chromium builds is empty (`video_toolbox_decompression_session_manager.mm`, the `#else` branch). WebCodecs `hardwareAcceleration` is a hint; see section 7.

**verified.** Errors Chromium actually distinguishes (`decoder_status.h`): `kFailed`, `kAborted` (reset), `kMalformedBitstream`, `kPlatformDecodeFailure`, `kKeyFrameRequired`, `kUnsupportedProfile`, `kUnsupportedCodec`, `kUnsupportedConfig`, `kUnsupportedEncryptionMode`, `kCantChangeCodec`, `kFailedToCreateDecoder`, `kTooManyDecoders`, `kMediaFoundationNotAvailable`, `kMissingCDM`. Android adds recoverable (`stop`/`configure`/`start`), transient (retry), and fatal, plus the two resource codes above. VideoToolbox reports `OSStatus` from format-description and block-buffer calls; Chromium turns a non-`noErr` into a media-log error and `Status::kFail`. WebCodecs surfaces one error callback and does not distinguish these.

## 5. Capability queries

**verified.** What each one can answer without decoding a frame:

- VideoToolbox: `VTIsHardwareDecodeSupported(CMVideoCodecType)` is a yes/no for a codec type. Chromium calls it for H.264, and for VP9 only after `VTRegisterSupplementalVideoDecoderIfAvailable`. It does not take profile, level, size, or frame rate. After creation, `kVTDecompressionPropertyKey_UsingHardwareAcceleratedVideoDecoder` tells you whether the session that was created is hardware. `RequireHardware…` turns "no" into a failed create. Source: `video_toolbox_video_decoder.cc`; `VTDecompressionProperties.h`.
- Android: `CodecCapabilities.isFeatureSupported` for adaptive playback; profile levels on `MediaCodecInfo`; `VideoCapabilities` for sizes (Chromium's format builder assumes max width and height, and comments that "some decoders on TVs interpret max width / height quite literally, and a crash can occur if these are exceeded"). Low-latency and secure-playback are separate features Chromium stores as `LowLatencyCapability` and `SecureCodecCapability` (`kClear` / `kEncrypted` / `kAny`-style splits in `video_accelerator_util.cc`). Colour and HDR are not a decode-capability bit in the configure path; they are format keys.
- D3D11: `GetVideoDecoderProfileCount` / `GetVideoDecoderProfile` enumerates GUIDs. `SupportsDevice` is "does this GUID appear?" Format support is a separate check used by `GetOutputDXGIFormat` and the profile helpers (they pass `DXGI_FORMAT_P010` and so on). The decoder descriptor includes the coded size, so "this profile at this size" is a create-time check, not a codec-type check.
- VA-API: `vaQueryConfigProfiles` style support. Chromium caches `IsProfileSupported(mode, va_profile)` and fails with `kUnsupportedProfile`. Max instance count is not a driver query in this code; it is a Chromium constant. I did not read `va.h` this session, so I am not asserting which `VAConfigAttrib` fields expose max width.
- V4L2: `VIDIOC_ENUM_FMT` on `OUTPUT` lists coded formats and "whether or not the decoder has a full-fledged bytestream parser and if the decoder supports dynamic resolution changes." `ENUM_FMT` on `CAPTURE` lists raw formats for the currently set coded format only. The real coded size, bit depth and minimum buffer count arrive with the source-change event, after bytes have been queued. So "maximum size" is not answered up front by the procedure the kernel document specifies.
- FFmpeg: `AVCodecParameters` describes a stream, not a device. Hardware support is "open a device and see," via `hw_device_ctx` / `get_format`. No portable query in `avcodec.h` returns "this GPU, this profile, this frame rate."
- Media Capabilities: `supported`, `smooth` ("decode … at the indicated framerate without dropping frames"), `powerEfficient` ("in a power efficient manner"). Inputs include codec string, size, bitrate, frame rate, and optionally `hdrMetadataType`, `colorGamut`, `transferFunction`. The spec says these are what the user agent is "able" to do, not a measured run. `hdrMetadataType` is only applicable to `media-source` and `file` decoding configurations.
- WebCodecs `isConfigSupported`: returns whether the user agent "can provide a codec that can decode the exact profile (where present), level (where present), and constraint bits (where present)." It does not return `smooth` or `powerEfficient`. "To reduce fingerprinting entropy, user agents can limit the configurations they provide to a common baseline subset." Chromium, if coded size is omitted, "guess[es] 720p … This choice should result in a preference for hardware decode" (`video_decoder.cc`). That guess is invisible to the caller.

**verified.** What they cannot answer without trying: whether this exact SPS (not just the profile) decodes; whether a second or third concurrent session still gets hardware (Apple: resources busy; Chromium: `kTooManyDecoders`); whether the driver's reported size limit is real (Chromium's TV comment); whether a V4L2 driver will parse this stream's bit depth; whether `powerEfficient` stays true at the moment of playback. Android's `ERROR_INSUFFICIENT_RESOURCE` is the runtime form of a query that was optimistic.

## 6. So a later encoder, audio codec, DRM stack, or alpha stream does not force a new shared type

### Encoder

**verified.** Chromium `VideoEncoder::Options` already needs, beyond anything a decoder config has: `Bitrate`, `framerate`, `frame_size`, `keyframe_interval` (default 10000), `LatencyMode` (`Realtime` or `Quality`), `SVCScalabilityMode`, `ContentHint` (`Camera` or `Screen`), encoded chroma and bit depth, `produce_annexb` per codec, and `manual_reference_buffer_control`. Per frame, `EncodeOptions` has `key_frame`, an optional quantizer "only when encoder configured with `kExternal` bitrate mode," and reference-buffer ids (`update_buffer`, `reference_buffers`). The output callback passes the encoded chunk and an optional `CodecDescription`, "a sequence of codec specific bytes, commonly known as extradata. If available, it should be given to the decoder as part of the decoder config." Some platforms "adjust the encoding size to meet hardware requirements."

**verified.** WebCodecs AVC registration: encoder `format` is `annexb` or `avc` (default `avc`). Per-frame `quantizer` is 0..51 for H.264. `alpha: "keep"` puts the alpha in `EncodedVideoChunkMetadata.alphaSideData`, not in the chunk. Scalability: issue 40, closed 2023, "basic support is now specified." Bernard Aboba's comment on that issue: hardware encoders "have not had very good support for SVC (particularly more exotic modes like spatial scalability or K-SVC)." Chromium's enum follows WebRTC-SVC and includes `L1T2`, `L1T3`, `L2T1`, `S2T1`, `S3T3`, and the `h` (hierarchical P) variants (`svc_scalability_mode.h`).

If the shared "codec setup" type has nowhere to put an output bitstream form, a per-frame key-frame request, a bitrate mode, or a description emitted beside the first chunk, an encoder cannot reuse it. Those are not decoder inputs; they are the mirror image of section 2.

### Audio

**verified.** `AudioDecoderConfig` is codec, sample format, channel layout (not just a count), sample rate, `extra_data`, encryption, `seek_preroll`, `codec_delay` ("the number of frames the decoder should discard"), and an optional profile. The comment on `extra_data`: "Vorbis codebooks or AAC AudioSpecificConfig." FFmpeg adds `block_align`, `frame_size`, `initial_padding`, `trailing_padding`, `seek_preroll`, and `AVChannelLayout`.

**verified.** Android's CSD table is the sharp edge: AAC is "decoder-specific information from ESDS" in `csd-0`. Opus is three buffers: identification header, pre-skip in nanoseconds as a native-endian `uint64` (overrides the header), and seek pre-roll in nanoseconds. Vorbis is identification header then setup header. FLAC is the `fLaC` marker plus STREAMINFO. Chromium's `GetCodecSpecificDataForAudio` implements that, and for AAC sets `KEY_IS_ADTS` from the profile (`kXHE_AAC` is the exception). A video-only "description blob" that is a single byte string cannot hold Opus's three buffers or AAC's ADTS-versus-AudioSpecificConfig choice without a convention.

Channel layout has to be a layout. Chromium's limits go to 32 channels for processing and 1024 "absolute" (`limits.h`). A `numberOfChannels` integer, which is all WebCodecs' audio config requires, loses the mapping.

### DRM

**verified.** Chromium's encryption is a stream-level `EncryptionScheme` plus per-buffer subsample entries. `limits::kMaxSubsamplesPerBuffer` is 65535, "matching the ISO 23001-7 `senc` wire bound." The H.264 accelerator comment: "SPS and PPS NALUs may not be encrypted," and the accelerator is given a `DecryptConfig` so it can tell which byte ranges are encrypted. Encrypted init "must contain a valid `cdm_id`" (`video_decode_accelerator.h`). Android configure takes a `MediaCrypto`; secure codecs are a distinct set (`MediaCodecBridge` `kSecure`, "all secure codecs are HW codecs"). Chromium's supported-config record has `allow_encrypted` and `require_encrypted` separately, because some decoders only exist as secure decoders (`supported_video_decoder_config.h`). V4L2 Chromium rejects encrypted configs with `kUnsupportedEncryptionMode`. VA-API has a separate protected mode that also requires `VAProfileProtected`.

What that means for a shared type: a frame from a secure decoder often cannot be imported as a normal GPU texture. Chromium's Android image-reader modes include `kAImageReaderSecureSurfaceControl`. A single "hardware buffer" type with no protected/clear distinction will either refuse DRM or punch a hole in the sandbox. Subsample maps (clear byte count, encrypted byte count, key id, IV, pattern) are per chunk, not per stream. Schemes in use are not one enum value on every platform: Widevine, PlayReady and FairPlay do not share a CDM. WebCodecs' `encryptionScheme` on `VideoDecoderConfig` is behind Chromium's `MediaSourceExtensionsForWebCodecs` flag (`video_decoder_config.idl`). I did not read the EME specification's codec-interaction details this session.

### Alpha

**verified.** Two different mechanisms, and neither is "a pixel format flag" alone:

- A second elementary stream (VP8/VP9 in WebM), which needs side data on each chunk. WebCodecs has that on the encoder (`alphaSideData`) and not on `EncodedVideoChunk` for the decoder (issue 377, still open in 2025).
- A codec that includes alpha (HEVC Annex F, `kCMVideoCodecType_HEVCWithAlpha`), which needs its own format description and a pixel format with an alpha plane. Chromium requests `420YpCbCr8VideoRange_8A_TriPlanar` when `has_alpha` is set.

Hardware-decoded colour plus separately decoded alpha cannot be combined on the GPU through the current WebCodecs API (Dale Curtis, issue 377). An interface that only has `AlphaMode` on the config, and no side-data slot on a chunk, can represent the HEVC case and not the WebM case.

## 7. Where WebCodecs is known to be limiting

All of these are **verified** against the spec text or the issue page.

- Hardware selection is a hint, and may be ignored. The spec tells a user agent that does not implement Media Capabilities, "for reasons of fingerprinting," to ignore `hardwareAcceleration`. Issue 896 (open, 2025): a caller using `prefer-hardware` to pick AV1 versus H.264 got a "supported" answer on Firefox and Safari for codecs that then ran in software. Chrome's `isConfigSupported` can return false for `prefer-hardware` when only software exists, which is a stronger reading than "hint." VideoToolbox can require hardware and fail the create; WebCodecs cannot express "require." Media Capabilities' `powerEfficient` is the bit that actually approximates "this will be hardware," and WebCodecs does not return it.
- `isConfigSupported` does not take a frame rate, a bitrate, or a HDR-metadata type. Media Capabilities does. Smoothness is not a WebCodecs result. Chromium substitutes 720p when size is omitted, so the answer depends on a default the caller did not set.
- Codec string and `description` can disagree, and the spec does not say which wins (`video_decoder_config.idl` TODO). The AVC registration overloads "is `description` present?" as the Annex B versus `avc` switch, which collides with `avc1` versus `avc3`.
- Colour override is specified as total ("override any in-band values") and is inconsistently implemented for partial overrides (issue 940, 2026). There is no per-frame colour callback. Chromium's native parser does the opposite for H.264: the SPS wins over the container.
- No side data on a chunk. That blocks WebM alpha (issue 377), and it is the natural place for HDR10+ (ST 2094-40) and Dolby Vision RPU, which are SEI or a parallel stream on top of an otherwise valid HEVC stream. Issue 384 (2021, Dale Sanders): "I am not currently proposing any HDR metadata. … I am uncertain about the future-compatibility of current ways of expressing this metadata, and have been told that it's not a trusted input to tonemapping anyway." HDR was "out of scope for WebCodecs v1." Static metadata can now travel in codec-private boxes (Chromium's `VideoDecoderHelper::GetHdrMetadata` copies it onto the config), but per-frame dynamic metadata has no field. Chromium's native `HDRMetadata` does have ST 2094-10, ST 2094-40, and AGTM.
- Alpha encode exists (`alpha: "keep"`, `alphaSideData`); alpha decode does not, and hardware frames cannot be zipped with a software alpha plane (issues 200 and 377).
- SVC is an encoder `scalabilityMode`. Decoders are assumed to accept what the codec requires; H.264/SVC is called out on issue 40 as something browsers do not actually decode. There is no decoder config for "temporal layer 0 only," which is what a conferencing client does when it drops a layer.
- `optimizeForLatency` is a hint. It does not select Android's required-low-latency codec name, and it does not set VideoToolbox `RealTime` versus `MaximizePowerEfficiency`.
- Back pressure is `decodeQueueSize` of requests not yet handed to the codec. The IDL's own TODO says this ignores the underlying codec. The pool stall in section 3 is invisible.
- `flush` and `reset` both demand a following key frame, and `flush`'s promise does not say whether it completed or was reset (IDL TODO). Android's "flush discards CSD" has no expression.
- Encryption is optional and flag-gated in Chromium's IDL. Subsample maps, secure output, and "this decoder only exists as a secure codec" are outside the config.
- Rotation and flip are metadata on the frame, which is right, but they are taken from the config at configure time and applied to every output frame (spec output steps). A mid-stream display-matrix change has no signal. The spec also says a decoder's active orientation, once set from the first encoded frame, rejects a later frame with a different rotation (`VideoEncoder` steps). That is an encoder constraint a player never has.
- Interlace. FFmpeg has `field_order`. I found no WebCodecs field for it in the config or frame IDL that was read. Chromium's `VideoFrame` metadata that was read (`video_frame_metadata.h`) has duration, frame rate, and capture times, not a field picture structure.
- Spatial / multi-view. VideoToolbox on macOS 14 / iOS 17 can deliver a `CMTaggedBufferGroup` of several images per decode (`VTDecompressionOutputMultiImageCallback`). Chromium's config has `VideoSpatialFormat`. WebCodecs' frame is one image.
- One error channel. Section 4's status list does not fit in a single exception without the application guessing whether to configure again, flush, or give up.
