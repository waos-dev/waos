# wasdk-adapter-waft

Waft over wasdk: Waft's embedder for a program, the platform an Waft app sees over the SDK's `views` (with its composition layers), `screens`, `system`, `windows`, `lifecycle`, `fonts`, `clipboard`, `menus`, `file_dialogs`, `opener`, `notifications`, `media_players`, `media_assets`, `image_codecs`, `video_frames`, `hardware_buffers`, `gpu_interop`, `cameras`, `permissions`, `http` and `files`, drawn with valo over `wasdk-wgpu`. `run(setup)` is the body of a program's `main`. It lives in `sdk/` until its API settles.

The docs and guides are at [waos.app/docs](https://waos.app/docs).

- **Takes:** `wasdk`, the generated bindings; `wasdk-wgpu` and `wgpu`, what the program's one device is; Waft's `waft-embedder` (the host traits), `waft-shell` (the client a host drives) and `waft-foundation` (the app), from Waft's checkout beside this workspace; valo, Waft's renderer, and `valo-fontmgr`'s `assemble`; `http`, the request and response values Waft's client takes; and `url`, which reads a picked file's `file:` URL back as its path inside the program.
- **Provides:** `run`, which runs an Waft app until it quits, itself or because the platform took its last view away, as a card swiped away in Android's Recents does; and `targets`, the `tracing` targets it records its work under, each frame of a video it draws among them, which a subscriber of the program's own reads.
- **Used by:** programs written as Waft apps, such as `examples/gallery`, `examples/copy-paste`, `examples/waft-menus`, `examples/waft-back`, `examples/waft-image`, `examples/waft-time`, `examples/waft-io`, `examples/player`, `builtin-apps/video-player` and `examples/camera`.

```rust
use waft::{IntoWidget, run_app};
use waft_cupertino::CupertinoApp;

#[wasdk::main]
async fn main() {
    wasdk_adapter_waft::run(|app| run_app(app, CupertinoApp::new().home(Home).into_widget())).await;
}
```

Waft's model and the WIT's map one to one (the design's decision 4):

- **Views.** The views the shell gave are Waft's `Platform::views` when the app starts; a view that arrives later on `view-changes` is the client's `view_added`, one that goes is `view_removed`, and a request that got none is `view_request_failed`. `Platform::request_view` is `request-view`, with every option of Waft's `WindowConfig` set on the `window-config`; the view that arrives carries the request's id and initial data. A view keeps the engine's id. A desktop's shell gives a program no view, so `run_app` asks for its window.
- **Each view's events,** carried field for field into Waft's Flutter shapes: metrics (with the screen the view is on now, and no system gesture insets, which the interface does not carry) as `view_metrics_changed`, pointers as Waft's `PointerReport`s, a signal reported as itself whatever movement it interrupts, to which the client adds the press numbers and movement Flutter's engine adds, keys as `KeyData`, each key's reply answered with whether the framework handled it or it typed into the text input; the user's copy, cut and paste as Waft's `clipboard_event`, a copy or a cut writing through the event's `copy-request`, and Edit's other commands as `edit_command`; focus, the text input's edits, actions and end, close requests, which the app decides on, and the user's Back, `pop-route`, as the client's `pop_route`, whose answer was given in advance: Waft's `Platform::set_framework_handles_back`, which Waft's app calls as its navigators come to have a route to pop and to have none, is `set-handles-back` on every view the program has, and on each that arrives after, so a Waft app goes back within itself with no code of its own. The style of the system's bars the framework works out after each frame, from the `AnnotatedRegion<SystemUiOverlayStyle>` its widgets put under each bar (Cupertino's navigation bar puts one), is `set-overlay-style` on that view (`ViewHost::set_overlay_style`), less the bars' colours, which the interface does not carry, the status bar's icons taken from iOS's brightness of the bar, reversed, where only that is said. A key the framework does not handle is typed into the view's text input here, as Waft's winit host types it, unless Control or Command is held. Where the program has a menu bar, the text input answers that its host provides Edit's commands (the menus proposal's decisions 8 and 10), so a text field leaves ⌘C, ⌘X and ⌘V, whose reply then says not handled, for the host's Edit menu, and acts on the copy, cut and paste events instead; elsewhere, as on Windows and Linux, the field handles Ctrl+C, Ctrl+X and Ctrl+V itself.
- **Frames,** by refresh: Waft's `Platform::request_frame(view)` is that view's `request-frame`. A refresh of a screen hands every view of the program it serves the same `frame`, each on its own stream, naming them all; once the frame of every named view the program still has has arrived, each after that view's earlier events, the client draws one `frame` of them all, one refresh at a time, never inside another call into the client. A view that goes meanwhile is not waited for, and a frame still on a view's events when the view went is dropped. The engine gives a view no frame while it is off screen or on no screen, so a hidden window draws nothing while the others keep drawing, and draws again once it shows. A view presents by drawing what Waft's `slices` makes of the scene, its slices as one picture with room made at each composition layer, with valo into the frame its surface hands out, wgpu's surface on the view (`wasdk_wgpu::SharedView`), configured again at the view's size whenever that has changed, then `set-layers`, naming each composition layer the scene places with its placement, the bottom-most first, and the queue's `present`, which presents the view. A frame that paints nothing besides its composition layers, and places the layers the view shows where it shows them, is not drawn, unless the view shows a frame that painted, which it replaces; one that places other layers, or the same elsewhere, is drawn, since the room for each is in the picture. A video a scene draws, a `VideoFrameView`'s, shows its reader's frame for the refresh's `display-time`, as Waft's own hosts ask for the frame of the vsync's target time, and while a view shows a video it asks for each refresh, takes its readers' new frames and draws its last scene again with them, without the framework, as Waft's hosts do; the framework draws only the views it asked a frame of.
- **Composition layers,** as Waft's `Compositor` over the WIT's, where the system has one (`Platform::compositor` answers from `get-compositor`, none where it answers none): a layer an app makes, for a `CompositionLayerView`, is a `composition-layer` the program holds, made opaque or not as the app asks, and shown beneath the view's picture while the frame on screen places it. A placement crosses mutator for mutator, the outermost first: a transform as its 16 values, column-major, a rectangle clip, a rounded-rectangle clip with each corner's radii, an opacity, and a path clip as the rectangle that bounds the path, which the WIT carries where it has no paths, the picture's room still cut by the exact path. A layer another compositor made is left out of the view's layers. A hardware buffer the app presents on a layer, one the WIT handed out, is the WIT's `present`, its `released` run once the WIT's answer comes, in a task of the program's own; the WIT's layer takes no children, a program placing its layers through its views', so a present's children are left out, and said so, and a buffer another host handed out goes back unshown.
- **Windows.** A view in a window answers it as Waft's `HostWindow`: its frame, title, showing, hiding and closing; its size limits, `size_limits` answering the WIT's `size-limits`, read once as the window arrives, none where it answers none; its move from the press under way (`drag`), whether it is maximized, maximizing and minimizing it, each the WIT's call of the same name; and what the system's settings say a double-click on a title bar does, `Unknown` where the WIT answers none. `is_minimized` and `is_occluded` answer false, as on Wayland, since the WIT's `window` does not carry them (decision 35); it has no native handle.
- **Screens,** with their ids, names, frames, visible frames, scales and refresh rates, as Waft's `Screens`, read again at each change; where the pointer is, no host here can say.
- **What the user set:** light or dark and the languages, kept and pushed at each change; the operating system as Waft's `TargetPlatform`; the user's local time zone, as Waft's `Platform::time_zone_offset` and `time_zone_name` over `utc-offset` and `time-zone-abbreviation`, asked at each call as Dart's `DateTime` asks them, an instant in seconds since the epoch turned into the WIT's, and UTC's zero and "UTC", Waft's defaults, where the system has no time zone; and the caption style, Waft's `CaptionSettings` over `get-caption-settings` where the system keeps them, setting for setting, `changed` resolving at the WIT's next style on `style-changes`, so an app's `SubtitleView` draws in it unchanged.
- **The lifecycle:** the state the program starts in as Waft's initial state, each change after pushed, and each request to end answered through the reply Waft's `request_app_exit` is handed; Waft's `AppExit::quit` ends `run`.
- **Fonts,** as decisions 36 and 37 set them: `ProgramFonts`, valo's `FontSource` over `fonts` (a family by name, Flutter's `CupertinoSystemText` and `CupertinoSystemDisplay` through `system-font` at 17 and 29 points with every weight from 100 to 900, and a character's face through `match-character` with the user's languages), each typeface parsed once, the first time it is handed out, from its tables rebuilt into a font file with valo's `assemble`, its fonts made with the typeface's id as their remote id and handed out as clones; and `ProgramGlyphs`, valo's `GlyphRaster` over the glyph calls, each naming the font's typeface, its point on the typeface's axes and the fake bold and italic valo asks for, given to valo with `Context::with_glyph_raster`. A font the app registers itself is drawn here. The families text without one of its own is drawn in, Waft's `Platform::default_font_families`, are native Waft's for the system the engine runs on.
- **The clipboard,** as Waft's `Clipboard`, where the platform has one: `items` is the WIT's `items`, each pasted item's `read` its `read`, the stream read to its end, and `write` its `write`, each form as the WIT carries it, bytes given as a stream, a file by its path inside the program, and a promised form or file answered from the source's requests by the producer Waft gave, in a task of the program's own until another copy replaces it: a form's bytes as one stream, a file's written into a `FileSink` over the request's stream as the producer makes them, and each followed by a `done` from the producer's result. After the event loop ends, `run` flushes the clipboard before it returns, while the app and its answering tasks are still there, as AppKit asks inside `terminate:`, so the forms the app promises outlive the program; its promised files end with it, and a producer that needs the app's own loop to finish is not answered then. Each change on the WIT's `changes`, the program's own copies among them, is the client's `clipboard_changed`. What the user copies, cuts or pastes through WaOS's Edit menu, Waft's `clipboard_event`, comes with the menus.

- **Menus,** each where the platform has the place: Waft's `MenuBar` over `get-menu-bar`, `PopupMenus` over `get-context-menus`, at a point in the view's logical pixels, which go over in its physical ones, and `TrayIcons` over `get-tray-icons`, each icon answered once the platform has made it, or with why it did not, and removed as Waft's app drops it, with its attached menu and the menu opened at it. A program has no Dock menu (decision 5 of the menus proposal). A menu goes over as the WIT's flat list, each entry naming the submenu it is in and keeping the id Waft's app gave it, a separator, which Waft gives none, taking one the menu leaves free; a choice comes back by that id. The menu bar's choices reach the client as `menu_selected`, and what the user does to a tray icon, and chooses in its attached menu, as `tray_icon_event`, on streams the loop reads a next item of only once it has pushed the one before, so a frozen program the engine thawed for one stays thawed until the app has handled it. `MenuBar::perform_key_equivalent` answers false: a program answers each key as it comes, and its host offers a key it left to the menu bar.

- **File dialogs,** where the platform has them: Waft's `FileDialogs` over `get-file-dialogs`, a function per kind, its options set on the WIT's resources, each a sheet on the window of the view it names while the program has it; each pick answered as `PickedFile::Path`, where WaOS mounted it (the file dialogs proposal's decision 4).
- **HTTP,** through WASI 0.3's own client (`http`): Waft's `HttpClient::send` builds the WIT's request from the method, the URI's scheme, authority and path, each header value appended as it came, and a body streamed by a task of the program's own; WASI's three timeouts from `SendOptions`; then the response's status, headers and body, which is a `BodyStream` over the WIT's stream with its trailers future, and WASI's `error-code` passed through case for case, as decision 10 has it. WASI follows no redirect, so the client follows them as `RedirectPolicy` asks, `TooManyRedirects` past the limit. The transmission future `Request::new` answers and the trailers future are never awaited before `send`: the module says why.
- **Files,** over WASI 0.3's file system: Waft's `Files` reads and writes a whole path, opens one with a mode and a cursor the adapter keeps, reads and writes at an offset and streams each way, reads metadata, lists a folder, makes folders, renames and deletes, a folder with what is in it. Every path is the program's, from the root WASI preopens, so it is the same files `std::fs` reaches: `/data`, `/cache`, `/tmp`, the user's mounts and a file picked for it; WASI's async calls are awaited, so a file read or write does not stop the view drawing.

- **Opening and being opened,** as the opening proposal's decisions 1, 2 and 6 set them: Waft's `Opener` over `get-opener`, a link, a file by its path inside the program and a file shown in the system's file manager each a call, a scheme the user refused failing with why, since Waft's `OpenError` has no refusal of its own, and `can_open_link` answering none, as the WIT does not ask it. What the user opens with the program, the WIT's `open-requests`, is the client's `open_requested`, each file a `PickedFile::Path` where WaOS mounted it, writable, so an app hears it through `App::set_open_requested_handler`, the request that started the program among them.

- **Notifications,** where the platform has them: Waft's `Notifications` over `get-notifications`, each notification built on the WIT's resource and posted, scheduled or removed by its id, a reply action Waft's `NotificationReplies` made added through the WIT's `notification-replies`, and replies and scheduling each where the platform has it; the permission is the `permissions` interface's `notifications` question, which `NotificationPermission::request` puts to the user. A post is the WIT's, which answers `denied` without asking while the user has not allowed the program, where Waft's native hosts ask first, so an app asks through the permission before it posts. What the user does to a notification, the WIT's `activations`, is the client's `notification_activated`, which an app hears through `App::set_notification_activated_handler`, the click that started the program among them, on a stream the loop reads a next item of only once it has pushed the one before.

- **Players,** where the system has them: Waft's `Players` over `get-media-players`, so an app's `Player`, `PlayerView` and `SubtitleView` work unchanged. A player's URL goes over as the WIT's source, a picked file's `file:` URL as its path inside the program and a link as it is, which WaOS checks against the program's network rules; a player's calls are the WIT's of the same names, a position in a WIT `duration`'s nanoseconds, a seek's tolerance the WIT's with no bound on a side as the longest duration, its tracks picked by their ids; its state, with its tracks, its position and its metadata are the WIT's, and its cues those the WIT's `cue-changes` said last, as the media styles them, which a task of the program's own keeps, as Waft reads them at once; `changed` resolves at the next change of the state, a jump of the position among them, the cues or the metadata, or as the player goes. Its picture goes to the WIT's layer behind a composition layer the app's compositor made, which a `PlayerView` makes, or to the WIT's reader behind one the app's readers made, and nowhere for any other output, as Waft has a host do with an output it did not make.
- **Media assets,** where the system reads media without playing it: Waft's `MediaAssets` over `get-media-assets`, one to one. An asset's URL goes over as a player's does, and each read is the WIT's `async func` of the same name, its tracks, metadata and failure a player's in Waft's terms and its picture Waft's `VideoFrame` over the WIT's frame, as a reader's frames are, so an app draws it as any frame; a read under way holds the WIT's asset until it answers.
- **Hardware buffers,** where the system allocates them: Waft's `HardwareBufferAllocator` over `get-hardware-buffer-allocator`, one to one, an allocation the WIT's `allocate`, its format and usage carried field for field, and a side of no pixels, which the WIT traps a program for, failing here first as `ImageErrorKind::Other`. Every buffer the WIT hands the program, one it allocated, a decoded image's or a frame's, is Waft's `HardwareBuffer` over it, its size and usage the WIT's and its pixels the WIT's `read-pixels`, which waits for the GPU work that drew into it.
- **GPU interop:** Waft's `Platform::import_texture` over `gpu-interop`: a buffer the WIT handed out imported as a texture on the program's device through the SDK (`wasdk_wgpu::import_texture`), which the WIT always gives, for what the buffer's usage names, holding the buffer, and a frame's buffer its frame, until the GPU is done with it; a buffer another host handed out is imported as none. The renderer imports a hardware buffer, and a frame's buffer, as an image this way.
- **Image codecs,** where the system has them: Waft's `image_codecs::ImageCodecs` over `get-image-codecs`, one to one, the hardware codecs read once, as the platform starts. The formats are the WIT's; an image opened from bytes, or from a file by its path inside the program, is the WIT's, what it says of itself read from it as Waft asks, its pictures Waft's, field for field; a picture decoded into the program's memory is the WIT's pixel buffer as valo's, field for field, which `Platform::import_pixels` uploads; a picture the hardware codecs decoded is the WIT's hardware buffer as Waft's `HardwareBuffer` (`hardware_buffers`), which `Platform::import_hardware_buffer` imports as an image with no copy, its texture on the renderer's device; and pixels and a hardware buffer, one the app allocated, a decoded image's or a frame's, encode through the WIT's calls of the same names, a buffer another host handed out failing as `Unsupported`. What the WIT traps a program for, a picture the image does not have, a size to fit of no pixels and a quality outside 0 to 1, fails here first, as `ImageErrorKind::Other`; a call under way holds the WIT's resource it is made on.
- **Frame readers,** where the system hands out frames: Waft's `VideoFrameReaders` over `get-video-frame-readers`, so an app's `VideoFrameView` works unchanged. A reader is the WIT's, and answers Waft's `frame_for` with the WIT reader's frame for that moment, turned from Waft's `Instant` into the WIT's `instant` on the program's clock (`moments`); the frame is Waft's `VideoFrame` over the WIT's, lent with its slot in the decoder's pool, its `hardware_buffer` Waft's over the WIT frame's, and its size and pixels the buffer's. The views draw any reader's frames as Waft's hosts do: `frame_for`, the frame's hardware buffer imported as a texture on the renderer's device (`gpu-interop`), which holds the frame until the GPU is done with it, and that imported into valo as an image, a frame with no texture there left undrawn.
- **Cameras,** where the system has them: Waft's `Cameras` over `get-cameras`, so an app's `CameraSession` and `CameraPreview` work unchanged. The cameras listed are the WIT's, with which way each faces, answered once the system has, and `changed` resolves at the WIT's next list on `changes`; a camera opens by its id, the WIT asking the user at the first use. A camera's formats and a session's are the WIT's, field for field, so a format read from a camera is found among its formats again. A session starts, once the system answers, with its preview on the WIT's layer behind a composition layer the app's compositor made, which a `CameraPreview` places, its frames in the WIT's reader behind one the app's readers made, each left out for any other, and its photos at the size named. What the WIT traps a program for, a format the camera does not list, photos at a size the format does not list and a photo of a session started without photos, fails here first, as Waft's hosts answer it. Recording is not offered to programs yet: a session starts without its movies, and a recording fails. Its state is the WIT's, an interruption's reason where the system gives one, `changed` resolving at the state's next change or as the session goes; a photo is the WIT's, a camera's error on the way failing with Waft's words for it, since Waft's photos fail with a reason alone.

- **Waft's own images,** a `MemoryImage`'s, an `AssetImage`'s and every other provider's: `Platform::open_image_codec`, dart:ui's `instantiateImageCodec`, over the same image codecs, `NoDecoder` where the system has none (`image_decoding`). The bytes open as the WIT's image, and each frame decodes as the framework asks for it, at its full size: by the hardware codecs, where the system has them, into a hardware buffer imported as a texture with no copy through the program's memory, and into the program's memory elsewhere, uploaded; either becomes an image on the renderer's device with its mip levels, as Waft's native hosts decode it. The frames are the WIT's pictures: a still image's one picture and a document's primary page are one frame, shown once, as Waft shows one picture of a document, and an animation's frames are shown as often as it says, each for as long as it says, Waft picking its own where it says nothing.

Anything else of Waft's platform the WIT does not carry yet the program has none of.

The crate compiles natively too, so `cargo clippy --workspace` reaches it and its conversions are tested natively, but only a component's imports mean anything.
