# wasdk-adapter-gpui

GPUI over wasdk: GPUI's platform for a program, the one Zed's UI framework needs beside its own (`Platform`, `PlatformWindow`, `PlatformDispatcher`, `PlatformTextSystem`), over the SDK's `views`, `windows`, `screens`, `system`, `lifecycle`, `fonts`, `clipboard`, `file_dialogs` and `opener`, drawn by GPUI's own wgpu renderer, `gpui_wgpu`, on the view's surface over `wasdk-wgpu`. `run(on_launch)` is the body of a program's `main`. It lives in `sdk/` until its API settles; `sdk/wasdk-adapter-waft` is its model.

- **Takes:** `wasdk`, the generated bindings; `wasdk-wgpu`, the wgpu backend a view's surface and the device are made on; GPUI's `gpui` and `gpui_wgpu`, from the branch `waos-gpui` of a fork of Zed (`https://github.com/xtyxtyx/zed`, by revision in the workspace's manifest): Zed's main of 2026-11-14 with three commits, which build GPUI on crates.io's wgpu 30, keep `gpui_wgpu`'s browser code to the browser's wasm, and add a context and a renderer for a WASI component (`WgpuContext::new_wasi`, `WgpuRenderer::new_from_surface_with_atlas`); `raw-window-handle`, the handles GPUI's windows answer; `uuid`, a display's id as GPUI keeps it.
- **Provides:** `run`, which runs a GPUI app until it quits, itself or because WaOS asked it to end; and `gpui`, re-exported.
- **Used by:** programs written as GPUI apps, such as `examples/gpui-hello`.

```rust
#[wasdk::main]
async fn main() {
    wasdk_adapter_gpui::run(|cx| {
        cx.open_window(WindowOptions::default(), |_, cx| cx.new(|_| Root)).unwrap();
    })
    .await;
}
```

Only a component has GPUI here: the crate is empty natively, so the workspace's native build does not build GPUI, and its checks run for `wasm32-wasip2` (`cargo clippy -p wasdk-adapter-gpui --target wasm32-wasip2`).

GPUI's model and the WIT's, as the adapter carries one into the other:

- **Starting.** `run` makes the program's device first, with `WgpuContext::new_wasi` on `wasdk_wgpu::instance()`, then the platform over it, then GPUI's app with `Application::with_platform`, launched with GPUI's `run_embedded`, the entry GPUI keeps for a wasm program, which returns at once; then it turns the loop until the app quits. The program's streams are opened before the platform reads the values they change.
- **Windows.** GPUI opens a window synchronously, and a program asks WaOS for a view, which arrives later on `view-changes`. So `open_window` asks with `request-view`, a `window-config` with the title, size, position and whether it resizes, and answers at once with a window pending its view: the bounds GPUI asked for, the first screen's scale, and an atlas made before the renderer, which GPUI asks for as the window opens. When the view arrives, carrying the request's id, the window makes `gpui_wgpu`'s renderer on the view's surface (`SharedView`), with that atlas, tells GPUI its size and asks for a frame. A window answers its frame, title, maximizing, minimizing and its move from the press under way (`start_window_move`, the WIT's `drag`) through the view's `window`. GPUI's `prompt` answers none, so GPUI draws its own prompts in the window, as on the web. An anchored pop-up is refused, so GPUI draws it in its window.
- **Frames,** on demand, wasdk's model and GPUI's: GPUI wakes the window when it is dirty (`frame_waker`, `schedule_frame`), which is the view's `request-frame`, once until the frame arrives; the `frame` that arrives runs GPUI's frame callback, which draws into the surface's texture and presents. A change of the view's size or scale reconfigures the renderer and redraws everything.
- **Work.** A program has one thread, so GPUI's foreground and background work share it: the dispatcher keeps three queues, timers by their deadline, the main thread's runnables, then the background's by priority, and the loop runs what is due for 8 ms between events, yielding while more is left so events keep arriving. A runnable that runs cannot be interrupted, so long background work holds the window for its length. The adapter's own asynchronous work (the clipboard's write, the file dialogs, the opener) runs as GPUI's tasks, never through `wasdk::spawn`: `wasdk::block_on`, which the text system and the clipboard's read wait with, takes up every task spawned since the program last awaited and waits for it too, so one that never ends, as `wasdk-wgpu`'s device listeners never do, would hold the read for ever. `run` awaits once after making the device, so those listeners go to the program's own task first.
- **Pointer,** in Flutter's `PointerData` vocabulary, as GPUI's mouse input: the button pressed or released is the one that changed in the buttons held, clicks are counted here, at `gpui_web`'s 400 ms and 5 logical pixels since the platform does not say the system's double-click interval, positions are logical, scroll signals are pixel scrolls, and a trackpad's pan and zoom are scroll steps and pinches.
- **Keys,** in Flutter's `KeyData` vocabulary, as GPUI's keystrokes: a character key by its lower-case character under the user's layout, a named key by GPUI's name, the modifiers kept from the modifier keys, and the text the key typed as `key_char`, none for a chord with Command or Control. A key GPUI leaves that typed text is typed into the focused input, as the platforms' text input does. The key's reply says whether either took it, so one neither took goes on to WaOS's menus.
- **Text input.** GPUI's input handler is `NSTextInputClient`'s shape and WaOS's `text-input` Flutter's: after each frame the adapter pushes the input method a window of the document, 1000 UTF-16 units either side of the selection, with the selection, the composing range and the caret's rectangle, and turns each value the input method sends back into GPUI's edits from its difference with the value pushed, marked text included.
- **Text,** over `gpui_wgpu`'s cosmic-text system, which shapes and rasterizes inside the program: fonts the program adds are used as they are; a family it names that it did not add is read from the system (`fonts.family`, each face's file whole through `open-stream`), `.SystemUIFont` being the system's interface font, read the first time it is named, by the family its file names itself (macOS calls it `.AppleSystemUIFont`, its file `System Font`); and a character no face read so far has is asked of the system (`match-character`, with the user's languages), whose face is read and the line laid out again. A face read is copied whole into the program's memory, 78 MB for macOS's PingFang SC; WaOS's glyph drawing (`glyph-alpha`) would avoid it, but `gpui_wgpu` has no seam for another rasterizer.
- **Displays,** the system's screens with their frames, visible frames and refresh rates, each with a UUID made from its id and name; GPUI hears a change and reads them again.
- **Light or dark** from `system`, with each window told at a change.
- **The clipboard's text:** GPUI's write goes on in a task; GPUI's read is synchronous, as Zed's call sites are, so it waits for the platform's answer with `wasdk::block_on`, holding the program's one thread for the read (9 ms for a short text).
- **Paths:** GPUI's prompts for paths are the system's file dialogs, a file, several or a folder, mounted writable at their paths, and a new path the save dialog; opening a link or a file, and showing one in the file manager, are the `opener`'s.
- **Cursor,** GPUI's styles as the WIT's CSS cursors, set on every view of the program; hidden until the pointer moves when GPUI asks.
- **The end:** GPUI's `quit`, and WaOS's request to end the program, which the adapter answers `exit`, run GPUI's quit handlers and end `run`.

Not carried yet: reading a collection's file once. A wasdk typeface does not say which file it is in, so each face of a collection is read whole on its own: the four faces of macOS's `Menlo.ttc` read its 2.1 MB four times, each in about 0.7 ms, and cosmic-text takes the whole collection each time. Also not carried: the menu bar (`set_menus`), GPUI's open requests and Dock menu, credentials, notifications, drops, the keyboard's layout (it answers "unknown", the keys coming already meant under it), window visibility (WaOS gives a view off screen no frames), transparent windows and full screen, accessibility (GPUI compiles AccessKit out on wasm).

The crate compiles natively only as an empty crate; only a component's imports mean anything.
