---
title: Compatibility
description: What WaOS promises a program built against an older version of its interface.
---

**A program you built keeps running.** A program built against a released WaOS runs on every later WaOS, untouched, as long as the interface it was built against is served, and that is at least a year after the interface that replaces it is released.

## What stays stable

The interface is three WIT packages, `wasdk:platform`, `wasdk:media` and `wasdk:program`, at `1.0.0` from the release that carries them. Each later `1.x` only adds: a new interface, function, method or type, marked `@since(version = 1.x)` in the [reference](/docs/reference). Nothing released is removed, renamed or changed in shape, and a function keeps its meaning. A record never gains a field and a variant or enum never gains a case: where more is needed, a new type or function comes beside the old one.

A program uses only what it calls. Built against `1.4.0`, it runs on any WaOS serving `1.4.0` or later, and on an older one too unless it calls something that came after that one.

WASI's packages a program imports (`wasi:http`, `wasi:sockets`, `wasi:clocks`, `wasi:webgpu` and the rest) are under the same promise, at the versions WaOS served when you built.

## What `@unstable` means

A new API starts as `@unstable(feature = name)`: it may still change or go in any release. WaOS gives it to a development install, which `waos run` and `waos install` make, and to a program whose package asks for it:

```toml
[package.metadata.waos]
unstable = ["name"]
```

In Rust, enable wasdk's `unstable` feature to see these APIs. WaOS's library tells the user that such a program uses interfaces that may still change. When an unstable API settles it becomes `@since`, with the same names and types, so a program that used it keeps running. If it changes instead, a program built against the old shape stops at its start with a message naming the feature, and runs again once rebuilt.

## When something must break

A break is a new version of the package, such as `wasdk:platform@2.0.0`. WaOS serves it beside the old one, so programs built against either run. The old version is served for at least a year after the new one is released, and across at least two WaOS releases; `waos build` warns while a program is built against a version on its way out.

## The SDK

These promises are about programs once built. Your source building against a newer `wasdk` follows Cargo's semver: within one `0.x` release of the crate, updating needs no change to your code.

A release of `waos` pairs with one `wasdk` and one Waft, and `waos new` writes those versions: `waos-cli` 0.3 with `wasdk` and `wasdk-adapter-waft` 0.3, and Waft 0.8. `wasdk-adapter-waft` is built on one Waft, so an app keeps every `waft` crate at that version; two Wafts in one build fail with mismatched types between them.

## How it is kept

Every change to the interface is checked against each released version. At each release, the built components of real programs, WaOS's own apps and examples among them, are kept, and every later WaOS is tested on them: each must start, draw and take input as it did.
