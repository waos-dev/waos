Waft is the UI framework WaOS apps are written with: Flutter's framework ported to Rust, with two kits of controls, WinUI's and Cupertino's. This page is Waft's own model. What the platform gives a program has a guide page each, with Waft's example: [windows](/docs/guide/windows), [Back](/docs/guide/back), [the system's bars](/docs/guide/system-bars), [keys](/docs/guide/keys), [the system's settings](/docs/guide/system), [WebGPU](/docs/guide/webgpu), [compositing](/docs/guide/compositing), [fonts](/docs/guide/fonts), [media players](/docs/guide/media-players), [cameras](/docs/guide/cameras), [audio](/docs/guide/audio), [menus](/docs/guide/menus), [file dialogs](/docs/guide/file-dialogs), [notifications](/docs/guide/notifications), [the clipboard](/docs/guide/clipboard), [processes](/docs/guide/processes), [the network](/docs/guide/network) and [workers](/docs/guide/workers).

## A WaOS app
`cargo waos new` writes this. A WaOS app is a Waft app run by `waft_embedder_wasdk`, Waft's embedder over WaOS:

```rust
// Waft's `State` methods take `self: Handle<Self>`, which needs nightly's arbitrary_self_types.
#![feature(arbitrary_self_types)]

#[wasdk::main]
async fn main() {
    waft_embedder_wasdk::run(start).await;
}

fn start(app: &mut App) {
    let window = WindowConfig { size: [1080.0, 780.0], ..WindowConfig::default() };
    run_app_with(app, widgets_app(), window);
    install_icon_font(app); // WinUI's icons; after run_app_with
}
```
`run_app_with` asks for a window configured so, on Android a task of its own; in WaOS's tabs on a phone, which give the app its tab's view, the configuration goes unused. `run_app(app, widget)` is the same with the default window. The program's `rust-toolchain.toml` picks the nightly with `wasm32-wasip2`; rustup fetches it on the first build.

## Widgets
Waft's core widgets are Flutter's: the same names, built, laid out and painted as Flutter's are, so Flutter's documentation tells what a widget does. A widget describes part of the UI, and `build` returns the widgets it is made of. What differs is Rust's:

- Builder methods take the place of named arguments: Flutter's `Text('Hi', maxLines: 1)` is `Text::new("Hi").max_lines(1)`, and a function such as `show_cupertino_dialog` takes them in order.
- Every call is passed `app`, which holds all state, so nothing closes over a widget.
- A callback is a `Listener`, called with `app`; one handed a value, such as a switch's, is a closure of `app` and the value. Flutter's pointer `Listener` widget is `waft_widgets::Listener`, in the `waft-widgets` crate.
- An app's state lives in entities ([State](#state)), where Flutter leaves it to packages.

Not in Waft: Material (`MaterialApp`, `Scaffold` and its controls; the kits are WinUI and Cupertino), `FutureBuilder` and `StreamBuilder` (a task and an entity do their work), `Form`, `PageView`, `AnimatedSwitcher`, `AnimatedList`, `Dismissible`, `ReorderableListView`, `InteractiveViewer`, `StatefulBuilder`, the `Router`, text selection outside a text field (`SelectionArea`), and accessibility. A panic in `build` ends the program, where Flutter paints its red error box. On WaOS, Waft's `Image` decodes nothing yet: decode with the platform's image codecs (`app.platform().image_codecs()`) and show the result with `RawImage`, as the Video Player's thumbnails do.

```rust
#[derive(Debug)]
struct Home;

impl StatelessWidget for Home {
    fn build(&self, app: &mut App, context: BuildContext) -> WidgetRef {
        let background = ThemeResources::of(app, context).solid_background_fill_color_base;
        ColoredBox::new(background)
            .child(Center::new().child(Button::text("Hello, WaOS", Listener::new(|_app| {}))))
            .into_widget()
    }
}
```
- `.into_widget()` makes any widget a `WidgetRef`, which is what children are.
- A widget with state of its own is a `StatefulWidget`. Its `State` keeps a `StateData` field and `state_accessors!()`, and `set_state` rebuilds it:

```rust
#[derive(Debug)]
struct Toggle;

impl StatefulWidget for Toggle {
    type State = ToggleState;
    fn create_state(&self) -> ToggleState { ToggleState { state: StateData::new(), on: false } }
}

struct ToggleState { state: StateData<Toggle>, on: bool }

impl State for ToggleState {
    type Widget = Toggle;
    waft::state_accessors!();

    fn build(self: Handle<Self>, app: &mut App, _context: BuildContext) -> WidgetRef {
        let label = if app.get(self).on { "On" } else { "Off" };
        Button::text(label, Listener::new(move |app| self.set_state(app, |state| state.on = !state.on)))
            .into_widget()
    }
}
```

## State
An app's state lives in entities, not in widgets. Reading an entity in `build` subscribes the widget to it, and `notify` rebuilds every widget that read it:

```rust
let count = app.new_entity(|_cx| 0);
let n = *app.read(&self.count);                            // in build
app.update(&count, |n, cx| { *n += 1; cx.notify(); });     // in a callback
```
Waft's README recommends three layers:

- **Logic:** the app's rules as plain Rust, which names neither `App` nor `Entity`, so it runs and is tested on its own.
- **State:** entities over the logic, where `App`, `Entity` and `Timer` are used. An entity whose type is an `EventEmitter` of an event tells what happened with `cx.emit(event)`, and another reacts through `cx.subscribe`, keeping the `Subscription` it answers, since dropping it ends the subscription. A callback from outside the app reaches an entity through `AsyncApp::post` ([Async work](#async-work)).
- **UI:** thin widgets, which read entities in `build`, call their methods from callbacks, and keep only view state, such as whether a panel is open.

A new feature is one entity and the widgets that show it:

```rust
#[derive(Default)]
struct Tally { count: u32 }                               // logic: plain Rust

impl Tally {
    fn add(&mut self) { self.count += 1; }
}

#[derive(Clone, Debug)]
struct Counter { tally: Entity<Tally> }                   // state: entities over the logic

impl Counter {
    fn add(&self, app: &mut App) {
        self.tally.update(app, |tally, cx| { tally.add(); cx.notify(); });
    }
}

#[derive(Debug)]
struct AddButton { counter: Counter }                     // UI: reads in build, calls from callbacks

impl StatelessWidget for AddButton {
    fn build(&self, app: &mut App, _context: BuildContext) -> WidgetRef {
        let label = format!("Added {}", self.counter.tally.read(app).count);
        let counter = self.counter.clone();
        Button::text(label, Listener::new(move |app| counter.add(app))).into_widget()
    }
}
```
[Waft's README](https://github.com/xtyxtyx/waft-ui#structuring-an-app) says more of the layers.

## Layout
Layout is Flutter's: constraints go down, sizes go up, and a parent places its children, as Flutter's [Understanding constraints](https://docs.flutter.dev/ui/layout/constraints) explains. So are the widgets: `Row`, `Column`, `Expanded`, `Flexible` and `Spacer`; `Padding`, `SizedBox`, `ConstrainedBox` and `AspectRatio`; `Center` and `Align`; `Stack` with `Positioned`; `Wrap`; `ListView` (`ListView::builder` for a long list), `GridView`, `SingleChildScrollView`, and `CustomScrollView` with slivers; `LayoutBuilder` and `MediaQuery` for the room there is; `Container`, `ColoredBox` and `DecoratedBox`. A `child` takes any widget, and `children` a list of `WidgetRef`s:

```rust
let notes = ListView::builder(|_app, _context, i| Some(Text::new(format!("Note {i}")).into_widget()))
    .item_count(100);
Column::new()
    .cross_axis_alignment(CrossAxisAlignment::Stretch)
    .children([
        Padding::new(EdgeInsetsGeometry::all(12.0)).child(Text::new("Notes")).into_widget(),
        Expanded::new(notes).into_widget(),
    ])
```

## The kits
The controls come from a kit over the core widgets. Try each in its gallery: [WinUI](https://winui-gallery.inset.rs), [Cupertino](https://cupertino-gallery.inset.rs).

**WinUI** (`waft-winui`) is the default, for an app on desktops and phones alike. Its controls are ports of Microsoft's WinUI, with XAML's names and behaviour, so [WinUI's documentation](https://learn.microsoft.com/windows/apps/design/controls/) tells what a control does. Most hold no value of their own: the app passes the value, and the control's callback asks for a change, which the app makes. A control that opens a popup needs an `Overlay` above it, which `WidgetsApp` gives.

```rust
let on = self.wifi.read(app).on;                           // in build
let wifi = self.wifi.clone();
ToggleSwitch::new(on, move |app, on| wifi.update(app, |wifi, cx| { wifi.on = on; cx.notify(); }))
```

| For | WinUI's controls |
| --- | --- |
| Buttons | `Button` (standard, accent or subtle), `HyperlinkButton` (a link's look; the app opens the link), `RepeatButton` (clicks again while held), `ToggleButton` (stays checked), `DropDownButton` (opens a flyout), `SplitButton` and `ToggleSplitButton` (an action, or a toggle, beside a button that opens a flyout) |
| Choices | `CheckBox` (two or three states), `RadioButton` (one of a group the app keeps), `ToggleSwitch` (on or off), `Slider` (a value in a range), `ComboBox` (an item from a drop-down list, or typed), `NumberBox` (a number or an expression, with spin buttons), `ColorPicker` (a colour from a spectrum, sliders, channels or hex) |
| Text | `TextBox` (one line or many), `PasswordBox` (hidden, with a reveal) |
| Menus, flyouts and dialogs | `MenuBar` (menus drawn in the window; the system's menu bar is in [Menus](/docs/guide/menus)), `MenuFlyout` (commands, checks, radio items and submenus), `Flyout` (any content, anchored to a control), `ContentDialog` (a modal question with buttons, `show_async`), `ToolTipService` with `ToolTip` (help on hover and focus) |
| Navigation | `NavigationView` (the app's pages in a pane that adapts to the width, or along the top), `TabView` (tabs to select, close and drag), `SelectorBar` (a few views of one page), `BreadcrumbBar` (the path to where the user is), `TreeView` (nested nodes to expand, select and reorder), `SplitView` (a pane beside or over the content) |
| Status | `ProgressBar` and `ProgressRing` (a value, or work going on), `InfoBar` (a message in the page, by severity), `InfoBadge` (a count, an icon or a dot) |
| Layout and look | `Page` (a window's content on its background, clear of a phone's bars and keyboard; [System bars](/docs/guide/system-bars)), `Grid` with `GridCell` (XAML's rows and columns, sized in pixels, auto or star), `Expander` (content shown or hidden under a header), `FontIcon` (a glyph, such as a `FluentSymbol` once `install_icon_font` has run), `PathIcon` (a shape), `ThemeScope` ([Theming](#theming)) |

**Cupertino** (`waft-cupertino`, `cargo waos new --template cupertino`) is for an app meant for phones alone. Its widgets are Flutter's Cupertino library.

| For | Cupertino's widgets |
| --- | --- |
| The app and its pages | `CupertinoApp`, `CupertinoPageScaffold` (a page: its navigation bar and content), `CupertinoNavigationBar`, `CupertinoSliverNavigationBar` (with a large title), `CupertinoNavigationBarBackButton`, `CupertinoPageRoute` (a page that slides in), `CupertinoSheetRoute` and `show_cupertino_sheet` (a page as a sheet) |
| Controls | `CupertinoButton` (plain, `tinted` or `filled`), `CupertinoSegmentedControl` (one of a few options), `CupertinoTextField` |
| Lists and forms | `CupertinoListSection` and `CupertinoListTile` (with `CupertinoListTileChevron`), `CupertinoExpansionTile` (a tile that reveals more), `CupertinoFormSection` and `CupertinoFormRow` |
| Dialogs and sheets | `CupertinoAlertDialog` with `CupertinoDialogAction`, shown by `show_cupertino_dialog`; `CupertinoActionSheet` with `CupertinoActionSheetAction`, shown by `show_cupertino_modal_popup`; `CupertinoPopupSurface` |
| Status | `CupertinoActivityIndicator` (a spinner), `CupertinoLinearActivityIndicator` (a bar) |
| Look | `CupertinoTheme` and `CupertinoThemeData`, `CupertinoColors`, `CupertinoIcons` (once `install_cupertino_icon_font` has run), `CupertinoScrollbar` |

Not in Waft's Cupertino: `CupertinoSwitch`, `CupertinoSlider`, `CupertinoCheckbox`, `CupertinoRadio`, `CupertinoSlidingSegmentedControl`, the pickers, `CupertinoSearchTextField`, `CupertinoContextMenu`, and the tab bar with `CupertinoTabScaffold`.

## Pages
Pages are kept by Flutter's `Navigator`: `Navigator::push(app, context, route)` shows a page over the others, and `Navigator::pop(app, context, result)` goes back, `push`'s future answering the `result`, an `Option<Rc<dyn Any>>`.

- **WinUI:** the template's `WidgetsApp` holds the pages, each a `PageRouteBuilder`, which shows its page with no animation. A window's main pages are usually a `NavigationView`'s instead: the app shows the selected item's page as its content.
- **Cupertino:** `CupertinoApp` is the app, and a `CupertinoPageRoute` a page that slides in from the right, its title what the next page's back button says.

```rust
// WinUI; `as_route` is the `Route` trait's
let route = PageRouteBuilder::new(app, Rc::new(|_app, _context, _, _| Details.into_widget()));
Navigator::push(app, context, route.as_route());
Navigator::pop(app, context, None);                          // in Details, back

// Cupertino
let page: WidgetBuilder = Rc::new(|_app, _context| CupertinoPageScaffold::new(Details).into_widget());
let route = CupertinoPageRoute::new(app, page).title(app, "Details".into());
Navigator::push(app, context, route.as_route());
```

## Theming
**WinUI.** `ThemeResources::of(app, context)` gives WinUI's theme resources, a field for each XAML key: colours, sizes, corner radii, fonts. They follow the system's light or dark unless a `ThemeScope` sets them: `ThemeScope::new(Theme::Dark, child)`, with `.accent(palette)` for an `AccentPalette` other than Windows' blue, sets them for a subtree, and `ThemeScope::overriding(child)` with `.any`, `.light` or `.dark` changes some for one control, as XAML's resource dictionaries do. Text takes WinUI's type ramp from `TextBlockStyle`:

```rust
let r = ThemeResources::of(app, context);
let title = Text::new("Notes").style(TextBlockStyle::Title.text_style(&r, r.text_fill_color_primary));

let green = AccentPalette { base: Color::from_argb(255, 16, 124, 16), ..AccentPalette::default() };
let dark = ThemeScope::new(Theme::Dark, page).accent(green);
let square = ThemeScope::overriding(field).any(|r| r.control_corner_radius = [0.0; 4]);
```
**Cupertino.** `CupertinoApp::theme` takes a `CupertinoThemeData`, built with its `with_*` setters, and `CupertinoTheme::of(app, context)` reads it. It follows the system's light or dark unless `with_brightness` sets one; `CupertinoColors` are iOS's, most with a light and a dark value.

```rust
let root = CupertinoApp::new()
    .theme(CupertinoThemeData::new().with_primary_color(CupertinoColors::SYSTEM_GREEN))
    .home(home);
let primary = CupertinoTheme::of(app, context).primary_color();     // in a widget's build
```

## Keys and shortcuts
Keys are Flutter's: a key goes to the widget with the focus, then up through its ancestors until one takes it. `Focus` takes the focus (`autofocus`) or hears keys itself (`on_key_event`).

- `CallbackShortcuts` runs a callback for a key while the focus is inside its child, taking the key even from a text field there, so it suits keys a field neither types nor edits with, such as ⌘N.
- `Shortcuts` maps keys to intents, and `Actions` intents to what they do. The app's own, `WidgetsApp::shortcuts` and `actions`, sit above the text fields' keys, so a field still types and moves its caret with them. Each replaces the app's defaults (Tab, Enter, Esc and what they do), so keep `WidgetsApp::default_shortcuts(app)` after your shortcuts, and `default_actions(app)` among your actions.
- A key is a `LogicalKeyboardKey`, from the `waft-services` crate, which the program adds to its dependencies.

```rust
let command_n = SingleActivator::new(LogicalKeyboardKey::KEY_N).meta(true);
let page = CallbackShortcuts::new(vec![(Rc::new(command_n), Listener::new(new_note))], Focus::new(page).autofocus(true));

let space: ShortcutActivatorRef = Rc::new(SingleActivator::new(LogicalKeyboardKey::SPACE));
let play: IntentRef = Rc::new(VoidCallbackIntent::new(Listener::new(play_pause)));
let shortcuts = std::iter::once((space, play)).chain(WidgetsApp::default_shortcuts(app)).collect();
let root = WidgetsApp::new(color).shortcuts(shortcuts).home(page);
```
On a desktop, a command on the menu bar takes its key there: `PlainPlatformMenuItem`'s `shortcut` shows the key in the system's menu, which chooses the item when nothing with the focus takes the key ([Menus](/docs/guide/menus)).

## Async work
An app runs on one thread, and its async work runs there as tasks. `app.spawn(async move |cx| …)` awaits any future, the platform's or wasdk's, and reaches the app again through `cx.update`; it starts once the current event is handled. `app.run_in_background(work)` answers a task with the work's result; on WaOS a program has one thread, so the work runs there too, after the current event, and long work still holds the UI up: work that long runs on a worker instead ([Workers](/docs/guide/workers)), started from a task. `Timer::new(app, duration, listener)` calls the listener once, after `duration`, and `cancel` stops it. A callback from outside the app hands it work through `AsyncApp::post`, on the `AsyncApp` that `app.to_async()` answers.

```rust
let counting = app.run_in_background(move || count_words(&text));
app.spawn(async move |cx| {
    let n = counting.await;
    cx.update(|app| words.update(app, |words, cx| { *words = n; cx.notify(); }));
});
let hiding = Timer::new(app, Duration::from_secs(3), Listener::new(hide));
```

## Testing
The logic and state layers ([State](#state)) are tested with `cargo test` on this computer, with no display: the logic as plain Rust, and the state under an `AppCell`, which holds an `App`. `cell.checkpoint()` runs the tasks and posts that are ready, and `cell.elapse(duration)` moves the app's clock on, firing the timers that come due and running what they start:

```rust
#[test]
fn a_timer_adds_one() {
    let cell = AppCell::new();
    let tally = cell.borrow_mut().new_entity(|_cx| Tally::default());
    let adding = tally.clone();
    Timer::new(&mut cell.borrow_mut(), Duration::from_secs(3), Listener::new(move |app| adding.update(app, |tally, _cx| tally.add())));
    cell.elapse(Duration::from_secs(3));
    assert_eq!(tally.read(&cell.borrow()).count, 1);
}
```
To see the app itself, `cargo waos run` it: `cargo waos screenshot` writes each window's picture, `cargo waos tap`, `press`, `drag`, `type`, `key` and `scroll` act at a point in its pixels, `cargo waos resize` sizes its window, and `cargo waos set` answers ahead what WaOS would ask its user, as [the agent's playbook](/agents.md) says.
