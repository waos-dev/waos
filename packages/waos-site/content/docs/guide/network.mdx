The network as WASI gives it: an HTTP client, `wasdk::http`, WASI 0.3's, whose requests a program awaits; sockets a program awaits, `wasdk::sockets`, WASI 0.3's; and the sockets of Rust's `std::net`, the same WASI 0.3 sockets, which block the program, its window with it, while they wait. What a program reaches is the user's to set in its settings in WaOS: the network, on for any domain unless the user limits it to some, and the local network (this computer, the local network and listening for connections), off unless the user turns it on. `localhost` and every name under it, such as `app.localhost`, are this computer on every system, as in a browser: WaOS answers them with `::1` and `127.0.0.1` without asking the system, so they fall under the local network, whatever domains the user limits the network to. WaOS sends HTTP through the system's proxy and checks a server's certificate as the system does; a program that brings its own TLS checks a server's chain with the system through `trust`.

## With wasdk

A GET, its status, a header and its body:

```rust
use wasdk::http::client;
use wasdk::http::types::{ErrorCode, Fields, Request, Response, Scheme};
use wasdk::wit_future;

/// Asks `host` for `path` over HTTPS: the status, the content type, and the body.
async fn get(host: &str, path: &str) -> Result<(u16, Option<String>, Vec<u8>), ErrorCode> {
    let headers = Fields::new();
    headers.append("accept", b"application/json").unwrap();
    // The request sends no trailers: the future answers Ok(None) once its writer is dropped.
    let (_, no_trailers) = wit_future::new(|| Ok(None));
    // `_sent` resolves once the request has gone, which is after `send`: never await it first.
    let (request, _sent) = Request::new(headers, None, no_trailers, None);
    request.set_scheme(Some(&Scheme::Https)).unwrap();
    request.set_authority(Some(host)).unwrap();
    request.set_path_with_query(Some(path)).unwrap();

    let response = client::send(request).await?;
    let status = response.get_status_code();
    let content_type = response.get_headers().get("content-type").into_iter().next();
    let content_type = content_type.map(|value| String::from_utf8_lossy(&value).into_owned());
    let (_, read) = wit_future::new(|| Ok(()));
    let (body, trailers) = Response::consume_body(response, read);
    let bytes = body.collect().await;
    // The body came whole, or the server broke off.
    trailers.await?;
    Ok((status, content_type, bytes))
}
```
> Neither future of `Request::new` is the request's answer: `_sent` resolves only after `client::send` has sent the request, and the trailers' writer is never written, only dropped. Awaiting or writing either one first waits forever, with no error.

> This is `wasi:http` 0.3. `outgoing_handler`, `OutgoingRequest`, `IncomingBody` and the `0.2` names are WASI 0.2's, and are not in `wasdk`: a request is `Request::new`, sent with `client::send`, and its body is `Response::consume_body`'s stream.

A request whose future is dropped before it resolves is cancelled, its connection closed; to give up after a time, race `client::send` against `monotonic_clock::wait_for`. A body the program sends is a stream it writes, as `wit_stream::new` makes one; once a write comes back with something unwritten, the server is no longer reading, and a further write traps.

Sockets, awaited through `wasdk::sockets`, or blocking through `std::net`:

```rust
// wasdk::sockets: a connection, awaited
let socket = TcpSocket::create(IpAddressFamily::Ipv4)?;
socket.connect(address).await?;
let (mut received, _) = socket.receive();

// std::net: blocks until it is done
let mut stream = TcpStream::connect(("example.com", 80))?;
```

## With Waft

Make the request from a task, so the window goes on drawing while it is out, and hand the answer to an entity:

```rust
let forecast = self.forecast.clone();
app.spawn(async move |cx| {
    let answer = get("api.example.com", "/forecast").await;
    cx.update(|app| forecast.update(app, |forecast, cx| {
        forecast.answer = Some(answer.map(|(_, _, body)| body));
        cx.notify();
    }));
});
```
Waft has an HTTP client of its own, `app.platform().http()`, which WaOS does not serve yet; once it does, Waft apps will use it, and `NetworkImage` with it.

## Where it's missing

WaOS answers a redirect rather than following it: the program reads its `location` and asks again, if it wants to. A request the user's settings refuse fails with `HttpRequestDenied` before anything is sent, a server whose certificate the system does not trust with `TlsCertificateError`; a lookup or a connection they refuse fails with `AccessDenied` through `wasdk::sockets` and `PermissionDenied` through `std::net`. Under a rule of some domains, an address with no name is refused. A switch turned off refuses new connections and requests; one already open stays. `permissions::network().request()` opens the switch's page in WaOS's settings for the user.

## Interface

`wasi:http/client@0.3.0` and `wasi:sockets@0.3.0`, with [`wasdk:platform/trust`](/docs/reference/wasdk-platform/trust) and the switches in [`wasdk:platform/permissions`](/docs/reference/wasdk-platform/permissions)
