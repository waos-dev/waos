**Program.** An app for WaOS: one WebAssembly component, written in Rust with wasdk, usually with Waft for its UI. The same file runs wherever WaOS runs. It starts with nothing, and reaches only what WaOS gives it.

**WaOS.** What runs programs: the WaOS app on macOS, Windows, Linux and Android, with iPhone next, or any app that embeds the `waos` engine. Each program runs on a thread of its own, compiled to the machine's code.

**View.** A rectangle of physical pixels a program draws in with the GPU, through wgpu. On a desktop, and on Android, a program asks for a window for each view it wants; in WaOS's tabs on a phone it is given its tab's screen. A view's events (pointer, keys, text input, frames) arrive on one stream.

**Window.** What holds a view: on a desktop a real window of the system's, with its title bar, size limits and menus, and on Android a task of its own, a card in Recents. An installed program is an app of its own: on macOS with its own Dock icon, and on Windows and Linux with its own taskbar or dock button, which can be pinned and starts it with WaOS closed, and its own entry in the Start menu or the app grid.

**Capabilities.** What a program uses beyond its views: files, network, fonts, processes, media players, cameras, audio, menus, file dialogs, notifications, clipboard. Each is an interface; one a platform lacks is absent, and the program goes on without it.

**Permissions.** A program gets no more than the user gives it. Its own `/data`, `/cache` and `/tmp`, a file the user picks, sound, menus and dialogs are free. Notifications, the camera and the microphone ask at first use. The network (on by default), the local network (off) and folders (none) are switches in the program's settings, and a machine to run commands on is one the user picks when the program asks. Every question WaOS asks has a row in the program's settings, which can hold an answer set ahead: allow or don't allow, a simulated camera or microphone, a path for a file dialog, a machine for the picker. A development run is the program's development install, `<id>.development`, a program of its own, so it has its own settings and data, apart from the program as published.

**The program's life.** A program is always in one of four states, each heard on `state-changes` in `lifecycle`: `resumed` while its user works in it, `inactive` while another program has the input, `hidden` when nothing of it shows — the moment to save to `/data` what it must not lose and let go of what it can make again — and `paused`, the platform itself in the background. From `hidden` on, the platform may stop the program where it stands, without another word, or end it: a stopped program goes on from where it stopped when its user comes back, and an ended one starts again from `/data`. WaOS never stops a program while it is audible or recording.

> When a frozen program thaws, its monotonic clock has jumped by the time it was frozen, so periodic work should not replay the periods it missed: Waft's `Timer::periodic` fires once and its `tick` jumps, as Dart's VM does; GPUI's timers are one-shot and fire once; Bevy caps a frame's delta; tokio's `interval` replays every missed tick unless given `MissedTickBehavior::Skip` (or `Delay`).

## Reading WIT signatures in Rust

`wasdk` re-exports the Rust bindings `wit-bindgen` generates directly from the WIT interfaces in the [reference](/docs/reference). One rule accounts for most parameter mismatches: **`async func` takes owned values (`String`, `Vec<T>`), while plain `func` borrows (`&str`, `&[T]`).** An async call produces a future that may outlive the caller's stack frame, so `wit-bindgen` generates owned arguments (`opener.open_link("https://example.com".into()).await`, `terminal.write(bytes).await`), whereas a synchronous call borrows its inputs (`config.set_title("Notes")`, `command.add_argument("status")`). A WIT `borrow<T>` resource parameter stays `&T` in both.

## The crates

An app names a few crates; `waos new` adds the first four and one kit.

| Crate | What it holds |
| --- | --- |
| `wasdk` | The platform: a module for each interface of the [reference](/docs/reference), as `wasdk::file_dialogs`; WASI's HTTP, sockets, clocks and files, as `wasdk::http`; `#[wasdk::main]`, `#[wasdk::worker]`, `spawn` and `block_on`. |
| `wasdk-adapter-waft` | `run`, which starts a Waft app on WaOS. |
| `waft` | Waft for an app: the widgets, `App`, `Entity`, `Ref`, `Handle`, `Timer`, `Listener`, `CustomPainter`, `TextPainter`, `PaintingBinding`, the painting and geometry types (`EdgeInsetsGeometry`, `Color`, `Size`, `Rect`, `TextStyle`, `PaintingStyle`, `Stroke`), `WindowConfig`, `MultiViewApp` and `run_app_with`. `waft::ui` is the engine's layer under it, with the platform's own types: `OpenOptions`, `PickedFile`, `Notification`, `CameraOutputs`, `Canvas`, `Paint`, `Path`. |
| `waft-widgets` | The widgets `waft` re-exports, named directly for what `waft` shadows: the pointer `Listener` widget is `waft_widgets::Listener`. |
| `waft-winui`, `waft-cupertino`, `waft-material` | A kit's controls and theme ([The kits](https://waft.rs/docs/kits)): `waft_winui::Button`, not `waft::Button`. |
| `waft-markdown` | Markdown parsing and rendering widgets (`Markdown`, `MarkdownBody`, `MarkdownStyleSheet`) for Waft. Added by hand. |
| `waft-services` | Keys (`LogicalKeyboardKey`), the clipboard and text input's services. Added by hand. |
| `waft-rendering` | Lower-level render objects beyond what `waft` re-exports (`CustomPainter` is already in `waft`). Added by hand. |
| `wasdk-wgpu` | wgpu 30's backend in WaOS, for an app that draws with the GPU itself ([GPU](/docs/guide/webgpu)). Added by hand. |

`use waft::*;` and the kit's `use waft_winui::*;` bring in what most code names, as the template has them.
