# waos-window

A program's window process on macOS, where each running program's windows are an app of its own (`docs/proposals/2026-10-29-macos-apps.md`): an Waft app holding one program's windows, `waos-program-window`'s, while the engine stays in WaOS. It is WaOS's window library, which every program's app bundle loads with its loader, as Chrome's app shims load the Chrome framework.

- **Takes:** `waos-program-window`, the windows and a program's menu and notification as Waft's; `waos-window-messages`, what it and WaOS say to each other, over Mach; `waos` and `waos-package`, for the program's records and its id; Waft, for the app, its menu bar, context menus, file dialogs and notifications, the pointer, keys and cursor of a prompt's dialog, and its macOS host, which shows WaOS's layers on a canvas; Foundation and AppKit, for what the bundle says, WaOS started through Launch Services, the app brought forward as a window that takes the focus or a file dialog opens, and the user's attention asked for while a prompt's dialog shows in the background; Core Animation, for the `CALayerHost` the layers are shown in.
- **Provides:** `libwaos_window.dylib`, the window library, whose entry is `waos_window_main_v1`; and `waos-program-loader`, the executable every program's bundle carries a copy of.
- **Used by:** each program's app bundle, which WaOS writes (`apps/waos`, `logic::program_apps`).

```sh
cargo build -p waos-window      # target/debug/libwaos_window.dylib and target/debug/waos-program-loader
```

**The loader** (`src/bin/waos-program-loader`) reads `WaOSWindowLibrary` from its bundle's `Info.plist`, `dlopen`s the library and calls its entry, so the process keeps the bundle's identity everywhere the system looks: Launch Services, `NSBundle`, its notification center, its About (measured: a generated, ad-hoc-signed bundle gave the process its own identity in Launch Services, `NSBundle`, `NSRunningApplication` and its own notification center, under `dev.waos.program.<id>`). It is one small executable for every program: a WaOS update changes the window code without rewriting the bundles, and the entry's name carries its version, so a library that changes what it expects renames it, a bundle's older loader finds none and ends, and WaOS rebuilds the bundle.

**The window process** (`src/window_process.rs`) reads which program it is, WaOS's data folder and where WaOS is from the bundle (`os::bundle_info`), starts its Waft app with no window, and on a thread of its own finds WaOS (`finding_waos`): the one answering at the bootstrap name of its data folder; for an app the user opened alone, from the Dock or the Finder, with none answering, a WaOS it starts hidden with its launcher closed (`os::starting_waos`), then looks for every 100 ms for up to a minute, as Chrome's shim does (`FindOrLaunchChrome`, `PollForChromeReady`). An app WaOS launched, told so by `--launched-by-waos`, starts none. It then says hello: which program it is, why it was launched, and what the system opened it with so far, with a port of its own. WaOS answers `Welcome`, with a port of the connection's, and the program's name; or `Refused`, and the app quits. Welcomed, it opens each window the program asks for, a window that takes the focus asking macOS to bring the app forward as it opens (`os::activation`: `-[NSApplication activate]`, macOS's cooperative activation, which the system honours when the app in front yielded to it, as WaOS yields it as it asks for the window; WaOS launches the app in the background, so nothing else brings it forward but the user), its canvas showing what the program's view shows, which stays in WaOS: the request names WaOS's layer context for the view, and the canvas shows it in a `CALayerHost` (`os::layer_host`, Core Animation's private class, declared and checked at run time as Chrome declares and checks it in `ui/base/cocoa/remote_layer_api`) through Waft's `MacOs::show_system_layer`, so the window process draws nothing of its own (decision 5 of the proposal); a new size shows only with the program's picture at it (decision 55 of `docs/proposals/2026-10-17-the-waos-project.md`): winit hands the window each step of a resize inside AppKit's step, before macOS shows the new size (a frame the program sets, which AppKit changes inside one of winit's calls, later in that turn of the run loop, before Core Animation commits it), and the window sends the size to WaOS with a fence of the window's transaction that commits it (`-[CAContext createFencePort]` on the window's context, as WebKit's UI process makes one in `createFence`) and waits there, its main thread blocked with no timeout, until WaOS says, after it sent the size, that the program's picture at that size is shown (`PictureShown`), WaOS having laid its layers out at that size with that picture under the fence, or at once where the picture it shows is of that size already, so the window's new size and the picture show together, as Flutter's macOS embedder waits in its view's `setFrameSize:` (`ResizeSynchronizer.swift`); the connection's thread records each picture WaOS says is shown, and what else ends the wait, before it hands anything to the main thread (`resize_waits`): the program's end and WaOS's going, and a request WaOS makes on the program's behalf whose answer the program awaits and the app gives from its main thread (a window to open, a prompt's dialog to show, a context menu, a file dialog, a notification to post, macOS's question for the program's notifications), since the program may wait for that answer before it draws, so the app cannot wait for its picture; the window then shows its new size without the picture at it, and no resize waits until the app answers, while one-way calls (a view's cursor, focus, text input or window, the menu bar) end nothing; while a window waits, the app's other windows and its menus wait with it, as a busy Mac app's do; nothing waits before a view's first picture, which WaOS says is shown as it shows it, nor while WaOS may serve the view no frames, out of sight (off screen or occluded, which the window reports apart) or on no screen as the window last reported it, since no picture would come, an occluded window waiting for nothing even while a tool watches the program, when WaOS serves it frames (decision 63); and a fence goes only with a size the window waits at, since WaOS keeps it until the picture; and it links each window to the program through WaOS (`program_link`): a view added is `WindowOpened`, with whether its window has size limits, whether it is maximized and what the system's settings say a double-click on a title bar does, what a window reports a `ViewReport`, a key a `Key` answered later by `KeyReplied`, input with the system's own stamps; and the program's calls on a view, arriving as `ViewCall`s, go to the window's queue (`connection`). A program's move of its window from a press (`drag`, decision 61 of `docs/proposals/2026-10-17-the-waos-project.md`) comes back after the press it heard, as soon as the program handles it, and is carried out from a wake of the main thread's loop outside any event's dispatch, where AppKit's current event is still the last the app dequeued: the press's own mouse-down, or the latest drag of it once the pointer moved, which Waft's host hands `performWindowDragWithEvent:` through winit, as Tauri does for a press in its web view; one that comes after the press ended moves nothing (measured: `currentEvent` is the last event the app dequeued, so a call outside a press does nothing). What the system opens the app with after the hello goes to WaOS as `Opened`. When the program ends, or WaOS goes, the windows close and the app quits.

**WaOS's prompts for the program** (`src/prompt_dialogs.rs`, decision 9 of the proposal) show in dialog windows of their own in the program's app, drawn in WaOS: a program may have several windows or none, so a prompt goes on none of them. WaOS sends `ShowPrompt` with the dialog's size and the layer context it draws the prompt in; the window process asks Waft for a window of that size, hidden, titled with the program's name, and once it arrives centres it on the screen of the program's front window, the focused one or else the last to arrive, or on the main screen while the program has none (`src/dialog_frame.rs`), and shows it, its canvas showing WaOS's context as a program's view's canvas does (`hosted_layers`), so the dialog too draws nothing of its own. Showing it leaves the app where it is: an app in the background asks for the user's attention instead (`os::attention`, AppKit's `requestUserAttention:`, informational, which bounces the Dock icon once), and lets that request go with the dialog. What Waft's host reports of the dialog's view goes back as the prompt's reports: its metrics as it is shown and as they change, whether it is in sight, its focus, and from its canvas (`src/prompt_canvas.rs`) its pointers, as the reports a host gives of a view (`src/prompt_pointers.rs`: a pointer added before its first report and removed once, a touch removed as it lifts), and every key, which WaOS's framework takes. The cursor over the canvas is left to the system, as Waft leaves it over a platform view, and WaOS's view's cursor and focus requests go to the dialog's view's host. `HidePrompt` closes the dialog; a dialog that goes otherwise, when the user closes it or no window could be made for it, is reported `Closed`. The process's views are built by one `MultiViewApp` from what each is, a window of the program's (`waos-program-window`'s `ProgramWindows::content_of`) or a prompt's dialog (`PromptDialogs::content_of`), each reporting its window's changes back, and a request to close one goes to what it shows.

**The program's menus** (`src/program_menus.rs`, decision 10 of the proposal) are its app's, since macOS shows the menu bar of the app in front. WaOS sends the program's bar whole, as the program set it (`SetMenuBar`), and the window process shows it through its Waft host's menu bar, each entry keeping the id the program gave it; a choice of one of the program's own items goes back to WaOS by that id (`MenuBarChosen`). Until WaOS sends a bar, as for a program that sets none, the host shows its standard one. The items the platform provides are the host's to carry out: hide, minimize, zoom, full screen and bring all to front act on the app's own windows, which are the program's, and hide others and show all on the other apps, WaOS among them; Edit's reach the focused view, whose edit events go to WaOS as the view's other reports do, and a key the program leaves is offered to the bar, so its shortcuts choose its items. WaOS asks for a context menu by an id of its own, naming the window of the view and the point in the view's physical pixels (`ShowContextMenu`); the window process opens it through its host at that point, in the view's logical pixels, and answers once it closes, with the item chosen or none (`ContextMenuClosed`), at once with none where no window shows that view.

**The program's file dialogs** (`src/program_file_dialogs.rs`, decisions 13 and 15 of the proposal) open in its app, the system's own panels, as a sheet on the program's window, which a dialog shown in WaOS could not be. WaOS asks for one by an id of its own, with what it offers as the engine's options and the window of the view the program named, or none (`OpenFileDialog`); the window process opens it through its host, a sheet on that window's view, or on its own where WaOS names none or that window is gone, as WaOS's own dialogs open, and brings the app forward as it shows (`os::activation`), since WaOS launches the app in the background for a program that asks for a dialog with no app running. It answers once the dialog closes, with the paths on the machine the user picked, none when the user cancelled (`FileDialogClosed`), at once with why where the host has no file dialogs. WaOS mounts the paths for the program as they are: the window process is WaOS's own code, checked at its hello, and decides nothing of what the program may reach, the user picks and the program names no path. A pick the system gives without a path, which macOS never does, fails the dialog.

**Quitting the app asks the program** (`src/program_quit.rs`, decision 12 of the proposal): asked by macOS to quit, from its menu, the Dock or by logging out, Waft's host asks the app, which answers later; the window process sends `QuitRequested`, and WaOS asks the program as its own Quit does and answers with the program's answer (`QuitAnswered`): exit, and the app quits as the program ends; cancel, and both go on. Until WaOS welcomes the app, its host quits it as any app's, and every quit still waiting when the app ends is answered exit. About is the host's, macOS's standard panel, which reads the name, version and icon of the program's bundle; the items the host provides for the app are titled with the bundle's name.

**The program's notifications** (`src/program_notifications.rs`, decision 14 of the proposal) are posted by its app, through its Waft host's, under the app's bundle, so they show under the program's name and icon and macOS holds a scheduled one under the bundle whether or not the app runs; each keeps the program's own id and title, the bundle being the program's alone, an action answered by typing made through the host's replies. WaOS asks for each post or schedule by an id of its own, with the program's notification and its time, none for now (`PostNotification`), and the window process carries them out in the order asked, answering each once the system has it, or why not (`NotificationPosted`): `denied` where macOS does not let the app notify, and why where the host has no notifications. macOS's own question for the app is put through the host's `NotificationPermission`, which asks the user only if they were never asked: when WaOS asks for it (`RequestNotificationPermission`), which the engine does after WaOS's own question, answered with whether macOS refuses the program (`NotificationPermissionAnswered`), and before the first post or schedule, for a program allowed in WaOS's settings that never asks. Whether macOS refuses the program its notifications goes to WaOS too (`NotificationPermission`), read from the host's permission without asking: as WaOS welcomes the app, after the question before the first post, each time the host says the app is resumed, the user having perhaps changed it in System Settings while the app was away, as Chromium's notification service reads it again each time its app becomes active, and each time WaOS asks (`ReadNotificationPermission`), which it does as WaOS itself comes to the front, since a user WaOS's settings page sent to System Settings comes back to WaOS, not to the app. A removal goes by the program's own id (`RemoveNotification`). A click on one of the program's notifications, or on one of its actions, or a reply, goes to WaOS as the program hears it (`NotificationActivated`); one before WaOS welcomed the app waits, and when the user's click launched the app while it did not run, the first is the reason its hello gives, so WaOS runs the program and hands it the click; the rest go once WaOS welcomed it.

A system without the class and methods a host needs has no window process: it ends at once. Waft's macOS host leaves activation to macOS and makes its GPU device only once a view paints something of its own (decision 5 of the proposal), so a window process that only places layers never draws.

The window library links the engine's crate for the program's records, which cross as they are; the linker leaves out what the window process does not reach.
