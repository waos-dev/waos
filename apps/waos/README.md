# waos-app

The WaOS app: the desktop and phone shells in Waft, with an entry per OS. It embeds the engine, gives each program this computer's capabilities, and implements the shell's traits: where views go, the compositor programs' layers are made on (Waft's, where it has one), prompts, the clipboard, file dialogs, menu bars, the system's opener, its notifications, its players, its reading of media, its image codecs, its frame readers and its cameras, the picker of a sound's output and what shows who records, and with what, the picker of a machine. A desktop's shell gives a program no view at start and makes windows on request, and so does Android's, each window a task of its own; a phone's deck gives each program in it its tab's view and refuses requests.

- **Takes:** `waos`, the engine; `waos-local`, this computer's capabilities; `waos-store`, its library of installed programs, and `waos-package`, the packages and listings the store reads; `waos-dev-protocol`, what `cargo waos` sends it; `waos-program-window`, the programs' windows it shows in its own process; `waos-window-messages`, a program's calls on a view as values, which a phone's tab queues for its view and which it and a program's app say to each other on macOS, over Mach; Waft, for its UI, with `waft-winui`'s Fluent controls and `waft-cupertino`'s widgets for the library's two layouts, Waft's winit host for what only macOS offers (WaOS's Dock icon clicked, hiding the app) and what only Windows offers (posting a program's notifications as the program), for its `CoreVideoFrame`, which a program's hardware buffer goes to Waft's codecs as, and in the tests for its Image I/O codecs without the event loop, `waft-single-instance`, which keeps one instance of WaOS and hands a later launch's activation token or right to the front to it; `png`, for the programs' icons on their windows and `cargo waos screenshot`'s pictures; `image`, for a program's icon scaled to each size of its `.ico` on Windows and to its shortcut's on Android; on Windows `windows-sys`, for the shell's known folders, and `windows`, for a program's Start menu shortcut; and on Android `jni`, for the app's cache folder, `ndk`, for the simulated camera's `AHardwareBuffer`s, `ndk-sys`, for the system's log, Waft's Android host, for its `AndroidHardwareBuffer`, which a program's hardware buffer goes to Waft's codecs as, and its `AndroidVideoFrame`, which a camera's frame comes to the engine from, `rustls-platform-verifier`, which is handed the application, and two Android libraries in `android/`, its Kotlin half and Kotlin's standard library.
- **Provides:** the WaOS app's executable, `waos`, which a person installs programs in and runs them from, and the library it is, which `cargo waft` bundles as `WaOS.app`.
- **Used by:** people, `cargo waos run`, `cargo waos screenshot`, `tap`, `press`, `drag`, `type`, `key` and `scroll`, and `waos open`, which is this executable.

## The app

WaOS is in the shape Waft's CLI builds an app from: the app is the library (`src/lib.rs`, a `cdylib` and an `rlib`), whose `main` is the entry, and `src/main.rs` only calls it. `[package.metadata.waft]` gives the bundle its identifier, `dev.waos.app`, its name, WaOS, its icon (`assets/icon.png`, 1024 px), and its one document type, the `.wapk`, WaOS's own (`dev.waos.wapk`), which the bundle declares and opens first, so a package double-clicked or opened with WaOS from the Finder reaches the library; the CLI signs the bundle with the hardened runtime and `macos/waos.entitlements`, which allows the executable memory wasmtime's compiled code needs and the mapping of code compiled earlier; without them the system kills WaOS.app as soon as a program starts in it. `[package.metadata.waft.macos]` also names what the bundle carries for the programs' apps, which the CLI builds with WaOS and signs before the bundle: `waos-window`'s loader in `Contents/Helpers` and its window library in `Contents/Frameworks` (decision 6 of `docs/proposals/2026-10-29-macos-apps.md`).

```sh
cargo waft run -p waos-app                    # builds WaOS.app and opens it
cargo waft build macos -p waos-app            # the bundle, under target/waft/macos/release
open target/waft/macos/release/WaOS.app
cargo run -p waos-app -- phone                 # the deck in a window of a phone's size, programs in its tabs
cargo run -p waos-app -- --launcher-closed     # the launcher closed at launch, as cargo waos run starts WaOS
cargo run -p waos-app -- open notes.md --program dev.waos.examples.opener   # files opened with a program
cargo run -p waos-app -- notes.wapk            # files opened with WaOS, as Windows and Linux open a file with an app
```

On Windows the `waos` executable is a GUI program (`#![windows_subsystem = "windows"]` in `src/main.rs`), so no console window opens with it, from the Start menu or a file opened with it; its entry first attaches it to the console of whatever started it, where that has one (Waft's `DefaultEmbedder::attach_to_parent_console`), so its log and `waos open`'s answers show in the terminal it was run from, and a standard stream the terminal redirected stays redirected. `cargo waos run` starts it with both redirected, so it stays apart from that terminal's console and its Ctrl-C.

Built so far, the third and fourth parts of step 5a of the design's work order, the desktop shell and quitting, step 6's library, the clipboard and the sound of step 7, and the menus of step 8. WaOS's own window is its launcher, beside a Dock icon and a menu with Quit. It starts the engine with what Waft reports of the machine and keeps it current (the screens, with their ids, names, sizes, scales, refresh rates, frames and visible frames, at each of Waft's metrics changes; light or dark; the languages; the caption style, where Waft's platform has caption settings, at each change Waft tells; and the user's time zone, which Waft does not report, by its IANA name as the system keeps it, read through jiff on every system (`os::time_zone`) and read again at each change the system announces where WaOS hears one: on macOS Foundation's `NSSystemTimeZoneDidChangeNotification` (`os::watch_time_zone`); on Android, Windows and Linux no change is heard yet, so a program keeps the zone WaOS read as it started until WaOS starts again, Android's `ACTION_TIMEZONE_CHANGED` needing a Java `BroadcastReceiver` the app has none of, Windows' `WM_TIMECHANGE` a window loop that is Waft's, and Linux's timedate1 `Timezone` property or a watch on `/etc/localtime` not built), and listens for `cargo waos run` at `waos_dev_protocol::listener_path()`. Each connection begins with a `Hello` exchange (`accept_hello`, protocol major `MAJOR`), refusing a mismatched major or legacy WaOS 0.2 client, and carries one request. A run (`dev_run`) checks first whether its environment can be prepared (`Upload::Refused` if not), then answers `Upload::Have` from the component's sidecar digest without blocking the async thread (or `Upload::Send` to receive it in parts). The component sent is kept under the app's caches, named by its program's id, and left as it is when it comes again unchanged, so its compiled code stays current and a second run of it compiles nothing, loaded off the main thread and run on a thread of its own as the program its id names (decision 11 of `docs/proposals/2026-10-23-permissions.md`), with that program's settings and its own folders, installed or not, its own id as `argv[0]` followed by the run's arguments, and the variables that run alone adds, as `cargo waos run --env NAME=VALUE` gave them (decision 68), and this computer's capabilities (`waos_local::LocalCapabilities`, made once at the start, so every program shares one font manager), its output going back as `Output` frames on the connection — bounded to 1 MiB in flight through async backpressure (`poll_write` returning `Pending` with a waker rather than blocking the program's thread) — `Started` first and `Ended` last with how it ended; a component that cannot load or run, or whose folders cannot be made, is `Refused` with why; the run is watched from its start while its connection is open (`RunningProgram::watch`, the design's decision 63), so its windows count as in sight though other windows cover them, and a tool's screenshot and input meet windows that draw, a minimized one staying out of sight; the connection closing ends the watch and stops the program; a run of an id already running, sent or opened from the library, stops that one first, and a connection running it hears `Ended(Replaced)`. The app logs each run's end with how long it ran and the frames it presented. Quit asks every program running whether it may end (`request_exit`, the engine thawing each while it owes the answer) and waits for every answer, with no time limit, as the experiment's desktop did: if every one agreed, WaOS stops every run, waits for the connections to hear `Ended(Stopped)`, removes the socket file, and quits; if any refused, nothing closes. A second Quit while the programs decide asks them again, each quit decided on its own, so a program decides what a second Quit means; a program that never answers keeps WaOS open until it is stopped, which its run's Ctrl-C does; a program that ends while asked has answered exit. `RUST_LOG` picks what the app and the engine write to standard error, the app's own and what every program writes at `info` and warnings elsewhere without it (`write_traces`), and a WaOS that `cargo waos run` started writes it to `~/Library/Logs/WaOS.log`; `frames=trace` adds every step of every frame, the shell's among them. `WAOS_NATIVE_UNWIND_INFO=1` in WaOS's environment compiles programs with native unwind information, for a native profiler or debugger to walk through a program's frames: turn it on only to profile or debug programs natively, since macOS takes seconds to drop a large program with it (7 s for the gallery's debug build), and nothing else needs it; a trap's backtrace does not.

While any program's code is being compiled or any of its windows is in sight, WaOS holds one macOS activity (`state::app_nap_exemption`, Waft's `MacOs::begin_user_activity`), so App Nap does not run its threads at background priority, and drops it when neither is; on another system nothing is held. An Inspector compile took 5 s with it against 9 min 15 s without (measured).

On macOS each running program's windows are an app of its own (`logic::program_apps`, `docs/proposals/2026-10-29-macos-apps.md`), as Chrome's web apps are app shims. Each program has a bundle, `dev.waos.program.<id>`: an installed program's in `~/Applications/WaOS Programs`, named after it, written from its package's name, version and icon at install, rewritten at an update and deleted at removal, what the system granted it reset first; a program run in development's in `~/Library/Caches/WaOS/apps`, named by its id, written at its first launch. Each is a copy of WaOS's loader (`apps/waos-window`), signed ad hoc with the hardened runtime and the leave to load WaOS's window library, and registered with Launch Services (`os::program_bundle`). WaOS keeps where each is and the code hash it was signed with in `program-apps.toml` in its data folder, each hash with its HMAC-SHA256 under a key WaOS keeps in the Keychain (`WaOS Safe Storage`, made on first use; `os::keychain`), as Chrome's `AppShimRegistry` keeps `cdhash_hmac`, and the system's version: when the system's version changes, every bundle is rebuilt, since Gatekeeper then distrusts ad-hoc signatures made before; and with each bundle what it was made from, the SHA-256 of the loader it carries a copy of and the paths of the window library and the WaOS it names (`bundles::made_from`): a bundle made from other files, an older WaOS's loader or another build's library, is written again at the next launch through WaOS, and as WaOS starts, as Chrome rewrites its app shims when Chrome updates. A program's app of another window protocol than this WaOS's is refused in one plain line of WaOS's log that names both protocols, and answered in WaOS's own, which it cannot read, so it ends rather than waits. Everything that reaches a program's app goes through one getter (decision 15 of the proposal, `logic::program_apps::app_reach`): the app is launched through Launch Services the first time something needs it, a window, a file dialog, a prompt or a notification for now, with no window of its own and not brought forward (`os::launch_services`), and everything that asks while it comes waits for that launch and gets the app in the order it asked; what opens only at a view the app already shows, or is sent as the app connects, takes the app only while it runs. What the user must see brings the app forward as it shows, by macOS's cooperative activation: as WaOS asks for a window that takes the focus, or a file dialog, it yields its activation to the app's bundle (`os::activation`, `-[NSApplication yieldActivationToApplicationWithBundleIdentifier:]`, queued on the main thread), which Launch Services did for it when it launched an app brought forward, and the app takes it as the window or the dialog opens; while WaOS is not in front the system decides, so a launch for anything else stays in the background. WaOS checks in the bootstrap name of its data folder, and every app's hello arrives there with the app's own port: WaOS reads the sender's audit token from the message, checks the record's HMAC, then the process's code hash against the one it kept (`os::code_signature`), and answers `Welcome` with a port of the connection's, or `Refused` with why, rebuilding a bundle whose code is not the one it signed or whose record the HMAC does not vouch for. A development build's signature changes at each build, so the Keychain asks once per build whether it may read the key, as it asks Chrome's own developers. An app WaOS launched is its running program's; an app the user opened alone, from the Dock or the Finder, which starts WaOS hidden when none answers, has its program run as the library opens it, with what the system opened the app with. From then on the program's windows open in its app, each view added to the program as the app reports it, the program's calls on it sent there as `ViewCall`s, and what the window reports, keys among it, carried to the view (`logic::program_apps::window_process`); when the app goes, its views go with it, and when the program ends, the app is told and quits. What a view shows stays in WaOS (decision 3 of the proposal): before WaOS asks the app for a window, it makes the view's canvas on Waft's compositor, the layer the engine presents the program's hardware buffers to with the program's composition layers beneath them, as in WaOS's own windows, and a layer context of its own (`os::layer_contexts`: Core Animation's private `CAContext`, declared and checked at run time as Chrome declares and checks it in `ui/base/cocoa/remote_layer_api`), whose id the window request carries; on the main thread, WaOS places the canvas in the context's root with Waft's `MacOs::place_layer_in` at the view's size as the window opens and at each size it reports after (`logic::program_apps::canvases`, `state::program_apps`), as decision 20 of `docs/proposals/2026-10-30-native-surfaces.md` has it, and lets canvas and context go with the window. A new size shows only with the program's picture at it (decision 55 of `docs/proposals/2026-10-17-the-waos-project.md`, `logic::program_apps::canvas_pictures`): the window waits inside the resize, and sends the size with a fence of the window's transaction that commits it, which WaOS keeps until the program presents a picture of that size, matched by size alone, as Flutter's macOS embedder matches a frame to its resize; that picture goes to the main thread, where WaOS sets the fence on the context in the transaction that lays the canvas out at that size with the picture, and lets go of it, as WebKit's web and GPU processes answer its UI process's fences (`TiledCoreAnimationDrawingArea::updateGeometry`, `LayerHostingContextManager::setVideoLayerSizeFenced`); then it tells the window the picture is shown (`PictureShown`), and the window's commit, which waits for the fence, shows the new size and the picture in one frame. Keeping the fence holds no window up, since the window commits the transaction carrying it only once it stops waiting. A resize to the size of the picture shown already is answered as the canvas is laid out at it. While the program awaits its app's answer to a request WaOS made of it (a window to open, a prompt's dialog, a context menu, a file dialog, a notification's post, macOS's question for its notifications), which the app gives from the main thread the window would wait on, nothing waits: WaOS lets a fence it keeps go as it makes the request, laying the canvas out at once, as the window's wait ends when the request arrives, and lays out at once a new size reported until the app answers; nothing waits before a view's first picture, of which WaOS tells the window as it shows it, and a new size without a fence, at which nothing waits, lays the canvas out at once. Every picture after one that went to the main thread follows it there until it is shown, so the canvas shows them in the order presented. The app's window shows the context in a `CALayerHost`. A system without the classes and methods a context needs has no programs' windows, said as an error. A launch that fails, or an app that ends before its hello, has its bundle rebuilt and is launched once more; a second failure fails everything that waited, with why. WaOS's prompts for a program are shown in a dialog window of their own in its app, whether or not the program has a window open there (decisions 9 and 15 of the proposal, `state::prompt_dialogs`), each taking the getter, so a program whose app does not run has it launched, in the background, and the prompt waits for it; drawn by WaOS: WaOS makes a composition layer for the prompt and a layer context of its own, places the layer in the context's root as it places a canvas, and asks the app for a dialog of the prompt's size showing the context, which the app centres on the screen of the program's front window, or the main screen while it has none, and shows without bringing itself forward, bouncing its Dock icon from the background instead; once the dialog says its size and scale, WaOS asks Waft's view embedder for a view drawing into the layer (`ViewEmbedder::add_view`, native-surfaces decisions 33 to 36), its initial data naming the prompt; the view arrives as every view does and WaOS's one builder builds the prompt's widget in it from that data (`ui::every_window`), and from then on hands the view what the dialog reports, through Waft's view embedder: its metrics, whether it is in sight, its pointers, each device under a random number of WaOS's own while it is reported (`logic::forwarded_pointers`), since the app's host numbers its devices as WaOS's does, and its focus; its keys go to Waft's framework as its shell hands it a host's (`KeyEventManager::handle_key_data`), so they reach the prompt where the framework's focus is. The view's cursor and focus requests go to the dialog; it takes no text. A prompt answered or put away has its view removed, its dialog hidden and its context let go; a dialog that goes otherwise, closed by the user or with its app, leaves the program's question unanswered. A prompt whose app never comes is put away unanswered, as one whose dialog went. A program's menu bar and context menus are its app's (decision 10 of the proposal), since macOS shows the menu bar of the app in front: WaOS sends the app the program's bar, whole, as the engine keeps it, each time the program sets it while the app is connected and as the app connects (`SetMenuBar`), and the app shows it through its Waft host's, sending back each choice of the program's own items by its id, which reaches the program's streams of choices; a program that set none has the host's standard bar. The items the platform provides are the app's host's: hide, minimize, zoom, full screen and bring all to front act on the app's own windows, which are the program's, and Edit's reach the focused view, whose edit events cross as the view's other reports do. A context menu goes to the app with an id of its own and the window of its view (`ShowContextMenu`), at the program's point in the view's physical pixels, and the program's call is answered when the app says it closed, with the item chosen or none (`ContextMenuClosed`), at once with none for a view the app does not show, and with none for every menu still open when the app goes (`logic::program_apps::awaited_answers`). Tray icons stay WaOS's, belonging to no window. The app's About is its host's, macOS's standard panel from the program's bundle. Quitting the app asks the program (decision 12 of the proposal): the app says the user quit it (`QuitRequested`), WaOS asks the program as its own Quit does, and answers with the program's answer (`QuitAnswered`), stopping a program that agrees, whose app then quits. A program's file dialogs open in its app (decisions 13 and 15 of the proposal), not in WaOS, which could not put them on the program's window and would come to the front: each takes the getter, so a program whose app does not run has it launched, with no window, and the dialog opens there on its own; it goes to the app with an id of its own, what it offers as the engine's options, and the window of the view it is a sheet on, or none for one on its own, as for a view no window there shows (`OpenFileDialog`), and the program's call is answered when the app says it closed, with the paths on the machine the user picked (`FileDialogClosed`), which the engine mounts as it mounts the picks of WaOS's own dialogs, since the app is WaOS's own code, checked at its hello, and the program names no path; with why for a dialog whose app never came, and for every dialog still open when the app goes (`logic::program_apps::file_dialogs`). A program's notifications are posted by its app, under its bundle (decisions 14 and 15 of the proposal, `logic::program_apps::notifications`), so they show under the program's name and icon, and macOS holds a scheduled one under the bundle whether or not the app runs: each post, schedule and removal takes the getter, so a program whose app does not run has it launched, in the background with no window, and the notification goes there with an id of its own, the program's notification as the engine keeps it and its time, none for now (`PostNotification`); the program's call is answered when the app says whether the system has it (`NotificationPosted`), with why for a post whose app never came or went first, and a removal goes there by the program's own id (`RemoveNotification`). Replies and scheduling are offered from the start, since macOS's notifications have both and a program's app runs from its bundle, where Waft's host has them. macOS's own question for the app is the engine's system permission (`ShellSystemPermission`): once the user allowed the program notifications in WaOS, the engine's `request` asks it, after WaOS's own question, and the app puts it (`RequestNotificationPermission`), answering whether macOS refuses the program (`NotificationPermissionAnswered`), with nothing when the app never came or went first; the app also puts it before its first post, for a program allowed in WaOS's settings that never asks. A post macOS refuses, at its question or later in System Settings, answers `denied`, and the program reads one state, granted only while both allow: the engine reads its `notifications` permission as `denied` while macOS refuses, the user's answer in WaOS kept as the user set it, from what the app says macOS said (`logic::program_apps::window_process`): its answer to the question, its read of the permission (`NotificationPermission`) as WaOS welcomes it, after its question before a post, each time it comes to the front, as Chromium's notification service reads it again each time its app becomes active, and each time WaOS asks it to read again (`ReadNotificationPermission`), which WaOS asks of every running program's app as WaOS itself comes to the front, launching none for it (`state::program_apps`), and each post's answer, `denied` or taken. Each goes to the program, through `RunningProgram::system_notifications_refused`, and to the library (`state::program_apps`), so the program's settings page says macOS refuses it, with a button that opens System Settings at the notifications of the program's app (`os::system_settings`: `x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=dev.waos.program.<id>`, the link Chrome opens for its own), since macOS asks only once. macOS says nothing when the user changes the permission in System Settings: a refusal made or lifted there reads so from the next of these moments, and a user the settings page sent there comes back to WaOS, not to the program's app, so WaOS's coming to the front puts the page right. A click on one of the program's notifications, or a reply, comes from its app to the program (`NotificationActivated`); a click that made macOS launch the app while the program did not run comes with the app's hello as the reason it was launched, and WaOS runs the program as the library opens it and hands it the click, which it hears once it listens (`logic::program_apps::server`). WaOS looks for the window library and the loader inside WaOS.app (`Contents/Frameworks`, `Contents/Helpers`), and, run outside one, beside its executable, where `cargo build -p waos-window` leaves them. A WaOS that misses either says so as an error naming what to build, and every window a program asks for fails with it: on macOS WaOS shows no program's windows itself, there being no second route.

Elsewhere, each view a program asks for is shown in an Waft window of its own, `waos-program-window`'s, made as the program set its `window-config` (an untitled window carries the program's name; a size left to the platform is Waft's). The request goes from the program's thread to the main thread, which asks Waft for the window; when the window's view arrives the program's view is added with everything it starts with (Waft's metrics and screen for the view, how it stands, the window's frame, the request), or the request fails with why, exactly once. The window shows the view's canvas: Waft's composition layer for the view, which the engine presents the program's hardware buffers to with the program's own composition layers beneath them as its children, each made on Waft's compositor (`waos-program-window`'s `WaftCompositor`) and placed where the program's view places it (a hardware buffer's release is the layer's, which Waft's macOS host works out at the layer's next present), under the cursor the program asks for, with a focus node that takes the keyboard when the window opens, when the canvas is pressed or when the program asks, and Waft's text input as the view's. Pointer and key events go to the program converted field for field, Flutter's shapes on both sides, each pointer added before its first event and each pointer event with the modifier keys Waft's keyboard holds, so the engine tells the program of those it missed; what the input methods do goes back as the view's text input events. After the view is added, the app reports on its `ProgramView` each change Waft reports: the metrics and the screen, the window's frame, its presence (the window's focus, whether the program hid it, and whether the window is minimized or occluded), and the user's request to close the window, which the program answers by closing it or not. A view whose window closed is taken away, and the windows of a program that ended close. What the program asks of its view, its window and its text input from its own thread reaches the main thread on one queue per view, in order. The screens' refreshes the engine asks for are waits on Waft's `Platform::vsync_waiter` (`logic::vsync_waiter`): the next refresh of a screen is served at the vsync Waft's own frames on that screen are drawn at, and is reported to the engine's `screen_refreshed`, which serves the programs' views on it; a screen's id is Waft's on both sides.

The programs' clipboard is Waft's (`state::clipboard`), the platform's one clipboard, as Waft's `Platform::clipboard` gives it; where Waft's platform has none, programs have none. A program's write and read go from its thread to the main thread on one queue (`logic::clipboard_calls`). There one task carries out each write through Waft's clipboard, a promised form or file left for the program to produce each time someone pastes it (`logic::clipboard`), a file's bytes carried from the program's thread into Waft's `FileSink` on the main thread, each write answered once Waft has taken it, and answers with what Waft lists after it, which the engine keeps as what is on the clipboard; a read is of an item of Waft's latest listing, by the listing's number and its place, and fails with `changed` for an item of an earlier one. The same task lists what is on the clipboard into the engine as WaOS starts, and each time Waft says another app changed it or a copy expired and was cleared (`ServicesBinding::clipboard`), so the engine's listing is always the latest; Waft's host does not report the app's own writes. When WaOS hears of another app's copy is Waft's host's to say. On macOS it is at the moments AppKit leaves an app to look at the pasteboard's `changeCount`, as Flutter's macOS embedder looks: when WaOS is activated, and when one of its windows gains the focus. WaOS does not poll, so a copy that reaches the pasteboard while WaOS stays active, as one from another device through Universal Clipboard, reaches the programs at the next of those moments.

The programs' menus are Waft's (`state::menus`), each where Waft's platform has the place. A program's menu bar is never WaOS's: on macOS it is its app's, and so are its context menus (decision 10 of `docs/proposals/2026-10-29-macos-apps.md`, below), and the other desktops have no menu bar. WaOS's own bar (`logic::menu_bar`), its app menu, Edit and Window, every item the platform's, is set once as WaOS starts, and macOS shows it while WaOS is in front. A program's context menus in WaOS's own windows and its tray icons go from its thread to the main thread on one queue (`logic::menu_calls`); the platform's Edit commands, wherever they come from, reach the focused view, which a program's canvas sends on as its view's `copy`, `cut`, `paste` and `edit` events (`ui::edit_commands`), a paste free of the read switch. A program's context menu in WaOS's own windows opens through Waft's at its view, in the view's logical pixels, and answers the choice; its tray icon is added to Waft's tray, what the user does to it and chooses in its attached menu reported to the program, and removed when the program lets it go or ends. A program's icon is answered once Waft has made it, with the menus Waft's icon offers, or with why Waft's tray did not show it, and what the user does to it reaches the program through the listener Waft's binding keeps for the icon. The programs' file dialogs in WaOS's own windows, where a program has no app of its own, are Waft's (`state::file_dialogs`), where Waft's platform has them: a program's dialog goes from its thread to the main thread on one queue (`logic::file_dialog_calls`), with what it offers in Waft's terms, and is shown as a sheet on the window of the program's view it names; the paths the user chose go back to the engine, which mounts them. A pick the system gives without a path, which the desktop systems never do, fails. Each key goes to the program as it comes, and the canvas keeps it from the rest of WaOS, since the program answers later, on its own thread; a key going down that the program leaves is then offered to Waft's menu bar (decision 9, `MenuBar::perform_key_equivalent`), as Chrome sends on a key its page did not consume, so a ⌘C a program's text field leaves chooses Edit's Copy, which sends the view its `copy` event. Waft's macOS host keeps the latest key-downs a few seconds to find the system's event by, so a reply later than that offers nothing. Where the platform has no menu bar, as on Windows and Linux, a key the program leaves goes nowhere further.

The programs' opener is Waft's (`state::opener`), where Waft's platform has one: what a program opens goes from its thread to the main thread on one queue (`logic::opener_calls`), once the engine's rules allow it, a link of a scheme its user allowed and a file by where it is on the machine, and is handed to Waft's `Opener`, a link to the app the system picks for its scheme, a file to the app it picks for its type or shown in its file manager; the program hears whether the system handed it on, or that no app opens it.

The programs' players are Waft's (`state::media_players`), where Waft's platform has them: a player a program opens, once the engine's rules allow its source, a link whose host the program may reach or the `file:` URL of a file inside its mounts, goes to the main thread on one queue (`logic::media_player_calls`), the app's key for it in each of its calls after, its removal last as the engine lets it go, and is opened there on Waft's `Players`, which Waft controls on the main thread; its picture goes to Waft's layer behind the program's composition layer (`waos_program_window::waft_layer`), or to Waft's reader behind the program's frame reader, and what the program asks, its tracks picked among them, is asked of Waft's `MediaPlayer`. Its state, its media's metadata (`logic::player_states`) and its cues (`logic::cues`), as the media styles them, are reported into the engine's `MediaPlayerReports` as it opens and each at its change after, with where the player is, read at each change before the state, which the engine moves the program's position on from, each change heard as Waft's own `Player` hears the host's, through `changed` asked before the state is read, until the program lets the player go; an opening asked while WaOS quits is reported failed at once.

The programs' media assets are Waft's (`state::media_assets`), where Waft's platform reads media: an asset a program opens, once the engine's rules allow its source as a player's, goes to the main thread on one queue (`logic::media_asset_calls`), the app's key for it in each read after, its removal last as the engine lets it go, and is opened there on Waft's `MediaAssets`; each read is asked of Waft's `MediaAsset` there and answered back once Waft has read it, its tracks, metadata and failure in the program's terms (`logic::player_states`) and its picture as the platform's own frame, as a reader's is (`logic::frame_readers`); a read WaOS cannot answer, as it quits, fails at once.

The programs' image codecs are Waft's (`state::image_codecs`), where Waft's platform has them, their formats and whether they have hardware codecs read once as WaOS starts, as they stay the same: an image a program opens, from its bytes or from its file where the engine found it on the machine, goes to the main thread on one queue (`logic::image_codec_calls`), is opened there on Waft's `image_codecs::ImageCodecs` and kept under the app's key once it opened, what it says of itself answered back in the program's terms (`logic::image_values`), and let go at once where the program no longer waits for it; each decoding and encoding after is asked of Waft's codecs there, its key in each call and its removal last as the engine lets it go, and answered back once Waft has: pixels in the program's terms, field for field, and a hardware buffer the hardware codecs decoded as the platform's own buffer, the `IOSurface` behind Waft's `SurfaceBuffer` (`logic::hardware_buffers`); a hardware buffer the program encodes, one it drew, a decoded image or a video frame's, goes to Waft as Waft's `SurfaceBuffer` over the program's `IOSurface`. A call WaOS cannot answer, as it quits, fails at once.

The programs' frame readers are Waft's (`logic::frame_readers`), where Waft's platform hands out frames: a reader a program makes is the engine's at once, and Waft's, made on Waft's `VideoFrameReaders` on the main thread, where they are, the first time a player or a camera is given it; before that it answers no frame, as a reader fed by nothing does. The program's thread asks Waft's reader for a frame directly, as Waft's readers are read from any thread, and hands the engine the frame it answers as the platform's own: on macOS and iOS the `CVPixelBuffer` behind Waft's `CoreVideoFrame`, retained, which holds the frame as Waft's does, and on Android the RGBA8 `AHardwareBuffer` behind Waft's `AndroidVideoFrame`, a reference more on it; each with the turn and the mirror Waft's frame shows it with.

The programs' notifications are their apps' on macOS (below), and elsewhere Waft's (`state::notifications`), where Waft's platform has them: a program's post, schedule and removal go from its thread to the main thread on one queue (`logic::notification_calls`), once the engine has its user's permission for the program, and are carried out through Waft's `Notifications`. Each notification has the id `<program id>/<its id>`, which keeps two programs' same id apart and says which program a click is for (`logic::system_notifications`). On Windows an installed program's are posted as the program itself, under its identity (below), through Waft's `Windows::notifications_of`: the toast shows the program's name and icon, which its Start menu shortcut makes known to Windows, Settings › Notifications lists the program apart from WaOS, and the title is the program's own. Every other program's, a program never installed, and every program's on Linux and Android, are posted under WaOS's own name, titled after the program's name as its user knows it, `Notes: Meeting at 3`, since Waft's notification has no subtitle: GNOME files a notification under the app it finds first for the sender's process, whatever app the notification names (measured on GNOME 50), so a program's there land under WaOS or under whichever of its programs' windows GNOME finds first, as decision 30 of `docs/proposals/2026-11-13-what-six-apps-found.md` accepts. An action answered by typing is Waft's reply action. The first time any program posts or schedules one, WaOS asks the system for its own permission through Waft's `NotificationPermission`, where the system keeps one; a notification the system does not let WaOS show fails, with why, since `denied` is the program's own permission's. Whether the system takes replies and schedules is read once, as WaOS starts. A click on a notification, at WaOS's launch or while it runs, reaches the app through Waft's `App::set_notification_activated_handler`, or, for one posted as a program on Windows, through the handler WaOS gave with its notifications, and goes by its id's prefix to the program, as files opened with a program go (`logic::opening`): the one running under the id, or else the installed one, opened first, which hears the click once it listens. A click on one of a program no longer installed, whose notifications the system keeps (decision 4 of the notifications proposal), is the library's problem, which tells the user the program is no longer installed, and the library comes into sight to say so.

The programs' cameras are Waft's (`state::cameras`), where Waft's platform has them and WaOS.app says why it uses them (`CAMERA_USAGE_DECLARED`, below): a listing, a wait for the list's next change, an opening, a start and a photo a program asks for go to the main thread on one queue (`logic::camera_calls`), each with where its answer goes, and are carried out there on Waft's `Cameras`, which Waft controls on the main thread, each answered once Waft's future is. A camera is opened by its id among those Waft lists then, `unplugged` for one no longer listed, once the engine has put the camera question to the program's user and the user allowed it; Waft then asks the system for WaOS the first time: macOS, or on Android the `CAMERA` permission's question, which a second program opening a camera meanwhile waits on. Its formats are read once, as it opens, and handed to the engine with it, as a session's format is with its start; a session starts in the Waft format the program's names, found among the camera's as Waft compares them, since a format goes over and back whole (`logic::camera_values`), its preview on Waft's layer behind the program's composition layer, its frames in Waft's reader behind the program's frame reader, made on Waft's readers the first time a camera or a player is given it, and its photos at the size named. Its state, an interruption with Waft's reason where it gives one, and its two rotation angles, Waft's two methods as the program's one record, are reported into the engine's `CaptureSessionReports` as it starts and at each change after, as Waft's own `CameraSession` hears the host's, until the program lets it go; a program asking for upright frames asks Waft's camera, whose start fails `not-supported` on Android; a photo is answered once Waft's is encoded, a session that does not run failing with Waft's words for it. A camera or a session the engine lets go of, or stops waiting for, is let go on the main thread too, and a call made while WaOS quits is answered at once.

The programs' sound is this computer's, `waos_local::LocalCapabilities`' `LocalAudio`: each program's contexts play on the system's default output, which the system mixes, or on another output its user picked for it. The app's picker of outputs (`logic::prompts`' `OutputPickerOnRequest`, the shell's `audio_output_picker`) puts a program's `select-audio-output` to its user as a question like the others: a sheet over the program's windows, or in a window of its own, with the outputs the system lists, a button each, scrolling when there are many, and Cancel; the output tapped is the program's to play on for the rest of its run, and Cancel, or the program ending, answers `not-allowed`. The library shows which programs record, and with what, where macOS shows only that WaOS does (`logic::recording_indicator`, `state::recordings`): a quiet banner above the home's grid, in either layout, naming each program with a microphone open, and each with a camera running, a sentence for each device, from the moment the engine says it records with it until it stops or ends; a device of WaOS's own, for a program answered simulated, is said simulated in a sentence of its own ("Camera is using the camera (simulated)."), so nobody takes it for the machine's.

Recording is on. macOS ends an app that opens the microphone or a camera unless its bundle's `Info.plist` says why it does, and a bundle signed with the hardened runtime is refused either unless its entitlements allow it: this crate's `[package.metadata.waft.usage_descriptions]` declares the microphone, "Programs you allow can record sound.", and the camera, "Programs you allow can use the camera.", which Waft's CLI writes into WaOS.app's `Info.plist` as `NSMicrophoneUsageDescription` and `NSCameraUsageDescription` and signs in as `com.apple.security.device.audio-input` and `com.apple.security.device.camera` beside `macos/waos.entitlements`' own, and on Android the camera's as `android.permission.CAMERA` in the manifest, with the camera a feature WaOS does not require. Each declaration decides its device alone, through a constant in `src/state/mod.rs` that is true while it stands: `MICROPHONE_USAGE_DECLARED` gives the programs this computer's sound with its microphone (`LocalCapabilities::new`, else `without_microphone`), so a program's `open-microphone` asks its user the microphone question, and `CAMERA_USAGE_DECLARED` gives the engine Waft's cameras. The app gives the engine its indicator of who records wherever either is declared, and the library shows the programs recording with each.

## On Android

```sh
cargo waft build apk -p waos-app              # the .apk, for 64-bit ARM, under target/waft/android
cargo waft run -d android -p waos-app         # built, installed and started on the device or the first emulator
```

Waft's Android host loads the library and calls `android_main` (`os::android`) once for the process, on the app's own thread, which runs `android_entry::main`; activities come and go under it as views of the one app: WaOS's traces go to the system's log under the tag `waos` (`adb logcat -s waos`), since Android gives an app no standard error, what programs print among them, as on a desktop in WaOS's log; the caches are under the app's cache folder (the application's `Context.getCacheDir`, read through JNI) and the store and WaOS's preferences under its files folder; and WaOS is laid out as a phone, the deck on the screen Android gives the launcher's activity (`LibraryPlace::Phone`, which on a desktop is a window of a phone's size; see The deck).

On Android a program opens as a task of its own (decisions 1, 9, 10 and 14 of `docs/proposals/2026-11-12-phone-programs-and-library.md`), as on a desktop it opens in windows: each view it asks for, its first among them, is a window of WaOS's own (`logic::placement`, `waos-program-window`'s `ViewWindows`), which Waft's Android host makes a document activity in a task of its own, a card in Recents titled with the window's title, or the program's name where it left it untitled, and with the program's icon from its package (`logic::program_faces`). The window's initial data names the program and whether it is the program's first window or an extra one (`waos-program-window`'s `RestorableWindow`). Opening a program that runs brings its front window's task forward (`state::bring_opened_programs_forward`). The user's Back goes to the program while it handles Back, and otherwise sends its task to the background, the program running on; a card swiped away takes its view away, and a program ends with its last view, as on a desktop with its last window. Every view arrives the same way, asked for or brought back by Android, and one `MultiViewApp` at the root builds each from what it is (`ui::every_window`): a program's window, a prompt's window of its own, or WaOS's own, which carries no initial data, the library's; a request to close one goes to what it shows. A window a running program asked for is its windows', which noted the request; a card Android brings back after the process died, which no running program asked for (`state::given_views`), starts its program again with it as its first window where it is the program's first (`Library::open_restored`), and closes at once where it is an extra one, having no program state behind it; a view with no initial data is WaOS's own, where the deck is. The settings' global page offers to show programs inside WaOS instead, in the deck's tabs (decision 2), off by default, which holds for programs opened after it; the choice is kept in a small preferences file of WaOS's own (`logic::preferences`), not among the store's settings, which are what programs are granted (`state::library::programs_open`). Programs opened without the library, from a notification or with files, open as tasks too. There is no command line, no single-instance claim, no launcher (Android has no desktop), and no dev server: `cargo waos` reaches no phone yet, and Android ends an app without asking it, so there is no quit to ask the programs about. A `.wapk` opened with WaOS through an intent to view, as the Files app opens one, reaches the library, which asks whether to install it, as on a desktop: a `file:` path in WaOS's own folders as it is, and a `content:` document, which Waft hands over with no path, first read whole on the main thread's executor and copied into a folder of its own under the caches' `packages` (`logic::package_copies`), named as the document is, since a package is opened from a file and kept open until it is installed, as Android's own package installer copies what it is handed. A name that is not a plain file name is refused, and a document that cannot be read is the library's problem. The copy is removed once its question is answered, installed or not, or once it turns out not to be a package, and copies an earlier run left are removed as WaOS starts.

An installed program has a shortcut of its own on Android, by its id, where Android keeps an app's shortcuts (`logic::program_shortcuts`, `state::library::shortcuts`, `os::android`'s `shortcuts`, through Waft's Android host's `Shortcuts`): a program installed for the first time asks the launcher to put it on the home screen, which asks the user, and so does Add to Home Screen on its held icon, offered where the launcher pins shortcuts; each program opened goes first among the recent programs on WaOS's own icon's menu, from where the user can drag it onto the home screen too. A shortcut has the program's name and its package's icon as an adaptive icon, the square in the middle the launcher shapes and its edge pixels beyond it, and a tap opens what the program opens in now: its first window, the task Android finds again by the window's initial data where the program runs, or, with programs shown inside WaOS, WaOS's own window with the program in its tab, which the tap's action names. What Android keeps is made to match what is installed as WaOS starts, after every install, update and removal, and when the user chooses where programs open: a removed program's shortcut is greyed out, since no app may remove a pinned one, and says so when tapped; one installed again is enabled. A tap on a removed program's shortcut that Android still had enabled brings WaOS's own window forward with the library's problem, as anything the library asks to be seen for does on a phone (`state::deck::home`).

HTTPS is checked by the system's certificate checker, as on every system (`waos`'s `trust`): `rustls-platform-verifier` asks Android's through its Kotlin class, which the package carries with Kotlin's standard library, two Android libraries `cargo waft` merges into it (`dependencies` under `[package.metadata.waft.android]`; the files and where they came from are in `android/`, with `android/NOTICE`). The class is found through the application's class loader, so the verifier is handed the VM and the application first thing in `android_entry::main` (`os::android`'s `certificates`), before the engine starts and anything connects; a source read over HTTPS and a program's request through `wasi:http` both go through it. The library's manifest asks for `INTERNET`, which WaOS asks for already, and names its network security configuration as the application's: plain HTTP is refused to the app's Java code, as Android refuses it by default from API 28, except to the certificate authorities' hosts that publish revocation lists over it, which the checker fetches; WaOS's own connections are made in Rust and do not go through it. The merge needs a `cargo waft` with Android libraries, which Waft's main branch does not have yet.

A program in a tab draws: the engine allocates its canvas's hardware buffers as `AHardwareBuffer`s (`waos`'s `os::android`), and the shell shows them on Waft's composition layers as Waft's `AndroidHardwareBuffer` over the same buffer, and takes back what a layer shows as the engine's (`waos-program-window`'s composition, `logic::hardware_buffers`), as on macOS it does over Apple's `IOSurface`. Waft's Android host has no hardware image codecs, so a program's buffer reaches no encoder there.

## The deck

On a phone, WaOS's one screen is the deck: tabs, as Safari's pages are on an iPhone (decision 3 of `docs/proposals/2026-11-12-phone-programs-and-library.md`), and `waos phone` shows the deck on a desktop too, in its window of a phone's size (decision 9 of `docs/proposals/2026-11-11-android-pictures.md`): the form factor is chosen at the entry, so the deck and its tests build and run on every system. On Android the deck holds programs only where the user chose to show them inside WaOS (see On Android); otherwise it is the home alone, and each program a task. The engine's placement places each program by where it was opened (`logic::program_places`): a program in a tab is refused every request for a view, as the views WIT says of a tab, and has the view its tab gave it as it started, as `PlacedView` with no window and no request (`state::deck::tab_view`), which `InstalledRuns::open` hands the run, setting where the program's views go before it starts; a program in windows hands none and asks for its windows.

Each tab is the home or a program (`logic::tab_list`, the rules as plain values, and `state::deck::tabs`, which ties them to the programs). The home is the library, as a browser's new-tab page: a tab is the home until a program is opened, and then that tab is the program's; a program that has a tab is brought into sight instead of opened again. There is one home at most, the last tab whenever it is open: going home goes to it, and makes it at the end where none is open. There is always a tab: the last one closed leaves a home, and the home alone cannot be closed. Closing a program's tab stops the program without asking, as a phone's switcher ends an app; a program that ended on its own keeps its view in its tab, which shows its last picture, dimmed, under its icon, its name and how it ended, until the tab is closed: a plain line, and for a failure the engine's own words beneath it, smaller and in gray, whole, so the user can read and report them, the page scrolling where they are longer than it. A program built for another version of the interface, which the engine cannot link (`waos::IncompatibleProgram`), says that it was built for a different version of WaOS and cannot run in this one, and to get an update of the program or update WaOS; one that asks for a role its user did not grant it (`waos::RoleNotGranted`), what the role is and that it did not start, and where to change it; any other failure, that it stopped because of a problem. On a desktop a program's end shows nowhere but the log, its windows closing, and `cargo waos run`, whose `Ended` carries the error's words. A program that could not start gives the tab back to the home. The library is kept with the home's tab (`state::deck::home`): a program that asks its user for one of its switches opens its settings page there and the deck goes home to show it, a program waiting for its user to leave a settings page hears so once the home's page is out of sight, and a home opened after the last one went starts on the grid of programs.

A tab's page is the deck's view above its bar along the bottom (`logic::tab_page`): the program's metrics are the page's, the system's bars at the top still covering it and the bar taking what the system covers at the bottom, sitting clear of the system's bottom padding or of its bottom gesture zone, whichever reaches higher, so no drag on the bar starts where Android's gesture navigation takes it, and they follow every change of the view's; a keyboard changes neither the page nor the bar, only what the page is told it covers. A page is laid out once, at that size, and from then on only moved, scaled uniformly and clipped to a rectangle with rounded corners, so a program is never told of a size it does not have, and its canvas, a composition layer the system places by a position, one scale and a crop, is never re-parented. Where every tab is drawn is one pure function of the deck's animated values (`logic::deck_geometry`), continuous in each of them: the strip of pages, with a gap between them, and the overview's grid of cards, two columns on a phone held upright and more in a wider view, each card the middle of its page. Each tab is placed on its own, by its own values, and no tab's place depends on another's: its flight says how far it is from its page on the strip to its card in the grid; a card in the grid stands still at its one size, moved only by the grid's scroll, its slot and its throw; and a page in flight is on the straight line between the two, in size and in place, carried off that line by the finger that drags it.

The deck's widgets (`ui::deck`) own those values, the fingers that drag them and the springs that settle them; no motion has a duration, so a finger catches any of them where it is, and the next spring starts from there at the speed it has. The bar (`bar`) holds a pill for each page on the strip, sliding with its page, and the tabs button; a program's pill is its icon and name, and the home's is a search field (`search_pill`) that filters the home's grid as the user types, the bar sitting above the keyboard while the field has it. A sideways drag on the bar moves the strip with the finger, resists past either end as a scroll view does, and settles on a page at the finger's speed, a flick moving on however little the strip moved (`strip`); past the last tab, while no home is open, is the home's page, which opens where the strip settles on it. An upward drag on the bar takes the current page into flight under the finger, as Safari's does, over a grid that stands still: from the moment the flight begins until the deck rests on a page again, every other tab is its card, in its slot at its size, behind the page, which uncovers the grid as it shrinks, nothing fading in. The page's size follows the finger's upward travel, down to its card's at half the page's height and a little past it against resistance, and the page stays under the finger both ways, its bottom edge as far above the finger as it was taken hold of; the release says open or closed, and the page springs from where it is at the finger's speed to its own slot, empty while it is away, or back to fill its box. The tabs button, Done and a tapped card are the same flight with no finger; a finger that comes down on a page in flight takes it over from where it is, and one anywhere else on the overview does nothing until the overview can be used; and each tab's flight is its own, on its own spring, so a card tapped while another page still lands flies as that one goes on landing (`overview_transition`). In the overview a tap grows a card into its page; a card thrown sideways flies off and its tab closes once it is gone, the others moving into its place at once, and a finger that catches it keeps the tab (`cards`); the grid scrolls when the cards do not fit (`grid_scroll`); a toolbar in the bar's place has a plus, which goes home, the number of tabs, and Done, its surface standing beneath the bar from the moment the page leaves the strip, the bar fading away over it in the flight's first quarter and its controls fading in over the next, so the two bars never show through each other (`overview_toolbar`); and a card's title and close button are painted with the card (`card_chrome`), so a page flying over a card covers them too. A page takes every touch on it: what takes the deck's touches while it does not show pages is a layer above them (`touch_layer`), which takes none while the deck rests on a page. A clip costs the renderer a pass over the whole picture whatever it cuts, so the deck's clips stay in the tree and clip only while the geometry says they cut something: a page's once it leaves the strip, a page on the strip filling its clip with square corners, and the pills' while the strip is off a page; at rest the deck clips nothing of its own. Each value a gesture moves has a grip (`grip`): a finger down holds it still, a drag takes over from where it is, a drag that hardly moved is a held finger lifting, and a grip dropped, because the deck was sent elsewhere from outside or its view changed size, leaves the finger still down with nothing. One rule settles the deck: wherever the tabs say it heads, the strip springs to the current tab's page and every tab's flight to its page or its card, unless a finger holds them; a tab chosen while the grid stands puts the strip on it at once, which moves no card, a page still in flight staying where it is. Every child of the deck's stack is keyed, so the toolbar coming and going, or the tabs painted in another order, builds nothing again: a gesture lives in the bar's and the touch layer's detectors.

What a program is told of its view follows the deck (`state::deck::tabs`): its view is on screen while its page is in sight, which is while the deck heads to its page or rests on it, and, for the page the deck last rested on, until the deck arrives somewhere else; it is focused, and holds the keyboard, only while the deck rests on its page and the deck's view has the input focus. So nothing changes while a finger drags the deck; a release that heads elsewhere puts the page headed to on screen at once and takes the focus from the page left, and the arrival takes the page left off screen and gives the page arrived at the focus. In the overview, at rest, no program is on screen, and each card shows its program's last picture.

The system's Back, which Waft's Android host asks of the app as `pop_route`, is the deck's (`ui::deck::back`, decision 8 of `docs/proposals/2026-11-12-phone-programs-and-library.md`), in this order: the overview, open or opening, closes, as Done closes it; a program's page whose program says it goes back within itself sends the program `pop-route`, which the program's tab keeps from its `set-handles-back` (`ShownView::handles_back`); any other program's page goes home, as the plus does, making the home at the end where none is open, the program keeping its tab and running on; and on the home a page of the library's other than its grid, getting programs or settings, goes back to the grid. On the grid the deck leaves the press, and Waft's host hands it to Android, which sends WaOS to the background. A keyboard up takes Back to hide itself before WaOS hears it. Each moves the deck through the calls of the control it names, with that control's springs and grips.

What the deck does not cover yet: a program opened another way than from the home on a phone, by files opened with it, a click on its notification, or `cargo waos run` on a desktop's `waos phone`, starts with no view, so it is refused the view it asks for; a program's prompts and file dialogs go where a desktop's go, in windows of their own, which a phone makes none of; on macOS `waos phone` still starts the programs' apps, which keep a program's menu bar, file dialogs and notifications as on the desktop, though the program shows in WaOS's window; a program opening does not grow out of its icon, and a tab still starting shows its program's icon and name rather than its last run's picture; and nothing tells a program where WaOS draws over it, which the bar never does, sitting beneath the page.

## The library

The library is one state over the store (`state::library`), which every layout shows and changes through the same calls: the programs installed, each to open and remove; the sources added, each with what it lists, to install, or to update when it lists an installed program at a newer version (`logic::offers`, by semver's precedence as the store compares); and the packages opened with WaOS or picked from a file, each waiting for the user to say whether to install it. The store is kept in `~/Library/Application Support/WaOS/store` (`%LOCALAPPDATA%\WaOS\store` on Windows, as the shell names the folder, local rather than roaming since installed programs are large and belong to one machine, `$XDG_DATA_HOME/waos/store` elsewhere), outside the caches. Reading a source, a download, an install from a source and a program's load run on the library's own tokio runtime, and their answers come back to the main thread; what was asked last and failed is the library's problem, shown until the next thing asked succeeds or the user dismisses it. A program's code is compiled when it is installed or updated, as Android compiles an app when it installs it, rather than at its first open (`logic::installed_code`): on a thread of its own, after the store put it in place, the program listed as compiling until its code is in the engine's code cache (`WaOS::compile`). An open waits for a compile of the program running rather than starting a second, and where the cache holds nothing current, as after an update of WaOS changed the engine, whose compatibility hash names the cache's files, the open compiles, the program listed as compiling meanwhile; nothing compiles every installed program at WaOS's start. A compile that fails is said in WaOS's log, and the program's open compiles again and says why it cannot. Removing a program removes its code from the cache first, while its component is there to find it by (`WaOS::remove_compiled`), and so does an update, for the version it replaces, before the store installs the new one: a run of the old version keeps the code it mapped, and an update that fails leaves the version installed to be compiled again at its next open. The code an earlier engine compiled stays in the cache, which nothing clears. Removing a program, and installing a package opened with WaOS, are questions first, which the user answers in the library's dialog; a package is opened, and so verified, before what it says is shown. Opening an installed program runs its component from the store (`Store::program`) as `cargo waos run` runs one, with this computer's capabilities, the grants of its own settings and its own folders, its output in WaOS's log; it is named by its id (`Program::named`), which names it among the runs, so a quit asks it too, and to the questions it puts; opening it again while it runs leaves it as it is. No run outlives the package it came from, so a reinstall starts the program afresh.
